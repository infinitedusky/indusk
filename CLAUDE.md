# dusk — Project Context

## What This Is

A pnpm + Turborepo monorepo containing the InDusk development system. The repo dogfoods its own skill system — the same plan/work/verify/context skills used to build features are also the product being showcased.

**Apps:**
- **indusk-mcp**: InDusk MCP server — dev system tooling with MCP tools, CLI (`init`/`update`/`init-docs`/`extensions`/`check-gates`/`infra`/`agent`), skills, hooks, lessons, and extensions. The `agent` subcommand (added in handoff-multi-agent Phase 2) drives the per-session presence bulletin — `agent register --task "..."`, `agent done`, `agent list`, `agent prune` — at `<projectRoot>/.indusk/agents/{sessionId}.md`. Session ID comes from `CLAUDE_CODE_SESSION_ID` (PID fallback); stale TTL governed by `agents.stale_ttl_minutes` in `.indusk/config.json` (default 60). `.indusk/extensions/` holds extension manifests (built-in + third-party). Published as `@infinitedusky/indusk-mcp`. OTel templates (`templates/instrumentation.ts`, `templates/filtering-exporter.ts`, `templates/logger.ts`, `templates/instrumentation.py`) are scaffolded by `init` into target projects. **SCM abstraction** at `apps/indusk-mcp/src/lib/scm/` — `detectScm(projectRoot)` runs at init/update time and writes `scm: "jj" | "git"` to `.indusk/config.json`; `getScm(projectRoot)` is the runtime source of truth. Don't shell out to jj or git directly outside `lib/scm` — go through the helper. The **`doppler` extension** (`apps/indusk-mcp/extensions/doppler/` — manifest + skill + `.env.example`) is the new Doppler-backed env layer (Doppler configs + plain docker-compose, per-worktree auto-provisioning) that will replace composable.env as the `init` default; landing across the `doppler-extension` plan's phases.
- **indusk-infra**: Bundled Docker container (`docker/Dockerfile.infra`) running FalkorDB + Graphiti MCP server. One container for all graph infrastructure. FalkorDB on port 6379, Graphiti on port 8100. Persistent volume `indusk-data` at `/data`. `GOOGLE_API_KEY` env var for Gemini LLM/embeddings. OTel export optional via `OTEL_EXPORTER_OTLP_ENDPOINT`.

**MCP servers** (registered in `.mcp.json` per project):
- **`indusk`** — InDusk MCP tools (lessons, plans, context, extensions, code graph)
- **`codegraphcontext`** (CGC) — structural code intelligence via FalkorDB graph queries
- **`graphiti`** — temporal knowledge graph (Phase 5.5 of graphiti-infrastructure). Captures decisions, contradictions, and lessons across sessions. 9 tools: `add_memory`, `search_nodes`, `search_memory_facts`, `get_episodes`, `get_entity_edge`, `delete_episode`, `delete_entity_edge`, `clear_graph`, `get_status`. Group ids isolate knowledge by project (`dusk`, `numero`, etc.) plus a `shared` group for cross-project conventions. Registered automatically by `indusk init` ≥ v1.10.0.
- **`dash0`** — observability (logs, traces, metrics) via the Dash0 hosted MCP. Use traces-first when investigating.
- **`excalidraw`** — hand-drawn diagrams.
- **indusk-docs**: VitePress 1.x documentation site with Mermaid diagrams and FullscreenDiagram component. Runs in Docker via composable.env. `pnpm turbo dev --filter=indusk-docs` for local dev.
- **indusk-admin**: Next.js (App Router) + React + Tailwind standalone web app at `apps/indusk-admin/`. Custom UI primitives in `src/components/ui/` (no shadcn-ui, no Radix). Read-only viewer over `.indusk/planning/` and `.indusk/eval/*`. **Hosted as a single long-lived daemon** via `indusk ui start` (1.27+ shape — see `.indusk/planning/admin-ui-hosting/`). `indusk ui start` spawns a detached `next start` serving every registered project; `indusk ui stop` SIGTERMs it; `indusk ui status` reports running/port/registered-projects. Daemon metadata at `~/.indusk/admin-ui.{pid,json,log}`. Bundled admin dir ships inside the indusk-mcp tarball at `apps/indusk-mcp/admin/`. Tests use `vitest-browser-mode` with `@vitest/browser-playwright` provider (real Chromium). Reuses parsers from `apps/indusk-mcp/src/lib/trajectory/` and `apps/indusk-mcp/src/lib/falsification/` — never duplicates parsing logic.

**Skills:**

| Skill | Status | Purpose |
|-------|--------|---------|
| planner | stable | Structured planning lifecycle: research → brief → ADR → impl → retrospective |
| work | stable | Execute impl checklists methodically, one item at a time |
| context | stable | Maintain living project memory in CLAUDE.md, shape impl docs to include per-phase context updates |
| verify | stable | Automated verification loop — type checks, lint, tests — integrated with work |
| document | stable | Per-phase documentation gate with Mermaid diagram guidance |

| highlight | stable | Flag a moment as worth remembering; eval agent materializes into a Graphiti episode |

**Agent Roles:**

InDusk runs work across three tiers. Each tier has a distinct responsibility, a bounded set of tools, and a different cadence. The boundary is enforced by the highlights queue and by which MCP tools each tier calls.

| Tier | Role | Writes | Cadence |
|------|------|--------|---------|
| **Working agent** | Does the task the user asked for — code, plans, tests, docs, handoffs. Flags moments worth remembering by calling `mcp__indusk__highlight`. | Code, plan files, `.indusk/highlights.jsonl` | Real-time, in-flow |
| **Eval agent** | Background judge that fires on every `jj describe` (and at session end via `/handoff`). Reads unprocessed highlights, writes structured Graphiti episodes with level-weighted edges, scores the commit against the rubric, writes unresolved findings. | Graphiti episodes (via `graph_capture`), `.indusk/highlights-processed.jsonl`, `.indusk/eval/results.log` | Asynchronous, per-commit + session-end |
| **Infrastructure** | The container, hooks, CLI, and validators that enforce invariants. Reindexes the graph, validates impl structure, blocks phase transitions with incomplete gates, runs `check-gates` / `check-catchup`, maintains `.indusk/graph/semantic-graph.log`. | Semantic graph event log, FalkorDB projections, validator error messages | On trigger (git/jj hooks, Claude Code PreToolUse/PostToolUse, `indusk graph sync`) |

The working agent never calls `mcp__graphiti__add_memory` or `mcp__indusk__graph_capture` in process skills. The eval agent is the sole structured writer to Graphiti at trigger points. The infrastructure tier is not an agent at all — it's the substrate.

## Conventions

- pnpm workspaces, Turborepo for task orchestration
- **Node 22 required** — Tailwind 4 native bindings need it
- **Biome for linting and formatting** — NOT ESLint. Single tool, single config. Run `biome check` not `eslint`
- **composable.env for environment management** — all apps run in Docker containers for local dev. Use `pnpm env:build` before `docker compose`. Use `pnpm ce` for all composable.env commands, never `npx ce`
- **`indusk doppler env-pull <profile>` materializes env from Doppler** (doppler extension) — reads the InDusk-level service token at `.indusk/extensions/doppler/.env`, runs `doppler secrets download --config <prefix>_<app>` per app (local→loc, staging→stg, production→prd), and writes `apps/<app>/.env.<profile>`. Those files plus the token `.env` are gitignored (idempotent `ensureGitignore()` block) — they are machine-local provisioning output and must NEVER be committed. `.env.test` is the exception (committed with safe defaults; not pulled). **`indusk worktree create <slug>` auto-provisions the new worktree's env** — after the setup script succeeds, `worktreeCreate` resolves the workbench root (walk-up) and calls `provisionWorktreeEnv(workbenchRoot, <workbench>/<slug>)`, reading the token from the workbench-level `.indusk/extensions/doppler/.env` and writing the worktree's `apps/*/.env.local`. It skips silently when doppler isn't configured (no token). Zero per-worktree env steps — the load-bearing guarantee. **doppler is `required: true`**, so `autoEnableExtensions` Pass 1 enables it on every `indusk init`/`update` (the "doppler default"; opt out via `disabled_extensions`). **composable.env is deprecated** but NOT a built-in extension (added externally via `ce add-skill`) — so deprecation is a non-destructive `ceDeprecationNotice()` (exported from `update.ts`) that init/update print when a `ce.json` is present, nudging toward doppler + numero's `composable-env-removal`. ce.json is never touched — legacy opt-in stays.
- Skills are markdown files in `.claude/skills/{name}/SKILL.md` — each concept has one canonical skill, others cross-reference
- **`.indusk/current.md` is the operational state layer; CLAUDE.md is the architectural layer** (handoff-multi-agent Phase 4). `current.md` answers "what is happening on this project right now?" — in-flight work, open questions, cursor position. CLAUDE.md answers "what is this project?" — architecture, conventions, key decisions. Working agents edit `current.md` in place as state solidifies during sessions and commit it like any other file (git-mediated visibility means other agents only see committed state). `/retrospective` is the existing distillation cadence — it folds operational state into CLAUDE.md's Key Decisions / Current State on plan close. The file is scaffolded by `indusk init` from `apps/indusk-mcp/templates/current.md` (sections: `## In Flight`, `## Open Questions`, `## Cursor`); `indusk update` migrates pre-1.29 projects idempotently (preserves user-edited content). Stale presence files are filtered from `indusk agent list` after `agents.stale_ttl_minutes` (default 60) — configured per-project in `.indusk/config.json`.
- **`/catchup` is pure-read + presence-register; `/handoff` is deprecated** (handoff-multi-agent Phase 3). Catchup writes only the current session's own `.indusk/agents/<sessionId>.md` via `indusk agent register`, then reads `.indusk/current.md` for operational state plus the existing lessons/health/context/Graphiti/plans/skills layers. Concurrent agents on one project no longer collide — no shared mutation surface during catchup. The old singleton `.claude/handoff.md` is gone; `/handoff` is now a four-step session-end ritual (promote operational state to `.indusk/current.md` → commit → `indusk agent done` → fire eval-trigger). Edit catchup and handoff via `apps/indusk-mcp/skills/{catchup,handoff}.md` — the existing `globSync("*.md")` in init/update syncs to consumers on next `indusk update`.
- **admin-ui reuses indusk-mcp parsers via workspace import** — never duplicate parsing logic. Trajectory and falsification log parsers live in `apps/indusk-mcp/src/lib/` and are exposed for cross-package consumption via subpath exports (`@infinitedusky/indusk-mcp/trajectory/parser`, `@infinitedusky/indusk-mcp/falsification/log`). The admin app imports them through the workspace dep `"@infinitedusky/indusk-mcp": "workspace:*"`. If a parser needs a new export to support admin-ui, add it to the original module rather than recreating it. Adding a new subpath export to indusk-mcp's `package.json` `exports` field is non-breaking (additive) and surfaces the API surface explicitly.
- **admin-ui sidebar order is canonical from `master.md`** — to reorder plans in the UI, edit `.indusk/planning/master.md`'s pipeline table. The sidebar reflects whatever `readMasterPlanOrder` parses (markdown links of the form `[plan-name](plan-name/brief.md)`, which dedupe by name). Plans NOT mentioned in master.md appear in an "Unordered" group at the bottom of the active section. Archived plans always render in a separate, collapsed `Archived (N)` section below the active list, regardless of master.md content.
- **`indusk init` and `indusk update` mutate `~/.indusk/projects.json`** — the project registry the admin-ui daemon reads. `init` appends via `addProject(projectRoot)`; `update` calls `validateProject(name)` + `touchProject(name)` (or `addProject` if the entry is missing / path diverged). Tests redirect with `INDUSK_HOME=<tmpdir>` rather than mocking `os.homedir()`. The registry module (`apps/indusk-mcp/src/lib/admin/registry.ts`) is the single entry point — never edit `projects.json` by hand from CLI code.
- **admin-ui routes are project-scoped**: `/` renders `<ProjectGrid>` (one card per registered project); per-project content lives under `/p/[project]/...`. The per-project sidebar + PlanList + ProjectSwitcher live in `apps/indusk-admin/src/app/p/[project]/layout.tsx`. Cross-project content (`/scorecards`, future cross-project signal) stays at top-level routes. The root layout (`app/layout.tsx`) is global-nav-only — don't push project data into it. `PlanList` accepts an optional `planHrefPrefix` prop (default `/plan/`); the per-project layout passes `/p/${project}/plan/` to namespace plan links.
- Plans follow the lifecycle: research → brief → ADR → impl → retrospective
- All planning docs live in `.indusk/planning/{kebab-case-name}/`
- Every impl phase has **four required gates** (verify, context, document) plus an **optional OTel gate**. The OTel gate fires by default. Set `otel.role` in `.indusk/config.json` to `"library"`, `"tool"`, or `"none"` to silence it for projects that don't produce runtime telemetry. dusk/indusk-mcp itself is `library` — its phases never have OTel sections.
- Plan gates are enforced via Claude Code hooks — the agent cannot skip verification/context/document items when advancing phases
- `.claude/hooks/` contains gate enforcement scripts installed by init (check-gates.js blocks execution, validate-impl-structure.js blocks writing, gate-reminder.js nudges)
- Every impl phase must have verification, otel, context, and document sections — enforced by hook at write time. Use `(none needed)` or `skip-reason:` to opt out.
- Health checks, init setup, and verification commands come from extensions — don't hardcode tool knowledge in indusk-mcp
- Three layers of defense: (1) Context/CLAUDE.md — advisory, (2) Biome rules — enforcement, (3) Hooks — gate enforcement, (4) Retrospective — learning. The quality ratchet only gets tighter.
- Use the planner skill before implementing significant features — don't jump to code
- `pnpm test` runs all tests, `pnpm turbo test --filter={app}` for scoped runs. Vitest configs use `passWithNoTests: true`
- Verification items in impl docs must be specific runnable commands with expected output — not "verify it works"
- Every new impl.md opens with a `## Test Trajectory` table after `## Boundary Map` and before `## Checklist`. Columns: `ID | Asserts | Writable at | Passes at | State` (optional: `Kind`, `Scope`). Phase Verification sections reference test IDs from the trajectory — not free-text checks. Deferred Verification rows (for genuinely untestable items) require three fields: `reason:`, `would require:`, `mitigation:`. The planner skill's impl.md template emits this shape; `trajectory: required` in frontmatter opts the impl into `validate-impl-structure.js` enforcement. See `.indusk/planning/tests-first-planning/adr.md`.
- Phase close requires every `Passes at: Phase N` trajectory row to be in `State: passing` (or `skipped`/`blocked` with a reason). The `check-gates` hook enforces this structurally — deferral is impossible by construction. The work skill updates the `State` column at phase start (to `writable`/`written`) and phase close (to `passing`/`skipped`/`blocked`). Library helpers live in `apps/indusk-mcp/src/lib/trajectory/state-ops.ts`.
- Retrospectives audit the trajectory at plan close — `auditPlanAtClose` from `apps/indusk-mcp/src/lib/trajectory/audit.ts` surfaces rows ending in `blocked` state and classifies every Deferred Verification row's `mitigation:` (telemetry-alert / scheduled-review / downstream-plan / canary-or-staging / feedback-signal / unclassified). Vague mitigations become retrospective findings that must be resolved or promoted to a concrete commitment before the plan archives.
- Every plan that completes impl runs `/falsify {plan}` before `/retrospective`. The ritual (a bounty hunt: investigate, hypothesize, write a failing test that confirms the hypothesis) writes an append-only log at `.indusk/planning/{plan}/falsification.md` via `apps/indusk-mcp/src/lib/falsification/log.ts`. Skipping requires both `falsification: skipped` AND `falsification_reason: "{non-empty text}"` in the impl frontmatter. See `.indusk/planning/falsification-ritual/adr.md`.
- Retrospective hard-blocks without falsification. The retrospective skill's Step 0 (Falsification Gate) refuses to proceed unless either `isFalsificationComplete(planRoot)` or `isFalsificationSkipped(implContent).skipped` is true. The work skill's Step 15 (Completion) directs users to run `/falsify` before `/retrospective`. Both are skill-level enforcement, not a validator hook — enough to carry the discipline without the rigidity of a Node-level block.
- `pnpm check` for lint/format check, `pnpm check:fix` to auto-fix, `pnpm format` for format-only
- After each retrospective, ask if mistakes could be caught by a Biome rule — if yes, add to biome.json and biome-rationale.md
- Before touching shared code, query the code graph (`analyze_code_relationships`) to understand blast radius
- Create `.cgcignore` in new projects to exclude build artifacts from graph indexing
- **Eval agent OTel is opt-in via `eval.otel.enabled` in `.indusk/config.json` or `INDUSK_EVAL_OTEL=1` env var.** Exports to `OTEL_EXPORTER_OTLP_ENDPOINT` (Dash0 or any OTLP HTTP receiver). **Dash0 dataset defaults to `agent`** and can be overridden per-project via `eval.otel.dataset` in config or per-invocation via `INDUSK_EVAL_OTEL_DATASET` env var — routed via the `Dash0-Dataset` header on the OTLP exporter. No-op when disabled — zero cost in normal operation. Graceful degradation when endpoint missing or SDK init fails — never blocks the eval agent itself. Call `initEvalOtel(projectRoot)` at the top of the evaluator entry; call `shutdownEvalOtel()` before `process.exit()` so batched spans flush.
- **The background process that scores every `jj describe` is called the eval agent or evaluator in code — never "judge".** Filenames (`evaluator-runner.ts`, `persistent-evaluator.ts`), symbols (`runEvaluatorSync`, `EvaluatorRunOptions`, `buildEvaluatorPrompt`), and log strings ("evaluator spawned", "evaluator completed") all use "evaluator". The term "judge" is retained only in historical changelog entries and archived planning docs.
- **Working agent writes highlights; eval agent writes Graphiti episodes.** At trigger points (brief acceptance, ADR acceptance, correction confirmation, retrospective lesson), the working agent calls `mcp__indusk__highlight` with a tag, a short note, and a level (`critical` / `important` / `note`). Highlights append to `.indusk/highlights.jsonl`. The eval agent (on `jj describe` and session end) reads unprocessed highlights via `highlights_unprocessed`, writes structured Graphiti episodes with level-weighted edges, and marks each entry done via `highlight_mark_processed`. The agent never calls `mcp__graphiti__add_memory` directly in process skills — trust the working-agent skills to flag moments, and let the eval agent materialize them. `/catchup` recalls via `mcp__graphiti__search_nodes` at session start.
- The semantic graph sync pipeline is adapter-agnostic by design (see `.indusk/research/anchor-overlay-pattern.md` Section 7). CGC is the first adapter; adding a new adapter means implementing `SemanticGraphAdapter` — the sync engine itself never changes. Enforced by sync-engine tests, which cannot import anything CGC-related.
- **Semantic graph features (`indusk graph sync`, Graphiti log capture) are jj-only in v1** (`git-or-jj-substrate` Phase 2). On `scm: "git"` projects, `runSync()` early-returns with a `git mode — semantic graph unavailable` stderr message; `captureWithLog()` warns once per session and skips the event-log mirror (Graphiti writes still succeed). Plans, lessons, eval, highlights, init/update — everything else works on git unchanged. Full git parity (stable event_id design, rebase-tolerant replay) is deferred to a follow-up plan; see `.indusk/planning/git-or-jj-substrate/research.md` "Three viable degrade modes".
- **Eval prompts and baseline CLI are SCM-aware** (`git-or-jj-substrate` Phase 3). `PromptBuilderOptions` accepts an optional `scm: "jj" | "git"` field; `buildEvaluatorPrompt` branches the diff-fetch command (`jj diff -r ${id}` for jj, `git show ${id}` for git). Defaults to `"jj"` when unset (backward-compat). Every caller (`evaluator-runner.ts`, `persistent-evaluator.ts`) passes `scm: getScm(projectRoot)`. The `indusk eval baseline --task` CLI branches at the commit-and-changeId step: jj uses `jj new` + `jj describe -m`, git uses `git commit --allow-empty -m` + `git rev-parse --short HEAD`. **Gotcha**: in `persistent-evaluator.ts`, the `scm` and `diffCommand` consts MUST be declared above the `try { withSpan(...) }` block — `buildArgsAndPrompt` is called inside the span callback and reads `diffCommand` from its enclosing scope; declaring them after the call puts them in TDZ and throws.
- **Skills are SCM-aware** (`git-or-jj-substrate` Phase 4). Two sibling skills: `apps/indusk-mcp/skills/jj.md` is the rich jj-mode reference (describe-then-do, `jj split`, bookmarks); `apps/indusk-mcp/skills/git.md` is the git-mode reference (trunk-based development, short-lived feature branches, `--force-with-lease`, merge + delete). The `jj.md` skill is BYTE-EQUAL to its pre-Phase-4 snapshot — pinned by a regression test against `apps/indusk-mcp/src/__tests__/fixtures/jj-skill-pre-phase-4.md`. Skills `work.md`, `highlight.md`, and `eval-review.md` are SCM-conditional in their commit-cadence and diff-fetch sections — show both forms with the asymmetry explained (jj describe-then-do vs git do-then-commit). Edit `git.md` for git-specific guidance; edit `jj.md` for jj-specific guidance; edit `work.md` for cross-cutting cadence rules. Skills auto-sync via `globSync("*.md")` in both `init.ts:426` and `update.ts:102` — adding a new `.md` file in `apps/indusk-mcp/skills/` propagates to consumers on next `update`.
- **The eval-trigger hook fires on `jj describe` AND `git commit`** (`git-or-jj-substrate` Phase 6, hardened in Phase 7). Both trigger patterns are matched in `apps/indusk-mcp/hooks/eval-trigger.js` via the **word-boundary regex** `/\b(jj describe|git commit)\b/` (NOT `String.includes` — Phase 7 hardening: substring matches false-positive on `git config user.email "git committer"`, `cat git-commit-template.md`, `echo "git commit"` inside string literals). Change-ID extraction tries jj first (`jj log -r @ --no-graph -T change_id`) and falls back to `git rev-parse --short HEAD` on jj failure — both must fail for the hook to skip silently. **The hook also reads `event.tool_response.exit_code`** and skips with `skip — bash command failed (exit_code=N)` when non-zero, so failed commits (no staged changes, pre-commit hook rejection, signing failure) don't trigger eval against the previous commit's SHA. `indusk graph status/rebuild` (CLI) and `mcp__indusk__graph_sync/rebuild/status` (MCP tools) all early-return on git-mode projects with the standard `git mode — semantic graph unavailable` message. Don't add new SCM-coupled CLI commands or MCP tools without branching on `getScm(projectRoot)` first — the precedent is established and the wrong default (silently-failed jj path) is the failure mode that the falsification ritual found. New trigger patterns added to the regex must respect word-boundary discipline.
- Use `indusk graph sync` to manually sync the semantic graph; `indusk graph rebuild` to clear and replay the runtime; `indusk graph status` for diagnostics. Also available as MCP tools (`graph_sync`, `graph_rebuild`, `graph_status`).
- **Eval hook fires on every `jj describe`** — a Claude Code PostToolUse hook spawns a background judge agent that scores work quality, writes derived insights to Graphiti, and logs scorecards to `.indusk/eval/results.log`. Disable with `eval.enabled: false` in `.indusk/config.json`. `indusk eval summary` for trends, `indusk eval baseline --task <path>` for baseline comparisons. Eval findings persist until fixed or ignored — the agent sees unresolved findings on every `jj describe`. `indusk eval findings` to list, `indusk eval fix <key>` / `indusk eval ignore <key>` to resolve. The eval judge is persistent per session — catchup runs once on first commit, subsequent commits reuse the session via `claude --resume`.
- `indusk infra start` to start the infrastructure container (FalkorDB + Graphiti). One command, idempotent. Creates `~/.indusk/config.env` on first run.
- `npx indusk-mcp init` to set up a new project with skills, CLAUDE.md, biome, OTel instrumentation, and MCP config
- `init` scaffolds OTel: `instrumentation.ts`, `filtering-exporter.ts`, `logger.ts` (Node.js/Next.js) or `instrumentation.py` (Python) — every project is observable from day one
- **`scm` field in `.indusk/config.json` is the runtime source of truth for which SCM (jj or plain git) the project uses.** Set once by `indusk init` via `detectScm()` (tries jj first, falls back to git); migrated by `indusk update` if missing. Read everywhere via `getScm(projectRoot)` from `apps/indusk-mcp/src/lib/scm/detect.ts` — don't re-detect per call. New code that needs change/commit IDs goes through `lib/scm`, not directly to jj or git binaries.
- **`/falsify` authors a Falsification Phase in the plan's impl.md** (as of 1.27.4) — it does NOT run tests inline. The skill investigates the code, forms specific hypotheses, captures each as a trajectory row (`Writable at: Phase 0`, `Passes at: Phase N+1`), and appends a new phase `### Phase N+1: Falsification — {summary}` with impl items for the fixes + standard gates. `/work` later picks up the phase like any other phase. `/retrospective`'s Step 0 gate accepts "all impl phases terminal" as a pass condition, alongside the legacy `isFalsificationComplete(planRoot)` check (for plans authored pre-1.27.4 with `falsification.md` files) and the `falsification: skipped` + `falsification_reason` frontmatter path. Never run `/falsify` with the intent of running tests inline — the ritual is phase-authoring only.
- **Worktree extension is opt-in via `indusk extensions enable worktree`** and applies to single-repo workbench-shaped projects only in v1. Flat workbench layout: trunk symlink (named after the wrapped repo, target = canonical clone elsewhere on disk) + active worktrees as sibling directories, all at the workbench root. Multi-repo workbenches (one workbench wrapping multiple repos, dawn-fde-toolkit-style) are deferred to a future "FDE agency" plan. `.indusk/config.json`'s `worktree.wrapped_repo` names the trunk; `worktree.sibling_parent` names the parent dir of canonical clones. Manifest declares `required: false` with no auto-detection. Lives at `apps/indusk-mcp/extensions/worktree/`; agent-facing reference is `apps/indusk-mcp/extensions/worktree/skill.md`. Lifecycle scaffolding ships across Phases 2–7 of the `indusk-worktree-extension` plan; Phase 1 is manifest + skill + index entries only.

## Known Gotchas

- **`.indusk/worktree-configs/<repo>.json` shape is defined by `apps/indusk-mcp/extensions/worktree/config.schema.json`** (worktree extension). Changes to required fields are breaking — bump the extension version and document the migration. Adding optional fields is non-breaking. Validator at `apps/indusk-mcp/src/lib/worktree/validate-config.ts` (exported via subpath `@infinitedusky/indusk-mcp/worktree/validate-config`); rejects unknown top-level keys (additionalProperties: false), so config typos surface immediately. The schema permits an optional `$schema` reference for IDE/LSP support.
- **Worktree extension `apply_commits[]` is upstream-file-overlay, NOT cherry-pick.** Each entry names a `sha` + `files[]`; `setup-worktree.sh` runs `git show <sha>:<file> > <file>` then `git update-index --skip-worktree <file>` so the overlaid content is invisible to `git status` / `git diff` / `git commit -a`. Known sharp edge: if the worktree's base branch is significantly behind main, the overlay's imports may point at files/types that don't exist in the worktree (module-not-found errors). Don't conflate with `git cherry-pick` — cherry-pick lands the commit's tree-diff onto your branch; apply_commits[] writes through specific files only and hides them from git.
- **Worktree extension preflight's env contract is `CHANGED_FILES` + `CHANGED_FILES_BIOME` + declarative `preflight_env{}` booleans.** Configs that want a new derived boolean add a key to `preflight_env{}` with glob patterns; the script's `_glob_to_regex` helper translates `**` → `.*`, `*` → `[^/]*`, `?` → `.`, escapes regex metachars, then matches each `CHANGED_FILES` line. Keys that match export as `"1"`; others empty. The script uses `set -u` so preflight commands referencing an undeclared `preflight_env` key (e.g., `$HAMMING_RELEVANT` when only `MIGRATIONS_RELEVANT` is declared) hit nounset; use `"${VAR:-}"` to read undeclared keys defensively. `when: <key>` on a preflight entry skips the entry when the key is empty/unset, surfacing `(skipped — $VAR is empty)` in stdout. Preflight rejects the trunk symlink as a target (preflight is feature-branch-only).
- **Worktree extension is per-developer scaffolding; the wrapped repo is the only shared/versioned thing.** The workbench (e.g., `~/code/sandbox/numero-workbench/`) is local-only — never pushed, never cloned by teammates. Each dev runs `indusk init --workbench` against the same wrapped repo and gets their own independent workbench with their own `.indusk/planning/`, `.indusk/eval/`, `.indusk/worktree-configs/`. Planning history does NOT sync between developers by design — keeps the wrapped repo clean (no `.indusk/`, no `.claude/`) and removes coupling between team members' InDusk usage. Trade-off: a new teammate's `.indusk/planning/` starts empty; they don't inherit your history. Acceptable for solo/async-collaborative workflows; if shared planning state matters later, that's a follow-up plan. Two setup workflows documented at `apps/docs/src/guide/worktree-setup.md` — Flow A (fresh setup) vs Flow B (migrate an existing project that has baked-in InDusk state).
- **Extension hooks that need to invoke scripts inside their own extension package use a TS shim that walks `__dirname` up to find the package root.** Pattern: extension manifest's hook is `indusk <ext> _<hook-name>` (e.g., `indusk worktree _on-enable`). A small internal CLI subcommand in `apps/indusk-mcp/src/bin/cli.ts` calls a function in `apps/indusk-mcp/src/bin/commands/<ext>.ts` that walks up from `__dirname` until it finds a `package.json` whose `name` is `@infinitedusky/indusk-mcp`, then shells out to `extensions/<ext>/hooks/<hook>.sh` from that root. Works for both global installs (`~/.pnpm/global/.../indusk-mcp/dist/bin/commands/`) and dev (`apps/indusk-mcp/dist/bin/commands/`). Necessary because extension hooks run from the user's project cwd and `runHook` in extensions.ts just shell-execs the command string — there's no built-in way for the hook to address sibling scripts in the extension's source dir. Use this pattern for any future extension whose hook needs more than a one-liner.
- **Worktree-internal state lives at `<per-worktree-gitdir>/indusk-overlay-state.json`** (typically `<canonical-clone>/.git/worktrees/<slug>/indusk-overlay-state.json`), NOT under the worktree's working tree. Reason: per-worktree `.git/info/exclude` is not a real thing (git's main worktree's exclude file is what counts, not per-worktree), so a state file in the working tree would always show up as untracked. Putting it under the gitdir makes it invisible to git entirely — git ignores its own internals by definition. `refresh-worktree.sh` reads this file to detect entries removed from `apply_commits[]` between runs (ADR D7 fix-in-scope: clears skip-worktree + restores from HEAD for those files, so the overlay's content goes away when the entry is removed from config).
- Tailwind 4 requires Node 22 — build fails on Node 18 with "Cannot find native binding" error
- Always use `pnpm ce`, not `npx ce` — the skill doc specifies pnpm
- Always run `pnpm env:build` before `docker compose` — use the ce-generated scripts
- Don't jump to implementation without planning — use the planner skill lifecycle
- composable.env binary is `ce`, not `composable.env` — the package.json script should be `"ce": "ce"`
- Skill files are `SKILL.md` (all caps), not `skill.md`

Discovered by the `/falsify` dogfood on the falsification-ritual plan itself (logged at `.indusk/planning/falsification-ritual/falsification.md`). Slug-style references are rejected — reorder overhead is intentional, per `.indusk/planning/tests-first-planning/adr.md` Section 6a. Temporal coherence (`Writable at ≤ Passes at`) is enforced by the validator; a reorder that breaks this fails at write time rather than silently.

If you edit inside a phase and the hook flags unrelated OTel/Verification gaps, the edit itself is fine but the file-as-a-whole has structural gaps. When adding a new trajectory field or changing parser behavior, update the TS source AND every JS port. The TS is tested (55 tests across `parser.test.ts`, `validator.test.ts`, `state-ops.test.ts`, `template.test.ts`); the JS ports are exercised via end-to-end hook invocations.
- **admin-ui markdown rendering**: Phase 4 picked `react-markdown` over `marked` because react-markdown returns a React element tree (no `dangerouslySetInnerHTML`, no separate sanitization step — XSS-safe by construction), is more idiomatic for Next.js server components, and the bundle-size delta is irrelevant for an admin UI. To swap libraries, change only `apps/indusk-admin/src/components/Markdown.tsx`; every call site uses `<Markdown>` not `<ReactMarkdown>`.
- **`next/link` in vitest browser tests**: `next/link` references Node-only globals (`process`) that aren't defined in the vitest browser runtime. Components that import `Link` need a `vi.mock("next/link", () => ({ default: MockLink, __esModule: true }))` stub at the top of the test file, where `MockLink` is a function component that renders a plain `<a href={href} {...rest}>{children}</a>`. Use a synchronous factory with a named function declaration — async factories with `await import("react")` cause timing issues with React 19's reconciler.
- **gray-matter behavior on malformed YAML differs by runtime**: in plain Node, `matter(badYaml)` throws (js-yaml propagates the parse error); inside vitest, the same call silently returns `data: {}` (the error gets swallowed somewhere in the module-resolution chain). The `apps/indusk-admin/src/lib/planning-reader.ts` reader detects malformed by structural signal: file starts with `---\n` + has closing `---` + parsed `data` is empty + the frontmatter block is non-trivial → malformed. Don't rely on gray-matter throwing.
- **indusk-mcp prepublishOnly bundles the admin app**: `pnpm build && pnpm --filter indusk-admin build && node scripts/bundle-admin.js`. The bundler copies the admin app's pre-built Next.js output (`.next/`, `package.json`, `next.config.ts`, `public/`) into `apps/indusk-mcp/admin/`, which the published tarball includes via the `files` array.
