# Changelog

All notable changes to InDusk MCP are documented here. Follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added
- **`hotfix` planner workflow** — a fifth workflow type for production-down emergencies. The fix ships first on its own `hotfix/{slug}` branch; the plan folder (`impl.md` only, no brief/test-plan/ADR) is created retroactively with a fixed three-phase shape: Phase 1 (Ship) documents the already-shipped fix with every gate deferred under `gate_policy: auto`; Phase 2 (Backfill) is the mandatory, fully-enforced phase (regression test + real verification/document gates); Phase 3 (Close) is a trivial single-item phase that exists solely to trigger `check-gates.js`'s existing phase-close check against Backfill's rows — a plan's terminal phase's own trajectory rows are otherwise never inspected (a general, previously-undocumented gap found mid-implementation, now a standing CLAUDE.md Known Gotcha). No new hook mechanism — reuses `gate_policy: auto` and the existing Phase-0 trajectory rule for reported bugs. See [Planner Hotfix Mode](/decisions/planner-hotfix-mode).

## [1.31.3] — 2026-06-28

### Fixed (eval-agent-mcp-access Phase 7 — malformed-line bypass defense)
- **`markProcessed` defends against malformed historic entries (Phase 7 falsification fix)** — Phase 6's write-time dedup (shipped in 1.31.2) relied on `readAllProcessed`, which silently skips malformed JSON lines via try/catch around `JSON.parse`. If `highlights-processed.jsonl` contains a corrupted entry for the target ID (truncated line from a crash mid-write, a hand-edit gone wrong, a version-format mismatch), the dedup check thought the ID wasn't present and appended a duplicate — Phase 6's contract silently broke for this specific input. **Fix**: a new file-private `isIdInRawProcessed(projectRoot, id)` helper scans the raw file content for the literal `"id":"<escaped id>"` substring via a JSON-safe regex (defensive metacharacter escaping). `markProcessed` calls it after the parsed-content check returns no match: if the raw bytes carry the ID, return `{ already_processed: true, original_processedAt: undefined }` without appending. The boolean is the load-bearing signal for the agent's STOP path; `original_processedAt` is undefined because the malformed entry didn't yield a parseable timestamp. The parser's read-side tolerance is preserved — `readAllProcessed` still skips the malformed line; the defense works around it on the WRITE side without changing the parser. Regression: 2 new cases in `highlights.test.ts` covering the malformed-truncated-JSON case and confirming `readAllProcessed` tolerance is preserved. Surfaced by the `/falsify` ritual run on the freshly-shipped 1.31.2 Phase 6 code.

## [1.31.2] — 2026-06-28

### Fixed (eval-agent-mcp-access Phase 6 — highlights dedup)
- **`markProcessed` rejects duplicate IDs at write time (1.31.2)** — T4's runtime audit of the 1.31.1 fix surfaced a gap: across 4 successful post-upgrade evals on dusk, the eval agent called `mcp__indusk__highlights_unprocessed` in only 3 of them. The 4th eval processed highlights from session memory instead, producing 43 duplicate `graph_capture` writes for the same 52 unique highlight IDs (`highlights-processed.jsonl` grew to 98 lines for 52 unique IDs). The dedup logic in `readUnprocessedHighlights` was correct (uses a Set on processed IDs) but `markProcessed` was designed as idempotent-append — duplicate writes silently accepted, no signal back to the agent. **Fix**: two-pronged. (a) Strengthened the Step 4 prompt instruction in `buildHighlightsInstructions` with a **CRITICAL** preamble: *"You MUST call `mcp__indusk__highlights_unprocessed` first. Do NOT process highlights from session memory. Do NOT read `.indusk/highlights.jsonl` directly. ONLY process IDs returned by the tool."* Plus an explicit instruction for the `already_processed: true` response: *"STOP processing it immediately. Do NOT call `mcp__indusk__graph_capture`."* (b) Changed `markProcessed` from idempotent-append to write-time rejection: if the ID is already in the processed log, return `{ already_processed: true, original_processedAt }` without appending. The agent's tool result now signals the redundancy so downstream `graph_capture` calls don't happen for already-done IDs. Regression: 3 new vitest cases in `apps/indusk-mcp/src/lib/highlights/highlights.test.ts` covering the new contract; T8 source-grep in the eval-resume-prompt test file pins the "MUST call" + "don't process from memory" + "already_processed" instructions in the helper body.

## [1.31.1] — 2026-06-28

### Fixed
- **Eval agent now drains the highlights queue on every commit, not just first-spawn (1.31.1)** — the `eval-agent-mcp-access` plan's April 1.23.x fix added `--mcp-config .mcp.json` + `--permission-mode bypassPermissions` to the spawn args, restoring MCP tool access in the inner Claude subprocess. That fix was correct AT THE TIME but a second bug went unnoticed: the *resume* path in `persistent-evaluator.ts:222-245` hand-rolled a minimal "Evaluate a new commit ... output the JSON scorecard" prompt and silently omitted Step 4 (process unprocessed highlights). The fresh-spawn path goes through `buildEvaluatorPrompt` (which includes Step 4); the resume path was the lean cousin. Across 197 evals on the persistent session (created 2026-04-19, last used 2026-06-28), the inner Claude received Step 4 exactly once — the April fresh spawn — and processed 3 highlights. Every commit since has been a resume that received no Step 4 instruction; the highlights queue stopped draining and grew unbounded (52 unprocessed at fix time). **Fix**: extracted the Step 4 highlights instruction into `buildHighlightsInstructions({ projectGroup })` in `prompt-builder.ts` and have the resume prompt prepend it. Both paths now reach the same instructions. Regression: `apps/indusk-mcp/src/__tests__/eval-resume-prompt-includes-highlights.test.ts` source-greps both the helper export and the call site in the resume branch, pinning the load-bearing call order (highlights instructions BEFORE the commit-evaluation literal). T4 (live smoke against the persistent session) verifies the runtime drain.

### Fixed (1.31.1 falsification ritual — H14, H15, H16)
- **Resume prompt no longer anchors the inner Claude to "as before" (H14)** — the pre-fix wording said `"answer the same evaluation questions as before"`. Inside a 197-turn persistent session where Step 4 was never previously provided, "as before" reads as "your last turns" and pulls Claude back to the pre-Phase-4 pattern of skipping Step 4. Reworded to `"answer the v1 rubric questions for this commit"` — present-tense direct instruction, no backwards-anchoring temporal modifier. Trailing `"as before — no commentary"` also dropped.
- **`buildHighlightsInstructions` explicitly handles the empty-list case (H15)** — the pre-fix helper text only handled `highlights_unprocessed` being *unavailable* (tool not loaded). Once the backlog drains (or in fresh projects), the tool returns `[]` and the inner Claude has undefined behavior — could hallucinate highlights, loop searching, or skip smoothly. Added an explicit branch: `If the tool returns an empty list (no unprocessed highlights), note "(no unprocessed highlights)" once and continue to the rubric — do not invent highlights, do not loop searching for them, do not call \`graph_capture\` speculatively.`
- **Source-grep regression for the 1.23.x MCP-access flags (H16)** — T3 from Phase 4 pins the prompt shape but not the spawn flags. If someone refactors `persistent-evaluator.ts`'s `args` list and removes `--mcp-config` or `bypassPermissions`, the inner Claude has no MCP tool surface and Step 4 fires into a void — silent return to the April-2026 failure mode. New T7 assertion: both flag literals appear in source with count ≥ 2 each (locking the resume + fresh spawn-arg sites in place).

### Fixed (1.31.0 falsification ritual — H1, H3, H5)
- **`indusk init` warns when the project is not a git repository** (H1) — Phase 4 deleted the pre-1.31.0 deferred-SCM stderr warning; nothing was added in its place. `indusk init` in a non-git directory got a green-looking init and the user discovered git was required only when `indusk graph sync` crashed or the eval hook silently skipped. The warning is back, scoped to "git is the only SCM" with `git init` named as the recovery. Informational — init still exits 0.
- **`indusk graph sync` translates git-state errors to friendly messages** (H3) — `runSync()` calls `getCurrentChangeId()` which awaits `execFileAsync("git", ["rev-parse", "--short", "HEAD"])`. Previously, the rejection propagated through `cli.ts`'s action as an unhandled `Error` with the raw `ChildProcess` stack trace. Now the CLI wraps the call in try/catch and translates "not a git repository" → "run `git init` first" / "unknown revision" → "run `git commit --allow-empty -m 'init'` first". Exits with code 1. The same translation lives in `tools/graph-tools.ts`'s `graph_sync` MCP handler so MCP callers get the same UX.
- **Eval-trigger `TRIGGER_RE` no longer matches `git commit-tree` / `git commit-graph`** (H5) — pre-existing bug inherited from the dual-form `\b(jj describe|git commit)\b` regex and not tightened during the Phase 2 collapse. JS's `\b` matches the `t`→`-` transition (word-char to non-word-char), so `\bgit commit\b` matched git plumbing commands. Tightened to `/\bgit commit(?=$|\s|;|&|\|)/` — lookahead requires end-of-string, whitespace, or a shell separator after `commit`. The porcelain `git commit ...` still matches; plumbing commands no longer fire the eval hook. New CLAUDE.md gotcha records the constraint so future regex changes don't reintroduce the bug.

## [1.31.0] — 2026-06-27

### Changed
- **SCM substrate is now git-only (1.31.0)** — InDusk's dual-SCM era (1.28.x–1.30.x) ends. Git is the only supported source control system. Existing `scm: "jj"` config fields become a no-op; `indusk update` emits a one-line stderr nudge (`scm field no longer used; safe to remove from .indusk/config.json`) and leaves the file unchanged. See [git-only-substrate](/decisions/git-only-substrate) for the full decision; see [Git workflow guide](/guide/scm) for the convention.

### Added
- **Semantic graph populates on every git project (Phase 1)** — `indusk graph sync`, `captureWithLog`, and the MCP `graph_*` tools now produce real events on git projects. The prior graceful-degrade no-op is gone. Rebase tolerance comes via content-keyed dedup at sync time (`existingByIdentity` on path + `existingByFingerprint` on blob hash) — `git rebase` produces noisy-replay-then-converge: extra `anchor.*` events get written; the runtime de-duplicates by `(path, blob_hash)` identity on the next sync; the system converges to current file state after one cycle. Provenance traceability is fuzzy (an event's `change_id` may name a rewritten commit) but functional correctness holds. Three obsolete tests (`git-mode-graph-sync.test.ts`, `git-mode-graph-cli.test.ts`, `git-mode-e2e.test.ts`) deleted; replaced by `git-tmp-project-graph-sync.test.ts` (T1, T3, T4) and `graph-capture-git-mode.test.ts` (T2, T5).
- **Eval pipeline collapsed to single-SCM (Phase 2)** — `apps/indusk-mcp/hooks/eval-trigger.js`'s `TRIGGER_RE` narrowed from `/\b(jj describe|git commit)\b/` to `/\bgit commit\b/`; change-ID extraction collapsed to a single `git rev-parse --short HEAD` call (no jj-first-then-fallback). `prompt-builder.ts` no longer accepts an `scm` field; `diffCommand` is `git show ${changeId}` everywhere. `persistent-evaluator.ts` + `evaluator-runner.ts` no longer call `getScm()`. `indusk eval baseline --task` collapsed to `git commit --allow-empty` + `git rev-parse --short HEAD`. The TDZ-on-scm-const gotcha in `persistent-evaluator.ts` is no longer applicable.
- **Skills collapsed to git-only (Phase 3)** — `apps/indusk-mcp/skills/jj.md` deleted. `work.md`'s dual-form `### If scm: "jj"` / `### If scm: "git"` commit-cadence sections collapsed to single-form do-then-commit on a feature branch. `highlight.md`'s "next commit (jj describe / git commit)" prose collapsed to "next `git commit`". `eval-review.md`'s dual `jj diff` / `git diff` examples collapsed to git-only. `git.md` lost its "if your project uses Jujutsu" framing.

### Removed
- **SCM abstraction layer (Phase 4)** — `apps/indusk-mcp/src/lib/scm/detect.ts`, `apps/indusk-mcp/src/lib/semantic-graph/jj.ts`, `getScm()`, `detectScm()`, `NoScmDetectedError`, `getJjReachable`, `NotAJjRepoError`. `lib/scm/index.ts` shrank from ~85 lines to ~60 (single git impl). `lib/semantic-graph/jj.test.ts` + `scm/detect.test.ts` + `scm-init-detection.test.ts` + `init-deferred-scm-warning.test.ts` deleted. `apps/docs/src/guide/scm.md` rewritten as "Source Control: Git". The `git-or-jj-substrate` planning brief gained a supersession banner.

### Fixed
- **eval-trigger hook now finds pnpm-global installs (1.30.2)** — pre-1.30.2, `apps/indusk-mcp/hooks/eval-trigger.js` checked two npm-style candidate paths (`<bin>/../lib/node_modules/...` and `<hook>/../../node_modules/...`) and gave up. ## [1.30.0] — 2026-06-27

### Added
- **Multi-agent coordination (1.30.0)** — concurrent Claude Code sessions on one project no longer collide. The old singleton `.claude/handoff.md` model had two reliable failure modes (catchup-mid-write blocking the other agent; handoff overwriting the previous handoff); both are structurally impossible in the new shape. **Three primitives**: (a) worktrees per agent (substrate from F1, already shipped), (b) **per-agent sections inside a single `.indusk/current.md`** — `## Project (shared)` anchor any agent edits, plus `## Session <short> — <task>` blocks each session owns, (c) the **`mcp__indusk__update_current_section` MCP tool** as the explicit write surface for the agent's own section (atomic read-modify-write). `/catchup` is pure-read for shared content (only side effect is `agent register` + the self-heartbeat in `list`); `/handoff` is a four-step session-end ritual: call `mcp__indusk__update_current_section` with the three section bodies → commit → `indusk agent done` → fire eval-trigger. Session ID comes from `CLAUDE_CODE_SESSION_ID` (UUID, inherited by subprocesses); fallback is `pid-<process.pid>`. Stale TTL configurable via `agents.stale_ttl_minutes` in `.indusk/config.json` (default 60). New `indusk agent register/done/list/prune` CLI — all operate on sections via the new `apps/indusk-mcp/src/lib/agents/current-md.ts` lib (parseCurrentMd / upsertSection / removeSection / pruneStaleSections / listSections). `indusk init` writes the new template, gitignores `.indusk/agents/` as precaution (the directory is no longer used), writes `agents.stale_ttl_minutes: 60`, and sets `.indusk/current.md merge=union` in `.gitattributes` so two branches appending different sections merge cleanly. `indusk update` SHA-detects the empty original-shape template and migrates idempotently; user-edited current.md content is preserved untouched. **Cross-machine coordination is out of scope for v1** (laptop ↔ desktop bulletins are local-only; future plan). **Rejected**: lock-and-snapshot state machine (reintroduces mutation races; serializes work), in-repo bulletin committed to main (noisy commits + merge conflicts), distributed locks (overkill for single-machine), per-worktree presence (fails visibility), fixed-section current.md + separate presence files (no explicit write surface for the agent; required dropping the write-side gap mid-plan and reshaping). **Section-shape design note**: the merge story works because each agent only appends its own block. `merge=union` plus a parser that splits delimiter-bounded blocks on `## Session` boundaries handles git's automatic dedup of trailing `---` lines. New user-facing guide at `/guide/multi-agent`; CLI reference at `/reference/cli/agent`; MCP tool entry at `/reference/tools/indusk-mcp#agent-tools`; skill references at `/reference/skills/catchup` and `/reference/skills/handoff`; ADR at `/decisions/multi-agent-coordination`. **Side finding**: surfaced a stray-quote typo in dusk's `.indusk/config.json` (introduced in b31c1d60) that was silently making the OTel role validator default-on for the past month — fixed in scope. Plans: `.indusk/planning/handoff-multi-agent/` (original — superseded in part) + `.indusk/planning/handoff-multi-agent-section-shape/` (final shape).

- **Extensions index — catalog + decision matrix at `apps/indusk-mcp/extensions/README.md` and `/reference/extensions/` (1.28.13)** — with three observability extensions (dash0, datadog, local-telemetry), one project-management extension (asana), four code-intelligence extensions (cgc, graphiti, sigma, falkordb), one browser-automation extension (chrome-devtools), two diagram/docs extensions (excalidraw, vitepress), one emit-side extension (otel), and seven domain-skill extensions (docker, nextjs, react, solidity, tailwind, testing, typescript), the seam between extensions started showing — agents had no single page to consult when the question was "which extension do I use for X?" and the differentiation prose was scattered across 19 individual skill.md files. The index closes that gap with a decision matrix table mapping problems → extensions (e.g., "Query staging/prod logs from a Datadog account" → `datadog`; "Query staging/prod logs from a Dash0 account" → `dash0`; "Local-only OTel during dev" → `local-telemetry`) plus a grouped catalog organized by problem space (observability query/emit, project management, code intelligence, browser automation, diagrams, framework skills). **Cross-references added** to the observability cluster's `See Also` sections (dash0, datadog, asana, local-telemetry) so navigation works in both directions: from any individual skill back to the index, and from the index forward to the individual skills. **Internal vs user-facing**: `apps/indusk-mcp/extensions/README.md` is the package-internal version; `apps/indusk-docs/src/reference/extensions/index.md` is the user-facing version (linked from the docs sidebar under Reference). Both stay in sync — the closing "Adding a new extension" section explicitly tells contributors to update both. Sidebar updated to expose the index as `Reference → Skills → Extensions Index`.

- **Asana MCP extension (1.28.13)** — opt-in project-management extension wrapping [Asana's official V2 remote MCP server](https://developers.asana.com/docs/using-asanas-mcp-server) at `https://mcp.asana.com/v2/mcp`. Mirrors the dash0/datadog extension shape: `apps/indusk-mcp/extensions/asana/{manifest.json, skill.md, .env.example}`. **Auth**: OAuth 2.0 with PKCE on first session launch — same shape as datadog (no API token in env vars). Tokens expire after 1 hour, refresh tokens handle renewal automatically. **Permissions are bounded by the user's existing Asana access** — MCP tokens cannot do anything the authorizing user couldn't already do via the Asana web UI; all actions appear as that user in audit logs. **No regional variants** — Asana is single-region, so `.env.example` has just one URL line. **V1 endpoint deprecates 2026-05-11** (3 days from this ship); we bake in V2 only — the deprecated `https://mcp.asana.com/sse` is intentionally not offered as a fallback. **Distinct problem space** from the observability extensions (dash0, datadog): Asana is for work coordination — tasks, projects, comments, custom fields. Reach for it when the question is about WHO is doing WHAT, not about service health. **Pre-registered clients only** — Asana V2 doesn't support dynamic client registration; Claude Code is pre-registered, so users don't need to register a client_id themselves; OAuth just works. **Not required-by-default** — opt-in like dash0/datadog; projects that don't use Asana see no change. Health check verifies the MCP server is registered in `.mcp.json`.

- **Datadog MCP extension (1.28.13)** — opt-in observability extension wrapping [Datadog's official remote MCP server](https://docs.datadoghq.com/bits_ai/mcp_server/) (launched March 2026, 16+ core tools plus toolset filtering for APM, Logs, Metrics, Monitors, Dashboards, Security Signals, Error Tracking, Feature Flags, DBM, LLM Observability). Mirrors the dash0 extension shape: `apps/indusk-mcp/extensions/datadog/{manifest.json, skill.md, .env.example}`. **Auth-model difference vs dash0**: Datadog uses **OAuth on first session launch** rather than a static Bearer token — `.env` only carries `DATADOG_MCP_URL` (regional endpoint), no secrets; OAuth completes in-browser. Setup: `cp .env.example .env`, uncomment your region's URL (US1/US3/US5/EU1/AP1/US1-FED supported), run `indusk extensions enable datadog`, complete OAuth on next Claude Code session. Toolset filtering via the `?toolsets=...` query param — defaults to `all` since Claude Code does its own client-side tool filtering. **Read-side only** — same convention as dash0: this extension configures how Claude queries Datadog, not how your services emit telemetry to Datadog (service-emit lives in your project's env-management setup). **Not required-by-default** — opt-in, like dash0; projects that don't use Datadog see no change. **No corresponding CLI** — Datadog's `dd-cli` is for emit-side instrumentation and isn't wired by this extension. Health check verifies the MCP server is registered in `.mcp.json`.

### Fixed
- **FullscreenDiagram component — three silent-failure bugs in the docs viewer (1.28.13)** — found while authoring docs on dawn-fde-toolkit; the same bugs were latent in dusk and in the template that `indusk init-docs` ships to consumer projects. **Bug A — underscore-prefix breaks `<script setup>` template bindings.** Handlers were declared as `_toggleExpand`, `_zoomIn`, `_zoomOut` (likely auto-fixed by `noUnusedVariables` + `argsIgnorePattern: "^_"` because the linter can't see template references). The template binds to `@click="toggleExpand"` etc. without the prefix, so Vue resolved bindings to `undefined` — clicks became silent no-ops. Fix: rename handlers without the prefix; add a Biome override disabling `noUnusedVariables` for `**/*.vue` (linter can't parse `<template>` blocks; the cost of letting unused script-setup vars slip is far smaller than silently broken click handlers). **Bug B — `bounds: true` + `boundsPadding: 0.1` silently locked panning** when the rendered SVG roughly filled the modal — drag did nothing because the constraints left zero pannable slack. Fix: `bounds: false` (Figma/Miro convention is unbounded panning with a reset button). **Bug C — wheel-to-zoom default felt wrong for diagram viewers.** `panzoom`'s default treats wheel as zoom; users expect wheel-to-pan with Cmd/Ctrl-wheel-to-zoom (matching every modern canvas tool). Fix: pass a `beforeWheel(e)` callback that pans on plain wheel and lets panzoom's zoom proceed when `e.ctrlKey || e.metaKey`. **Files changed**: `apps/indusk-docs/src/.vitepress/components/FullscreenDiagram.vue` (the dusk docs site copy), `apps/indusk-mcp/templates/FullscreenDiagram.vue` (the template `init-docs` ships to consumer projects), `biome.json` (override added), `biome-rationale.md` (entry added documenting why the override exists). Both .vue files are now byte-equal copies of the same fixed source. **Convention** (not enforced, project-by-project): wrap every mermaid block in `<FullscreenDiagram>` with blank lines around the inner fenced block — VitePress requires the blank lines to parse the mermaid markdown inside the Vue component. Will become the default in the `init-docs` scaffold once the convention stabilizes.

### Added
- **`get_project_info` MCP tool + community-graphiti-group-id-underscores lesson — close the silent-empty Graphiti recall loop (1.28.13)** — surfaced 2026-05-07 on dawn-fde-toolkit: agent queried `mcp__graphiti__search_nodes({ group_ids: ["dawn-fde-toolkit"] })`, got empty results, concluded "graph empty." Two failure modes were stacked: (1) hyphens in `group_id` hit a RediSearch syntax error which the lib catches and returns empty; (2) falling back to no `group_ids` filter doesn't scan all groups — also returns empty. Both look identical to "graph has nothing." InDusk's `getProjectGroupId(projectRoot)` already sanitizes hyphen → underscore on writes, but the agent had no callable tool to learn the sanitized form on reads — the `/catchup` skill literally said "call `getProjectGroupId(projectRoot)`," which is unreachable from agent context. **What changes**: (1) New `mcp__indusk__get_project_info` tool returns runtime project metadata as JSON: `project_group` (sanitized form), `scm`, `planning_dir`, `otel_role`, `otel_gate_emits`, `eval_enabled`, `eval_model`, plus a `graphiti_group_recall_example` block showing the exact `group_ids: [project_group, "shared"]` shape to use. Single source of truth for project metadata the agent needs at runtime — consolidates fields previously requiring 4 different reads (`getProjectGroupId`, `getScm`, `shouldEmitOtelGate`, `getEvalModel`). (2) `/catchup` skill prose rewritten — agents now call `mcp__indusk__get_project_info` to learn `project_group`, then pass it explicitly to graphiti queries. Old text said "the project group comes from `getProjectGroupId(projectRoot)`" which the agent couldn't actually invoke. (3) New community lesson `community-graphiti-group-id-underscores.md` documents both failure modes (RediSearch syntax error on hyphens; silent empty on missing filter) with the recovery shape. Lessons sync to all projects via `indusk update`. (4) `mcp__indusk__get_project_info` added to `init.ts` catchup permission allowlist so fresh inits don't see a permission prompt; existing projects will see a one-time prompt (low friction). **Why this matters**: silent empty was the worst failure mode — looked identical to "Graphiti is just empty" and the agent moved on without realizing it had skipped the recall step entirely. The lesson + tool surface make the convention impossible to miss.

- **`eval.model` config field — switches the eval agent's first-call model; defaults to `"sonnet"` (1.28.13)** — empirical pricing analysis on dawn-fde-toolkit revealed that fresh first-call evals running on Opus cost ~$4–7 each (matches Opus pricing math: 73K cache_create × $18.75/M + 1.83M cache_read × $1.50/M ≈ $4.35), while resume calls drop to ~$0.80 each (matches Sonnet math, not Opus). Lists the **behavioral assertions** that must be true for the feature to work, plus the **mechanism** by which each will be tested (vitest unit / vitest integration / e2e script / manual user test / etc.) — but NOT the test code. Discipline: assertions must be behavioral (user-visible) not functional (function/type/internal). "User can sign in with Google" not "googleAuth() returns a JWT." If a non-engineer stakeholder couldn't read an assertion without you explaining a function name, rewrite it. The test plan becomes the source rows for the impl's Test Trajectory: one trajectory row per assertion, with `Writable at`/`Passes at` columns added during impl authoring. Lifecycle now: `research → brief → test-plan → adr → impl → retrospective`. Optional first-class skip: bugfix/refactor workflows continue to skip the test plan; feature workflows include it by default. Will be evaluated on the next Numero feature; if it adds friction without payoff, easy to remove (single planner skill change).
- **Trajectory rationale validator + earliest-writable discipline (1.21.1)** — opt-in fifth trajectory rule. Every trajectory row whose `Writable at` is later than Phase 0 must have a matching entry in a `### Trajectory Rationale` subsection naming what prevents authoring the test before plan code lands. Phase 0 (the pre-plan baseline — "writable today against the current stack") is the default and needs no rationale, so the subsection only fills with the rows that actually require justification. Enable per impl with `rationale: required` in frontmatter; the planner skill template now sets it by default for new impls. The rationale-quality test asks *does this describe a compile error against today's symbols, or does it describe an uninteresting failure mode?* If the latter, the row is a rubber-stamp — move it to Phase 0 (red-for-uninteresting-reason is the whole point of an early-writable test, since it stays red through every intermediate phase as a tripwire). Legitimate Phase 1+ rationales: TypeScript imports of not-yet-exported symbols, constructor signatures that don't yet accept the test's args, enum values not yet defined. Validator rule `rationale-completeness` flags missing Phase 1+ entries and stale entries; mirrors across `.claude/hooks/validate-impl-structure.js` (write-time gate), `apps/indusk-mcp/hooks/validate-impl-structure.js` (package source for `indusk update` to propagate), and `apps/indusk-mcp/src/lib/trajectory/validator.ts` (TS source). 7 new tests (T13–T16 + composite cases + Phase 0 exemption) in validator.test.ts. New lesson `test-red-at-earliest-writable-phase.md` codifies the rule, the rationale-quality test, and the compile-error-vs-rubber-stamp framework.
- **ADR template now opens with a Goal section (1.21.1)** — every new `adr.md` now includes a `## Goal` section immediately before `## Y-Statement`. One bolded sentence states the headline outcome in plain language ("what will be true when this ADR's decisions ship that isn't true today"), followed by a 2-4 sentence paragraph grounding the goal in user-visible terms and naming at least one current failure the decision fixes. The Y-statement's seven canonical clauses remain unchanged — the Goal lets a reader skim the headline without hunting through them. Ships via the planner skill template at `apps/indusk-mcp/skills/planner.md`; `indusk update` copies it into each project's `.claude/skills/planner/SKILL.md`.

### Fixed
- **Eval agent hook-spawn silent crash (1.19.1)** — the PostToolUse hook at `apps/indusk-mcp/hooks/eval-trigger.js` spawned the evaluator as `node --input-type=module -e <inline-script>` where the inline script's first two statements used CJS `require()` for fs and path. `require` is undefined in ESM scope → `ReferenceError` at parse, line 2, before any user code ran. `stdio: "ignore"` swallowed the stderr. **Every hook-spawned evaluator since at least 2026-04-11 crashed silently** — scorecards stopped appearing in `.indusk/eval/results.log`, the system looked idle, nothing surfaced. Direct invocations (via `indusk eval` subcommands and ad-hoc node scripts) were unaffected. Fix: inline script now uses ESM-native `import { mkdirSync, appendFileSync } from "node:fs"` and `import { dirname, join } from "node:path"`. Belt-and-suspenders: added `process.on("uncaughtException")` + `process.on("unhandledRejection")` handlers that write an `error: true` entry to `results.log` before `process.exit(1)` — so the next silent-failure class is loud. Diagnosed via the predecessor OTel plan's falsification ritual; regression test grep-asserts the fix. See the [eval overview's Known Failure Modes section](/reference/eval/overview#known-failure-modes) for the debugging recipe.
- **Eval agent dataset routing via composable.env (1.18.2)** — when `OTEL_EXPORTER_OTLP_HEADERS` env var is set with a `Dash0-Dataset=<project-dataset>` entry (composable.env default), exporter-constructor headers lose — OTel spec says env beats constructor. Fixed by (1) adding `EVAL_AGENT_DATASET` env var to the dataset resolution chain (priority: `INDUSK_EVAL_OTEL_DATASET` > `EVAL_AGENT_DATASET` > config `eval.otel.dataset` > `"agent"` default), and (2) rewriting `Dash0-Dataset=<old>` to `Dash0-Dataset=<eval-agent-dataset>` in `OTEL_EXPORTER_OTLP_HEADERS` in-place before the exporter reads it. Confirmed end-to-end via `dash0 spans query --dataset agent`: `final-smoke-via-ce-env` span landed in the agent dataset with `EVAL_AGENT_DATASET=agent` + `DASH0_DATASET=indusk-test` in the shell env. See `env/components/dash0.env` for the composable.env wiring.
- **Eval agent OTel header env parsing (1.18.1)** — the OTel SDK's `OTEL_EXPORTER_OTLP_HEADERS` env parser silently drops Bearer tokens that contain a space (e.g., `Authorization=Bearer auth_xxx`). Result: exports retry-looped to no effect even though `initEvalOtel` logged success. Fixed by reading `DASH0_API_TOKEN` directly in `otel.ts` and attaching `Authorization: Bearer ${DASH0_API_TOKEN}` to the exporter constructor's `headers` option. User-set `OTEL_EXPORTER_OTLP_HEADERS` env still takes precedence per OTel spec. Diagnosed via `dash0 spans query` showing our test probe reached Dash0 only when headers were hardcoded in the constructor.
