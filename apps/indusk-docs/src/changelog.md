## [Unreleased]

### Added
- **Local telemetry — new required-by-default extension + machine-global daemon (1.28.0)** — the first Arc 1 capability after admin-ui-hosting: every InDusk project now gets a localhost OTel backend for free. A new `local-telemetry` extension (required-by-default on every `indusk init` / `indusk update`) runs a machine-global daemon — Jaeger v2.17.0 + OTel Collector core 0.150.1 as native binaries, not containers — that absorbs dev-profile traces and logs and exposes them to both the agent (via MCP) and you (via `indusk telemetry *` CLI). Staging/prod OTel continues to route to Dash0 unchanged; only the `development` profile redirects to `http://localhost:4318`. **Daemon lifecycle**: `indusk telemetry start | stop | restart | status` — parallel shape to `indusk ui *`; metadata at `~/.indusk/telemetry.{pid,json,log}`, registry at `~/.indusk/telemetry/projects.json`. Both PIDs (Jaeger + otelcol) tracked and identity-verified via `verifyIdentity(pid, port)` (PID liveness + port listening) — same pattern that hardened the admin-UI daemon in 1.27.5. **Binary distribution**: four platform-specific npm packages at `@infinitedusky/telemetry-binaries-{darwin-arm64,darwin-x64,linux-arm64,linux-x64}`, listed as `optionalDependencies` on indusk-mcp with matching `os`/`cpu` filters — npm installs exactly one per consumer machine (esbuild/swc/biome pattern, zero custom download code). Build script at `scripts/build-telemetry-binaries.sh` fetches + SHA-verifies + packs per-platform; pins in `packages/telemetry-binaries-shared/UPSTREAM.json`. **Headline spike finding**: Jaeger v2 IS an OTel Collector distribution (ships `otlp` receiver, `batch`/`memory_limiter`/`filter` processors, `jaeger_storage`/`jaeger_query`/`healthcheckv2`/`jaeger_mcp` extensions) — one binary for the entire trace path. A separate otelcol core binary handles the log path (the `file` exporter Jaeger doesn't ship). Query latency measured at p95=12.2ms (40× under the 500ms budget). **Agent surface — traces**: Jaeger's bundled `jaeger_mcp` extension is wired directly into every registered project's `.mcp.json` (same pattern as dash0's cloud MCP). The agent gets 8 pre-computed tools (`search_traces`, `get_trace_topology`, `get_span_details`, `get_services`, `get_span_names`, `get_trace_errors`, `get_critical_path`, `health`) without indusk-mcp wrapping them. **Agent surface — logs**: custom `tail_logs` MCP tool in indusk-mcp filters the otelcol JSONL sink by `service` / `level` / `since_minutes` / `limit`. **Human CLI**: `indusk telemetry tail | trace | services | reset` mirror the agent surface for terminal diagnosis. **Required-by-default resolution**: `autoEnableExtensions` split into two passes — Pass 1 iterates required extensions and enables every `required: true` extension not in `.indusk/config.json`'s new `disabled_extensions` array, Pass 2 runs the original detection-based flow. Both `indusk init` and `indusk update` call `autoEnableExtensions`, so fresh scaffolds AND pre-1.28 project upgrades pick up local-telemetry identically. **Escape hatch**: hand-edit `.indusk/config.json` to add `"disabled_extensions": ["local-telemetry"]` — init and update both honor it silently. No CLI affordance; opting out is deliberate and rare. **Hook plumbing fix** (surfaced by Phase 6 tests): `extensionsDisable` now fires `on_disable` BEFORE renaming the manifest dir, symmetrical to how `extensionsEnable` fires `on_init`/`on_enable` — pre-1.28 the CLI silently skipped `on_disable`, so `indusk extensions disable local-telemetry` would rename the manifest but never run `indusk telemetry deregister`, leaving daemons running and `.mcp.json` stale. Also new: `INDUSK_BIN` env var overrides `indusk ` in hook shell commands (test-critical for pre-1.28 global + pre-release tarballs), telemetry registry realpath-normalizes paths (macOS `/var` ↔ `/private/var` phantom-no-match fix), Jaeger's self-metrics disabled via `service.telemetry.metrics.level: none` (port 8888 cross-spawn conflict fix, test flakiness 50% → 0%). Tests: 10 telemetry tests across 5 files (T2/T6/T12/T18/T19/T20/T23 + 3 cases in enable/disable/upgrade). Full architecture + ADR at [`reference/telemetry/overview`](/reference/telemetry/overview), CLI reference at [`reference/telemetry/cli`](/reference/telemetry/cli). Foundation for two downstream plans: `telemetry-watcher-agent` (local-only async observer) and `unified-telemetry-query` (later user-facing Jaeger + Dash0 translation layer).

- **Admin UI remembers collapsible section state across page reloads (1.27.7)** — the Brief section (and every other `<CollapsibleSection>`: Research, Test Plan, ADR, each Phase) no longer re-opens itself on every visit after the user has explicitly closed it. Surfaced by the user mid-dogfood on admin-ui-hosting: "every time I come, the brief is open when I have to close it." Fix: `<CollapsibleSection>` accepts an optional `persistKey` prop; when set, the initial state reads from `localStorage[persistKey]` (encoded as `"1"` / `"0"`) with `defaultOpen` fallback, and every toggle writes back. Key convention is `plan:{planName}:section:{slug}` for top-level sections and `plan:{planName}:phase:{N}` for phase collapsibles — stable across re-renders, scoped per-plan so navigating between plans doesn't clobber state. Without `persistKey`, the component behaves exactly as before (ephemeral, `defaultOpen` on every render). SSR/privacy-mode safe: `typeof window` guard, try/catch around both reads and writes, swallowed exceptions fall through to `defaultOpen`. Admin UI wires `persistKey` into every CollapsibleSection in `PlanDetail` — Research, Brief, Test Plan, ADR, and every phase (pre, falsification, follow-up). Tests: 4 new component tests in `CollapsibleSection.test.tsx` (absent-key fallback, stored "0" overrides defaultOpen=true, stored "1" overrides defaultOpen=false, toggle round-trip writes) + 2 new tests in `PlanDetail.test.tsx` (PlanDetail wires persistKey → pre-seeded "0" renders Brief closed; absent storage renders Brief open). See [admin-ui component-conventions](/reference/admin-ui/component-conventions#collapsiblesection-persistence-1-27-7) for the persistKey key convention + SSR/hydration behavior + testing guidance.

### Fixed
- **Admin UI daemon + registry + cwd-walk-up hardening (1.27.5)** — four defensive fixes surfaced by the `/falsify admin-ui-hosting` pass (the first dogfood of the new phase-authoring flow). **(1) Daemon identity verification**: `daemonStatus()` and `daemonStop()` in `apps/indusk-mcp/src/lib/admin/daemon.ts` now gate on a combined `isAlive(pid) && isPortListening(port)` check, not bare `isAlive` alone. After a daemon crash the OS can recycle the PID to an unrelated process (bash, postgres, another vitest); without the port check, `uiStart`'s double-start guard would refuse to spawn and blame a stranger, and `uiStop` would SIGTERM them. On identity mismatch, `daemonStatus` sweeps the stale PID+meta files; `daemonStop` likewise cleans up and returns `stopped:true` without signaling. **(2) Registry quarantine**: `readRegistry()` in `apps/indusk-mcp/src/lib/admin/registry.ts` now renames a malformed `projects.json` to `projects.json.corrupt.{ISO}.bak` before returning `emptyRegistry()`, so the next `writeRegistry` creates a fresh file without silently overwriting the damaged bytes. Previously, hand-editing a registry typo could destroy every registered project with no recovery path; now the original contents are preserved alongside the fresh file, and a stderr warning names the backup path. **(3) Cwd walk-up in bare `indusk ui`**: `resolveOpenPath()` now walks up cwd's parents (capped at 40 ancestors) to find the nearest registered project, matching realpath against each registered project's realpath. Previously the function did an exact-string compare against the project's root, so `cd apps/indusk-mcp && indusk ui` silently fell through to `/` instead of opening the project's page — regressing T16's cwd-aware promise for any invocation deeper than the project root. **(4) Test-mock fix**: `apps/indusk-admin/src/app/p/[project]/page.test.tsx` was missing `readProjectResearch` in its `@/lib/planning-reader` mock, so the test file failed to load after Phase 6 added `readProjectResearch` to the per-project layout. Phase 6's regression check relied on `tsc --noEmit`, which doesn't import the test file; added to the mock and the file loads. Tests: `apps/indusk-mcp/src/lib/admin/__tests__/daemon-identity.test.ts` (2 cases), `registry-quarantine.test.ts` (2 cases), `apps/indusk-mcp/src/__tests__/resolve-open-path-walkup.test.ts` (4 cases). 8 new green assertions total; all Phase 1–6 admin-ui and indusk-mcp admin tests still pass. This release is the first landing of a Phase authored by `/falsify` under the new 1.27.4 phase-authoring flow.

### Changed
- **`/falsify` becomes a phase-authoring action (1.27.4)** — the falsification ritual no longer runs tests inline; it investigates the plan, forms specific hypotheses, and appends a new Falsification Phase to the plan's `impl.md` with trajectory rows for the hypothesis tests + implementation items for the fixes + standard Verification / Context / Document gates. The plan's impl status stays `in-progress`; `/work` picks up the phase later like any other phase. `/retrospective`'s Step 0 gate gains a third pass condition: "all impl phases terminal" (alongside the existing legacy `isFalsificationComplete` check and the `falsification: skipped` + reason frontmatter path). **Backwards compatible** — plans authored under the old ritual that have completed `falsification.md` files continue to work unchanged; the `apps/indusk-mcp/src/lib/falsification/log.ts` library is kept in place for legacy reads. **Motivation**: the old sidecar-log shape was invisible in admin UI (phases render; log files don't), and forced immediate test execution (no way to capture hypotheses now and execute later). The new shape makes falsification visible (phases render), deferrable (capture now, run later), and traceable (the plan's phase sequence shows normal work → falsification → fix phases → close). Also removes the three-outcome-per-hypothesis branching ("fix in scope / spawn new plan / accept as finding") — in-scope fixes become items in the Falsification Phase, which is the new default; "spawn new plan" stays available for genuinely large gaps but isn't decided inside the ritual; "accept as finding" is gone (findings that deserve record either become phase items or surface in retrospective, not a sidecar log). Skill files updated: `apps/indusk-mcp/skills/falsify.md` + `apps/indusk-mcp/skills/retrospective.md` (+ mirrored to `.claude/skills/*/SKILL.md`); guide doc `apps/indusk-docs/src/guide/falsification-ritual.md` rewritten with phase-authoring walkthrough + legacy-plans section. Regression test `apps/indusk-mcp/src/__tests__/retrospective-gate-backcompat.test.ts` locks in that legacy `falsification.md` plans still pass the gate (3/3 assertions). Three pending retros (`admin-ui-hosting`, `indusk-admin-ui`, `eval-agent-mcp-access`) will be the first real uses of the new flow.

### Added
- **`indusk ui restart` subcommand (1.27.1)** — stops the running daemon (if any) and starts a fresh one in a single command. Picks up a new admin bundle after `npm i -g @infinitedusky/indusk-mcp@<newer>` without forcing users to chain `indusk ui stop && indusk ui start`. Honors `--port` / `--no-open` via `optsWithGlobals()` just like `start`. If no daemon is running, the stop half prints `Admin UI is not running.` and the start half runs normally — equivalent to a plain `start`. `start` intentionally continues to no-op when a daemon is already running (T4's contract), so `restart` is the load-bearing path for upgrade flows. Two new tests in `admin-cli-lifecycle.test.ts` cover the running-daemon case (new PID returned, stop + start both in output) and the no-daemon case (no-op stop, fresh start). Surfaced while smoke-testing 1.27.0 on dusk — old 1.26.0 CLI processes (which didn't daemonize and ran `next dev` in the foreground) had to be killed by hand before 1.27.0 could take port 3939, and there was no one-command recovery.

### Added
- **Admin UI hosted as a single long-lived daemon (1.27.0)** — replaces the broken per-project `indusk ui` model from 1.26.0. The admin UI is now served by one native Node daemon that covers every InDusk project on the machine, not a new Next.js instance per project. New CLI shape: `indusk ui start` spawns the daemon (detached, survives terminal close), `indusk ui stop` SIGTERMs it, `indusk ui status` reports running/port/registered-project count, and bare `indusk ui` is aliased to `start` with cwd-aware browser open (inside a registered project → `/p/{this-project}/`, outside → `/`). Daemon metadata lives at `~/.indusk/admin-ui.{pid,json,log}`. Multi-project via `~/.indusk/projects.json` registry, populated transparently by `indusk init` (appends) and `indusk update` (validates + touches). Routes restructured to `/p/[project]/...` with `/` as the project grid (one card per registered project, each linking into its namespace) and `/scorecards` walking every registered project's `.indusk/eval/results.log` with project labels and cross-project sort. Stale/deleted registry entries render a 200-page `StaleProjectFailurePage` with a "needs reconfiguration" recovery hint (`cd` + `indusk update`), never 500 or 404. Bundling variant A3: `prepublishOnly` runs `pnpm build && pnpm --filter indusk-admin build && node scripts/bundle-admin.js`, copying the pre-built Next.js production output into `apps/indusk-mcp/admin/` and shipping it in the tarball — consumers need zero extra tooling (no `pnpm install`, no `next build`, no workspace assumption). Tarball size ~12 MB (cap 50 MB). **Breaking change from 1.26.0**: the per-project `indusk ui` is removed; 1.26.0 users must run `indusk init` once per project to register (or `indusk update` for already-init'd projects), then `indusk ui start` from anywhere. Three implementation gotchas baked into CLAUDE.md: (1) `commander@13` silently drops duplicate options when declared on both parent + child subcommands — options live only on the parent, subcommands read via `this.optsWithGlobals()`; (2) vitest `fileParallelism: false` in the node project because multiple HTTP smoke tests each spawn `next dev` and parallel CPU contention makes `next dev` miss its "Ready in" stdout within 30s; (3) `resolveOpenPath()` normalizes registry paths and `process.cwd()` via `safeRealpathSync` because macOS `mkdtempSync` returns `/var/folders/...` while `process.cwd()` returns `/private/var/folders/...` — raw string compare silently misses. See [Admin UI Overview](/reference/admin-ui/overview) and [Admin UI CLI](/reference/admin-ui/cli) for the daemon model, routing tree, env vars, and recovery procedures.

### Fixed
- **`rationale_baseline` frontmatter regex anchored to line start (1.25.1)** — surfaced by the `/falsify` ritual against `rationale-baseline-frontmatter` immediately after 1.25.0 shipped: the JS hook port's `/rationale_baseline:\s*(\d+)/` regex was not line-anchored, so a frontmatter whose `title:` value happened to contain the literal substring `rationale_baseline: 1` (e.g., a documentation plan about the key itself) silently inherited that baseline from the title's substring. A Phase-1 row that should have required rationale would silently pass. Fix: changed to `/^rationale_baseline:\s*(\d+)/m` — the `m` flag + `^` anchor require the key to appear at the start of a line, i.e., as a top-level YAML key. Mirrored across `apps/indusk-mcp/hooks/validate-impl-structure.js` and `.claude/hooks/validate-impl-structure.js`. Two regression tests in `apps/indusk-mcp/src/__tests__/rationale-baseline-falsify-substring.test.ts`: substring-only attack must be rejected (validator exits 2), legitimate top-level key must still be honored (validator exits 0). The same unanchored-regex shape exists for sibling keys (`gate_policy:`, `rationale:`, `trajectory:`, `workflow:`) but those are presence/enum checks where false-positive risk is far lower than for an integer-valued key — intentionally out of scope. Demonstration of the falsification ritual catching a real bug introduced one publish ago — exactly the discipline pattern that `eval-scorecard-format-fix` retro identified as load-bearing.

### Added
- **Trajectory `rationale_baseline` frontmatter key (1.25.0)** — plans can declare their writable baseline via `rationale_baseline: N` (integer, default `0`). Rows with `Writable at <= baseline` are exempt from the `### Trajectory Rationale` subsection. Use when Phase 1 IS the enabling work — refactors, schema migrations, scaffolding plans where "writable today against the current stack" is meaningless because the current stack is what's being replaced. Default `0` preserves all existing plan behavior; the change is purely additive. The validator's two error messages are baseline-aware (`"later than Phase ${baseline}"` instead of hardcoded `"Phase 0"`), so operators see the rule the plan declared, not the global default. Mirrored across TS source (`apps/indusk-mcp/src/lib/trajectory/validator.ts`), JS hook port (`apps/indusk-mcp/hooks/validate-impl-structure.js`), and project install (`.claude/hooks/validate-impl-structure.js`). 5 unit tests + 5 subprocess-based parity fixtures (`apps/indusk-mcp/src/__tests__/rationale-baseline-parity.test.ts`) verifying TS source ↔ JS hook port produce identical pass/fail decisions on shared input. Surfaced from Numero's `table-lifecycle-unification` plan: 41 of 44 trajectory rows were `Writable at: Phase 1` because Phase 1 was "rename DB tables + author compat views" — tests couldn't be written against pre-migration state without literally reverting production code. The hook nevertheless demanded rationale for all 41 rows, fired on every Edit to impl.md, and agents routed around it via Write-based heredocs (which bypass `PreToolUse:Edit` entirely). The rail-integrity problem: a gate designed to catch real authoring mistakes fired on legitimate usage and taught the agent to ignore it. With this fix, Numero's three queued plans (`restart-recovery`, `coc4-verification-debt-audit`, `drop-compat-views`) — each with Phase 1 as enabling work — can be authored cleanly. Docs: new "Trajectory Rationale and the `rationale_baseline` key" section in `apps/indusk-docs/src/guide/test-trajectory.md` documenting the key, the previously-undocumented `rationale: required` opt-in, and a frontmatter key reference table.

### Fixed
- **Eval scorecard timestamps reflect actual completion time (1.24.3)** — the scorecard's `timestamp` field was being filled in by the LLM (per the prompt: `"timestamp": "{ISO 8601 now}"`) but the LLM doesn't know the real current time and tends to round to convenient values like 5-minute marks (e.g. `2026-04-19T18:25:00Z`). The wrapper code overrode `usage` and `telemetryPosted` after parsing the scorecard but didn't override `timestamp` — so the model's guess survived to disk. Reading `results.log` showed timestamps clustered at suspiciously round times. Fix: override `scorecard.timestamp = new Date().toISOString()` immediately after `JSON.parse` in all 3 spawn paths (persistent-evaluator's resume + fresh, evaluator-runner's background + sync). ### Changed
- **Work skill: describe-then-do order is load-bearing (1.24.2)** — work skill's commit guidance restructured to make the order explicit and unmissable: `jj new` → `jj describe -m "..."` (intent in present/future tense) → do the work → check item off → repeat. Added an explicit anti-pattern callout naming WHY describe-after-do is broken: (a) the eval agent fires on `jj describe` and scores against whatever description is current at that moment, so late descriptions mean the agent scores work that's already done with no intent context; (b) the working copy IS the current commit in jj, so any uncommitted state automatically gets attributed to the previous unit's description if you don't `jj new` first.
