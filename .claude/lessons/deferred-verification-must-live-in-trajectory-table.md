# Deferred Verification items must live in the trajectory table, not a Verification-gate bullet — or the close-out auditor never sees them

A plan's mitigation-drift auditor (`auditPlanAtClose`) reads the Test Trajectory table to find Deferred Verification rows — it does not parse prose bullets inside a phase's `#### Phase N Verification` gate section. dawn-external-orchestrator authored its A8 acceptance item ("comparative quality read is Sandy's human judgment") as a Verification-gate bullet rather than a trajectory-table row with a `reason:`/`would require:`/`mitigation:` block. The result: `auditPlanAtClose` returned `deferred: []` and the audit never saw the plan's only deferred item, even though A8 was later correctly resolved by an explicit human sign-off.

**Why it matters:** the auditor's whole job is to catch a deferred item that never got its follow-through — a human-judgment gate that silently never got judged. If the item isn't shaped as the auditor expects, that safety net has a hole exactly where it matters most (the one thing that was intentionally deferred). This didn't cause harm here only because the sign-off happened anyway, by habit rather than by being caught.

**What to do instead:** any Deferred Verification content — "this can't be structurally verified, a human must judge it" — belongs in the Test Trajectory table as a proper row (with `reason:`, `would require:`, `mitigation:`), never as a bullet under a phase's Verification gate, even when it reads naturally as prose there. If a future case makes gate-bullet deferred items unavoidable, the auditor itself needs to also parse those bullets — but the simpler, immediate fix is authoring discipline: deferred verification is trajectory-table shaped, full stop.
