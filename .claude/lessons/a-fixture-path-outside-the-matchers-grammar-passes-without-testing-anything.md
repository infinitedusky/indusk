# A fixture's literal path/string must be checked against the matcher's actual grammar (prefix list, regex) — a path the grammar never reads makes the test pass or fail for the wrong reason

context-tiers A22 (indusk context check-pointers walking each declared repo's context files, commit 9a216c2c) first wrote its workbench fixture with `src/real.ts` / `src/missing.ts` paths. `checkAllContextPointers`'s pointer grammar (`POINTER_PREFIXES` in `apps/indusk-mcp/src/lib/context-pointers.ts`) only recognizes `.indusk`, `apps`, `docker`, `packages`, `.claude` as pointer-shaped prefixes — `src/...` is invisible to it. The fixture would have kept the test red after the actual fix landed, but for the wrong reason: not because the repo-root-resolution bug was still present, but because the pointer scanner never extracted a `src/...` reference as a pointer at all. The test was corrected to use `apps/real/thing.ts` / `apps/gone/thing.ts`, which the grammar does read, making the assertion actually exercise the code path it claims to test.

This is a sibling failure mode to `a-green-falsification-row-can-be-green-for-an-uninteresting-reason` (pass for an uninteresting reason) and `a-test-that-fails-to-load-is-not-a-red-test-drive-signature-changes-through-a-stable-boundary` (red because the test never loaded) — a third way a test's exit code can be disconnected from the behavior it claims to verify: the fixture data itself falls outside the scope of whatever regex/prefix-list/allowlist the code under test uses to decide what counts as input. None of exit code, pass, or fail tells you this happened; only reading the matcher's actual grammar and checking the fixture's literals against it does.

**How to apply:** whenever a test fixture embeds a literal string/path that a regex, prefix list, token grammar, or allowlist is supposed to recognize (pointer prefixes, lesson tokens, glob patterns, env var name patterns), before trusting the test's red/green, read the matcher's actual pattern and confirm the fixture's literal falls inside it — don't assume a plausible-looking path like `src/foo.ts` is in scope just because it reads naturally as "a file path." Grep the pattern definition and manually check the literal against it, the same way you'd fault-inject to verify a red test is red for the right reason.

See `.indusk/planning/archive/context-tiers/impl.md` (A22 note) and `apps/indusk-mcp/src/__tests__/context-tiers-pointers.test.ts`.
