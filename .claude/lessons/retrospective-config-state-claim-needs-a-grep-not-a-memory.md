# A retrospective's Quality section claim about a config file's current state ("rule X is not enabled") must be grepped against that file, not recalled from memory of an earlier commit

The planner-promises retrospective (`.indusk/planning/planner-promises/retrospective.md`, Quality section) wrote: "One unused import (`gray-matter`) went unflagged; the Biome config does not enable `noUnusedImports`, and enabling it is a repository-wide change, not this plan's." This is false: `biome.json` has had `"noUnusedImports": "error"` enabled since 2026-03-19 (`biome-rationale.md`), which predates this plan by over six months and covers the entire plan's lifetime. The claim was very likely true for a brief moment mid-plan (an unused `gray-matter` import that existed transiently in one commit before a later refactor commit removed it — confirmed no file in `lib/promises/` currently has an unused gray-matter import), but by the time the retrospective was written, the author recalled "biome didn't catch this" from that moment rather than re-checking the config file's actual current rule set.

Why: a retrospective's Quality section is the input the project explicitly uses to decide "what mistake could become a rule" (CLAUDE.md: "the ratchet only tightens... the retrospective's own quality audit asks what mistake could become a rule"). A wrong claim here doesn't just mislead a reader — it risks the opposite of a ratchet: a future session reading "noUnusedImports isn't enabled, enabling it would be a repo-wide change" might believe that gap still exists and either re-propose work that's already done, or trust a false sense that this class of bug can slip through today.

How to apply: before writing a retrospective (or any plan document) sentence of the form "the config does/doesn't enable X" or "X is/isn't currently true," grep the actual config file in the same turn, even if you're confident you remember checking it earlier in the session — the codebase can have changed since, or the memory may be of a transient state rather than the current one. This generalizes audit-a-docs-claim-against-the-code-before-publishing-not-at-retrospective (which is about reading an implementing function's control flow) to the narrower, cheaper case of a static config file's boolean/enum state, which has no excuse for being unchecked since it's a single grep.
