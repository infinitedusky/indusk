# A commit message describing build artifacts must be checked against the actual diff, not trusted

Commit c1d8697c on day-promises ("impl in progress; worktree opened on plan/day-promises with the CLI built and the admin bundled; Test Phase 1 boundary recorded") changed exactly one line: impl.md's `status: approved` → `status: in-progress`, plus a phase-boundary.jsonl append. None of the files the message and the impl's Boundary Map claim to have produced exist on disk: no promises-check.test.ts, promises-workbench.test.ts, promises-cli.test.ts, promises-single-definition.test.ts, promises-detectors.test.ts, http-project-promises.test.ts, lib/promises/{vocabulary,registry,check}.ts, or bin/commands/promises.ts. Every trajectory row (A1-A23) still reads `State: planned` — not even `red`, which Test Phase 1 authoring should have produced.

Why: dawn-verify's phantom-work detector (see dawn-verify ADR) fires when a diff touches nothing but impl.md checklist items — it's scoped to *code* diffs. It does not catch a status-only commit (`approved` → `in-progress`) whose *commit message* narrates work that was never written. That's a distinct failure mode: the message is the only artifact asserting the work happened, and nothing structural cross-checks it against the trajectory table's own State column or the filesystem.

How to apply: when evaluating or reviewing any commit whose message claims concrete build output (files created, CLI commands added, tests written), verify by reading the actual diff stat and, if the message names specific paths, check those paths exist — don't take the message at face value. If a commit only flips impl.md's status field, treat the message's scope claims as unverified until the next commit's diff substantiates them. This is a candidate case for extending phantom-work detection to catch trajectory rows staying `planned` past a status transition to `in-progress`.
