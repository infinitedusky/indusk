# A bookkeeping filter that whitelists "the plan's own folder" can leak exactly what it exists to hide, when that folder holds both the clean record and the mutable session notes

plan-review-subagent's falsification phase (Build Phase 4, finding A15) caught this in `apps/indusk-mcp/src/lib/audit/inputs.ts`: `isBookkeeping(path, planDir)` excludes everything under `.indusk/` from the auditor's diff EXCEPT the plan's own folder (`path.startsWith(".indusk/") && !path.startsWith(`${planDir}/`)`). The exception exists for a real reason — the plan's own documents need to reach the auditor. But the plan's own `impl.md` is also where falsification and cleanup append their findings as prose after approval, and the diff computes against the branch's full history since the trunk, so those appended phases show up in the diff verbatim — leaking exactly what the promise `the-auditor-sees-the-plan-not-the-session` says must not reach the reader ("nothing … from the builder's own findings"). The architecture had already solved this correctly for the *document* fields (`implAsApproved` is read at the approval merge, so it excludes the later phases) but the *diff* field, computed separately with a cruder path-based filter, didn't inherit that same care.

Why this matters: a directory-prefix whitelist is a structural rule ("this path is fine"), but "fine to share" and "lives in this folder" are not the same property once a folder accumulates both a clean, versioned record (the approved snapshot) and ongoing mutable annotations (the builder's running notes) side by side. The whitelist can't tell them apart, because it only sees paths, not provenance.

How to apply: when building a filter that whitelists a folder specifically so one trusted artifact can pass through, ask whether anything else lives in that same folder that the filter is supposed to keep out. If a single folder holds both "the thing this exists to share" and "the thing this exists to hide," filtering by path alone is not enough — filter by the artifact's version/provenance instead (as the document fields in this same code already correctly do, reading the approved git ref rather than the working copy). This is a different failure mode from general single-definition duplication (see `structural-single-definition-test-for-must-agree-invariants`) — it's specifically about a directory-scoped allow-rule being broader than the trust boundary it's meant to enforce.
