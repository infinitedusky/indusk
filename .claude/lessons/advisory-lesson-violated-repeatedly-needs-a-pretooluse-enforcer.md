# An advisory lesson that keeps getting violated needs a PreToolUse enforcer, not a fourth retrospective entry restating it

The lesson `edit-plan-documents-only-through-the-edit-tool-not-sed-or-heredoc` has now been violated in three separate plans: dawn-workbench-execution (where it was first written), planner-promises (where the same mistake truncated another session's uncommitted current.md and destroyed 147 lines, unrecoverably), and admin-plan-authoring (three more script-based impl.md edits). Each time, the lesson was advisory — nothing in the tool-call path actually refuses a `sed -i`, a Python `open(path, "w")`, or a heredoc redirect against a plan document, so the gate hooks (which only fire on Edit/Write tool calls) never see these writes at all.

Why it matters: a lesson's title loading "hot" every catchup is not the same as the rule being enforced. An advisory lesson relies on the working agent remembering and choosing to comply, every single time, under time pressure, for the entire lifetime of the project — and this project's own history shows that fails on a roughly one-plan-in-three cadence for this specific rule. Three strikes against the same advisory lesson is a strong signal that the lesson has reached the end of its usefulness as advice and needs to become a structural guard.

What to do: when a lesson is violated for a second or third time despite being recorded, stop re-recording it in the next retrospective and instead build the enforcer it's been asking for. For this specific case: a PreToolUse Bash hook that refuses shell-based writes (`sed -i`, `python -c "open(...,'w')"`, heredoc redirects, etc.) targeting `.indusk/planning/**/*.md` or `.indusk/current.md`, forcing every edit through Edit/Write where the existing gate chain already runs. More generally — when `list_lessons` or a retrospective shows the same advisory lesson's title recurring across unrelated plans, that repetition is itself the signal to promote it from advisory to guarded, not to write it down a fourth time.
