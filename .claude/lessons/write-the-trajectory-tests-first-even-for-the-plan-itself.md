# Authoring the tests before the code finds contradictions in the plan's own design docs that research, brief, and ADR all missed

A plan's research, brief, and ADR can all agree on a design that is silently self-contradictory — and the contradiction survives three rounds of prose review because prose doesn't force you to state both halves of a rule in the same breath. Writing the actual test assertions does, because each assertion has to be checked against the others as literal executable claims, not paraphrased intentions.

**What happened:** `test-phase-structure`'s research, brief, and ADR all agreed on two rules: A1 ("an impl with no test phase is refused") and A4 ("every existing impl still validates with no edits"). Both sound reasonable individually. But every one of the 52 existing impls has no test phase — so A1 and A4 directly contradict each other. This was invisible across three planning documents and became visible within minutes of actually writing the test assertions side by side. The resolution — a `test_phases: required` frontmatter opt-in, mirroring the existing `trajectory: required` pattern — became the hinge the plan's entire zero-migration story depended on.

**A second, sharper finding from the same session:** A4's premise ("all 52 impls validate today") was simply checked and found **false** — nine already failed for unrelated reasons. Rewriting A4 as a differential guard (pin the nine known failures by name, assert no NEW failures) was both more honest than the false blanket claim and stricter than it: a new regression can no longer hide inside a pre-existing failure the way it could under "all pass."

**Why it matters:** design documents describe intent in prose, which tolerates a level of ambiguity that executable assertions do not. The gap between "the design sounds coherent" and "the two rules as literally stated can both be true simultaneously" only closes when you write down the actual test cases and check them against each other — which is exactly the point of test-first authoring, applied reflexively to the plan's own trajectory rows, not just to the code the plan produces.

**How to apply:** when a plan's Test Trajectory has rows that individually sound right, don't defer checking them against each other until implementation — read the full set of assertions together immediately after drafting them, specifically hunting for a pair that can't both hold given the actual state of the codebase (not the assumed state). If a "true today" claim underlies an assertion (like "all N files currently do X"), verify it directly against the repo rather than trusting the design doc's assertion of it — see `.indusk/planning/test-phase-structure/` for the full resolution.
