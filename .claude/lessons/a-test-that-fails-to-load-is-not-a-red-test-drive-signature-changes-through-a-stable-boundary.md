# A unit test written against a not-yet-existing function signature fails to LOAD, not to assert — that is a missing test wearing a failing test's clothes, and it is indistinguishable from real red by exit code alone

worktree-config-schema-pointer's A8 was first authored as a unit test calling `topUpManagedIgnore(root, { layoutDeclared })` before that second parameter existed on the function. The test failed — but it failed with a transform/parse or type error, not a failing `expect()`. That is an absent test, not a red one: the suite never ran the assertion, so "it's red" was true in the trivial sense that the exit code was non-zero, but false in the sense that mattered (does the code exhibit the bug this test claims to catch?). It was rewritten to drive the fix through `workbench sync`, a CLI boundary that already existed and was stable across the signature change, and only then went genuinely red on its own assertion.

**How to apply:** when TDD-authoring a test for a fix that changes a function's signature (new parameter, renamed export, changed return shape), do not call the not-yet-changed function directly from the new test — it will fail to load/typecheck, and that failure looks identical to a real red in CI output (non-zero exit) while proving nothing about the bug. Either author the test against a stable boundary one layer up (a CLI command, an HTTP handler, a public API) that doesn't need to know about the internal signature change, or make the signature change first (as a no-op) and write the assertion second. This is the authoring-time counterpart to `a-green-falsification-row-can-be-green-for-an-uninteresting-reason` — both ask "does this test's pass/fail state actually mean what I think it means," just on opposite sides of red/green.
