# The test suite usually isn't slow — the schedule asking for it at the wrong moment is; move the "when," don't build a dedup mechanism

Before building a mechanism to make a slow check cheaper (caching, skip-keys, dedup), ask whether the check is running at the wrong point in the lifecycle at all. In release-checks-run-once (dusk, 2026-10-08, archived at `.indusk/planning/archive/release-checks-run-once/`), the slow tier was 2,000 fast tests in ~2 min plus 220 system tests in 6-8 min — ordinary for a system suite. The actual problem was that dusk has no CI, so the retrospective skill made the laptop run CI's job in the foreground at every landing, twice (once at landing, again unchanged at release). The five test levels already declare when each should run (unit, integration, system, e2e, slow/promise); the fix is to change the contract row's "when" (after landing, in the background, a red run treated as a broken promise) rather than inventing a skip-key/cache mechanism to avoid re-running the same cost in the same wrong place.

**Why:** a dedup mechanism (like the skip-key built in this same plan, see `a-skip-key-over-nothing-is-covered-by-every-run`) treats the symptom — the same cost paid twice — without asking whether the cost should be paid synchronously at all. Sandy's hindsight (retro-hindsight, same plan): "ask 'where does the wait belong?' before 'how do we run it once?'" — a short conversation about what the slow tier is for in a project whose releases are its own dev loop would have produced a smaller plan than the skip-key mechanism that got built first.

**How to apply:** when a plan's brief frames the problem as "X is slow, make it not block," check the project's own test-level contract (or write one) for whether X is scheduled at the right lifecycle point before designing a mechanism to make running it twice cheaper. A moved schedule can obsolete a mechanism that took a full build phase to get right.
