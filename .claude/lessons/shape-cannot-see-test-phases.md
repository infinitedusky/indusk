# Shape's `prepareShapeReview`/`verificationIsGreen` key by plain phase number, so on a test-phase-structure impl "phase 1" always resolves to Build Phase 1 — Test Phase 1 can never be Shape-reviewed by the library

`apps/indusk-mcp/src/lib/shape/shape.ts`'s `verificationIsGreen(implBody, phase)` calls `shape/impl-blocks.ts`'s `gateHeading(phase, "Verification")`, which is a re-export of `impl-headings.ts`'s `gateHeadingFor(phase, gate)` — a *different* function from the general `gateHeading(kind)` also defined in `impl-headings.ts`, despite the shared name. `gateHeadingFor`'s regex is `^####\s+(?:Build\s+)?Phase\s+${phase}\s+${gate}\b` — it matches `#### Phase N Verification` and `#### Build Phase N Verification`, but never `#### Test Phase N Verification`.

Shape (the plan's craft-review library, called from `/work`) predates test-phase-structure (the `### Test Phase N` / `### Build Phase N` two-sequence convention). On any impl using both sequences, calling Shape with `phase: 1` can only ever resolve to Build Phase 1's Verification gate. Test Phase 1 — which in the test-phase-structure convention is often the register for every authored-red assertion and carries its own Verification gate — is structurally invisible to `prepareShapeReview`. Worse, if Test Phase 1's gate is still open while Build Phase 1's is closed, or vice versa, `verificationIsGreen` reports whichever build-numbered gate it found, which may not be the phase the caller meant at all.

This was found by hand while reviewing workbench-trust-fixes' test plan and brief (2026-09-09/10) — the actual Shape review for that plan's Test Phase 1 had to be done manually from the same inputs the library would have used, because the library itself reported "not green" after the phase's own gate was already closed.

**How to apply:**
- Before trusting `prepareShapeReview`'s "skipped: verification is not green" outcome on any test-phase-structure impl, check by hand whether the phase in question is a Test Phase — the library's silence there is a blind spot, not a real refusal.
- The fix is a phase key that carries kind alongside number (an ordinal or a `{kind: "test"|"build", number}` pair), threaded through `verificationIsGreen`, `verificationGateLines`, and `gateHeading` in `shape/impl-blocks.ts`. Follow the same single-definition discipline `impl-headings.ts` already established for `TEST_PHASE_HEADING` vs `PHASE_HEADING` vs `ANY_PHASE_HEADING` — three deliberately distinct patterns for three distinct questions, not one pattern trying to answer all three.
- This is the same class of gap `check-placement-phase-boundary-vs-close` and `validator-must-reject-zero-parsed-phases` describe: a checker built before a vocabulary expanded, silently narrowed to the old vocabulary rather than erroring on the new one.

See `.indusk/planning/workbench-trust-fixes/test-plan.md` and `brief.md` (2026-09-09 revision) for the plan this was found on, and `apps/indusk-mcp/src/lib/impl-headings.ts` for the phase-kind pattern discipline the fix should follow.
