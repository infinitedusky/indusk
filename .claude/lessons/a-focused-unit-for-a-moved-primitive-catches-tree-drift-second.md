# A correct git primitive filed under a domain folder (verify/git.ts) is already duplication waiting to happen — the "primitive belongs in lib/git.ts" rule is about where the FIRST copy sits, not just where later copies land

A small, correct helper like `headSha()` (`git rev-parse HEAD`) living inside a domain folder (`lib/verify/git.ts`) looks harmless — it's right, it's small, it works. But its location is itself the seed of duplication: a sibling domain (the run lane) needing the same primitive won't think to import from `verify/`, because a domain folder reads as "verify's business," not "the shared git primitive module." It writes its own copy instead — in dawn-workbench-execution this happened twice in the same lane (inline `rev-parse HEAD` in the commit cadence, then a separate nullable `headOf` in the loop) before anyone noticed all three (verify's, and the run lane's two) were the same fact.

Fix: `headSha`/`headShaOrNull` moved to `lib/git.ts` (the project's actual git-primitives module, not a domain-specific one), pinned by `head-sha-single-definition.test.ts` — the sixth instance of this project's "structural single-definition test" pattern for a primitive multiple lanes must agree on.

How to apply: when adding a small, genuinely-correct git/filesystem/parsing primitive, ask not just "does this already exist" but "if I were a different feature written six months from now, would I look for this here?" A primitive filed under `lib/<domain>/` is invisible to every domain that isn't that one. The single-definition test (asserting exactly one implementation exists, not just asserting behavior) is what catches a second domain re-deriving the same thing before it happens twice, not just when it already has.
