# A brief's promise can be approved on the belief that existing pieces already compose into it — verify by actually running them in the target scenario before approving, not after

A promise sentence like "one command writes the keep-list" or "X already does Y" sounds safe to approve when the component pieces (a command, a registration mechanism, an extension hook) are known to exist. But existing separately is not the same as composing into the promised behavior in the actual scenario the promise describes (a fresh clone, a new worktree, a bare checkout). The gap is invisible until someone actually runs the command in that exact scenario.

**Why:** untrack-mcp-json (dusk, 2026-10-12, archived at `.indusk/planning/archive/untrack-mcp-json/`). The promise "the project's declared servers get written by one command" was approved because `indusk update`, `init`, and extension registration all existed. Measured only after approval — in a real clone — `indusk update` created no `.mcp.json` at all (its MCP handling was guarded by the file already existing) and no built-in extension declared an `add_command` for `update` to call. The promise had to be narrowed after the fact and a trajectory row retired. The retrospective's own words: "I measured it only after approval... The promise was believed because the pieces existed; none of them did what the sentence needed in a clone."

**How to apply:** before a brief's promise is approved, if the promise claims an existing mechanism already produces the described behavior, actually run that mechanism once in the literal scenario the promise names (a bare clone, a fresh worktree, an empty directory) — not a mental trace through the code. "Run update and init against a bare clone before drafting the promise, as the first step of the plan, not after approval" (the retrospective's own 'What We'd Do Differently'). This is the brief-approval-stage counterpart to `falsify-a-tool-you-dont-own-against-the-real-tool-not-assumption` (which covers the same gap for hypotheses about external tools during falsification) — here the thing under-verified is the project's own command, and the stage is approval, not falsification.
