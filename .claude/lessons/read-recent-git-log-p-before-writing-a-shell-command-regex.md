# Before authoring a regex that judges shell commands (a hook, a trigger, a filter), read the last two days of `git log -p` for the actual command shapes in use and write each as a Test Phase 1 red case — don't wait for falsification to find them

trunk-guard's retrospective hindsight: the three falsification-found spelling holes in the commit gate (`git -C x commit`, `cd x && git commit`, `bash -c "git commit"`, `git commit -am`, `git commit -m x <path>` — see [[falsify-shell-reading-hooks-against-the-spellings-agents-use]] for the full list and fix) were all present in the same repository's git history from the same day the hook was written. They were discoverable by reading `git log -p` before writing the regex, not just by falsifying after. Had they been read first, each would have been a Test Phase 1 row instead of a falsification-phase fix — cheaper by one full ritual pass.

Rule: when a task is "write a pattern that recognizes command X," the cheapest oracle for what shapes to test against is the project's own recent history of running that command, not the pattern-author's mental model of how the command is typically written. `git log -p` (or the session transcript, for commands run in-session rather than committed) over the last one-to-two days is usually enough to surface real variance — options before the verb, command chaining, quoting, flag clusters — that a first-principles regex misses.

Second, smaller finding from the same retrospective: open a plan's worktree with the admin bundle already built. Two full-suite runs in trunk-guard's cleanup went red on an environment gap — nine `indusk ui` daemon tests and the tarball test fail in a fresh worktree that hasn't run the admin's build step yet. Wire this into the worktree-kickoff checklist item alongside `indusk worktree create` so a fresh worktree's first full-suite run isn't spent debugging an environment difference that has nothing to do with the plan's own changes.
