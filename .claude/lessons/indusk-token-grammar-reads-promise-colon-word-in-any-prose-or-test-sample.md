# InDusk's `promise: <word>` token grammar matches after any comment opener, anywhere — prose and test sample code become undeclared registry claims and fail `indusk promises check`

The vscode-extension plan hit `indusk promises check` refusals multiple times (commit 605864bb: "fix(vscode-extension): reword a comment the registry check read as a promise token") because the token grammar reads `promise: <word>` as a registry claim wherever it appears after a comment opener — including in ordinary prose comments ("by source and promise: told") and in test sample/fixture strings meant only to exercise the parser, not declare anything.

**Why it matters**: this isn't a lint nit — a false-positive token match fails `indusk promises check` at landing, blocking the commit, and the fix is easy to get wrong twice in the same plan (it happened more than once in vscode-extension) because the trigger is any `promise:` substring after a comment marker, not just a deliberately-authored declaration.

**How to apply**: when writing prose comments or test sample/fixture text near promise-related code, never let the literal sequence "promise:" appear followed by what looks like a name — word the comment around the colon (e.g. "by source and promise, told" instead of "by source and promise: told"), and build sample token lines through the project's fixture helper (`site()` in vscode-extension's `fixture.ts`) rather than hand-typing a line containing the token syntax. Check with `indusk promises check` before landing if a file touches promise code and contains the word "promise" near a colon.
