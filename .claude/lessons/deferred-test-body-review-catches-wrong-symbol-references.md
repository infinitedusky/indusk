# A deferred test body's "will it compile" review question catches wrong-symbol references before the phase that would hit them as load errors

Test Phase 1 in the test-phase-structure convention requires every deferred test body to be reviewed against two questions: will it compile at the phase it names, and does it assert what it claims. The first question isn't redundant with just writing the body carefully — in writing-skill's Test Phase 1 (commit 49042d49), A6's first-draft deferred body called a `tmpProject` helper that doesn't exist in the fixture file; the real helper is `paperProject`. Had this gone unreviewed, Build Phase 2 would have hit it as a module load error (the whole test file fails to import) rather than a clean assertion failure — exactly the "none fails on a missing import" anti-pattern the Test Phase 1 Verification gate explicitly checks for elsewhere in the same impl.

Why: a deferred body is authored against code that doesn't exist yet, so nothing running today can catch a wrong symbol reference — there's no red/green signal until the phase that makes the symbol real. The review step is the only thing standing between a plausible-looking deferred test and a load-time failure that would masquerade as "the feature isn't built yet" instead of "the test itself is wrong."

How to apply: when authoring a Deferred to Build Phase N test body, actually check every symbol it references against the real fixture/helper files that exist right now — not just the ones the plan document assumes will exist. A deferred body that imports or calls something not yet in the codebase is expected; a deferred body that calls something with the wrong name for what will exist is a bug hiding until the deferral resolves.
