# A feature's regression net can be blind to the exact shape it was built for, because that fixture must be invented rather than copied from an existing one

Twelve versioned-workbench defects were found by *using* the feature after its plan closed green, and workbench-trust-fixes found four more surfaces (run, cleanup, eval attribution, restore) failing silently in that same shape — because no test fixture anywhere in the codebase had a git-initialized workbench root. Every existing "workbench fixture" reproduced the pre-1.37 shape (root NOT a git repo), which is exactly the shape the feature was built to move away from. A fixture copied from an existing one inherits the existing one's blind spots by construction (the same principle as `point-the-tool-at-itself-before-calling-it-done`, one level earlier in the pipeline): nobody had to write a new fixture, so nobody noticed the new fixture was the untested case.

**Why this specific fixture was the risky one:** every *other* fixture in the suite predates the feature and was validated against real behavior at some point. The fixture for the NEW shape has never been validated against anything — it has to be invented from the feature's own design, with no existing behavior to check it against. That asymmetry (old fixtures are proven, new-shape fixtures are unproven-by-construction) is the general risk, not specific to workbenches.

**The fix, and the general pattern:** author the fixture for the new shape FIRST, as its own reusable helper (`src/__tests__/helpers/versioned-workbench.ts`), before writing any test that uses it. workbench-trust-fixes did this and twelve of its thirteen new test files stood on that one helper — meaning the fixture-authoring effort amortized across the whole plan rather than being reinvented per test (and risking a subtly different, still-wrong fixture in each file).

**How to apply:** when a plan changes what shape of environment a feature operates in (a new topology, a new file layout, a new protocol version), ask explicitly: does any existing fixture actually reproduce the NEW shape, or does every fixture still reproduce the shape that existed before this feature? If the answer is "every fixture predates the change," that is the fixture most worth writing first, and it is exactly the one a plan is likely to skip, because writing it doesn't feel like writing a test — it feels like test infrastructure, and test infrastructure is what gets deferred under time pressure.

See `.indusk/planning/workbench-trust-fixes/` (Test Phase 1, `helpers/versioned-workbench.ts`) and `.indusk/planning/archive/versioned-workbench/` retrospective for the twelve original defects this same gap produced.
