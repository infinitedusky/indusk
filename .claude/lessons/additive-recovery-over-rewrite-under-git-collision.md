# When a concurrent-session git collision happens, recover additively — never rewrite history under time pressure

Working in a shared (non-worktree-isolated) git checkout while another live session is also committing can cause HEAD to move out from under you — a commit you make can land on the wrong branch if the other session switched branches in between your own operations. This happened mid-session: another Claude Code session was actively committing to a different branch in the same working directory, and a planning-doc commit landed on their branch instead of the intended one.

The instinct under time pressure is to "just reset it back" — but `git reset --hard` (or any history rewrite) on a branch someone else might commit to next is exactly the wrong move: if they commit again before you finish rewriting, you can lose their work, and even if you're careful, you're gambling with someone else's in-flight state. This project's own safety tooling blocks `git reset --hard` outright and suggests "add a new commit on top instead" — that's the correct instinct, not a limitation to work around.

The actual safe recovery: `git revert <bad-commit>` (additive — safe even if the other session commits again mid-recovery, since it doesn't touch existing history) to undo the stray commit's effect on their branch, then recreate your own branch cleanly (delete + recreate off a known-good point, e.g. `origin/main`) since it's unpushed and has no unique value beyond what you can recover via cherry-pick. Once recovered, move all subsequent work into an isolated `git worktree` per branch — this eliminates the whole collision class going forward rather than just recovering from one instance of it.
