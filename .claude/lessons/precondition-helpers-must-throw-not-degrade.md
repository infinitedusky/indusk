# A helper that establishes a test's precondition must throw when it can't establish it — a degraded return value lets every downstream assertion pass while proving nothing

A test that depends on a precondition (e.g. "jj is not on PATH", "the fixture directory is empty", "the mock server is listening") needs that precondition to be genuinely true before its assertions mean anything. If the helper that sets up the precondition fails silently — catches its own error and returns some fallback value instead of throwing — the test proceeds as if the precondition held, and every subsequent assertion is now testing nothing.

**What happened:** `jj-residue-rip-out`'s test helper `pathWithoutJj()` was meant to strip jj's directory from `PATH` so a test could assert "jj is unreachable." It located jj by spawning `which jj`; when that spawn failed (because a caller had already narrowed `PATH` for an unrelated reason), the function's fallback was `return process.env.PATH ?? ""` — the **unmodified** PATH, with jj's directory still in it. The precondition "jj is absent" was silently false. Every test built on top of this helper had been passing since it was authored, and had been proving nothing the entire time — "git still resolves" passed while "jj does not resolve" would have failed, had it ever actually run against a PATH without jj.

**Why it matters:** this is a more insidious version of a test that trivially passes — it isn't obviously vacuous (like an empty test body), it's a test with real assertions against a precondition silently swapped out from under it. Nothing in the test output distinguishes "the precondition held and the assertion passed" from "the precondition silently failed to establish and the assertion passed against the wrong state."

**The rule:** a helper whose job is to establish a test precondition must **throw** when it cannot establish that precondition — never catch the failure and return a degraded or unchanged value as if nothing happened. Additionally, the test itself should assert the precondition explicitly (e.g. `expect(pathHasNoJj(result.PATH)).toBe(true)`) before asserting the behavior that depends on it, so a future refactor of the helper can't reintroduce the same silent degradation without a test catching it immediately.

See `.indusk/planning/jj-residue-rip-out/` (the `pathWithoutJj` → `gitOnlyPath` cleanup) for the full incident.
