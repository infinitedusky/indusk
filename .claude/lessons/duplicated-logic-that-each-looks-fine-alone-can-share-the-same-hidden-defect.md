# Two independent copies of the same logic, each reviewed and looking correct in isolation, can still share an identical latent defect — the defect is only visible once you put the copies side by side

In promise-sources (`.indusk/planning/archive/promise-sources/`), both `promises status`'s failure-text builder and `promises watch`'s hint builder independently re-read the same raw `promises.jaeger` config to construct user-facing advice. Each copy, reviewed on its own, looked like reasonable code. Both printed the identical wrong message — "Check undefined is up" — for the malformed config case (`jaeger` as a string instead of an object) found in A8/A10. Neither build phase's tests caught it, because each test exercised only its own copy in isolation and neither happened to probe the shared bad input. The defect was found at cleanup, specifically because cleanup's job is to look at the changed files side by side for duplication — the two copies being visibly similar prompted comparing their actual behavior, which surfaced the shared bug. The fix extracted one `sourceAdvice` function, built directly from the failure object rather than re-deriving it from raw config, so there is now exactly one place that can be wrong.

**How to apply:** when a cleanup/craft review finds the same logic duplicated in two or more places (the rule-of-three trigger this project already uses), don't just judge whether each copy looks correct independently — actively test or trace both copies against the same inputs, especially malformed/edge-case inputs, before concluding the duplication is merely stylistic. Independently-written-but-similar code is at elevated risk of sharing the same blind spot, because whatever assumption led one author to miss a case often leads a near-identical second implementation to miss the same case. Prefer deriving user-facing messages directly from a typed failure/error value rather than having multiple call sites each re-derive the message from raw upstream data.
