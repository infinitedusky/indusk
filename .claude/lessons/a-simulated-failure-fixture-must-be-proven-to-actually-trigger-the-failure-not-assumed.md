# Writing a file at a lock's path (e.g. .git/index.lock) to simulate a held lock doesn't prove the code under test actually hit the failure branch — run the test and check it's genuinely red before trusting the "authored red" claim

incident-recording's commit 7623ba3a claimed "A27–A31 red" for five new falsification tests (promise: a-production-break-is-recorded-unasked / a-break-reaches-the-working-agent). Running the file directly after the commit: A30 and A31 were genuinely red as claimed, but A27, A28, and A29 all passed already — against the unmodified, pre-fix implementation the falsification phase (76f2178a) had argued should fail.

A27's fixture writes an empty file to `.git/index.lock` to simulate a concurrent git process holding the lock, then calls `record()` twice expecting both passes to fail to commit and mark themselves `broken`, then removes the lock and expects a third pass to finish the job. The test's own assertions passed — but passing assertions after a simulated failure don't by themselves prove the simulated failure path was taken; they're also satisfiable if the lock file silently had no effect on the `execFile`-based `git commit` call (e.g. a different lock semantics than expected, a race between the touch and the git invocation, or the assertions being loose enough to also hold on the "nothing failed, nothing to retry" path).

Applies to any test that manufactures an external failure condition by touching a resource (a lock file, a disconnected socket, a corrupted file) rather than injecting a fake/throwing dependency directly: verify the simulated condition actually produces the intended error by checking it against the UNMODIFIED code first (the same "author RED, then verify RED, not green by accident" discipline the project already applies to feature code) — don't trust that writing to the same path a real lock would use reproduces the real lock's blocking behavior. This project's own `a-falsification-hypothesis-test-that-passes-on-day-one-is-not-automatically-a-real-falsification-test` lesson covers the adjacent case (a test that happens to pass from day one); this is the sharper, more dangerous version — a test *claimed* red in the commit message that was actually already green, undermining the entire point of the falsification phase for those three rows. See `.indusk/planning/incident-recording/impl.md`'s A27 row and `src/lib/promises/record.test.ts`.
