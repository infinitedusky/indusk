# The retrospective is due the day every close-out ritual (falsify, cleanup) is satisfied — a plan that sits "done but unarchived" for days is discovered, not scheduled, and the discovery is always some other plan's close-out noticing

hook-cwd-independence's own retrospective hindsight: every ritual (falsification, cleanup) was satisfied on 2026-09-15, but the retrospective itself — and the plan's archival — didn't happen until 2026-09-17, two days later, and only because an unrelated plan's close-out (trunk-guard's) noticed the gap while doing its own bookkeeping. Nothing was wrong with the work; the plan just sat in a "ready to close but not closed" state with nobody's task queue pointing at it.

Rule: when `/falsify` and `/cleanup` both report terminal on the same day, run `/retrospective` that day, in the same session if possible — don't let "the code is done" substitute for "the plan is closed." A plan's `list_plans` next-step and CLAUDE.md's Current State are both stale for every day between ritual-completion and retrospective, and the only reliable way this gets caught today is a human or another plan's close-out stumbling into it — which is itself unreliable (it depends on some other plan's close-out happening to look).

Second, smaller finding from the same retrospective: a fix whose correctness depends on a variable being unset (see [[a-host-variable-fallback-must-degrade-to-old-behavior-not-an-unreachable-path]]) should have that exact case — the shipped string evaluated with the variable unset — as a Test Phase 1 red row, not something falsification finds later. hook-cwd-independence's A6 (testing the unset-variable case) was writable as early as Phase 0, meaning the information needed to write it was available from the start; it just wasn't written until later.
