# Stopping a fault's trigger does not clear the violation it already caused — only a recorded fix does

The seat-holds demo's fault-toggle button was originally labeled "Fix it," with UI copy claiming "turn it off and the promise holds again." This was corrected (commit 56397ad4) to "Stop the fault," with copy stating the promise stays broken until the break is recorded as an incident and fixed — because that is how InDusk's promise model actually works: per the promise-timeline brief, a violation's color follows its incident's state, and "the moment an incident is marked fixed its past reds turn purple: history keeps every break, and only an unfixed one reads red." Removing the condition that caused a violation (here, turning off the fault) stops *future* violations; it does not retroactively mend the one already recorded.

Why: a promise like "released, never late" is a claim about every release, not just the current one. Once any release is marked violated, that's a permanent fact in the trace history. A demo, UI label, or doc that implies "stop the bad condition → the promise is fine again" teaches the wrong mental model of what a promise violation means in this system, and the mistake is easy to make because the surface behavior (page looks normal again) is identical to the surface behavior of an actual fix.

How to apply: when writing UI copy, docs, or demo scripts that describe recovering from a promise violation, say explicitly that recovery requires the violation to be recorded and the incident fixed (`promises watch` / `promises fix`) — never phrase merely stopping the triggering condition as "fixing" or "holding again." Check this phrasing in any new promise-facing surface (admin UI, CLI output, example apps).
