# Claude Code hook commands registered as cwd-relative paths (`node .claude/hooks/x.js`) silently stop enforcing the moment the session cwd isn't the repo root — MODULE_NOT_FOUND exits 1, not 2, and the model never sees it

dusk's own `.claude/settings.json` registers every hook by a cwd-relative command: `"node .claude/hooks/check-gates.js"`, `"node .claude/hooks/validate-impl-structure.js"`, etc. — confirmed by reading the file directly. `check-gates.js` itself correctly uses `process.exit(2)` as its blocking convention (verified: four call sites). But Claude Code treats *any* hook exit code other than 2 as non-blocking, and does not surface the error to the model. So when the session's cwd drifts to a subdirectory — `apps/indusk-mcp`, which is where most test-running commands (`pnpm test`, `pnpm exec vitest`) leave the shell — the relative path resolves to a nonexistent location (`apps/indusk-mcp/.claude/hooks/check-gates.js`), node throws `MODULE_NOT_FOUND`, the process exits 1, and Claude Code silently lets the tool call proceed as if the gate had run and passed.

Independently reproduced in this eval session: `cd apps/indusk-mcp && node .claude/hooks/check-gates.js < /dev/null` throws `Cannot find module '.../apps/indusk-mcp/.claude/hooks/check-gates.js'`, `code: 'MODULE_NOT_FOUND'`, exit 1 — while `process.exit(2)` calls sit live in the file at lines 261/366/402/455.

**The scope of the damage in this repo, per workbench-trust-fixes' retrospective:** the working agent believed hooks were enforcing Build Phases 2–9 of that plan because the hooks never complained — but they were silently failing to load for most of that work, because the session cwd sat in `apps/indusk-mcp` (where test commands leave it) rather than the repo root. Two trajectory rows (A1, A3, `Passes at: Build Phase 1`) were left `written` through eight later phase closes that Gate B exists to refuse, and were only flipped to `passing` at the retrospective; the close-out's own `auditPlanAtClose` / `checkRetrospectiveReadiness` never caught this because neither looks at row states at all — the first reports `blocked` and deferred rows only, the second checks that the ritual *phases* have every checkbox ticked.

**Same shape as the gate-reminder bug** (`hook-output-needs-a-channel-that-reaches-the-model`): the enforcement logic existed and was correct; the delivery mechanism silently died. Hook silence and "no hook installed" are indistinguishable from inside the session.

**How to apply:**
1. Enforcement hook commands must resolve their own script path via `$CLAUDE_PROJECT_DIR` (or an equivalent absolute-resolution mechanism), never a bare relative path — a cwd-relative hook command is a hook that only enforces from one specific working directory.
2. Until that's fixed project-wide: `cd` back to the repo root before any impl edit or commit in this repo — every gate here is one `cd apps/indusk-mcp` away from silently off.
3. Never read hook silence as approval. A close-out ritual should replay the gate logic (e.g. `check-gates`'s Gate A/Gate B) over the *entire final state* at close, not just trust that per-item silence during the session meant per-item enforcement happened.
4. The retrospective skill's own text already promises "every Passes at row is terminal" as a check — this incident shows the promise wasn't backed by an actual replay-the-gates step in the library, only by a reader's diligence. A ritual's promise and a ritual's mechanism can drift apart the same way any other spec/implementation pair can.

Filed in the plan as `hook-cwd-independence` — a fix that should land before `dawn-workbench-execution`, which would otherwise execute under the same silently-disarmed gates. See `.indusk/planning/workbench-trust-fixes/` retrospective for the full incident.
