# Isolating a test suite means isolating every process it starts, in every tier — a leak shows up as files in your home directory or a bill, not a failing test

From `bookkeeping-lives-where-it-is-read` (`.indusk/planning/archive/bookkeeping-lives-where-it-is-read/retrospective.md`): the everyday test suite got a temporary `INDUSK_HOME`, but the system tier — which has its own config setup, separate from the everyday suite's — did not, and its real `claude` sessions wrote six folders into the developer's actual home before the full run caught it. Separately, an older test ran the eval hook with `--source handoff` against this repository just to prove it doesn't hang; evaluation is enabled here, so every `pnpm test` run silently started a real, paid evaluator session scoring HEAD. One was caught still running.

Why it matters: both leaks were invisible in test output — no assertion failed, nothing turned red. One leak shows up as files accumulating in `~`; the other shows up as a bill. Neither announces itself the way a failing test does, so "the tests pass" is not evidence that isolation holds.

How to apply: when isolating a test suite's environment (temp `INDUSK_HOME`, disabled network calls, stubbed subprocess spawns), audit every tier separately — the everyday tier's fix does not automatically propagate to the system tier if it has its own setup path. Any test that invokes a real external process (a `claude` session, an eval hook, anything that costs money or writes outside a temp dir) must run with evaluation/billing explicitly off and a scoped temp home, verified by checking for stray artifacts after a run — not just by reading green test output. Related but distinct from [[pin-env-at-the-shared-spawn-helper-not-per-file]] (that lesson is about per-file env pinning losing to a developer's shell-exported var; this one is about a tier that never had the pin applied to it at all, plus a cost leak from a test that shouldn't have hit a real paid backend).
