# A hand-written status word and a derived position are two stores of one fact — read progress from the derived store, keep the hand-written field as the author's declaration only

When a document has both a manually-set field (e.g. `status: in-progress`) and a position that can be computed from the actual file contents (which phases are checked off, which gates have closed), any reader that trusts the hand-written field is trusting that an agent remembered to update it on every transition. The two can and do drift — a plan built but not yet falsified read `completed` in the nav while its own page, computed from the real file state, said `Falsify`.

**Why:** nav-stage-matches-plan-page (dusk, 2026-10-16, archived at `.indusk/planning/archive/nav-stage-matches-plan-page/`). The fix moved "which step is a plan at" out of a private, status-word-trusting function into one exported `stepAt`, computed from the plan's actual file position, used by both the nav and "Needs you." The retrospective's own words: "A hand-written status word and a derived position are two stores of one fact; any reader of the first trusts the agent to have edited it. Read progress from the derived one, keep the field as the author's declaration." The audit found two more readers of the old status word (a project card, a markdown export) that the builder's own fix had missed — fixed the same way in Build Phase 2.

**How to apply:** when a document carries both a hand-set field and a computable position, build one function that derives the position from the real file/data state, and route every reader (not just the one you're fixing) through it. Grep for every reader of the hand-written field before calling the fix done — a second or third reader of the stale field is easy to miss, as it was here.
