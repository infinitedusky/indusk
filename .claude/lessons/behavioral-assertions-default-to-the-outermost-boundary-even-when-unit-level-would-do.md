# "Assertions are behavioural" plus "prefer a real boundary for real red" together pushed every test in a plan to the slowest, outermost door (HTTP + real Jaeger + next dev) — tests are for regressions, promises are for monitoring, and most behavioral claims don't need the full stack to prove

In promise-timeline (`.indusk/planning/archive/promise-timeline/`), two sound-sounding principles combined to produce a slow test suite: "every assertion should describe user-visible behavior" and "prefer testing against a real boundary (a real server, a real Jaeger) over a fake, for red that means something." Applied together to every test in the plan, this pushed almost all of them — including ones that were really about pure logic like "which cell colour does this set of runs produce" — through the outermost door: an HTTP request to a running `next dev` admin, reading from a real local Jaeger. About 190 of the admin suite's 247 seconds were spent this way.

The retrospective's correction, attributed to Sandy: tests are for regressions (catching something that broke, as fast and cheaply as possible, in CI on every commit), promises are for monitoring (whether the deployed system is doing what it's supposed to, continuously, in production). Conflating "this must be testable as real behavior" with "this must be tested at the outermost boundary" produces test suites that are slow for no correctness benefit, because most of what was being asserted (a pure function of inputs like "given these marks, which colour") doesn't need a server or a database to prove — only the parts that genuinely depend on wiring across a boundary (does the HTTP route call the right function, does Jaeger actually return what was written) need the expensive path.

**How to apply:** when a test plan's mechanism column defaults every row to the same (expensive) test kind, stop and ask which rows are actually testing pure decision logic versus which are testing that a boundary (HTTP, a database, a real backend) is wired correctly. Prefer the smallest test kind that can expose a real regression: a pure unit test for "what color does this input produce," reserving integration/HTTP/real-backend tests for the wiring itself. A follow-on plan, `test-kinds`, was opened from this retrospective to make this structural: a test plan's mechanism column should name the test kind explicitly (not just "integration" by default), the smallest kind is the default unless a row's assertion genuinely requires a boundary, and code that makes a decision should take its clock and its inputs as parameters so the decision itself is testable without any infrastructure at all.

See `.indusk/planning/archive/promise-timeline/retrospective.md` ("What We Learned" / hindsight), and the `test-kinds` plan it opened.
