# A fix for a bug falsification found can itself introduce a worse bug, and both the original fix and its own tests can look green — only a reader who did not write either will ask what the fix newly allows

When falsification finds a real defect and a fix is written for it, the natural test to add is one that proves the defect is now prevented. That test passing, plus the original falsification row now passing, both look like success — but neither one asks what the fix's mechanism newly permits elsewhere. An opt-out or bypass added to patch one specific case can silently defeat the very invariant the fix was meant to restore, in a different case nobody wrote a row for.

**Why:** sessions-per-plan (dusk, 2026-10-14, archived at `.indusk/planning/archive/sessions-per-plan/`). Falsification found A14 (a build lost its session-cap slot between its steps, letting the next step slip past the cap) and fixed it with an `inBuild` opt-out from the cap check. That fix let builds exceed the cap entirely: pressing Build on several plans at once admitted all of them, and every later step then skipped the cap check too. Both A14's own row and the fix's own test passed — the opt-out did exactly what it was asked to do, which was the problem. Only the cold-reader audit, examining the mechanism itself rather than re-running the rows that already passed, asked whether the total could still exceed `max`. No row had ever asserted that. The real fix (Build Phase 5) replaced the opt-out with `admitBuild`: a build holds one place for its whole lifetime, correctly, with a new row (A15) asserting the total stays bounded.

**How to apply:** when writing a fix for a falsification-found defect, before accepting the fix as done, ask explicitly: "what does this fix's mechanism now allow that didn't exist before — an opt-out, a flag, a new code path — and is there a row asserting that new path can't be abused the same way the original bug was?" An opt-out or a flag added under time pressure to patch one case is exactly the shape of change a fresh, independent reader (an audit, a second person) should specifically interrogate, because the builder who just wrote the fix is the least likely to see past its intended use.
