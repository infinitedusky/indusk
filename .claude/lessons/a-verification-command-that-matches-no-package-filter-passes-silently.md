# A pnpm --filter command naming a package that doesn't exist prints "No projects matched" and exits 0 — a Verification item written from memory instead of a run can look green while proving nothing

During promise-sources (`.indusk/planning/archive/promise-sources/`), the plan's impl.md wrote `pnpm --filter @infinitedusky/indusk-admin exec vitest run ...` into two Verification items — but the actual package name is `indusk-admin`, not `@infinitedusky/indusk-admin` (only `indusk-mcp` is scoped). `pnpm --filter` with a name matching no workspace package prints "No projects matched" and exits 0, indistinguishable from "ran zero relevant tests because none needed running." The retrospective found this had already happened in one other archived plan before this one. Nothing false was actually recorded in either case — the tests were run some other way in practice — but the Verification item as written would pass while testing nothing.

**How to apply:** when writing a `pnpm --filter <name>` (or any package-manager filter/workspace-selector command) into a plan's Verification item, copy it from a command that has actually been run in this session, never reconstruct the package name from memory or by pattern-matching against a sibling package's scoped name. Prefer `pnpm --filter <name> --fail-if-no-match` (or the equivalent for other package managers) so a typo'd or renamed filter fails loudly instead of silently matching nothing. More generally: a check that a Verification command's named package/filter actually resolves to something in the workspace would catch this class of defect before it ships in a plan document — raised in promise-sources' retrospective as a candidate validator, not yet built.

See `.indusk/planning/archive/promise-sources/retrospective.md` ("What We Learned", "Shape and quality").
