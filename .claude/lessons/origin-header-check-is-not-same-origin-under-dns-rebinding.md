# Comparing Origin to Host is not a same-origin check — under DNS rebinding both can name the attacker's own site

admin-plan-authoring's falsification found that a server bound to loopback (127.0.0.1) which validates requests by comparing the `Origin` header against the `Host` header does not actually enforce same-origin: under DNS rebinding, an attacker's page can cause the victim's browser to send requests where `Origin` and `Host` both resolve to a hostname the attacker controls, since the attacker controls the DNS record both headers end up reflecting. The two headers agreeing with each other proves nothing about the request's actual origin — it only proves internal consistency of two values the attacker-controlled page can also control.

Why it matters: binding a server to loopback is often treated as "safe by network boundary," and a same-origin-looking header check feels like defense in depth on top of that. But the Origin-vs-Host comparison is checking the wrong invariant — it should check the request's actual Host against the server's own known hostnames/addresses (e.g. `localhost`, `127.0.0.1`, the loopback interface), not against another header the same malicious request also carries. A route that hands out a session id (or any other credential-shaped value) on a GET is exactly what an attacker needs next once they get a request through — read-only routes need the same check as mutating ones.

What to do: for any server bound to loopback that also validates request origin, check the Host header against a fixed allowlist of the server's own names/addresses (`isAdminHost`/an equivalent `adminOnly` guard), not against the Origin header. Apply this check to every route, including GETs — a credential- or id-handing-out read is as dangerous as a write once an attacker can reach it. See `.indusk/planning/admin-plan-authoring/` (or its archive, once landed) for the admin daemon's `isAdminHost`/`adminOnly` implementation.
