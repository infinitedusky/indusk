# A guard added at one call site of a shared operation does not protect a second call site that bypasses the shared function and re-implements the unsafe path directly

`contract.ts`'s `checkFolder` (backing `promises check` and `promises contract`) safely read an impl via `readImpl`, which catches gray-matter parse failures and returns `{ok:false, error}` instead of throwing. `confirm.ts`'s `confirmPlan` needed the same impl text but called `rowProofs(registry, plan, implText)` directly — `rowProofs` → `rowsNamingIn` → `parseTrajectory(matter(implText).content)`, and gray-matter's `matter()` throws on malformed YAML frontmatter. A broken impl.md crashed `promises confirm` with a raw stack trace while `promises check`/`contract` already refused cleanly on the same input.

Why: the safety check existed in the codebase (readImpl, in contract.ts) by the time confirm.ts was written, but confirm.ts's author reached for rowProofs directly instead of routing through readImpl first — so the fix (planner-promises A35, commit e3bbf099) wasn't "add a new capability," it was "export the existing private function and call it at the second site too." A function's existence in one module doesn't mean every caller that needs its guarantee actually calls it.

How to apply: when adding a new caller of a multi-step read/parse pipeline that another caller already guards against malformed input, check whether that guard is centralized (a single reader function) or duplicated inline at the first call site. If centralized but not exported, export it and call it — don't re-derive the unsafe path. If a bug report says "X works but Y doesn't" for the same underlying data, suspect exactly this: one path goes through the safe reader, the other doesn't.
