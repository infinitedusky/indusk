# A test that isolates its data directory (a temp HOME) does not isolate a background process a tool opportunistically starts there — relying on every caller to remember a reap helper is not a fix, it's a recurring leak

dusk's InDusk test suite leaked real telemetry daemon (Jaeger + otelcol) processes twice from the same root cause, five weeks apart. On 2026-08-13, 2,058 orphaned processes were found holding 17.1 GB; the fix adopted then was a *convention* — `stopTelemetryForHome(testHome)` (`apps/indusk-mcp/src/__tests__/helpers/telemetry-reap.ts`), which every test suite that runs the CLI against a temporary `INDUSK_HOME` was supposed to call. On 2026-10-03, 860 orphaned processes were found again (`.indusk/planning/test-daemons-never-leak/brief.md`, `.../test-plan.md`): three test files called the reap helper; every other test that ran `init` or `update` through a temp home did not, because nothing forced it to, and parallelizing the test suite (merged 2026-10-02) multiplied the number of temp homes created per run.

The underlying mechanism: `init` enables the `local-telemetry` extension, whose `on_enable` hook runs `indusk telemetry register`, which — finding no daemon registered for that `INDUSK_HOME` — opportunistically **starts one**, detached, surviving the test process. Pinning `INDUSK_HOME` to a temp directory correctly isolates the daemon's *config and data*; it does nothing to stop the *process* from being spawned and persisting after the test exits. A convention asking every test author to remember to call a cleanup helper is exactly as reliable as any other "please remember to" rule — it degrades the moment a new test is added by someone who doesn't know the convention exists, and the project's own retrospectives have repeatedly found that discipline without enforcement erodes.

The fix accepted the second time (test-daemons-never-leak): an environment switch, set once for the whole test process (not just inside one CLI helper, because several tests start the CLI with their own environment), that `register` honors by skipping its opportunistic start — registration still happens, so tests *about* registration still work, but the real daemon spawn never occurs from inside the everyday suite. A guard at the end of the everyday suite independently checks that no telemetry process is running from a temporary test home, and fails naming the offender, so the next instance of this class of leak is a red test rather than a number found by accident months later.

**How to apply:** when a test needs to isolate a tool's *side effects* (not just its config/data path) — specifically, any case where initializing something opportunistically spawns a real background process, daemon, server, or external resource — do not rely on a temp directory alone, and do not rely on every test author remembering to call a cleanup/reap function. Default the behavior off for the whole test process via an environment switch read at the point the spawn would happen, and add an end-of-suite guard that actively checks for and names any leaked resource, so a regression is caught structurally rather than discovered as a pile of orphaned processes. This generalizes beyond telemetry daemons to any "init-like" code path wired to auto-provision real infrastructure (background servers, scheduled jobs, file watchers, containers) under test.

See `.indusk/planning/test-daemons-never-leak/brief.md`, `.indusk/planning/test-daemons-never-leak/test-plan.md`, and the 2026-08-13 prior fix in `apps/indusk-mcp/src/__tests__/helpers/telemetry-reap.ts`.
