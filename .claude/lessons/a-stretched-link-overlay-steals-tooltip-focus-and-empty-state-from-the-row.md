# Stretching a link over a whole row (to make the row clickable) moves every pointer/keyboard interaction to the link — a tooltip, the focus ring, and empty-state behavior must be re-asserted there, not assumed to still work

A common pattern for making an entire row clickable while still containing other controls is to stretch an `<a>` (or similar) as an absolutely-positioned overlay across the row, with the visible controls layered on top. This correctly routes clicks and keyboard focus to the link — but it also means the browser's hover/focus targeting now hits the link first, not the element a person actually hovers over. Anything that depended on being the direct target (a native `title` tooltip on a truncated label, a focus ring drawn on a specific child, a conditional empty-slot style) silently stops working unless it's explicitly re-wired to the link.

**Why:** nav-row-legible (dusk, 2026-10-16, archived at `.indusk/planning/archive/nav-row-legible/`). The row was restructured so a worktree mark could sit beside the stage, with the title's link stretched over the whole row as a container. Falsification found three things the stretch took away: the full-name tooltip on a truncated title, the whole-row keyboard focus ring, and a `worktree={null}` slot that still rendered the container form instead of the plain-link form. The retrospective's own words: "A control inside a row whose click area is a link needs the link stretched over the row by an overlay; everything the pointer or keyboard meets then moves to the link (title, focus ring) and has to be re-asserted there."

**How to apply:** when converting a row's click target from "the text itself is the link" to "an overlay stretched across the row," explicitly check and re-test: (1) any native tooltip (`title` attribute) that was on the original text element, (2) the focus ring's visible target and keyboard-navigation behavior, (3) any conditional rendering keyed on the presence/absence of a slot (an empty state should not accidentally switch layout forms). Write these as Test Phase 1 rows when the overlay decision is made, not discovered later in falsification — they are direct, predictable consequences of the overlay pattern, not edge cases.
