# An impl's Verification checkoff citing a specific test/file count from memory drifts from the actual command's output — paste the real number, or don't state one

Three consecutive Build Phase Verification checkoffs in planner-promises (commits 7b2e9086, 56023a28, 3d7f4994) stated specific test counts and file counts in prose ("54 tests red... 19 passing", "116 tests... about 2s", "23 files, 212 tests") that did not reproduce when the named vitest command was actually re-run — the real numbers were smaller every time (52/8, 103/10, 158/19 via the closest reproducible interpretation), and in the last case even broadening the command to `vitest related` over every changed file came in at 158, not 212. In every case the qualitative verdict (all intended tests pass, all intended tests are red) was independently confirmed true — only the specific numbers were wrong.

The likely mechanism: the agent ran the command, read a "pass/fail" summary, and then wrote down a count from memory or from a slightly different invocation (a different file set, a different glob) rather than copy-pasting the actual `Test Files`/`Tests` line from that exact run's output into the checkoff.

**How to apply:** when an impl's Verification checkoff states a specific number (test count, file count, timing), copy it directly from the terminal output of the exact command written in that checkoff — do not recall it, round it, or state a number from a related-but-different run. If the exact number isn't going to be re-verified by a reader, consider stating only the qualitative verdict ("all pass," "all red on their own assertion") instead of a specific count that invites a false sense of precision. A Verification checkoff's entire purpose is to be a checkable record — a wrong number in it is worse than no number, because it looks precise and isn't.
