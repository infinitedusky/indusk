# Work that decides whether a cached result is reused (a served-build judgement, a configuration hash) gets trajectory rows when it is added, not tests alone

In looks-check-speed the served-build judgement and the configuration hash shipped in Build Phase 3 with unit tests but "no trajectory row". They decide whether a look is reported held without being opened, which the audit called the plan's riskiest untracked work, and the audit and falsification phase then found a stale-server record, a missing checker identity and a build-in-the-key design that defeated the speed goal. When a build adds an input to a reuse key or a rule about when a cached result stands, add a row under the plan's promise in the same phase so it is in the register the audit and phase close read. See .indusk/planning/looks-check-speed/retrospective.md (What We'd Do Differently) and audit.md.
