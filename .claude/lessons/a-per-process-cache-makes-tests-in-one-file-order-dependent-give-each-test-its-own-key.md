# A test asserting "one call per cache window" can pass or fail based on test execution order within the same file — if an earlier test in the same process already populated the cache for the same key, the assertion under test counts zero and the test is meaningless, not green for the right reason

During watcher-heartbeat (`.indusk/planning/archive/watcher-heartbeat/`), trajectory row A4 (asserting that reading promise health repeatedly within 30 s sends exactly one probe, not one per read) initially counted zero probes rather than one. The cause: `probeWatcher`'s cache (`lib/promises/probe.ts`) is keyed per-process by the query URL, and test A1 — which ran earlier in the same file, against the same daemon — had already warmed the cache for that URL before A4's assertion ran. A4 wasn't exercising "does the cache dedupe repeated reads" at all; it was exercising "does the cache still hold an entry from an unrelated earlier test," which happened to also report zero new probes, for the wrong reason.

A related finding in the same plan: an older plan's single-definition pin (`day-always-on`'s trajectory row A29, pinning URL normalization to one written definition) caught two copies this plan's own authoring had introduced — a rule-of-three pin written for one reason paid off on a plan that never knew the pin existed.

**How to apply:** when a test asserts a property of a cache, rate limiter, debounce, or any other piece of per-process or per-key state that persists across test cases in the same file or process, give that test its own fresh key (its own daemon instance, its own URL, its own identifier) rather than reusing a shared fixture other tests in the same suite also touch. A test for "does caching work" must control for "has something else already populated this cache" — otherwise the test's pass/fail outcome depends on file-level execution order, which is exactly the kind of flakiness-by-coincidence that looks green until the suite is reordered, parallelized, or a new test is inserted earlier in the file. Separately: single-definition pins (a trajectory row asserting one canonical implementation of some logic) are worth writing even when their immediate motivation is narrow — they catch duplication in future plans that have no knowledge the pin exists.
