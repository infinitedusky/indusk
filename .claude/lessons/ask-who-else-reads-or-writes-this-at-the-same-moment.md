# When an ADR moves state from many places to one shared place, ask "who else reads or writes this at the same moment?" before accepting it

From `bookkeeping-lives-where-it-is-read` (`.indusk/planning/archive/bookkeeping-lives-where-it-is-read/adr.md` and retrospective): the ADR consolidated per-checkout machine state (highlights, processed list, evaluator session) into one shared `~/.indusk/projects/<project>/` location. Each checkout's private file had been silently giving it isolation for free — its own id counter, its own processed list, its own evaluator session — none of which the ADR named as a property being given up. Sharing the state needed a lock, "holds" semantics, and per-checkout keys to recover that isolation, and falsification (goal-flipped bounty hunt) found all seven concurrency gaps the ADR had missed.

Why it matters: consolidation ADRs read as pure simplification ("one place instead of many") and that framing hides the question that actually matters — moving from N private copies to 1 shared copy turns every implicit per-copy guarantee into an explicit concurrency problem someone has to solve. The ADR will not surface this on its own; nothing about "fewer places to look" prompts you to ask about simultaneity.

How to apply: when a plan's ADR proposes moving ANY kind of per-instance/per-checkout/per-process state into one shared location, add an explicit question to the ADR or brief: "who else reads or writes this at the same moment, and what did the old per-instance copy give us for free that the shared copy doesn't?" Answer it before acceptance, not at falsification — a paragraph at ADR time is cheaper than an entire extra phase discovered later.
