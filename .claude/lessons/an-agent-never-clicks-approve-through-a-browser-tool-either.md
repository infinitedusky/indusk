# An agent never presses the cockpit's Approve through a browser tool (Playwright MCP, chrome-devtools) — the click carries the page's own fetch metadata, so no hook or header can tell it from the person

**The rule.** Approval of a mockup is a person's act in the cockpit. That includes the case where the agent has a browser tool: opening `indusk ui`, navigating to the app's Looks page and clicking Approve (or Select all + Approve) is an agent approving, however real the HTTP request looks. Draw, propose, say what to open, and stop.

**Why it is a rule and not enforcement.** The approve route requires `Host`/`Origin` from the admin and `Sec-Fetch-Site: same-origin`, and the guard hook refuses Write, Edit and Bash that write `approved.json` or name `/api/looks/…/approve`. A Playwright MCP or chrome-devtools click is a genuine browser request from the admin's own page: same-origin header, no Bash command, no Write/Edit — so the route accepts it and no hook sees the MCP tool. The recorded approver is `git config user.name`, the same name the person's commits carry. The ui-promises audit (`.indusk/planning/ui-promises/audit.md`, 'which skip reason would you not accept' and 'does each row prove its sentence') found this gap; the plan's ADR names scripts and forged headers as the residual but not an ordinary agent tool.

**How to apply.** Do not use a browser tool on the Looks page's Approve or select-all controls, and do not report a mockup as approved on the strength of a record entry you caused. Reading the page, opening a mockup at each device to look at it, and taking a screenshot are fine. If a task seems to need the mockup approved to proceed, stop and ask the person to press Approve. Companion to `a-mockup-is-approved-only-through-the-cockpit` (who) and `a-mockup-is-approved-in-the-checkout-it-is-worked-in` (where).

**Open.** A real control would be a per-render token a browser tool cannot obtain, or a confirmation outside the browser the agent drives; neither exists yet.
