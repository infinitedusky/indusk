# A Test-Phase red commit must fail only on its new assertion — changing a shared type/model's shape can break an unrelated, unmodified test by TypeError, not just the one you're adding

In the Test Phase / Build Phase trajectory pattern, a red-step commit is supposed to go red on exactly the new assertion it adds, proving a well-formed hypothesis before the Build Phase makes it green.

In vscode-extension plan Build Phase 7 (commit 01db2b66, "test(vscode-extension): A29 red against an empty groups stub"), the red commit changed `PanelModel`'s shape in `core/panel.ts` — removing the `rest: PanelPromise[]` field and replacing it with `groups: PanelGroup[]` — in the same commit that added the new A29 test. But an existing, unmodified test (the A23 case in `panel.test.ts`, line ~59) still referenced `m.rest.map(...)` and `m.rest[0]?.state`. Because `rest` no longer existed on `PanelModel`, that pre-existing test now failed too — not on a clean assertion mismatch, but via `TypeError: Cannot read properties of undefined (reading 'map')`, and it would also fail a `tsc` type check (`Property 'rest' does not exist on type 'PanelModel'`). This went uncaught because `vitest run` (no `--typecheck`) transpiles types away and doesn't surface the type error at that boundary.

The impl.md Build Phase 7 Verification entry recorded "red at 01db2b66 ... each on its own assertion" — which undersold what actually happened: two different failure modes landed in one red commit, only one of them the intended one. The fix (`m.groups.flatMap((g) => g.promises)`) landed one commit later, in the Build Phase's green commit (bfbbf172), folded in with the real implementation — so it was never isolated or called out as its own fix.

**Why it matters**: a red step that also incidentally breaks something else loses its diagnostic value — you can no longer tell, from the test output alone, whether the new behavior is unimplemented (the intended red) or whether you've broken something unrelated (an accident). It also means a `tsc`/biome check run between the red and green commits would fail for a reason nobody intended to be in the red-step's story.

**How to apply**: when a red-step commit changes a shared interface's shape (removing/renaming a field, not just adding one), grep every call site and test assertion that touches the removed/renamed field *in that same commit*, and migrate them together — even though the point of the red step is "don't implement the behavior yet." Renaming/removing a field is a mechanical, zero-risk edit distinct from implementing new behavior; it belongs in the red commit alongside the new failing test, not deferred to the green commit. If a red commit's failure list includes a test that isn't the one named in the commit message, that's a signal the interface change leaked into territory the red step didn't intend to touch.
