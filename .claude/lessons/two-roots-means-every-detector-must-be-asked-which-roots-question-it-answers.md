# When a feature splits execution across two roots (a plan repo and a code repo, or any similar split), every existing detector/check must be individually re-asked "which root's question does this answer" — assuming a detector already knows, or defaulting all of them to one root, produces detectors silently answering the wrong root's question

dawn-workbench-execution introduced a plan-root/code-root split for workbench execution, and every single fix in the plan turned out to be the same shape: an existing detector or config lookup was implicitly answering a one-root world's question and needed to be told, explicitly, which root it should actually be asking. Goalpost drift and "which trajectory items became checked" are plan-repo questions (the plan documents live there). Red-test detection and "what else changed in the code" are code-repo questions (the code lives there). Phantom-work detection genuinely needs to read both. And the test command itself is *configured* where the plan lives (`.indusk/config.json` is in the plan repo) but must *run* where the code lives — a distinction the plan's own retrospective names as `configRoot` vs `root`, two different roots for what looks like one setting.

Why this recurs: before the split, "the root" was unambiguous, so every detector, config reader, and command-runner had exactly one directory to reach for and never had to declare which question it was answering. The split doesn't just add a second root — it retroactively makes every existing single-root assumption a landmine, because nothing about the code as originally written distinguishes "this needs the plan root" from "this needs the code root"; both were the same directory.

How to apply: when introducing any feature that splits a previously-single execution context into two (or more) roots, don't just wire the new split into the entry points — walk every existing detector, config lookup, and path resolution that used to take "the root" as an implicit single argument, and explicitly classify each one as plan-question, code-question, or both-question before deciding which root(s) it now receives. Treat "this detector obviously already knows which root it wants" as false until verified.
