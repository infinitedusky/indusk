# Manually smoke-testing an admin UI page for in-progress work in a worktree cannot use `indusk ui restart`

During day-promises Build Phase 4 verification, the plan called for `indusk ui restart` to manually smoke-test the new Promises page. Sandy corrected this in the session (noted verbatim in impl.md's Build Phase 4 Verification item, 2026-09-18): the global admin daemon serves the globally installed bundle and its registry (`~/.indusk/projects.json`) maps project names to their registered checkout paths — for `dusk` that's the trunk, which has no `.indusk/promises/` registry yet because the feature is still on `plan/day-promises` in a worktree. Worktrees are not separately registered projects.

Why: the admin UI is a machine-global daemon (see `/decisions/admin-ui-hosting`) that reads `~/.indusk/projects.json` to resolve a project name to a filesystem path. Restarting it just picks up a newer *bundled admin build*; it does not change which checkout a project name points to, and it cannot see a worktree's uncommitted/unmerged state under a different registry entry.

How to apply: to manually verify an admin page against in-progress worktree state before merge, run the admin directly (`next dev` in `apps/indusk-admin`) with a throwaway `INDUSK_HOME` pointing a temporary registry entry at the worktree path — not `indusk ui restart` against the real daemon. The real daemon will show the feature correctly only after merge to trunk and `indusk update`. This is distinct from the registry-leak-scan testing convention (`INDUSK_HOME` pinned per test) — this is about manual/interactive smoke testing, not automated tests.
