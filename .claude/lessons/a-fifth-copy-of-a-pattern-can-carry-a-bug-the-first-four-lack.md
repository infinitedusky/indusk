# When N near-duplicate code blocks share a shape "by comment" rather than by shared code, a new (N+1)th copy can introduce a bug none of the first N have — extract the shared function before writing the next copy, not after

trunk-guard's cleanup phase found that `update.ts` had four "ensure this hook is registered" blocks, each hand-written to the same shape but never sharing code — only a comment saying they were parallel. When the trunk-guard hook needed a fifth ensure-block (this time inside `init.ts`'s settings-merge path, not `update.ts`), the new copy carried a duplicate-matcher-group bug that none of the first four had, because it was written fresh against the pattern-by-eye rather than against a shared function that would have carried the first four's already-debugged logic forward.

The general shape: N copies of "the same thing," similar enough to recognize as siblings, different enough that nobody extracted them. Copy N+1 doesn't inherit the first N's fixes — it inherits only what the author remembered to copy, and a fresh write is a fresh chance to introduce a defect the others already avoided by accident or by an earlier fix.

Rule: the moment a task requires writing a second (or later) copy of a pattern that already exists twice or more in the codebase, that is the trigger to extract the shared function first — not "we'll consolidate later," because "later" is exactly when the next silent divergence happens. trunk-guard's cleanup extracted `ensureHookRegistered` as the one registration path (`update.ts` −81/+14 lines) after the fifth copy's bug was found, which fixed this instance but is the reactive version of the same rule the project already states for git primitives ([[a-focused-unit-for-a-moved-primitive-catches-tree-drift]]): a correct copy filed anywhere but the single shared definition is already duplication waiting to happen, and it's cheaper to notice at the second copy than at the fifth.
