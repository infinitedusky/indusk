# A new data source that only covers recent history silently gives a wrong answer for everything older — "unknown" and "wrong" are different answers, and the easy default (null/not-found) is usually the wrong one

When a feature starts reading a new source of truth that was only recently introduced (a log line a skill started writing on a specific date, a commit-message convention that started at a specific release), every record that predates the source's start gets silently misread as if the source answered "no" — rather than "this source cannot speak to this record at all."

**Case:** dusk's `display-names` plan added two time-bounded sources: the retrospective's "Landed on main at …" line (written starting 2026-09-18) and `chore(release): <version>` trunk commits (started at version 1.36.1). Plans older than each source's start date were initially read as "never landed" (80 of 111 archived plans) or, after that was fixed, misattributed to the *first* commit the new source could see ("released 1.36.1" for every plan that actually shipped years earlier, including ones that shipped in 1.32.0 and 1.30.0). Both are the same shape of bug: the absence of a matching record was read as a negative fact about the world, when it was actually a limitation of the source.

**The fix pattern:** for every new time-bounded source, explicitly ask "what does this source say about things that predate it?" and give that case its own fallback — usually an older, less precise source that still has partial coverage (here: the retrospective's bare frontmatter `date` as a landing-date fallback; the changelog's older, differently-formatted release records as a release fallback) — rather than letting the new source's silence become the answer. A plan's design document (ADR, brief) should name this fallback explicitly, because a generically-worded promise ("shows the release that shipped it") invites a reader to assume the obvious implementation already handles it, when it doesn't.

**When to reach for this:** any time you wire up a feature to read structured history that started being recorded partway through a project's life — git tags/commits with a adopted-partway convention, a log format that changed, a field added to a schema after other data existed. Treat "no record found because the record type started later" as a distinct case from "no record found because the thing never happened."
