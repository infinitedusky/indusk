# A positive verification result proves some mechanism fired, not that it was the specific mechanism the claim is about — when the claim is about WHICH artifact is in play, the test must vary that artifact

A single observation that "the expected behavior happened" is not evidence that it happened via the path being tested, if more than one path could produce the same observable outcome. This is a sharper version of "assert the resolved value, not just that nothing crashed" — here, the value IS resolved and IS correct-looking, but its correctness doesn't prove it came from where you think.

Found 2026-09-14/15 verifying that a VS Code `$schema` pointer actually drives schema resolution (worktree-config-schema-pointer, U1 manual smoke): a single type-mismatch diagnostic ("Incorrect type. Expected 'string'.") proves *some* JSON schema loaded and flagged the field — not that it came from the file the `$schema` pointer names. VS Code can resolve schemas by other means (workspace settings, extension-contributed schemas, `$schema` URL match). An even earlier attempt credited Copilot's inline ghost-text suggestion as if it were schema-driven completion; it was present identically whether the pointer resolved or not.

The proof that actually distinguishes "this pointer is what's driving it" is a controlled contrast: two schema files that disagree about one rule, the pointer flipped between them with everything else held constant, and the diagnostic changing to match whichever file is currently named. Only a variation in the artifact under test, paired with a variation in the outcome, ties the outcome to that specific artifact.

How to apply: whenever a verification claim is "X is being used" (this config, this schema, this code path, this build), don't stop at one observation that looks like X's effect — construct a contrast where swapping X (and only X) changes the observed result. One green check proves *a* mechanism worked; it never proves *which* one, and it never proves you didn't just get lucky.
