# Two individually-correct rules can contradict each other at a specific junction — fix the symptom locally, but route the cause to wherever it's actually visible

admin-plan-authoring hit a case where two rules this project holds — "never commit another session's uncommitted work" and "never land onto a dirty trunk" — directly contradicted each other at InDusk's own operational bookkeeping on main: landing a plan requires a clean trunk, but another session's legitimate in-progress bookkeeping (uncommitted current.md edits, etc.) is exactly the kind of "other work" that must never be silently committed or discarded on someone else's behalf. Neither rule is wrong; they simply collide at this one junction.

Why it matters: when a contradiction like this surfaces, the instinct is to patch wherever the collision happened — and that patch (admin-plan-authoring: `approve`/`land` now commit bookkeeping themselves, and the review lists other in-flight work) is the right immediate fix, because it resolves the actual blocking symptom. But the patch doesn't explain *why* bookkeeping was sitting uncommitted in the way in the first place — that root cause is a different, more general problem (where should ambient operational bookkeeping live, and when should it get committed) that deserves its own treatment rather than being buried inside the plan that happened to trip over it.

What to do: when two correct rules contradict at a specific spot, fix the immediate collision where it blocks you, but don't let that local fix stand in for diagnosing the actual root cause — write the root cause up as its own concern (admin-plan-authoring routed it to a separate draft brief, `bookkeeping-lives-where-it-is-read`) so it gets considered on its own terms instead of only ever being patched reactively at each new collision site.
