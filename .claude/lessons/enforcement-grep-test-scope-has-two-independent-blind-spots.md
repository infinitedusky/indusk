# A "search for X, expect zero matches" enforcement test has two independent scopes that must each be audited — narrowing either produces a guard that's green for the wrong reason

A grep-style enforcement test ("scan these paths for these patterns, expect zero matches") has two orthogonal dimensions that can each fail silently: **path scope** (which directories/files get scanned) and **pattern scope** (what shape of violation the patterns can match). Either one being too narrow produces a test that stays green while the thing it claims to prevent is actually present — and the two failures compound independently, so auditing one does not catch the other.

**What happened:** `git-only-substrate` (1.31.0) declared jj removed from InDusk, backed by an enforcement test (`scm-rip-out-grep.test.ts`) that searched for TypeScript symbol names (`getScm`, `jj.ts`, `NotAJjRepoError`, `getJjReachable`) across `apps/indusk-mcp/src/`. The test stayed green for **seven weeks** while `apps/indusk-admin/src/lib/vcs.ts` — created two months *before* the rip-out and never touched by it — called `execFileSync("jj", ...)` on every scorecard render. Both scope dimensions were too narrow: the path scope never included `apps/indusk-admin/`, and even if it had, the pattern scope only matched TS identifiers, not an argv-level string literal passed to a subprocess call. A correct pattern with the old path scope, or a correct path scope with the old pattern, would each still have missed it — both gaps had to close together.

**Why it matters:** a green "rip-out" or "removal" enforcement test creates the belief that the removal is complete and verified. That belief is load-bearing — later work builds on the assumption, and nobody re-checks a passing test. The project's own `git-only-substrate` retrospective had already flagged "zero matches in production source was green" as a gate falsification had to see past once; this is the same failure mode surviving undetected inside the very test meant to catch it.

**The rule:** when authoring or auditing a "search and expect zero" enforcement test, separately interrogate both dimensions: (1) **Path scope** — does this scan every app/package where the removed thing could plausibly have lived, not just the one you were working in when you wrote the test? (2) **Pattern scope** — does this match the violation at every level it could appear (symbol name, string literal, subprocess argv, config value), not just the shape you happened to think of? A scripted, exhaustive census (see [[scripted-census-over-manual-survey-for-fan-out-counts]]) is the right tool for establishing both scopes, not a manual read of "the files I remember touching."
