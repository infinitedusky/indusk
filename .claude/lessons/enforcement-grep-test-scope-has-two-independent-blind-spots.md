# A "search for X, expect zero matches" enforcement test has (at least) four independent scopes that must each be audited — narrowing any one produces a guard that's green for the wrong reason

A grep-style enforcement test ("scan these paths for these patterns, expect zero matches") has several orthogonal dimensions that can each fail silently: **path scope** (which directories get scanned), **pattern scope** (what shape of violation the patterns can match), **matching granularity** (line-at-a-time vs whole-file), and **file-type scope** (which extensions are scanned at all). Any one being too narrow produces a test that stays green while the thing it claims to prevent is actually present — and the failures compound independently, so auditing one dimension does not catch a gap in another.

**What happened, in two rounds.** `git-only-substrate` (1.31.0) declared jj removed from InDusk, backed by an enforcement test (`scm-rip-out-grep.test.ts`) that searched TypeScript symbol names across `apps/indusk-mcp/src/`. It stayed green for **seven weeks** while `apps/indusk-admin/src/lib/vcs.ts` — created two months *before* the rip-out — called `execFileSync("jj", ...)` on every scorecard render. Two scope dimensions were too narrow: **path scope** never included `apps/indusk-admin/`, and **pattern scope** only matched TS identifiers, not an argv-level string literal. `jj-residue-rip-out` fixed both and widened the test — then its own falsification round found **two more**, in the corrected test itself:

- **Matching granularity.** The corrected audit still tested one line at a time. The real call site was formatted across lines (`execFileSync(\n  "jj",\n  ...)`), so even a correct argv-level pattern missed it — the violating text was never on one line. Fix: match against whole-file content with patterns whose `\s*` spans newlines, not per-line.
- **File-type scope.** The widened audit still scanned only `.ts`/`.tsx` in the two apps it knew about. It was blind to `.js` (hooks), `.md` (skills, docs, prose), and `.json` (extension manifests) — every one of which ships to consumers. This is what let `apps/docs/src/guide/getting-started.md` advertise a `/jj` slash command whose skill file had been deleted five minor versions earlier: the first page a new user reads, invisible to a `.ts`-only scan.

A related mechanical trap surfaced during the same widening: a shared matcher function reusing a global (`/g`) regex across multiple files' content leaks `pattern.lastIndex` between calls — the second file silently gets fewer matches than the first purely from stateful regex reuse, independent of any of the four scope dimensions above. Reset `lastIndex` before each use, or construct a fresh `RegExp` per file.

**Why it matters:** a green "rip-out" or "removal" enforcement test creates the belief that the removal is complete and verified. That belief is load-bearing. The project's own `git-only-substrate` retrospective had already flagged "zero matches in production source was green" as a gate falsification had to see past once; the *widened* replacement test needed a second falsification round to find that it still had two uncorrected dimensions — narrowing a known gap does not guarantee no gap remains.

**The rule:** when authoring or auditing a "search and expect zero" enforcement test, separately interrogate at least four dimensions: (1) **Path scope** — every app/package where the thing could plausibly live, not just the one you were working in. (2) **Pattern scope** — every shape the violation could take (symbol name, string literal, subprocess argv, config value). (3) **Matching granularity** — whole-file, not line-at-a-time, or a multi-line construct slips through even a correct pattern. (4) **File-type scope** — every extension that ships to a consumer (code, hooks, docs, manifests), not just the language you were thinking in. Treat a first-pass widening as provisional and falsify it again rather than trusting that fixing the two dimensions you found closes the class. A scripted, exhaustive census (see [[scripted-census-over-manual-survey-for-fan-out-counts]]) is the right tool for establishing scope, not a manual read of "the files I remember touching."
