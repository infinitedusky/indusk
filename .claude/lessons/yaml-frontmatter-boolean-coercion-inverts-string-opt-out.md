# A frontmatter opt-out flag checked by string equality silently inverts when YAML coerces the value to a boolean

A frontmatter "opt-out" flag whose logic is a string comparison — e.g. `data.worktree === "none"` → skip, else create — has a footgun: YAML parses `false`/`no`/`off`/`yes`/`on` as **booleans or reserved words**, not strings. `worktree: false` (the most natural way a user expresses "no worktree") becomes boolean `false`, so `typeof value !== "string"` short-circuits to the default branch — the user gets exactly what they tried to opt out of. Discovered in the worktree-visibility plan's falsification round: `resolveWorktreeDecision` only honored the literal string `"none"`, so `worktree: false` silently returned `"create"`. gray-matter (js-yaml) confirmed live: `worktree: false` → `false` (boolean); `worktree: no`/`off` → strings under js-yaml 4.x, but still `!== "none"` → also wrong.

The trap is that the happy-path test (`worktree: none` → skip) passes, and the author never types `worktree: false` because they already know the keyword is `none`. The person who hits it is the user expressing intent the natural way.

What to do: for any boolean-intent frontmatter flag, treat the opt-out as a **type-aware predicate**, not a string equality. Handle boolean `false` explicitly, and accept the common falsy strings (`none`/`no`/`off`/`false`/`skip`) case-insensitively. Keep the safe default for everything else. Relatedly — the load-bearing environment facts belong in the test matrix: the same plan's `agent list` recompute wiped state when run from a non-git cwd, because the tests only exercised git cwds even though the workbench root (a normal place to run the command) is intentionally not a git repo. Both bugs were one user-keystroke / one `cd` away and shipped past a "completed" impl; falsification caught them.
