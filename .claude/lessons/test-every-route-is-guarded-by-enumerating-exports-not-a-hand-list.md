# A test asserting "every route is guarded" must enumerate the route modules and their exported handlers — a hand-written list of routes will miss some

admin-plan-authoring's first version of a test asserting every admin route is guarded (A34) used a hand-written list of route paths to check against the guard. That hand list missed two real GET handlers (`sessions`, `plans/build`) — they simply weren't in the list, so the test silently passed while two routes remained unguarded.

Why it matters: a security- or invariant-enforcing test that is supposed to cover "every X" is only as complete as whatever enumerates the X's. A hand-maintained list drifts the moment a new route is added and nobody remembers to add it to the list too — the test keeps passing, having silently stopped checking anything new. This is the same shape of failure as a reader that drops what it cannot parse (see `a-reader-that-drops-what-it-cannot-read-passes-every-rule-above-it`): the enumeration itself becomes the single point where coverage silently narrows.

What to do: when a test needs to assert a property over "every route" (or every command, every hook, every promise, any similarly open-ended set), derive the set by reading the actual source — the directory's file list, the module's exports — rather than hand-typing it into the test. `admin-hosts.test.ts` fixed this by reading each route module's exports and comparing against the directory listing, so a new route file or a new exported handler is picked up automatically. See `.indusk/planning/admin-plan-authoring/` for `admin-hosts.test.ts`.
