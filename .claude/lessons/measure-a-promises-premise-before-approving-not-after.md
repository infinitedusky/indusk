# A promise sentence can be believed true because its pieces exist in the codebase — approve it only after actually running the command it describes, not after confirming the pieces are present

A promise like "one command writes the keep-list" can look safe to accept because every piece it names already exists (an `init` step, an extension-registration mechanism) — but "the pieces exist" is not the same claim as "running the command produces the described result." The gap between those two claims is invisible until someone actually runs the command against a fresh/bare checkout and watches what comes out.

**Why:** untrack-mcp-json (dusk, 2026-10-11, archived at `.indusk/planning/archive/untrack-mcp-json/`). The brief's second promise ("the project's declared servers are written by one command") was approved on the belief that `init`'s MCP handling plus a built-in extension's registration would produce it. It was only measured after approval: `indusk update` created no `.mcp.json` at all (its MCP handling was guarded by the file already existing), `init` created one holding only `indusk`, and no built-in extension declared the `add_command` hook `update` needed to run. The promise had to be narrowed after the fact, and a trajectory row (T4) was retired because it could never pass as originally worded.

**How to apply:** when a brief's promise describes what a command does, run that exact command against a fresh clone or bare checkout as the plan's first step — before, not after, the brief is approved — and write the promise from what was actually observed, not from an inventory of pieces that look like they should combine into the claimed behavior. This is the command-level analog of "write a promise sentence from what its rows can prove" ([[write-a-promise-sentence-from-what-its-rows-can-prove]]): there, the gap was between a wide quantifier and narrow test rows; here, the gap is between a claimed mechanism and a never-run command.
