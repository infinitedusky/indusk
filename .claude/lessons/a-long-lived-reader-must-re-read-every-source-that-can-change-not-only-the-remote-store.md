# A long-lived polling reader must re-read every input that can change during its lifetime, not just the remote store it was built to watch — the local registry and incidents file change too

vscode-extension's `promises health --every <seconds>` command reads the project's promise registry (including incidents) once at startup and then polls only the remote telemetry source (Jaeger) on each subsequent tick. The implicit assumption was "only the remote store changes during a session" — but a promise marked fixed (its incident closed, changing the registry's on-disk incidents file) during that same long-lived process stayed shown as red/broken in the editor until the extension was reloaded, because the health computation combined a fresh telemetry read with a stale, startup-time registry read.

**Why it matters**: a long-lived reader's correctness depends on identifying *every* input to its computed state that can mutate during its lifetime, not just the one input that's obviously "live" (the remote store it was explicitly built to watch). A local file that's normally static (a registry, a config) stops being safely cacheable the moment the process's lifetime can span an edit to it.

**How to apply**: for any process that polls on an interval and holds state in memory across ticks, enumerate every file/store its output depends on and re-read all of them each tick (or react to file-change events for the ones that are cheap to watch) — do not special-case "the thing I'm polling for" as the only freshness concern. When adding a new on-disk input to a computation that already lives inside a polling loop, default to re-reading it every tick unless there's a measured cost reason not to, and treat "it normally doesn't change mid-session" as insufficient justification once the reader's lifetime is unbounded.
