# A leftover-resource guard chained after tests with `&&` never runs on the failing or crashed run most likely to leave one behind — and a guard that checks one instant of a process list will name something already exiting

From `test-daemons-never-leak` (`.indusk/planning/archive/test-daemons-never-leak/`), discovered during its falsification phase — the leftover-telemetry-daemon guard (`apps/indusk-mcp/scripts/with-daemon-guard.js`, checking via `check-test-daemons.js`) was chained after the test command with `&&`, so a failing or crashed test run — exactly the run most likely to leave a daemon behind — skipped the guard entirely. Separately, `test:system`, the tier that starts daemons on purpose, had no guard at all.

Why it matters: "report the leak" sounds complete but silently means "report the leak, on passing runs only" unless the test plan says otherwise explicitly. A guard's value is concentrated in the failure case; chaining it with `&&` protects exactly the runs where nothing could go wrong. Separately, the guard's first system-tier run named a daemon that was already stopping — a single instant of `ps` caught it mid-shutdown. A guard that cries wolf on a process that's already exiting is the kind that gets switched off, which defeats its purpose as surely as never running it.

How to apply: when writing a cleanup/leftover-resource guard, (1) run it unconditionally after the test command (not `&&`-chained) so a failing run still reports what it left behind, and (2) give it a grace period — re-check after a short delay — before naming something as still running, rather than trusting one snapshot. When writing the test plan for this kind of guard, state "runs even when the tests fail" as its own assertion, not an implied detail of "report the leak" (see highlight note for the test-plan-authoring angle, same root cause).
