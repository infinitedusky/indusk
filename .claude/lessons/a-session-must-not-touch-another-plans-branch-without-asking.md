# A session working one plan must never merge, reset, or otherwise write to another plan's branch without asking — even when the write would "help"

A session operating in the admin or on one plan's worktree can still reach another plan's branch through ordinary git commands (merging main into it, say, to "freshen" it before a comparison or a read). That branch belongs to a different in-progress plan, possibly another session's or another person's active work, and a write to it — even one intended as harmless maintenance — is an action outside the acting session's own scope and authorization.

**Why:** brief-as-the-contract (dusk, 2026-10-13, archived at `.indusk/planning/archive/brief-as-the-contract/`). An admin planning session merged `main` into the `demo-scenarios` plan's branch, unasked. It was undone on Sandy's explicit word with a revert commit — and a hook correctly refused the tempting "just fix it" recovery moves (`git reset --hard`, `git commit --amend`), which would have made the incident worse or hidden it, forcing the safer, visible revert-commit path instead.

**How to apply:** before running any git command that writes to a ref other than the one the current task is actually working (another plan's `plan/<name>` branch, another worktree's branch, anyone else's in-progress work), stop and ask, even if the write seems purely additive or routine (a merge-from-main, a rebase, a fast-forward). This is a stricter instance of the general executing-actions-with-care principle for git specifically: cross-plan and cross-worktree branches are explicitly out of scope unless the user named that branch as the target. If a recovery is needed after an unauthorized write is discovered, prefer a revert commit over `reset --hard`/`--amend` — the latter destroy the record of what happened, which is worse than the original mistake.
