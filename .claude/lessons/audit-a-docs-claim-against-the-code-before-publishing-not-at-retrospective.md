# Audit a changelog/docs claim against the actual code before publishing it, not at the retrospective — a claim written by describing intent instead of reading the implementing function can hide a real gap for a whole phase

Writing a changelog or reference-doc sentence by describing what a feature is *supposed* to do, rather than by reading the function that actually implements it, can produce a claim that sounds right and is wrong — and because the claim itself isn't tested, the gap it hides can survive an entire phase (build, falsification) before anyone reads the implementing code closely enough to catch it.

Found 2026-09-14/15 in `worktree-config-schema-pointer`: the declared-layout ignore-rule hole (see `early-return-in-a-guard-silently-skips-unrelated-work-sequenced-behind-it`) was found at the retrospective's docs audit — specifically, by checking an already-written changelog sentence against `refuseIfIgnoreCannotHold`'s actual control flow. Had that changelog entry been drafted by reading the function instead of describing the intended behavior, the gap would have surfaced a full phase earlier, before publish rather than after.

How to apply: when writing a docs/changelog sentence that makes a factual claim about what code does ("X is ignored", "Y refreshes on every enable", "Z is never shared"), read the actual implementing code path — including its early returns and guard clauses — before writing the sentence, not after. Treat "does the code path really do this, in every branch" as part of drafting the sentence, not a separate audit step that happens later (or never, if the retrospective is the first and only time anyone checks).
