# Never edit a file that may hold another live session's uncommitted work with a script that opens it for writing before reading it — truncation destroys what it hasn't read yet

During planner-promises's archival step (commit 0529fdff, confessed in retrospective.md), an agent meant to change one line of `.indusk/current.md`'s shared region and ran the Python-equivalent of `open(p, "w").write(fix(open(p).read()))` — a single expression. `open(p, "w")` truncates the file to zero bytes as its very first side effect, before the right-hand side's `open(p).read()` ever runs (and even if the reads happened first, the file held another session's uncommitted edits that only existed in a different process's memory or a different edit, not yet reflected in `fix`'s input). The worktree's `current.md` held 237 uncommitted lines written by a live eval session; 147 of them — that session's actual notes — were permanently lost. No backup, no Time Machine, no transcript held the write.

Why: `current.md` is explicitly a multi-agent coordination file (see `/decisions/multi-agent-coordination`) — it has a `current.md.lock` file lock and a dedicated `mcp__indusk__update_current_section` MCP write surface specifically because concurrent sessions each hold uncommitted state in it between their own commits. A script-level open-for-write bypasses the lock entirely and has no way to know another session's in-memory or uncommitted intent before clobbering the bytes it would have read. "I'll read it, transform it, write it back" is only safe when nothing else can write to the same file between the read and the write — which is never guaranteed for a shared coordination file, and is actively false the moment the open-for-write happens before the read in the same expression.

How to apply: never edit `.indusk/current.md` (or any file multiple live sessions write to) via a raw script/heredoc/`open(path,"w")` pattern — use the Edit tool (which diffs against the current on-disk content) or the dedicated `update_current_section` tool, never a blind open-write. More generally: before writing any file, ask "could another process hold uncommitted intent for this file right now" — if yes, the write must be read-check-write with a lock, or routed through the tool that owns that invariant, never a bare open-for-write.
