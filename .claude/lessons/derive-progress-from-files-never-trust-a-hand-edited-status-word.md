# A hand-written status field and a derived position are two stores of the same fact — read progress from what's actually on disk, keep the hand-written field as a declaration only

When a document carries both a manually-set field (e.g. frontmatter `status:`) and the actual, inspectable state of the work (which phases are checked off, which gates passed, what the files show), any reader that trusts the manual field is trusting that whoever last touched the document remembered to update it. That assumption breaks silently — the field drifts from reality, and every downstream display built on it (a nav row, a dashboard card, an exported summary) inherits the staleness.

**Why:** nav-stage-matches-plan-page (dusk, 2026-10-16, archived at `.indusk/planning/archive/nav-stage-matches-plan-page/`). A plan built but not yet falsified read "completed" in the admin's nav — because the nav trusted the impl's hand-written `status:` word — while the plan's own page, which derived its step from the actual phase/gate state, correctly showed "Falsify." The fix: a single exported function (`stepAt` in `plans/steps`) that derives the step from the files, used by every reader (the nav, Needs you, and — found only by the cold audit — the project card and the exported markdown, two more readers of the stale field nobody had grepped for). The retrospective's own words: "A hand-written status word and a derived position are two stores of one fact; any reader of the first trusts the agent to have edited it. Read progress from the derived one, keep the field as the author's declaration."

**How to apply:** when a document has both a manually-maintained status/progress field and enough structural information to derive that same fact (phases, checkboxes, gate states), build one function that derives it and route every display through that function — never let a second reader independently trust the manual field. Before accepting a fix like this as complete, grep broadly for every place that reads the old field, not just the one display where the bug was first noticed; this plan found two additional readers only via a fresh audit, not the builder's own search.
