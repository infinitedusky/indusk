# Show the person the built thing before running falsification, not between falsification and cleanup — their first look generates scope that belongs in the build, not as a late add-on

In the vscode-extension plan, Sandy's first look at the built extension produced two new promises, a project title, and plan-based grouping — all real, wanted scope — but it happened between the falsification phase and the cleanup phase, after the goal-flipped bug hunt had already run and spent its effort on the build as it stood, not on the build as the user actually wanted it.

**Why it matters**: falsification is specifically a goal-flip — "stop trying to prove it works, go hunt for what's broken" — against a fixed target. When the user's first real look at the thing changes that target (adds scope, reveals a different grouping is wanted, surfaces a missing title) after falsification already ran, the falsification effort was partly spent hunting bugs in a shape of the product that was about to change anyway, and the newly-added scope goes in having had no falsification pass of its own unless a new one is explicitly scheduled for it.

**How to apply**: schedule the first human look at a working build — not a description of it, the actual running thing — before the falsification phase, same principle as [[run-the-live-check-before-falsification-not-last]] (vscode-extension's A28/live-check ordering lesson, which made the same correction for automated live checks). Treat the user's first-look feedback as input that can still reshape the build phases, then run falsification against the shape that's actually shipping, not an earlier one.
