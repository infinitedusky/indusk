# A plan status meaning "correctly protected, awaiting a human step" can sit unclosed indefinitely — every system that touches it is working exactly as designed, and nothing asks how long it's been waiting

indusk-makeover's impl sat with `stageStatus: completed` for 53 days between finishing its checklist and getting a retrospective written. Every system that could plausibly have caught this was doing its job correctly: `list_plans { active: true }` reported it as active (confirmed against `plan-tools.ts:19,244` — `completed` is explicitly in the active-status set, "completed = awaiting close-out rituals"), and `archive-dead`'s dead-draft sweep refused to touch it (confirmed against `archive-dead.ts:28-32` — `completed` is in `BLOCKING_STATUSES`, the exact protection that exists so a plan awaiting its retrospective is never swept as abandoned). Both behaviors are correct in isolation. The gap is that "correctly protected and visible" is not the same as "someone will act on it" — visibility is a precondition for a human noticing, not a trigger that makes noticing happen. Only a deliberate, out-of-band sweep through every plan folder outside the normal sequence (a one-time reconciliation pass, 2026-09-14) actually closed it.

**Why this is a distinct failure from the usual "detector doesn't know about a new status" class** (see `register-new-vocabulary-with-every-keyed-detector`): this isn't a detector failing to recognize `completed` — every detector recognizes it and handles it exactly as intended. The gap is structural: no detector's *job* is "how long has this plan sat in this state," because that's an age/duration question, not a status-membership question, and nothing in the plan lifecycle currently asks it.

**How to apply:** for any status that means "correctly finished with the machine part, waiting on a human step" (a completed impl awaiting retrospective, an approved PR awaiting merge, a resolved ticket awaiting close), ask whether anything checks how long it's been in that state — not just whether it's currently valid to be in that state. If the answer is "nothing checks age, only membership," that status is a plan (or ticket, or PR) that can sit forever with every system reporting it as healthy. The fix isn't a new durable primitive to track it (see `reopenable-beats-new-durable-primitive-when-resting-state-must-stay-bounded` for why not) — it's a bounded-age check: a ritual gate that refuses (or at least flags) a plan left in a "waiting on human" status past some threshold, the same way the existing decay layer already ages out draft plans on the other end of the lifecycle.

See `.indusk/planning/archive/indusk-makeover/retrospective.md` (2026-09-14) and the 2026-09-14 plan-sequence reconciliation for the concrete case.
