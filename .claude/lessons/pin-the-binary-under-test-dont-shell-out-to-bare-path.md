# A test that shells out to a bare command name runs whatever is on PATH, not the code under test

If a test (or a hook a test triggers) invokes a CLI by bare name — `indusk telemetry register`, `git`, `docker`, etc. — it resolves from the shell's PATH, which in a dev environment is very likely the globally installed version, not the package's own built artifact. In dusk, `init`'s extension hook ran `indusk telemetry register`, and every "everyday" Vitest suite that exercised `init` was silently testing the developer's global 1.57.2 install, never the code under test. A fix (`INDUSK_SKIP_TELEMETRY_AUTOSTART`) stayed red for a reason unrelated to the fix itself — the switch never reached the binary that could honor it.

Fix: pin the binary explicitly in the test environment (dusk set `INDUSK_BIN` to the package's own built CLI path in both everyday Vitest configs) rather than relying on PATH resolution. Before trusting that a behavior-changing switch "reached" the code, check which binary a test actually invokes — add a quick `which <cmd>` / log-the-resolved-path check if there's any doubt, especially when a test stays red after a fix that looks correct in isolation.
