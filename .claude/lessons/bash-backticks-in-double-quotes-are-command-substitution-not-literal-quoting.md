# Never use backticks to render a literal command name inside a double-quoted bash string — bash treats them as command substitution, not markdown-style code quoting

apps/indusk-mcp/scripts/release-guard.sh's already-published refusal message wrote `` "`pnpm release` publishes whatever version package.json holds; it never bumps." `` intending the backticks as prose emphasis (like markdown). Bash parsed them as command substitution: every time the guard's check 4 fired against an already-published version, it executed `pnpm release`, which re-entered the guard, which fired check 4 again — infinite recursion. The path had never executed until 1.51.0 was accidentally published twice and a third attempt hung two terminals (fixed in 62644069, changelog in apps/docs/src/changelog.md).

Why: bash backticks are always command substitution inside double quotes, with zero exception for "just formatting text" — there is no bash-native way to render a literal backtick-quoted command name without escaping (`\``) or switching to single quotes. The bug was invisible in code review because it reads exactly like intended prose, and it was invisible in testing because the already-published path is rare (only hit when the version truly needs bumping) — it shipped in 1.51.0's own release script and only fired on that same version.

How to apply: when writing user-facing messages inside bash scripts (fail/echo/printf strings), never use backticks to indicate a command or code span — use single quotes ('pnpm release') or escape them (\`pnpm release\`) instead. When reviewing or authoring any bash string containing backticks, check whether they're inside double quotes; if so, verify deliberately whether command substitution is intended.
