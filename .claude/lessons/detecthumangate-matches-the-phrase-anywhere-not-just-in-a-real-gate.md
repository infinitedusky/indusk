# detectHumanGate (lib/build/judgement.ts) matches /deferred verification/i anywhere in an unchecked checklist item — mentioning the phrase stops an unattended build, even in a non-gate note

plan-review-subagent's cleanup phase hit this directly: a "reviewed, left as-is" checklist item that merely referenced the trajectory's deferred-verification subsection by name (in passing, to explain why no extraction was needed) matched `detectHumanGate`'s `/deferred verification/i` pattern. `indusk plans next` then answered `judgement` instead of continuing — an unattended build would have stopped at a note that was never meant to block anything. The item had to be reworded before commit to avoid the phrase.

Why: the detector is a substring/regex match over free text, with no check for *structural position* — whether the phrase appears inside an actual Deferred Verification entry (`reason:`/`would require:`/`mitigation:`) versus an unrelated sentence that just happens to name that heading. A regex that fires on *mentioning* a concept cannot distinguish that from *being* an instance of the concept.

How to apply: when writing any checklist item, Shape finding, or cleanup note in an impl.md, avoid incidentally using phrases that match known gate-detection patterns (`deferred verification`, and by the same logic any other heading-derived trigger phrase) unless the item genuinely is that gate. If you need to reference a heading or concept by name in prose, paraphrase it or quote it in a way that breaks the literal match (e.g. backticks around the heading, or restructuring the sentence). Longer-term, `detectHumanGate` itself should be tightened to check structural position (is this text inside a `### Deferred Verification` block, not just a checklist item anywhere in the document) rather than a bare case-insensitive substring/regex over the whole item — but until that lands, the practical rule is: don't say "deferred verification" unless you mean the gate.
