# A verification command like `pnpm --filter <wrong-name>` that matches no package prints "No projects matched" and exits 0 — a Verification item that was never actually run as written still reads green

During promise-sources (`.indusk/planning/archive/promise-sources/`), the plan's own impl.md wrote `pnpm --filter @infinitedusky/indusk-admin exec vitest run ...` into two Verification checklist items — but the package is actually named `indusk-admin` (no scope prefix in its `package.json` `name` field), not `@infinitedusky/indusk-admin`. pnpm's `--filter` with a name that matches zero packages prints "No projects matched" and exits 0, so a Verification item copied from a similar-looking but wrong command silently reports success without running anything. The retrospective notes an earlier archived plan made the identical mistake. In this case the actual tests were run some other way during the session, so nothing false was recorded — but the command as written in the plan document proves nothing and would mislead a future reader who re-runs it verbatim.

**How to apply:** never write a Verification command (or any runnable check in a plan document) from memory or by analogy to a similar package's name — copy it from a command that has actually been executed and confirmed to run real tests, or verify the exact `--filter` target against the package's real `name` field in `package.json` before committing it to the plan. Prefer `pnpm --filter <name> --fail-if-no-match` (or the equivalent for other package managers) so a typo'd or renamed filter target fails loudly instead of silently exiting 0. This generalizes beyond pnpm: any verification step whose "it ran and passed" signal is indistinguishable from "it found nothing to run" is a check that can pass for the wrong reason.
