# Two independent copies of the same error-advice logic can each look locally correct while producing the identical wrong output for the same bad input — the shared defect is invisible until cleanup puts the copies side by side

During promise-sources (`.indusk/planning/archive/promise-sources/`), `status`'s failure-text code and `watch`'s hint code each independently re-read the raw `promises.jaeger` config to build a human-readable suggestion when a source failed. For a malformed config value (the same input from trajectory row A8 — a bare string where an object belongs), both copies produced the exact same wrong message: "Check undefined is up." Neither copy was individually "buggy" in a way code review of either site alone would likely catch — each read the config the same (wrong) way and each printed a plausible-looking error template. The defect was only surfaced when cleanup (Build Phase 6) reviewed both call sites together and noticed the duplication itself, at which point the shared wrongness became obvious. The fix extracted one `sourceAdvice` function (`lib/promises/sources.ts`) that builds its message from the typed failure object (`JaegerUnreachable | WatcherBlind`) rather than re-deriving it from raw config at each call site.

**How to apply:** when two or more places in a codebase independently implement "explain this failure to the user" (or any derived/interpretive logic, as opposed to a straight data pass-through), treat that duplication itself as a code smell worth resolving even before a bug is found — not just for the usual DRY reasons, but because duplicated interpretive logic can fail identically and silently at both sites, which single-site code review cannot catch. When reviewing or cleaning up a plan's changed files, explicitly look for near-identical blocks of advice/formatting/interpretation logic and diff them against each other, not just against the single-site "does this look right" question.
