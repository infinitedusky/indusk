# A workbench root IS a git repository that receives real commits (every checkbox, every brief) — an eval-attribution invariant framed as "never score against the workbench" is itself wrong, not just incomplete

workbench-trust-fixes' original invariant (A7, from the research/brief) was "a commit made from a workbench-root cwd is never attributed to the workbench repo." Falsification (A20) found this framing itself is wrong, not just an edge case away from right: the workbench repo genuinely receives commits too — every trajectory checkbox toggle and every plan-document edit lands there — so "never the workbench" would score a legitimate plan-document commit against the CODE repo's unrelated HEAD, which is exactly the same class of mis-attribution bug the original invariant existed to prevent, just pointed the other direction.

**The corrected invariant:** "a commit is attributed to the repository that actually received it" — resolved by comparing HEADs (newer HEAD wins, since that's the repo the commit actually landed in), with the code repo winning a tie (deliberate: a genuine tie is rare and the code repo is the higher-value default to score against), and the choice logged explicitly as `attribution` so the decision is auditable rather than implicit.

**Why this matters as a "do not reintroduce" warning, not just a "we fixed it":** the wrong framing ("never the workbench") is intuitively appealing — it reads as the obviously-safe, conservative rule, the kind of blanket exclusion that sounds like it can't possibly be wrong. That's exactly what makes it dangerous to reintroduce later: a future contributor reasoning from first principles about "how should eval-attribution work in a workbench" is likely to independently re-derive "never score the workbench" as the safe-sounding answer, without the falsification context that shows it silently mis-scores a real, common case (plan-document commits, which happen constantly).

**How to apply:** when an invariant sounds obviously conservative/safe ("never X"), check whether X is actually a case that legitimately occurs — a blanket exclusion is only safe if the excluded case never has a legitimate instance. If it does, the invariant needs to discriminate between legitimate and illegitimate instances of X, not exclude X wholesale. Record the corrected invariant explicitly alongside the wrong one it replaces, the way this plan's research/impl now do, so a future reader sees both the rule and the reasoning that ruled out the more intuitive-sounding alternative.
