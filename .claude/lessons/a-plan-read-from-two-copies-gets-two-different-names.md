# A plan's fields read from the trunk checkout vs. its own unmerged worktree can disagree — every reader naming a plan must resolve the same copy through one shared resolver

When a plan's documents exist both in the main checkout (stale, pre-merge) and in the plan's own worktree (current, where the branch's edits actually live), two different code paths reading "the same plan's title/name/field" can silently read two different copies and disagree — not because either reader is wrong, but because nothing routes both through the same copy-resolution rule.

**Why:** plan-stories (dusk, 2026-10-15, archived at `.indusk/planning/archive/plan-stories/`). The nav read a plan's title from the worktree copy; `readHealthNames` read it from the trunk's. Until the branch landed, the same plan showed two different names in two different parts of the admin. Found only by falsification (Build Phase 6), fixed by making `readHealthNames` async over the package's shared copy resolver (worktree-first) instead of its own direct trunk read. The retrospective's own words: "One plan read from two copies gets two names. Every reader that names a plan has to resolve the same copy (worktree first) through one resolver. A second walk of the assignments is a second rule."

**How to apply:** when a project has a worktree-per-plan model (an unmerged branch's documents live in its own worktree, stale copies exist in the trunk checkout until merge), any new code that reads a plan's fields must go through the one established copy-resolution function, never write its own direct read of the trunk or the worktree. Grep for every existing reader of that same field before adding a new one — a second hand-rolled "walk the assignments and find the right copy" is a second place for this exact bug to recur.
