# An enabled extension's on_enable hook never fires again on indusk update — autoEnableExtensions skips what's already enabled, extensionsUpdate is third-party-only, so any file it materialized is frozen at enable-time unless the manifest declares on_update

`indusk update` runs `autoEnableExtensions` (skips any extension already enabled — it only turns on new required-by-default ones) and `extensionsUpdate` (only re-syncs third-party extensions' declared files, never re-runs a built-in extension's `on_enable`). So any file a built-in extension's `on_enable` hook materializes into a consumer project — a starter config, a copied schema, a scaffolded script — is frozen at whatever version was live when the extension was enabled. A changelog entry promising a fix "arrives on the next enable or `indusk update`" is false for already-enabled extensions unless the extension's manifest explicitly declares an `on_update` hook that re-runs the relevant step.

Found 2026-09-14/15 in worktree-config-schema-pointer: the initial fix shipped a schema file via `on_enable.sh` and the changelog said it would reach existing projects "on the next enable or `indusk update`" — untrue, since nothing in `update` re-runs `on_enable` for the already-enabled `worktree` extension. Fixed by adding an explicit re-run step in `update.ts` for extensions that declare their `on_enable` idempotent.

Corollary: a package-owned file materialized this way is per-machine state, not shared project content — if the workbench sync ignore rules don't name it explicitly, `workbench sync` will offer it to the shared context repo, and teammates on different package versions will fight over it on every enable (see `early-return-in-a-guard-silently-skips-unrelated-work-sequenced-behind-it` for how that specific ignore-rule gap slipped through here).

How to apply: when a fix or new feature lives inside an `on_enable` hook, and the change needs to reach projects that already have the extension enabled, either (a) add an explicit update-time re-run step naming that extension, or (b) write the changelog/docs claim only for newly-enabled projects and say so. Never write "arrives on update" without checking `update.ts` actually re-runs the hook that produces it.
