# A string sourced from outside the repository (a deployed system, a webhook, a span) must be sanitized where it enters a plan document, not trusted because it only "adds a field"

When a value that originates from a system InDusk does not control (a marked OTel span, in day-always-on's case) is interpolated into a plan artifact — YAML frontmatter, or markdown a human is required to author — the naive assumption is "worst case it adds a stray field." That assumption is wrong in two independent ways, both confirmed with a red test in day-always-on's falsification phase (A28, `apps/indusk-mcp/src/__tests__/always-on-falsification.test.ts`):

1. **It can break the parser entirely, not just add a field.** `recordViolations` (`apps/indusk-mcp/src/lib/promises/incidents.ts`) interpolated a span's `deployment.environment` raw into an incident's YAML frontmatter above `status: open`. Setting `deployment.environment` to a string containing a `promise:`-shaped line does not add a second key — it creates a **duplicate mapping key**, which `js-yaml` throws on. The registry parser then fails on that one file, and because the registry is read as a whole, **the entire promise registry stops parsing** — a deployed application can take every promise's status offline by choosing one span attribute.
2. **It can forge content a human is supposed to have written.** The violation's `symptom` string lands in the incident body. A symptom containing markdown heading syntax can inject a second `## Root cause` section — the exact section the registry's workflow requires a person to author as an attestation. The forged section is indistinguishable from a real one to any reader that just checks the heading exists.

**Do**: sanitize at the boundary where an untrusted string crosses into a structured document — at the write call (`recordViolations`), not at every reader. Reject or strip line separators and structural syntax (YAML key/mapping syntax, markdown heading markers) before the value is interpolated, never after. The general form of the mistake: treating "this value only sets one field" as safe reasoning about a string that is concatenated (not structurally emitted) into a format where position and syntax both carry meaning — YAML mapping keys, markdown headings, shell arguments, and SQL are all instances of the same trap.

This generalizes the project's existing rule that "a safety argument written in a comment is not enforced by the code around it" (see `/reference/cli/workbench`) one step further: an *absence* of any argument at all — no comment, no check — for a value whose origin is a system outside your trust boundary is the same gap, just undocumented. Any future field carried from a marked span (or any other externally-controlled input) into a `.md`/`.yaml` plan document needs this same boundary check before it ships, not discovered by the next falsification pass.

See `.indusk/planning/day-always-on/impl.md` (Build Phase 7, A28) and `/guide/always-on`.
