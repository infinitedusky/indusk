# A promise's statement is rewritten only via `indusk promises change`, never by editing the registry file's text directly — hand-editing loses the History line that should record what it replaced

In demo-app-template (2026-10-07), a live check found the seat-holds example's "Fix it" button and the plan's own promise wording were both wrong: stopping the fault doesn't mend a broken promise, InDusk already models recovery as unrecorded → open incident → fixed, and "it holds again" was never true. The fix correctly reworded the promise's statement in `.indusk/promises/the-demo-break-is-caught-locally.md` and updated the brief, test-plan, and the page's button text. But the registry file's own `## History` section shows only `declared` then (two commits later) `enforced` — no entry recording that the statement was ever changed, even though `promisesChange`'s own doc comment says a call through it "keeps the sentence it replaced" in History. The brief's own `**Changes**` section was also left at `None`, when the planning rules require it to carry the exact new sentence for a promise changed after declaration.

Why: the registry's History is the only audit trail of what a promise used to say. A hand-edit to the statement text bypasses `indusk promises change <name> --plan --statement --reason`, so nothing records the prior wording — silently erasing the exact kind of conceptual bug (a promise whose sentence doesn't match what the system actually does) that this live check was meant to catch. The same gap means `indusk promises confirm` can't verify the change against the brief's Changes section, because that section was never updated either.

How to apply: when a live check or any correction changes what a promise's statement says, after it's already been declared, run `indusk promises change <name> --plan <plan> --statement "<new sentence>" --reason "<why>"` — never edit the frontmatter/body text in `.indusk/promises/<name>.md` directly. In the same edit, update the brief's `**Changes**` section with the exact new sentence (see [[feedback_cite_plan_ids_with_provenance]] for the related rule that `promises confirm` needs an exact-sentence match, not prose describing the change).
