# A refusal message that names a path, command, or value is making a factual claim — test that claim the way you'd test any other output, because a correct decision to refuse can still carry a wrong message

verify's refusal message correctly identified that it should refuse (the logic was right) but told the user to run verify at a directory that did not exist (A13, workbench-trust-fixes). The refusal itself was the right call — verify genuinely could not proceed — but its remediation instruction was a silent wrong answer wearing an honest refusal's clothes: a user following it exactly as written would hit a second, confusing failure, and have no reason to suspect the tool's advice rather than their own understanding.

**Why this is a distinct bug class from "the refusal logic is wrong":** a refusal's *decision* (refuse vs. proceed) and its *message content* (what to do instead) are two different pieces of output, and testing only that "the right code path fired" (i.e., that a refusal happened) says nothing about whether the message is actually true. This is the same shape as `assert-the-resolved-value-not-just-that-nothing-crashed` applied to error paths specifically: a test that asserts "verify refuses on this fixture" and stops there is exactly as blind to a wrong path in the message as a test that asserts "restore exits 0" is blind to a self-referential symlink.

**How to apply:** any refusal, error, or log message that names a concrete path, command, identifier, or value is making a checkable factual claim, not decorative text. Test it the way you'd test any other output — for a path, assert `existsSync(namedPath)` is true; for a suggested command, consider whether it's the actual command that would work. Do this especially for refusal paths, which get written once under the assumption "this case never fires in practice" and then genuinely don't fire again until the exact production conditions the message was written for actually occur — by which point the codebase may have moved and the message's assumptions with it.

See `.indusk/planning/workbench-trust-fixes/` (A13, `resolveVerifyRoots`'s refusal message) for the concrete case.
