# Never edit a live-check copy of a real project to make it run faster — trimming "slow" setup can silently remove what the check depends on

During workbench-plan-authoring's live check, numero's `post_create` hook was emptied to speed up the check — but that hook was what installed dependencies the build actually needed, so the edit silently broke the very thing being tested. Separately, the same live check hit a known, already-documented gap (untrusted projects making every session ask for permission) within minutes of real use, and Sandy's response was simply "just fix it" rather than treating the documented gap as acceptable because it was already known.

Why it matters: a live check's value comes from running the real thing under real conditions. "Real" includes the setup steps that look like slow overhead but are actually load-bearing — trimming them to make the check faster changes what's being tested without changing what the check believes it's testing, so a pass after trimming proves nothing about the untrimmed path. This is the same principle as "copy a real project, don't fake one" taken one step further: having copied it, don't then edit the copy's setup for convenience.

What to do: when a live check needs to run faster, speed it up by choosing a smaller or more targeted fixture, or by running fewer scenarios — never by hand-editing the copy's own setup/install steps, since those steps are usually exactly the part real-world use depends on and tests are meant to exercise. Relatedly: check whether a session is already running in a target project before restarting the admin against it (another finding from the same live check) — a live check against a live system can collide with its own prior run.
