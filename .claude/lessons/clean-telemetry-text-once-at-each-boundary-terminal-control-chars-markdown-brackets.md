# Text carried in a telemetry span (symptom, trace id, source reason) is untrusted input — clean it once at each boundary where it stops being plain text: a control character before a terminal, a bracket before Markdown

vscode-extension's editor surfaces span-derived text (a promise's break symptom, trace id, source reason) in two different rendering contexts: a VS Code terminal command line (the "Fix with Claude" action) and a Markdown hover. Both are injection surfaces for text that was written by whatever process sent the span, not by this project — a symptom string is exactly as trustworthy as a webhook payload.

Two concrete failure modes drove this (A20, A21 in the vscode-extension plan): a control character in a symptom string reaching a terminal command line is a keystroke, not a printable character — a Ctrl-C byte ends a quoted shell string early and lets whatever follows execute as a separate command. A bracket or other Markdown-significant character reaching a hover tooltip is link/formatting syntax, not literal text — `[click here](javascript:...)`-shaped content renders as a clickable link, not an escaped string.

**Why it matters**: these are two different threat models (shell injection vs. Markdown/rendering injection) hitting the same untrusted string at two different exit points. Sanitizing once, generically, "because telemetry text is untrusted" is not specific enough — each boundary needs the cleaning rule appropriate to what that boundary interprets as structure.

**How to apply**: identify every place a telemetry-derived string stops being "just text" and becomes input to something that parses structure out of it (a shell command line, a Markdown renderer, an HTML body, a YAML document), and apply the boundary-specific cleaner immediately before that exact hand-off, not earlier and not generically — vscode-extension's `cleanFacts` (one line, strips control characters, for the terminal) and `asText` (Markdown-escapes, for the hover) are the two concrete examples. This is the same general class the existing lesson [[untrusted-external-strings-into-plan-documents-need-boundary-sanitization]] names for a different boundary (YAML/markdown plan documents, from day-always-on) — different target format, same principle: sanitize at the specific write/render call where untrusted text crosses into structure, not "once, somewhere, for safety."
