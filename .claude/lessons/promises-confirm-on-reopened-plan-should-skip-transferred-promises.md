# indusk promises confirm on a reopened Maintenance plan refuses when a later plan has taken over its promises via promises change — its own suggested fix would hand ownership back incorrectly

storybook-components' Maintenance phase tried to rerun `indusk promises confirm storybook-components` to completion as part of closing, and it refused: `mockups-draw-components-as-stories` had since taken over wider versions of the same promise sentences via `promises change`, and `confirm`'s own suggested remediation would run `promises change` again to hand the sentences back to storybook-components with their old wording — undoing the legitimate ownership transfer.

**Why:** `confirm` assumes the plan asking is still the promise's rightful current owner. It has no notion that a promise it once stated can legitimately move to a newer plan's broader restatement, so its refusal path actively recommends regressing the promise's text. This is a distinct gap from [[promise-statement-edits-go-through-promises-change-not-by-hand]] (which is about bypassing `promises change` entirely) — here the tool itself, used as directed, would make the wrong edit.

**How to apply:** on a Maintenance re-close of an archived plan, before running `indusk promises confirm`, check whether each of the plan's declared promises is still owned by that plan (`owner:` field in `.indusk/promises/<name>.md`) or has since moved to a different plan. If ownership moved, skip confirming that promise from the reopened plan — it was already confirmed at the plan's first close, as storybook-components' retrospective states — and do not follow `confirm`'s suggested `promises change` fix, since it would revert the newer, wider promise text. This is a tooling gap in `confirm` worth fixing in `lib/promises/` itself (recognize promises transferred since the plan's prior close and skip them without erroring), not just a workaround to repeat by hand each time.
