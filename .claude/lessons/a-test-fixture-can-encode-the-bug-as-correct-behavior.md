# A test fixture can encode the bug itself — a fixture that produces the buggy output asserts that output as the correct baseline, and nothing downstream questions it

When a fixture is built by running the real (buggy) code path and capturing its output as the expected baseline, the fixture bakes the bug in as "correct" — every test built against that fixture passes by construction, and no amount of re-reading the test or the code it calls will surface the problem, because both agree with each other. The only way out is reading the fixture's actual content cold, against what the real-world input should produce, independent of what the code currently does.

**Why:** release-records-its-failures (dusk, 2026-10-10, archived at `.indusk/planning/archive/release-records-its-failures/`), audit finding A29. A9's rerun fixture was built by capturing a report where a flaky file was simply missing — so "a file absent from the report means it passed" was encoded as the asserted-correct behavior, and the A9/A10/A28 fixtures all agreed. Three build phases plus a falsification phase read the rerun logic and the fixture together and saw nothing wrong, because fixture and code told the same (wrong) story. The audit — a fresh reader with no stake in the code that produced the fixture — caught it by asking what "passed" actually meant, not by re-running the same tests.

**How to apply:** when a fixture is captured output from the system under test rather than hand-written from the spec, treat it as suspect: have someone (or something) with no authorship stake in the code read the fixture's content against the real-world behavior it's supposed to represent, not against what the code currently emits. This is exactly the kind of gap a fresh-reader audit step is positioned to catch that the builder's own falsification pass, run by the same person who wrote the fixture, is not.
