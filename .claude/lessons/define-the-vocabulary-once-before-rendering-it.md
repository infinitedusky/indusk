# Define the lifecycle vocabulary once and export it before any UI renders it — a view that composes its own lifecycle from parser output drifts silently the first time a stage is added

The admin's phase view had its own heading regex, written before Test Phases existed. When `### Test Phase N` arrived, every impl written after that rendered wrong for a month — test phases invisible, rows attached to the wrong phase — and nothing failed, because the admin was composing "what is a phase" from its own reading of the document rather than from the package that defines it. Two other partial copies existed: the plan parser's private stage order (which skipped `test-plan`) and the retrospective gate's restated ritual words. Three definitions, three drifts, all silent.

admin-ui-phase-progress wrote the lifecycle once (`lib/lifecycle.ts`: positions as nouns, activities as verbs inside `executing`, gate stages, ritual order), made `parsePlan`, the gate and the admin read it, and pinned single-definition. Then — the part that keeps it true — the admin's label maps are declared `satisfies Record<PlanPosition, …>` etc., so a union gaining a member fails the type-check, and a render-parity test renders every member and names the one without a label. The convention: a plan that adds a stage adds its rendering in the same plan, as a Document gate item.

Rule: when a UI shows the state of a system, the states come from an exported definition the system itself reads, and the UI's completeness over that definition is type-checked (`satisfies Record<Union, …>`) and rendered in a parity test. "Composing it in the view" is a fourth definition with no pin. Corollary from the same plan: two spellings for two audiences is fine (logs say `Build Phase 4`, the page says `Phase 4`), but each spelling is defined once and a component never reaches for the other audience's word.
