# "Isolation per source" (or per-backend, per-replica, per-shard) has three distinct failure axes — a bad answer, a malformed configuration, and unbounded time — and a design that isolates only the first still lets the other two take every source down together

During promise-sources (`.indusk/planning/archive/promise-sources/`), the whole point of the plan was that one source's failure (local or production) must never hide or break the other. The build phases (1-4) tested this thoroughly for the "answer" axis — unreachable, watcher-blind — and that axis genuinely worked in isolation. Falsification (Build Phase 5) found the design was not actually isolated on two other axes, both only discovered by constructing realistic bad inputs the happy-path tests never produced:

- **Configuration (A8):** a malformed `promises.jaeger` value in config — a bare string (`"https://..."`) where an object was expected — threw a `TypeError` from deep inside URL-parsing code (`url.trim()`) before the per-source isolation logic ever ran. This exception propagated out and killed the read for *every* source, including `local`, which had nothing to do with the malformed config.
- **Time (A9):** the probe's outbound send ignored the caller's own timeout budget. A host that accepts a TCP connection and then never answers (a realistic cloud-networking failure mode, not a crafted edge case) held a 2-second admin read open for 7 seconds — the slow/silent source stalled the whole read even though it never raised an exception.

Cleanup then found a third, related defect: two separate call sites (`status`'s failure text and `watch`'s hint) each independently re-read the raw config to build human-readable advice, and both printed the identical wrong message ("Check undefined is up") for the same malformed-config case — each copy looked correct in isolation, and the duplication was only visible once cleanup put them side by side.

**How to apply:** when designing or testing any mechanism meant to isolate failures across multiple sources/backends/replicas/shards, explicitly enumerate and test all three axes before calling it isolated: (1) a source answering with a clear error, (2) a source whose own configuration is malformed in a way that could throw before the isolation boundary is reached, and (3) a source that accepts input but never responds, within or past the caller's intended timeout. A test suite built only from well-formed config and servers that cleanly answer-or-refuse will not find axes 2 or 3 — they require deliberately constructing a malformed config value and a connection that hangs. Write test-plan rows for all three axes up front rather than discovering the gap in falsification.
