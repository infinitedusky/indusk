# A "skip if already covered" key must prove it covers something — a misdeclared scope gives no key, never an empty one

If a cache/skip key is computed from a declared file scope (a glob, a `covers` list, a path set), and that scope can be misdeclared (typo, empty list, moved file) so it matches zero files, the computed key must detect "nothing matched" and refuse to produce a key — not silently hash an empty set. An empty-set hash is a constant, so every run produces the same key and the skip logic treats every run as "already covered by a previous green run," permanently disabling the check it exists to perform.

**Why:** release-checks-run-once (dusk, 2026-10-08, archived at `.indusk/planning/archive/release-checks-run-once/`) built `indusk checks slow --unless-covered`, keying a skip decision on the content hash of files a project declares under `workflow.steps.release.covers`. Falsification (Build Phase 4, row A11 in that plan's impl.md) found that a typo'd `covers` entry matched no tracked file and still produced a key — meaning every subsequent run, regardless of actual changes, was treated as covered. The fix (`whyNoKey` in `apps/indusk-mcp/src/lib/checks/key.ts`) makes the key function return null and name which entry/empty-list/dirty-file caused it whenever the declared scope resolves to nothing, so the skip logic always falls through to actually running the check.

**How to apply:** when building any "skip because a prior green run already covers this" mechanism keyed on a declared file scope, add an explicit test for the zero-files case before trusting the hash — assert that an empty or non-matching scope produces no key (and ideally surfaces why), not a hash that happens to be stable.
