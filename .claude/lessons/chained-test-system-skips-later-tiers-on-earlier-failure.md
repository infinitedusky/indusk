# `pnpm test:system`'s per-package tiers must not be `&&`-chained — an earlier failure must not skip a later tier

The root `test:system` script ran `pnpm --filter @infinitedusky/indusk-mcp test:system && pnpm --filter indusk-admin test:system`. When indusk-mcp's tier failed (even on something unrelated, like a leaked daemon the guard named, with every test green), the `&&` skipped indusk-admin's tier entirely — so indusk-admin's own system-tier regressions surfaced only when `pnpm release` ran it, not at landing. This is the same root cause as `a-cleanup-guard-chained-with-and-is-skipped-on-the-failure-it-exists-for` (an `&&` chain protects exactly the run where something already went wrong) but a different subject: that lesson is about a leftover-resource guard, this is about a multi-package test tier sequence.

Concretely: 1.66.0 was cut once (commit d9fa2e33), then the admin's scorecards page was found reading from the old `.indusk/eval/` path (a regression from the bookkeeping-lives-where-it-is-read plan) only at release time, because the `&&` chain had hidden it through every earlier `pnpm test:system` run. Fixed in d182205c by running each package's tier unconditionally (`sh -c '...; mcp=$?; ...; admin=$?; [ $mcp -eq 0 ] && [ $admin -eq 0 ]'`) and adding a pinned test (`test-daemons-guard.test.ts`, "every package's system tier runs, whatever the one before it did") asserting the root script's `test:system` does not contain a `&&`-chained `test:system` invocation.

How to apply: any script that runs N independent test tiers across packages (`turbo`, a hand-written `&&` chain, etc.) must run every tier regardless of an earlier one's exit code, and must still exit non-zero if any tier failed. Pin this with a test reading the script string, not just by eyeballing the package.json — the whole point of the bug was that it was invisible until `pnpm release`, the one place all tiers are forced to run.
