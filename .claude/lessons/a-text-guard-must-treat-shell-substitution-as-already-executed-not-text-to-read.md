# A guard that reads a shell command's text for a forbidden pattern must know that `$(...)`, backticks, and `<(...)` execute before the guard ever sees the surrounding arguments

A text-based guard that inspects a shell command string for a forbidden call (e.g. refusing `plans reapprove` appearing anywhere in the command) can be bypassed by wrapping the forbidden call in command or process substitution: `$(plans reapprove ...)`, backtick-quoted `` `plans reapprove ...` ``, or `<(plans reapprove ...)`. The shell runs the substitution and expands it to its output *before* the outer command line is even assembled — so by the time any text-reading guard inspects the line, the forbidden call has already run, and the guard sees only its output text, not the command that produced it.

**Why:** cockpit-redraw (dusk, 2026-10-14, archived at `.indusk/planning/archive/cockpit-redraw/`), Build Phase 4 falsification. A reader guard (`echo`, `cat`-style exemption logic) exempted a segment that actually ran `plans reapprove` inside a `$(...)` substitution, and `reapprovePlan` invoked through an interpreter (not a direct shell command) was unseen entirely. The retrospective's own words: "A text guard's reader exemption must not cover what the shell runs first. `$(…)`, backticks and `<(…)` execute before the reader sees its arguments." Both gaps were fixed in the same falsification phase.

**How to apply:** when writing or auditing a guard that inspects a command string for a forbidden subcommand, explicitly test the three shell substitution forms (`$(...)`, backticks, `<(...)`) as well as invocation through an interpreter (`sh -c`, `node -e`, `python -c`) wrapping the forbidden call — these are exactly the forms that run before any text-level inspection can see them. A guard that only pattern-matches the literal command line, without accounting for what the shell evaluates first, is checking the wrong moment.
