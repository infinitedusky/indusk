# When a schema grows an optional field for a new capability (like a cross-repo split), treat the field's absence as a stated interpretation rule ("written before the split existed") rather than writing a data migration — the rule is testable on day one and nothing existing has to change

Adding a new capability that only some records will have (dawn-workbench-execution: a verify ledger record's `codeSha`, a queued eval's `repo` — both new fields that only exist for records written after a workbench-split feature landed) creates a choice: migrate every existing record to carry the new field with some computed/default value, or state a rule for what an absent field means and let every reader apply that rule.

The rule-not-migration approach was chosen and worked cleanly: a ledger record without `codeSha` is read as "this baseline predates the split" and the code repo bootstraps from its root commit instead; a queued eval without `repo` is attributed by comparing HEAD timestamps across the declared repos, the same fallback that existed before the split. Nothing already on disk needed rewriting, and the rule itself — "absent means predates the feature" — was testable from the very first day the field existed, without needing a corpus of pre-existing records to migrate against.

How to apply: when a new optional field distinguishes "old" from "new" records, resist writing a backfill/migration script by default. First ask whether a stated interpretation rule for the field's absence is sufficient and correct — it usually is when the absence genuinely means "written before this feature existed," and it composes better with the project's existing "archived/historical records are read-only, don't repair them" convention (see the impl-corpus regression-guard pattern: archived history is recorded, not repaired). Only reach for an actual migration when the absent-field meaning is ambiguous or the fallback behavior would be wrong for some existing records.
