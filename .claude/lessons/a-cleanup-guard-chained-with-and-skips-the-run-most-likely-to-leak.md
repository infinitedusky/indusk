# A leftover-resource guard chained after tests with && never runs on the failing/crashed test run — and one checked at a single instant mistakes shutdown-in-progress for a leak

During test-daemons-never-leak (dusk), Build Phase 1's first attempt at an end-of-suite leak guard chained it after the test command with `&&`. That operator short-circuits on a non-zero exit — so the guard was skipped on exactly the runs most likely to have left something behind (a crashed or failing test is the scenario a leak guard exists for). Falsification caught this. A second, related failure mode: a guard that reads the process list at one instant can catch a daemon that is still in its normal shutdown sequence and report it as a leak — a false positive that, left unfixed, trains people to ignore or disable the guard.

**Why:** `&&` means "run the next command only if this one succeeded" — the opposite of what a safety-net guard needs ("run regardless, so I catch the cases where things went wrong"). And a resource that takes any nonzero time to tear down will look "still there" to a check with no grace period, indistinguishable from an actual leak.

**How to apply:** chain a cleanup/leak guard with `;` or a shell construct that runs unconditionally (or run it in a separate step/job that always executes), never `&&`, when its entire purpose is to catch the failure case. Give the guard a grace period (poll-with-timeout, not a single instant check) before reporting a resource as leaked, or it cries wolf on normal shutdown timing and gets switched off. See `.indusk/planning/test-daemons-never-leak/brief.md`, `.../test-plan.md`, and `with-daemon-guard.js`.
