# A mockup is approved and the record committed in the checkout it is worked in — on the plan's branch, never through main — so the approval merges with the mockups it judges

**The rule.** `approve` reads the mockup and foundation from, and commits `approved.json` in, the checkout it is given — the plan's worktree on its branch, or the project's own checkout — through `commitNote` with `anyBranch`. The cockpit's Looks page reads a chosen checkout (`?checkout=<plan>`, defaulting to the one worktree that holds mockups `main` lacks) and Approve sends it; the route resolves a plan name from the plan-worktree record, never a path, and refuses a plan with no such worktree (404). Tooling never reaches around a plan's branch to commit its look on `main`.

**Why.** Sandy corrected Build Phase 4's design on 2026-10-11 (recorded in ui-promises' impl Build Phase 5, 'reverses Build Phase 4's approve against main'). Approving against `main` made a mockup drawn in a plan worktree 'no mockup' to the writer, so a person could not approve what they were looking at, and put a plan's approval on the trunk before its mockups merged. An approval is bound to the mockup's content hash, so it belongs in the commit history that carries that mockup and lands with it.

**How to apply.** A new tool that records a person's decision about a plan's artifact commits it where the artifact is, resolved from the plan-worktree record (never from a client-supplied path). Do not read 'bookkeeping notes are committed on main' (`/decisions/bookkeeping-lives-where-it-is-read`) as covering a record bound to a content hash of a file that has not merged. Docs and context entries written before the reversal still say `main` — the admin CLAUDE.md entry, the admin overview page's Approve paragraph and Build Phase 4's forward intelligence — and are corrected, not re-copied.

**Open at the time of writing.** The dashboard's look standing and `indusk looks check` still read the project's own checkout, so a plan's look is held on the dashboard only once merged.
