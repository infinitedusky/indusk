# Checking off a Phase Verification item does not update the Test Trajectory table's State column — do both in the same edit, or the table silently lags the checklist

An impl's Test Trajectory table (the `| ID | Asserts | Test | Writable at | Passes at | State |` table) and its per-phase Verification checklist items are two separate artifacts that both claim to say whether a trajectory row is done. Checking off `- [x] A4, A6, A7, A10 pass` in a phase's Verification block does nothing to the table's State column — that's a separate edit.

**Correction (2026-08-09, commit ed5a702e): this IS structurally enforced, just not at the phase where the gap is introduced.** `check-gates` (pinned by `state-ops.test.ts` T17/T18) blocks a *later* phase's edit if an earlier phase's trajectory rows aren't in a terminal state — the enforcement fires at the next phase boundary, not the moment the stale Verification checkbox is checked. That's why the gap can survive two full commits before anyone notices: nothing stops you from closing Phase 3 with a stale table, but the very next attempt to touch Phase 4 gets blocked with a message naming exactly what's missing. Trust the hook to eventually catch it — but don't rely on that delay; the sequence below still cost two wasted commits before the block fired.

Seen twice in a row in dusk's lifecycle-rebalance plan before the hook caught it:
- Commit 241ad9fa checked off Phase 3's implementation items and shipped code making A4/A6/A7/A10 genuinely pass, but never touched the trajectory table — State stayed `written` for all four.
- Commit b3c98eec, titled "Phase 3 green — all 12 trajectory rows terminal" and checking off the Phase 3 Verification item itself (`A4, A6, A7, A10 pass`), *still* didn't touch the table. Independently verified: `pnpm vitest run` genuinely showed 137/138 files passing (only a known pre-existing daemon-identity flake), so the code claim was true — but `grep -E "^\| A[0-9]+ " impl.md` after this commit still shows A4/A6/A7/A10 at State `written`, contradicting the commit's own headline claim.
- Commit ed5a702e: the very next edit (a Phase 4 checklist item) was rejected by `check-gates` for exactly this reason, and the commit fixed the root cause — flipping all four State cells to `passing` — rather than working around the block.

The gap is invisible from the diff of either of the first two commits alone — you have to grep the live trajectory table separately from reading the commit message to catch it before the hook does. When a commit message asserts "all N trajectory rows terminal" or similarly declares rows done, that claim is a promise about the Test Trajectory table specifically, not about the checklist. Verify it by grepping the table's State column for the named rows before trusting the sentence, and when authoring such a commit, edit both the checklist checkbox and the table's State cell for every row it names, in the same commit — don't wait for check-gates to force it one phase later.
