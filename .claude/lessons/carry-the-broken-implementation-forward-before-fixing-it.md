# When consolidating or replacing an implementation suspected of being wrong, carry the broken version into the new test first, so the test goes genuinely red against the actual defect

When a cleanup or refactor replaces an implementation you already suspect is flawed, there's a temptation to just write the correct version directly — you know roughly what's wrong, so why author the broken one first? Because writing the fix straight away produces a green test immediately, and a test that has never been red against the real defect has not actually described that defect. The next person reading the test sees a passing assertion with no record of what failure it was written to catch.

**What happened:** `jj-residue-rip-out`'s cleanup phase needed to consolidate a fragile PATH-stripping helper (`pathWithoutJj`). Rather than writing the corrected version directly, the plan first extracted the **existing, broken** algorithm into the new test location and ran the new test against it — and that test went red, but not for the predicted reason. The predicted defect was narrower (failing when git and jj share a directory); the actual defect was worse: the helper located jj via a bare `which` spawn, and when that spawn failed under a narrowed `PATH`, it silently fell back to returning `PATH` unchanged — the exact failure later described in [[precondition-helpers-must-throw-not-degrade]]. Writing the correct implementation straight away would have produced a green test on the first try and left this real failure mode completely undescribed by any test.

**Why it matters:** a red test authored against the broken implementation is direct evidence that the test can distinguish broken from fixed. A test authored only against the already-correct implementation has never demonstrated that capability — it's plausible, not proven, that it would have caught the original bug.

**The rule:** when a cleanup or refactor plan replaces an implementation suspected of being wrong, extract or carry forward the *broken* version first, write the test against it, and confirm the test goes red for the actual reason (not just any reason) before writing the fix. This costs one extra step and often surfaces that the real defect is different from — usually worse than — what was predicted.

See `.indusk/planning/jj-residue-rip-out/` (commit `69b861aa`, "one implementation... and it is the correct one") for the full incident.
