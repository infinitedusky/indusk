# When evaluating a specific commit, uncommitted changes in the shared working tree silently test the WRONG code — isolate with a disposable worktree before running tests against a historical commit

While evaluating commit 1914466b (planner-promises), running `pnpm exec vitest run src/__tests__/promises-withdraw.test.ts` directly in the shared worktree showed all 9 tests passing — seemingly contradicting the commit's own claim of being "written red... RED: promises withdraw is not a command." The shared worktree had substantial uncommitted modifications on top of that commit (from a later, unreviewed session that had already implemented the withdraw command), so the test run silently exercised that newer, uncommitted code instead of the code that existed at the commit being evaluated. `git status --short` revealed the contamination; re-running the exact test in a disposable `git worktree add` checkout of the commit, with a fresh `tsc` build, correctly reproduced 8/8 failures exactly as the commit claimed.

**How to apply:** before running `pnpm test`/`vitest` to verify a claim about a *specific historical commit* (not the current HEAD), check `git status --short` for uncommitted changes in the shared worktree first. If any exist, don't trust a green or red result from testing in place — create an isolated `git worktree add /tmp/<name> <sha>`, symlink `node_modules`, build, and test there instead, then remove the worktree afterward (`git worktree remove --force`). This applies generally whenever "run the tests to check an eval/historical claim" and "the current directory has pending edits" are both true.
