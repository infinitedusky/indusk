# Before a live check in a real project, name its installed InDusk version — the admin drives whatever skills that project actually has, silently

workbench-plan-authoring's live check ran against numero, a real project on branch `staging` in an untrusted workbench, running InDusk 1.56.0 — several releases behind, from before planner-promises shipped. Its planner wrote no promises, because 1.56.0's planner skill doesn't know to ask for them. Nothing failed loudly: the admin simply drove the project with whatever skills and hooks that project's own `.claude/skills/` and `.claude/hooks/` actually contained, which silently diverged from what the live check's author assumed (the latest skills, matching the plan being tested).

Why it matters: a live check's entire point is to run the real system in real conditions — but "real conditions" includes whatever version of the tooling that project happens to have installed, which can be arbitrarily stale relative to the plan under test. A live check against an old installation doesn't fail cleanly; it quietly exercises old behavior and reports success or failure against the wrong baseline, the same shape of problem as `run-the-product-in-a-project-it-was-not-built-in` (a live check also needs to know *which* version of the product it's running).

What to do: before running a live check against any real, pre-existing project (not a scratch fixture), check and name its installed InDusk version (`indusk --version` or read its `.claude/skills/` for the relevant skill's content) as part of the check's setup, and update it first if the plan under test depends on skills/hooks that version doesn't have. Don't assume a real project happens to be current just because it's real. See `.indusk/planning/archive/workbench-plan-authoring/retrospective.md`.
