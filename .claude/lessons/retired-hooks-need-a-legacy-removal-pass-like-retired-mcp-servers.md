# Deleting a hook from the package source doesn't remove it from consumers — orphaned hooks keep firing forever

When a hook is retired from `apps/indusk-mcp/hooks/` (the package source), every project that ever ran `init`/`update` while that hook still existed keeps its installed copy in `.claude/hooks/` AND its registration in `.claude/settings.json` — nothing in `init`/`update` removes a hook the package has since dropped. The result: unmaintained, orphaned code keeps firing on every matching tool call, indefinitely, in every consumer that installed it before the deletion.

**The concrete case:** `check-plan-order.js` was dropped from the package at some point (context-beam cleanup era), but dusk's own `.claude/hooks/check-plan-order.js` still exists and is still registered in `.claude/settings.json` — found while researching dawn-hook-parity's hook inventory, where the plan initially assumed the file was simply gone (see the ground-truth-verification lesson this same finding forced). It fires on every matching tool call today, running code nobody maintains or tests anymore.

**Root cause:** `init`/`update` install hooks via `globSync` over the package's `hooks/` directory (additive), but there is no corresponding removal step for hooks the package has since dropped. The project already has exactly this pattern solved for a different retiring-artifact class: `LEGACY_MCP_SERVERS` in `apps/indusk-mcp/src/lib/mcp-migration.ts`, called by both `init` and `update`, explicitly strips retired MCP server registrations. No equivalent `LEGACY_HOOKS` list or removal pass exists for hooks.

**The fix:** build a `LEGACY_HOOKS` removal pass mirroring `mcp-migration.ts` — a list of hook filenames the package has retired, called by both `init` and `update`, that deletes the installed file AND strips its `settings.json` registration. Until this exists, any hook ever shipped and later retired remains permanently live in every project that installed it before the retirement, with no mechanism to ever clean it up short of manual intervention.

**Why it generalizes:** any system that installs files/registrations additively via a package-sync step needs an equally deliberate removal step for the artifact's full lifecycle (add → retire), or removed-from-source quietly becomes "removed from new installs only" — a much weaker guarantee than the deletion commit's message implies.
