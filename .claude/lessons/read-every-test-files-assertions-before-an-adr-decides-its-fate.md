# An ADR that decides a test file's fate ("delete it", "keep one as a contract test") from its file name or its general purpose, without reading every individual assertion inside it, will get the fate wrong when the file also covers things its stated purpose doesn't mention

In test-kinds (`.indusk/planning/archive/test-kinds/`), the accepted ADR said "delete the eight [admin HTTP promise] files, keep one trimmed contract test" — a decision made from the list of file names and their general purpose (checking what a chip or cell shows). When Build Phase 2 actually read every assertion inside each of the eight files before deleting them, it found that six of the eight also asserted page-level behavior — incident bands, the source switch in the URL, the sidebar's red mark, the watcher-blind banner, live refresh, the monitor segment — that no unit test (written in Build Phase 1 to replace the files' "chip/cell rule" assertions) actually reached. The impl's own stated rule, "delete a file only when every assertion it made is covered," caught this and correctly moved those six files to the system tier instead of deleting them, rather than silently losing their coverage.

The root cause: the ADR's decision was made by reasoning about what a file is *for*, not by reading what it actually *asserts*. A test file's name and its primary purpose don't guarantee it asserts only that purpose — files accumulate secondary assertions over time (here, UI/page-rendering checks that got bundled into the same file as backend-rule checks because they shared test setup).

**How to apply:** when a design decision (an ADR, a brief, or an impl) proposes deleting, replacing, or substantially trimming an existing test file based on a plan to replace "what it checks" with something else, read every individual assertion/expectation inside that file before finalizing the decision — not just its name, its describe-block titles, or a summary of its general purpose. A file can and often does assert more than its stated purpose suggests. Write the actual deletion/replacement decision as a checklist item with an explicit gate ("delete only once every assertion in this file is covered by [specific replacement]"), verified file by file, rather than as a blanket decision made at design time from a list of names.
