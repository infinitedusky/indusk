# A plan that changes a system-wide invariant (such as phases running one at a time) must list the existing prompts, hooks and refusals that assume the old invariant, not only the new modules it adds

Why: run-the-graph changed "phases run one at a time" to "phases run side by side" and its first impl listed only new modules. The cold read of the slice then found existing code built on the old invariant: the work prompt (tells a session to work every open phase in order), `check-gates.js` (refuses ticks while an earlier phase in document order has open gate items), `next-step.ts` (stops for a judgement only on the first open phase), `resumeAfterQuestion` (refuses with "already building"), and the merge check against the red-by-design rows a test phase writes. Three of these would have stopped the plan working at all. No planning step asked what already assumes the old invariant.

What to do: when a plan changes an invariant the system has always had (one at a time, one per plan, ordered by document position, first open item), add an impl section that greps for every reader of the old unit (prompts, hooks, parsers, refusals, admin routes) and gives each a task or a stated reason it is unaffected. Do this before the first cold read; the planner should ask "what in the existing code relies on this staying true?" for each invariant the brief's promises change.
