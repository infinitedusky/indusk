# When a recurring problem tempts you toward a new always-open primitive, prefer making the existing thing reopenable on a specific trigger — closed must stay the resting state

A recurring pattern — the same concern needing attention across multiple closed units of work — looks like it wants a new durable, never-archived primitive (a "subsystem," a persistent tracking object, anything that accumulates state forever). Resist that by default. The alternative is to make the existing unit **reopenable on a specific, evidenced trigger**, so the resting state (closed/archived) stays the default and the active surface doesn't grow without bound.

**Why:** the plan-lifecycle decision (2026-08-11, `.indusk/planning/midnight/brief.md` Amendment + `apps/docs/src/guide/plan-lifecycle.md`) diagnosed a real problem — four archived plans (`bulletproof-state` × 4) for one concern, because InDusk's plan lifecycle was linear and closing meant closing. The `midnight` brief's original fix was a new `subsystem` primitive: durable, append-only, never archived. It was rejected in favor of adding one state (`monitor`) and one edge (`reopen`) to the existing plan lifecycle, specifically because a durable primitive is unbounded by construction — plans are already "52 and counting," and `indusk-makeover` built a 60KB budget and a decay layer specifically to fight unbounded active surface. A `subsystem` would have reintroduced exactly what the decay layer exists to prevent.

**The general shape:** don't invent a new noun that never closes just because the current unit closes too eagerly. Instead, ask what specific, nameable trigger should reopen the existing unit — and require that trigger to be evidence (a violation, a failure, a name), not a prediction ("this might need revisiting"). The lesson's own reversal condition is the model: build the durable primitive only if the evidence contradicts the assumption twice — e.g., an expectation that genuinely belongs to no plan, or is created by one plan and violated by another's code. Prediction doesn't justify the unbounded primitive; repeated evidence does.

**How to apply:** when a plan/ADR is about to propose a new always-open, never-closed structure to solve "this keeps coming back," check whether "make the existing thing reopenable on a named trigger, closed-by-default" solves it instead — and if you reject that in favor of the durable primitive, write down what evidence would prove you wrong.
