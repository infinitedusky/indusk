# A sudden burst of unrelated test failures (dozens, same app) is more likely a concurrent process holding a shared lock than a real regression — look for the other process before re-running

The eval agent, grading a branch's commits, runs that branch's test suite in the same worktree the branch's own developer may still be using. In `test-daemons-never-leak`, this produced 38-39 false failures in the admin app's HTTP tests — the evaluator's `next dev` process held `.next/`'s build lock while a person's concurrent `pnpm test` ran in the same worktree. The same suite passed 343/343 run alone. The failure signature (a large, suspiciously round number of failures, all in one app, no clear logical connection between them) is itself the diagnostic: a real regression from a code change usually fails a coherent subset of tests tied to what changed, not an undifferentiated mass across one app's entire suite.

**How to apply:** when a test run produces a large burst of failures that don't obviously relate to the diff being evaluated, check for another process in the same worktree before concluding the branch is broken or re-running blindly (`ps` for another `next dev`/test runner, check for a `.next/` or similar build-lock directory, check if another agent/session is registered against the same worktree via `indusk agent list`). This needs a structural fix of its own — evaluate against a snapshot/isolated worktree, or make concurrent runs visible to each other — noted as unresolved in `test-daemons-never-leak`'s retrospective.
