# After committing, check what actually landed with `git show --stat` — don't trust that the paths you passed to `git add` are the paths that got committed

During admin-plan-type, a commit was given three file paths to stage and commit, but the resulting commit recorded only two — for a reason that was never established (a typo, a path that didn't match, a pre-commit hook silently dropping one, or the file already being clean). Nobody noticed until later because the commit command's own success (`git commit` exiting 0) was taken as proof the intended contents landed.

**Rule:** after any commit — especially one built from multiple explicit paths rather than `git add -A` — run `git show --stat` (or `git show <sha> --stat`) and check the file list against what was intended, before moving on. `git commit` exiting 0 only means *some* commit was created; it says nothing about whether every path you named is in it. This is the same discipline as checking a formatter's actual diff rather than trusting its exit code (see [[scope-biome-write-to-changed-files-not-whole-directories]] for the sibling case where a formatter ran successfully but touched the wrong files) — a clean exit from a mutating command is not evidence the mutation matched intent.
