# A promise about the recorder/evaluator itself can be unprovable in the project that declares it, because marks are filtered to the reading project's own id

incident-recording's A7 ("`promises status` reads the recorder's marks like any promise's") blocked during Build Phase 6 on a real architectural gap, not a missing credential. `readSource` in apps/indusk-mcp/src/lib/promises/sources.ts passes `project: markProjectId(root)` into every mark query — every read is server-side filtered to the reading checkout's own project id (`config.ts`'s `markProjectId`, the configured `graphiti.groupId` or else the main checkout's folder name). This is deliberate and correct: day-monitor A28 chose it specifically so a worktree's marks aren't dropped from its own trunk's view.

But it has a consequence nobody had traced through for a *self-referential* promise: `a-production-break-is-recorded-unasked` is proven by the admin's recorder loop, which only runs for a project that names a production source (`promises.jaeger`). dusk itself names none — the loop literally never runs for dusk — so the only marks that promise ever gets come from whatever *other* project the admin happens to be watching (here, a scratch copy of the seat-holds example). Those marks carry that project's id, not dusk's, so `promises status` run inside dusk filters them out and reports "not seen" even while the marks genuinely exist in the same Jaeger, seven of them, visibly.

The evaluator's `every-commit-evaluated` promise doesn't have this problem only because the evaluator happens to run *for dusk itself* — the coincidence masked the general issue.

Applies whenever a promise's proof mechanism is a loop/daemon/evaluator that runs against a different project than the one declaring the promise: check whether the reading side's project-scoped filter (or any per-tenant/per-workspace read scope) can ever see marks written under another tenant's id, before writing the trajectory row that assumes `status`/`watch` will "just work." The fix is a design decision, not a bug fix: give the declaring project a production source of its own, re-tag the pass's mark under the promise's owning project instead of the recording project, or rewrite the row to read from wherever the mark actually lands. See `.indusk/planning/incident-recording/impl.md`'s A7 blocker (2026-10-08) and `/decisions/incident-recording`.
