# An accepted ADR decision can be refuted by a test that already exists in the codebase — run the full existing suite early in a build phase, not only at its close, so the refutation surfaces before more code is built on the wrong contract

During promise-sources (`.indusk/planning/archive/promise-sources/`), the accepted ADR's decision D3 stated: "`promises status` exits 2 when *any* source is unreachable or blind." This was a reasonable-sounding design decision, reviewed and accepted before implementation. But an existing test from a different, already-landed plan — `always-on-source.test.ts`'s row A10, asserting that a project naming a production server with no local daemon running exits 0 — went red the moment D3's "any source fails → exit 2" rule was implemented. The existing test was right: "any source" would have made `promises status` exit non-zero on every laptop that doesn't happen to have its local telemetry daemon running, which is an extremely common state and not actually a failure worth a non-zero exit. The design was corrected mid-build: the exit code now follows the alarm source (production when it exists, local otherwise) rather than any source.

**How to apply:** after writing the first chunk of new code in a build phase (not just at the phase's close, and not just the new trajectory rows' own tests), run the full existing test suite for the area being touched. An ADR being "accepted" means the humans involved found it reasonable, not that it has been checked against every behavior the existing code already guarantees — only a running test actually encodes that. The earlier this check happens in a build phase, the less work gets built on top of a contract that is about to be revised. This is a known risk source: brand-new trajectory rows are written to prove the new decision; it's the suite from *before* this plan that proves whether the new decision quietly breaks something already promised.
