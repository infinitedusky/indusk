# A dedup/processed ledger checked by a path-local read cannot see marks made in another worktree of the same repo — resolve to one copy, don't trust the local file

admin-plan-type's eight retrospective highlights (h-20261001-007 through -014) were each processed twice: once by an eval-agent session running on trunk, once by a session running in the plan's own worktree (worktree-per-plan is this project's default). `highlights-processed.jsonl` lives at a path under `.indusk/`, which is per-checkout — each worktree has its own working copy of that file. `highlight_mark_processed`'s duplicate-rejection check reads the local copy, so neither checkout's eval session could see the other's marks, and both materialized lessons for the same underlying findings. Result: 11 lesson files for roughly 6 distinct lessons, several near-duplicate pairs landed in the same commit (see the admin-plan-type retrospective's "Landing" section and `e6872a1e`).

**Rule:** any append-only or dedup-checked ledger that lives under a path git worktrees each get their own copy of (not a shared git-dir file, not something `merge=union` reconciles at commit time) is unsafe to read as ground truth from more than one checkout. Before trusting a local "have I already done X" check, ask whether another live worktree of the same repo could have an independent copy of the same file with different content.

**How to apply:** this project already solved the analogous problem for finding a plan's current working copy — `lib/worktree/plan-worktrees.ts`'s `resolveExecutionRoots`/record-based resolution, instead of assuming the cwd's copy is authoritative. The eval rail's processed-ledger check (and the highlights queue itself) needs the same shape: resolve to one canonical copy (or merge across known worktrees) before checking or writing, rather than trusting whatever `.indusk/highlights-processed.jsonl` happens to contain in the current checkout. As of this lesson, this is an acknowledged, unowned defect — no plan has picked it up yet.
