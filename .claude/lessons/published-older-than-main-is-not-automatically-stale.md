# A published version number older than main's HEAD does not mean the publish is stale — check whether the commits ahead of the release commit are pre-existing unpublished work or new work added after the bump, via git rev-list <release-commit>..HEAD, before concluding anything needs republishing

Seeing that `main` is N commits ahead of the last `chore(release): <version>` commit is not itself evidence the publish is stale or wrong. It only means N commits exist that the published tarball doesn't contain — which is normal and expected between releases. The failure mode is inverting cause and effect: assuming "published version < HEAD" implies "the publish needs to happen again" or "the user's recent publish is already outdated."

Found 2026-09-15: a session concluded a user's just-made publish was stale because main was 27 commits ahead of the release commit — but all 27 of those commits were the session's OWN work, added after the bump, because the version bump had been committed mid-plan (right after a Build Phase merged, triggered by the word "publish" coming up) while the close-out rituals (falsify, cleanup, retrospective) still had four more defects to find. The publish was correct and current at the moment it was made; the work that came after it was the plan continuing, not evidence of staleness.

The fix that makes this checkable rather than inferred: `git rev-list <release-commit>..HEAD` names exactly what's unpublished. Read that list — and whether those commits are new work the current session added, versus genuinely unshipped features — before saying anything about whether a publish is current. Never infer staleness from the version number alone.

Related, enforced by mechanism: `enabling-extension-ships-manifest-not-files-it-points-at`'s sibling rule for this exact incident is in CLAUDE.md ("the version bump is the LAST commit of a plan... if a ritual finds work after a bump, revert the bump") and `apps/indusk-mcp/scripts/release-guard.sh`, which refuses `pnpm release` unless HEAD is exactly the release commit. See `.indusk/planning/master.md`'s small-queue entry proposing `check_health` surface this three-way delta (installed/published/working-tree) automatically.
