# A test's launch/environment flags can quietly narrow what it proves to less than its name claims — a visible side effect, not the test, may be the only clue

A test can pass indefinitely while asserting something materially narrower than its name or intent, when a launch flag or environment setting silently excludes the real code path from ever running. The test is green, the assertion it does make is true, and nobody notices the gap because nothing fails — the only signal is an incidental, easy-to-dismiss side effect visible to a human who happens to be watching.

**Why:** system-tests-catch-up (dusk, 2026-10-09, archived at `.indusk/planning/archive/system-tests-catch-up/`), vscode-extension's install-contract test (A16/A5). The test's intent was "the installed extension activates." It ran VS Code with `--disable-extensions` and loaded the extension's folder directly in development mode — so the actual install-and-activate path was never exercised; the test proved only that the extension's code didn't crash when force-loaded. Sandy noticed every system-tier run opened a visible VS Code window announcing all extensions were disabled, and asked whether the test tested what it claimed. It did not. The fix added a real probe-extension fixture so the installed path is genuinely exercised (A5).

**How to apply:** when a test's launch command carries flags like `--disable-extensions`, `--no-sandbox`, mock/stub env vars, or a "development mode" load instead of the real deploy/install path, explicitly check whether any of those flags exclude the exact behavior the test's name claims to prove. A side effect visible only incidentally (a window, a log line, a warning) during a routine run is worth investigating, not dismissing — it may be the only signal that a test's assertion is narrower than advertised.
