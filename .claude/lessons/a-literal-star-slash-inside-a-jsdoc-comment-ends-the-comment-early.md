# Writing a literal `*/` sequence inside a `/** ... */` docblock (even inside backticks, e.g. documenting a glob pattern like `/*/`) closes the comment early and breaks the parser — JS/TS comments don't nest and don't respect markdown code-span escaping

A JSDoc comment documenting ignore/glob patterns that happen to contain `*/` (e.g. explaining a deny-by-default rule written as `/*/`  in a .gitignore) will silently truncate the comment at that `*/`, leaving the rest of the docblock and everything after it as loose code — the parser sees an "unterminated string" or similar cascading syntax error, often reported far from the real cause. Backticks around the pattern (intended as markdown code-span styling) do nothing to protect it: JS block comments have no escaping mechanism and don't know about markdown.

Found in `apps/indusk-mcp/src/__tests__/worktree-config-schema-versioned.test.ts` (worktree-config-schema-pointer, Phase 4, uncommitted at the time): a docblock explaining that a fix must not append `/*/` to a declared workbench's ignore file wrote that literal sequence inside a `/** ... */` comment, breaking oxc/Vite's transform with "Unterminated string" pointing at a much later line.

**How to apply:** when documenting a glob/deny pattern that ends in `*/` inside a `/** */` comment, break the sequence — insert a space, zero-width marker, or escape like `*\/` or `` * / `` — or move the pattern to a `//` line comment instead. Grep for `\*/` appearing mid-comment (not at the comment's own close) as a fast check when a file fails to parse with no other obvious cause.
