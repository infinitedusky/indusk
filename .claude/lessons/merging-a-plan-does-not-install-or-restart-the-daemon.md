# Merging a plan's branch lands the code on trunk; it does not by itself run pnpm install:local or restart a running daemon

`daemon-found-not-guessed` merged to main, and its retrospective's own closing addendum admits: "Installed with `pnpm install:local` the same day (the land had not run it; trunk's build lacked the plan's code until then); this machine's daemon restarted from trunk's binaries at 17:50Z." The merge commit alone did not install the new build into this machine's global `indusk`, and did not restart the already-running telemetry daemon onto the new port block — both had to be done as explicit, separate follow-up actions.

This sharpens, rather than duplicates, the existing lessons `dusk-installs-its-own-build-not-published-per-plan` (which states landing links the checkout, no npm publish needed) and `unchanged-indusk-version-proves-nothing-about-install` (which says the version string doesn't prove an install happened). Neither one said the merge itself can leave the install step undone. The gap also explains a related incident this session: a `current.md` entry (`34b7e3cd3`) stated a daemon port change as already-true operational fact about 17 hours before the plan had even landed — i.e. premature in the other direction. Together: a claim that infrastructure changed is only as good as confirming (a) the plan actually landed (check the archive, not just the branch), and (b) `pnpm install:local` (or the daemon restart) actually ran after that landing — neither follows automatically from the other.

**Why:** the merge-and-delete branch workflow only moves code to trunk; InDusk's own "landing installs the build" convention is a *further*, separate step a person or agent must still trigger, and a long-running daemon process doesn't pick up new binaries just because trunk changed.

**How to apply:** after merging a plan that changes a long-running local process (the telemetry daemon, the admin's `indusk ui` daemon, any machine-global binary), don't assume the running instance reflects the merge. Check whether `pnpm install:local` ran and whether the process was restarted, before writing or trusting any current.md claim that the new behavior is live.
