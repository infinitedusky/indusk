# A single-definition pin that scans the whole tree for a string/pattern (not a module import) is never selected by per-phase `vitest related <changed files>` — it only fires at landing

`vitest related <changed files>` selects tests by import graph: it runs a test only if that test (or something it imports) depends on a changed file. A single-definition guard that instead scans the whole source tree for a string literal, a regex pattern, or a shell-command spelling (e.g. "no file outside lib/git.ts may call `git rev-parse HEAD` directly") has no import relationship to the files it's checking — it's a grep, not a dependency. So a phase that introduces exactly the violation the pin exists to catch never triggers it; only the whole suite (run at landing) does, because `vitest related` can't see the tie.

**Why:** two plans in a row hit this independently. display-names (dusk, 2026-10-10, archived at `.indusk/planning/archive/display-names/`), Build Phase 5: `display.ts` spelled `"ADR"` inline, which `lifecycle-single-definition.test.ts` A26 forbids outside `workflow-types.ts` — caught only by the whole suite at landing, not by any phase's own verification. release-records-its-failures (dusk, 2026-10-10, archived at `.indusk/planning/archive/release-records-its-failures/`), Build Phase 1: `headCommit` spelled `rev-parse HEAD` itself, forbidden by `head-sha-single-definition.test.ts` A19 outside `lib/git.ts` — same story, same tier gap.

**How to apply:** a phase that introduces a new string literal, a shell command, or any hand-spelled value that duplicates a primitive guarded by a single-definition pin should explicitly run that pin's test file (`src/__tests__/*single-definition*.test.ts` or equivalent), not rely on `vitest related` to pick it up — it won't. This is a candidate for the work skill's per-phase verification step: when a phase's diff touches a file with a known single-definition guard elsewhere in the tree, name that guard's test explicitly rather than trusting the related-file selector.
