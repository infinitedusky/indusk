# A test tier that runs at no scheduled moment (not landing, not phase close, not release) goes stale silently until something else finally runs it

If a test tier's trigger moment gets removed or reassigned (e.g. moved from "every phase close" to "after release" as part of a scheduling fix) without a replacement moment actually wired in before the old one is gone, the tier stops running entirely — not slower, not deferred, just silent. The first thing that finally runs it discovers everything that drifted since the gap opened, all at once, looking like a sudden pile of failures rather than what it is: accumulated staleness with no error at any point along the way.

**Why:** system-tests-catch-up (dusk, 2026-10-09, archived at `.indusk/planning/archive/system-tests-catch-up/`). From 2026-10-08 the system tier ran at neither landing nor phase close (a gap opened by the release-checks-run-once/workflow.steps scheduling change). The first run after two unrelated deliberate behavior changes was a release, which stopped on three tests that had gone stale — none a product bug, each asserting behavior a deliberate change had already replaced. The retrospective's own words: "A tier that runs at nobody's moment falls behind silently."

**How to apply:** whenever a scheduling change removes a test tier's trigger from one lifecycle point (landing, phase close) with the intent of adding it at another (release, background), verify the new trigger is actually wired and running before treating the old one as removed — don't let a tier go from "runs somewhere" to "runs nowhere" even briefly. If a long-silent gap is suspected, check when a given tier last actually ran, not just whether a step that's supposed to trigger it exists in config.
