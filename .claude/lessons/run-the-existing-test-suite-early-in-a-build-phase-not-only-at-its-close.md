# An ADR decision accepted on paper can be refuted by a single existing test on first run — run the full existing suite early in a build phase that changes shared behavior, not only as its closing verification step

promise-sources' ADR (`.indusk/planning/archive/promise-sources/adr.md`, decision D3) specified that `promises status` exits 2 when *any* source fails. This was accepted design, written and reviewed before any code changed. On the very first run of the existing suite after implementing it, `always-on-source.test.ts`'s row A10 — an existing, already-passing test asserting that a project naming a production server with no local daemon running exits 0 — went red. The "any source fails → exit 2" rule, applied literally, would have made every `status` run fail on any laptop without a telemetry daemon currently running, which is an extremely common state and clearly not the intended behavior. The ADR's own author had not noticed this consequence when writing D3; an existing regression test caught what design review did not. The fix: the exit code now follows only the "alarm source" (production when one exists, local otherwise), not the worst of all sources.

**How to apply:** when a build phase changes behavior that existing tests already cover — especially cross-cutting behavior like exit codes, top-level API shapes, or defaults — run the full existing test suite (or at least the directly-adjacent suites) as an early step within the build phase, not only as its closing Verification gate. A design decision that looks correct in an ADR's prose can be mechanically refuted by a single test the design didn't account for, and catching that on the first run (rather than after building out several more dependent pieces on the wrong contract) is cheaper to fix. This generalizes the project's existing Test Trajectory discipline: an existing passing row is itself a live check on any new design decision that touches its surface area.
