# A refusal that holds only because of an unrelated environmental fact is not a guarantee — check what protects it before changing that fact

A safety check can be correct today for the wrong reason: not because it explicitly verifies its precondition, but because some other, unrelated fact about the environment happens to make the dangerous case unreachable. That kind of refusal is fragile in a specific way — it doesn't erode gradually, it disappears the instant the unrelated fact changes, and nothing about the refusal's own code will tell you that's about to happen.

**What happened:** `dusk`'s cleanup and verify libraries refuse to run several checks (phantom-work detection, `assertGitRepo`-gated verification) against a workbench root, and the code comment for that refusal even names the reason: "a workbench root is deliberately not a git repo." The refusal is correct, but *why* it fires is an accident of the workbench root's current shape, not an explicit check for the actual danger (a diff that structurally cannot contain the code being verified). The `versioned-workbench` plan's ADR proposed making the workbench root a git repo — and the moment that lands, the refusal stops firing, not because anyone touched the refusal's code, but because the fact it silently depended on became false. Verify would then run against a workbench repo whose diff can never contain the wrapped repo's code (the code lives across a symlink), and phantom detection — which fires when nothing outside `impl.md` changed — would flag every honestly-completed item as phantom, because in a workbench repo nothing outside `.indusk/` and `.claude/` ever changes when code is written. A precondition that held by coincidence became a confident wrong answer with zero code change to the check itself.

**Why it matters:** an explicit check that stops working fails loudly — the check's own logic breaks, and that's discoverable by reading the check. A check that stops working because an *unrelated* fact changed underneath it fails silently everywhere at once, on a schedule set by a completely different piece of work that has no reason to know the check exists. The failure mode is worse than a bug: it's a false positive storm (every real pass reported as a failure) or a false negative storm (every real failure reported as a pass), and "a detector that cries wolf gets disabled, taking its real catches with it" — so the blast radius outlives the specific bug.

**The rule:** when a safety check, refusal, or gate is correct today, ask explicitly *what makes it correct* — is it checking the actual danger, or is it riding on a fact about the environment that happens to be true right now? If it's the latter, before any plan changes that fact, the check must be rewritten to test the real danger directly (here: "can this diff even contain the code in question," not "is this directory a git repo"). Encode the new check in the same commit or phase that changes the fact the old refusal depended on — don't let the gap between "fact changes" and "check catches up" become a window where every downstream user trusts a refusal that's already gone quiet.

See `.indusk/planning/versioned-workbench/adr.md` (decision D8) for the full incident — caught during ADR authoring, before any code shipped, which is the cheapest point to catch this class of defect.
