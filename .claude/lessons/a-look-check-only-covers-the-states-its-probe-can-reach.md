# A UI look-check promise is only as strong as the states its automated probe can actually put the page into — a state no seed can reach is never checked, however "held by value" the promise sounds

A look/visual-regression check that approves a component or screen "by value" (pinned to a hash, checked automatically) sounds like full coverage, but it only ever exercises the states its check harness can actually drive the app into. A state that requires a running process, a live session, or some other hard-to-seed precondition is invisible to the check even though the promise's wording implies every state is held.

**Why:** new-project-flow (dusk, 2026-10-14, archived at `.indusk/planning/archive/new-project-flow/`). The approved conversation mockup always showed chat bubbles; the actual build instead showed the shared session panel while an agent was running — and the looks check passed throughout, because it only ever opened the conversation state with no agent running (no seed existed to start one). The retrospective's own words: "A look check is only as good as the states it can reach... The live conversation was never checked because no seed could start an agent." The gap was found only when a person (Sandy) actually used the feature.

**How to apply:** when a UI promise is "held by value" through an automated check, explicitly enumerate the states the promise claims to cover and verify the check's harness can actually seed each one (a running agent, an error state, an empty-vs-populated state) — not just the default, easiest-to-reach state. A promise that reads as "every state held" but whose check can only reach one state is narrower than its own wording; either give the check a way to reach the state or narrow the promise to say what's actually covered.
