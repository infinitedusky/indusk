# The eval agent runs a branch's tests in the same worktree it's grading — a concurrent human test run in that worktree produces false failures (shared `.next/` lock, shared ports) that look like real regressions

From `test-daemons-never-leak`'s retrospective (`.indusk/planning/archive/test-daemons-never-leak/retrospective.md`, "Getting to Done" + "Insights Worth Carrying Forward"): two full test runs showed 38-39 admin HTTP test failures that had nothing to do with the plan under test. The eval agent, scoring that branch's commits, was running the admin's HTTP tests in the same worktree at the same time as a person's own `pnpm test` — its `next dev` instance held the app's `.next/` build lock. The admin suite alone was 343/343; the collision, not a code defect, produced the failures.

Why it matters: this project's eval agent runs in the same worktree it is grading (confirmed again in this very session — `indusk agent list` reported a 3-way worktree collision on `test-kinds` while scoring commit 58862ba3). A mass of failures that don't match the diff under review is a strong signal to check for a concurrent process before concluding the commit broke something.

How to apply: when a test run (yours or the eval agent's) reports a surprising wall of failures unrelated to the diff being evaluated, check for another live process in the same worktree (`indusk agent list`'s collision warning, or `ps`/port checks for `next dev`) before re-running or concluding regression. The retrospective explicitly flagged this as "not this plan's to fix; recorded for a plan of its own" — the underlying fix (evaluate against a snapshot, or make concurrent runs visible) is still open as of this writing.
