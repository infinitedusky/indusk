# A falsification hypothesis about a tool you don't own must be checked against that real tool before you fix anything — the assumption may already be wrong

admin-plan-authoring's falsification (A36) assumed that a project's Claude Code allow rule would let a headless planning session write unasked. When checked against the real `claude` CLI, an untrusted folder's allow rule was not honoured, and the write was asked about anyway — the premise behind the hypothesis was simply false. The row was dropped (Sandy's decision), not fixed, because there was nothing to fix: an allow rule is the developer's explicit choice, and the CLI's actual behavior (asking anyway in an untrusted folder) was fine as-is.

Why it matters: falsification hunts for ways a design could be wrong by forming hypotheses and testing them — but a hypothesis about behavior you do not control (an external CLI, a third-party API, the OS) is itself a claim that can be wrong before you ever get to the code under test. Fixing code to compensate for an assumed behavior of an external tool, without first confirming the tool actually behaves that way, risks building a workaround for a problem that doesn't exist, or missing the real problem entirely.

What to do: when a falsification hypothesis (or any bug hypothesis) rests on how an external, unowned tool behaves, run that tool directly and observe the real behavior before writing a fix. If the real behavior differs from the assumption, the row may simply be dropped — the "defect" was in the mental model, not the code. See `.indusk/planning/admin-plan-authoring/` (or its archive) for A36's falsification write-up.
