# Meeting the rule of three doesn't obligate extraction — if a specific future plan is already the designated single home for the pattern, extracting now just means that plan has to un-extract it first

workbench-trust-fixes wrote the same "this is a workbench, its code lives in X" refusal message at three call sites (`run.ts`, `cleanup/oversized.ts`, `verify/roots.ts`) — the rule of three was met, which is normally the trigger to extract a shared helper. Cleanup still declined to extract, because `dawn-workbench-execution`'s `resolveExecutionRoots` is the already-named, already-scoped designated single home for exactly this class of logic. Extracting a local helper now would mean that plan's job becomes "replace the local helper with the real one" instead of "add the real one" — net negative work, and a second definition to keep in sync in the meantime.

**Why the rule of three isn't unconditional:** the rule of three is a heuristic for "this pattern is real, not coincidental" — it doesn't say WHEN to extract, only THAT the pattern is worth naming. When the destination for the extraction is already decided (a named plan, not a hypothetical future one), extracting into a throwaway local helper is strictly worse than leaving the duplication in place with a comment pointing at the real destination — the duplication is honest about being temporary, where a premature local abstraction looks permanent and has to be discovered and unwound later.

**How to apply:** before extracting on the rule of three, check whether a specific, already-scoped plan is the designated owner of that consolidation. If yes: leave the duplication, and record the decision with its reason at the site (or in the plan) so the next reader — including the plan that will do the real extraction — can see it was a deliberate deferral, not an oversight. This is the closing half of `one-resolution-function-per-shared-relationship`: knowing a shared relationship needs one resolver doesn't mean THIS commit is where that resolver gets built, if a better-scoped commit already claims the job.

See `.indusk/planning/workbench-trust-fixes/` and `.indusk/planning/dawn-workbench-execution/` (`resolveExecutionRoots`) for the concrete case.
