# When a monorepo task runner stops at the first failing package, every later package's own failures go unseen — diagnose a red root run with --continue, not package-by-package

A task runner (Turborepo, and similarly most monorepo orchestrators) that stops the whole run on the first package's failure means every package ordered after the failing one never actually runs its tests that invocation — their status is simply unknown, not green. Fixing the first failure and re-running can surface an entirely new, previously-invisible set of failures in the next package, which looks like regression but is really first contact.

**Why:** main-suite-green (dusk, 2026-10-15, archived at `.indusk/planning/archive/main-suite-green/`). The admin package's test timeouts had always failed first in the root `pnpm test` run, so turbo never got to running `apps/indusk-mcp`'s own tests — its timeouts "had never been seen because the admin always failed first." Only after the admin was fixed did the mcp package's own root-run timeouts appear for the first time. The retrospective's own words: "A failing package hides every package after it." The fix going forward, named in 'What We'd Do Differently': "Diagnose a red root run with `turbo run test --continue`, so every package's failures show in the first run rather than one package at a time."

**How to apply:** when debugging a red root-level test run in a Turborepo (or similar) monorepo, use the runner's continue-on-failure flag from the first diagnostic pass, not after exhausting the first failure — otherwise each fix-and-rerun cycle can surface a "new" failure that was actually there the whole time, wasting a full cycle discovering it only exists because nothing ran it yet.
