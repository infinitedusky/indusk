# A gate whose on-switch lives in the file it guards is not a gate — every new gate gets a test row for how it is switched off, and by whom

If a check runs only while some field is present in a document the guarded agent may edit, deleting the field turns the check off for every later action. Design and test the off-switch of every new gate, not only its refusals.

Why: in brief-as-the-contract (2026-10-13) the amendment refusal in `check-gates.js` ran only while the impl's frontmatter carried `approved_brief:`, and impl edits are explicitly not amendments, so removing that one line disabled the gate. The same gate also ran after the `<!-- skip-gates -->` escape, so a marker stepped past it. The builder's own falsification phase did not find either; the cold audit did (`.indusk/planning/brief-as-the-contract/audit.md`, findings 3). Build Phase 8 fixed both for the Edit and Write tools: the amendment check runs before any skip marker, and an edit that removes or changes `approved_brief:` is refused.

How to apply: for each new gate add a trajectory row that asks "how is this switched off, and who can do it?", covering (1) the field or file that enables it, (2) any escape marker or policy that runs earlier, and (3) every tool shape that can write the enabling field (Edit, Write, MultiEdit, a shell write). Prefer making an absent enabling field a refusal over a skip. Known remaining limits of the hook lane: MultiEdit is not replayed by `applyEdit`, and shell writes are not seen by hooks; treating an approved impl with no recorded hash as unreadable closes both.
