# Hunt the security boundary before the live check, not after — an unfalsified boundary with no trajectory row of its own can sit open through the entire live run

admin-plan-authoring's DNS-rebinding hole (see `origin-header-check-is-not-same-origin-under-dns-rebinding`) sat open through the plan's entire live check because the origin/Host check was never given its own trajectory row — it was folded into a broader "the admin only accepts local requests" assertion rather than being falsified as its own specific boundary. The live check exercised the real system end-to-end and still didn't catch it, because nothing in the test suite was specifically trying to break that boundary; the live check proves the happy path works, not that an adversarial path is blocked.

Why it matters: this mirrors `run-the-live-check-before-falsification-not-last` (a general sequencing lesson from planner-promises) but sharpens it for security-shaped boundaries specifically: a live check answers "does this work as intended," while falsification answers "can this be broken" — and a boundary that nobody wrote a falsification hypothesis against gets neither kind of scrutiny unless someone happens to think of it. Running the live check first (per the general lesson) surfaces functional gaps, but a security boundary needs its own explicit falsification pass regardless of when the live check runs, because the live check's own happy-path traffic will never trigger it.

What to do: any boundary a build phase introduces that is security-relevant (auth, origin/host checks, trust boundaries, permission gates) should get its own falsification hypothesis and trajectory row before the live check runs — not folded into a broader functional assertion, and not left to the live check to discover by accident. If a security boundary has no row of its own, treat that absence as a gap to fill, the same way an untested code path is a gap to fill.
