# Pin test environment (INDUSK_HOME and the like) in the shared spawn helper, not per test file — a per-file `??=` yields to the developer's shell and a scan that checks for the string is satisfied either way

Seven test suites spawned `indusk init` with the developer's environment and registered a temp directory in the real `~/.indusk/projects.json` on every run — 2,307 entries, 11 alive, when measured. The first fix was per-file: `process.env.INDUSK_HOME ??= mkdtempSync(...)` in each offender plus a grep scan asserting every CLI-spawning test mentions `INDUSK_HOME`. Falsification found two holes by reading: `??=` yields to a developer who exports `INDUSK_HOME` in their shell (a documented, user-facing variable), so the leak resumes silently for exactly those developers; and the scan's command list (`init|update|ui`) was narrower than the set of registering commands (`setup` delegates to `init`).

Rule: when every test already goes through one spawn helper (`runCli`), the pin belongs there — unconditionally, a fresh temp home per process, with an explicit caller override — and the per-file scan becomes the second line, not the first. A rule each file must remember is a rule some file will forget or get subtly wrong; a rule in the chokepoint cannot be forgotten. And when a scan enumerates commands, derive the list from the same fact the code uses (which commands write the registry), or at least test the scan against a fixture spawn of each.
