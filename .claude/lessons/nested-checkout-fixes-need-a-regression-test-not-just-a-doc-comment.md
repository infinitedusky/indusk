# A fix for a path-resolution bug found via an accidental fixture collision (not a targeted test) needs its own regression test before the phase closes — a doc comment isn't a guard

admin-plan-worktrees Build Phase 3 (commit 446f30f3) found that `repositoryOf` (`apps/indusk-mcp/src/lib/worktree/plan-worktrees.ts`) climbed from a nested InDusk project up to the enclosing repository's toplevel and misattributed the enclosing repo's plans as the nested project's own. The bug was discovered by accident: `apps/indusk-admin/test-fixtures/sample-project` happens to sit inside the dusk repo, so an existing fixture reproduced it.

The fix (`git rev-parse --show-toplevel` compared against the asked checkout path, returning `null` — no resolver applied — when they differ) is correct and has a good doc comment explaining the rationale. But no test in `apps/indusk-mcp/src/__tests__/` or `apps/indusk-admin/src/__tests__/` references `repositoryOf`, `show-toplevel`, `sample-project`, or "nested" — nothing pins the corrected behavior. A future refactor of `repositoryOf` or `resolvePlanCopies` could silently reintroduce the misattribution with nothing red to catch it.

How to apply: when a bug is found via an incidental fixture/environment collision rather than a targeted test — a strong signal it's a real, previously-latent defect, not a hypothetical — treat closing that phase's Verification gate as incomplete until a test exists that reproduces the original failure mode and asserts the fix. This is the same discipline the project's Test Trajectory / Regression Guards convention already requires for planned rows; it applies with equal force to bugs discovered mid-phase, not just ones authored red at Test Phase 1.
