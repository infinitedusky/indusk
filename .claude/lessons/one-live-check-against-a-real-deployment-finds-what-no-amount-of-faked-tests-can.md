# A single manual smoke test against the real deployed server found a defect (an un-normalized project-tag comparison silently dropping marks) that the entire booted-server, real-Jaeger local test suite never caught — a live check against production, even just once per feature, is worth more than scaling up local fakes or local-server tests

In promise-timeline (`.indusk/planning/archive/promise-timeline/`), trajectory row A13 ran the finished feature against the real deployed Fly server as a manual smoke test — the expected result was simply "red, then open, then purple, then green" as a break was introduced and fixed. In the course of running it, a real bug surfaced: a trace tagged `timeline-smoke` was silently being dropped and attributed to a different project, because the project id gets normalized (`timeline_smoke`) somewhere in the pipeline but the tag comparison compared the raw, unnormalized string. Nothing in the system said a run had been dropped — it simply vanished from the data a person would see. This became its own falsification row (A15) once found.

This defect was invisible to every other test in the plan, including the ones run against a real local Jaeger and a real locally-started always-on server, because none of those tests exercised the specific code path that normalizes project ids differently in two places that should agree. Only a check against the actual deployed infrastructure, with its actual configuration and actual request path, surfaced the mismatch.

**How to apply:** even when a plan has extensive test coverage against real local backends (a real Jaeger, a real spawned server), a manual or scripted smoke check against the actual production/deployed target — run at least once per feature that touches deployed behavior — is not redundant with that local coverage. Local "real backend" tests still run in a controlled, locally-configured environment that can diverge from production's actual configuration and code paths in ways no amount of local realism will catch. This doesn't mean testing everything against production; it means not skipping the one live check on the theory that extensive local real-backend testing already covers it.
