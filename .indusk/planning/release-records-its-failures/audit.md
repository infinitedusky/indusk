# Audit — release-records-its-failures

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/__tests__/release-report.test.ts:117` — `a-flake-opens-nothing` says a flake is a file that "fails and then passes" on its rerun. A9 is the trajectory row asserting that a file which fails and then passes on its rerun is listed as a flake and opens nothing. Its rerun report is `junitReport({})`, which has no testcase at all for the claimed file. So A9 proves that a file *missing* from the rerun report is a flake, not that a passing file is. The code matches the test: `settle.ts:40` keeps only the files the second report still marks failed, and `settle.ts:37` ignores the rerun's exit code. A rerun that rewrites a report without running the file (a filter that matches nothing, or a crash that still writes an empty report) turns a real failure into a flake that opens nothing (confidence: high on the code; moderate on how often it happens in practice).
- `apps/indusk-mcp/src/lib/release/bugfix-plan.ts:106` — `an-unclaimed-failure-opens-a-bugfix-plan` promises that a later failure "reuses that plan while it is open". `chooseName` treats a plan as open only when it has a worktree copy (`source === "worktree"`). A `fix-<stem>` plan that landed but is not yet archived sits on the trunk as `.indusk/planning/fix-<stem>/`, so `chooseName` picks that same name again. `startPlan` then refuses with "already has a folder on the trunk" (`lib/plans/start.ts:66`). The same refusal happens when a `plan/fix-<stem>` branch is left over with no worktree (`start.ts:76`). Both refusals are caught at `route.ts:194`, so the file stays `unrouted` at this release and every release after it. A17 is the row asserting that a later failure of the same file adds to its open bugfix plan rather than opening another. It covers only a plan open in its worktree whose brief contains the exact path.
- `apps/indusk-mcp/src/lib/release/bugfix-plan.ts:73` — reuse also depends on the open plan's `brief.md` or `research.md` still containing the file path verbatim (`namesFile`). Once someone edits the brief so the exact path is gone, the next failure opens a second plan, `fix-<stem>-<package>`, for the same file. That contradicts "one draft bugfix plan for its file", and no row covers it.
- `apps/indusk-mcp/src/__tests__/release-junit.contract.test.ts:85` — A8 is the contract row asserting that dusk's slow tests, run with the declared reporter, write a JUnit report whose failed cases name the failing files. It reads only `apps/indusk-mcp/vitest.system.config.ts` and regex-matches `classname="…fail.test.ts"`. It never runs the report through `failedFiles` or `underReport`, never checks that the name resolves to the repo-relative path that trajectory `Test` cells use, never checks that the output lands under the declared glob `apps/*/test-results/system.junit.xml`, and never touches the admin or vscode-extension configs. So "read from the test report the project declares" is proven only for the fixture shape in A6, not for dusk's real three-package reports.
- `apps/indusk-mcp/src/lib/release/junit.ts:104` — `a-failure-is-read-from-the-report` names no test only when there is "no readable report". `failedFiles` returns `UNREADABLE` for the whole set as soon as any one matching file fails to validate (`:104`, `:107`, `:114`). With three per-package reports, two valid and one truncated, the release says "the slow tests failed", names no test and routes nothing, even though readable reports exist. A7, the row asserting that a red run with a missing or unreadable report names no test and opens nothing, tests only the single-report case.
- `apps/indusk-mcp/src/__tests__/release-run.test.ts:41` — for `a-release-runs-as-its-project-declares`, A1–A5, A20 and A21 (the rows on order, outcome, a missing declaration, the covered skip and a non-npm command) leave two of the promise's paths unproven: `when: before` with a green slow run going on to publish, and `done_when: green` with a green run reporting done and exiting 0. Every `before` and every `done_when: green` row is a red run. No row exercises the validation of the declaration either (`steps.ts:92`).
- `apps/indusk-mcp/src/__tests__/release-incident.test.ts:132` — `an-open-incident-stays-loud` is a must-not-break promise: an incident a release opens shows in catchup, `promise_health`, `promises status` and the admin. A14 is the row asserting that the incident shows in `promises status` and `promise_health` with its age. It asserts only those two readers, not catchup or the admin.
- `apps/indusk-mcp/src/__tests__/release-dusk-declaration.test.ts:19` — the changed `dusk-installs-its-own-build` promise ends "and what they find is recorded". A18 is the row asserting that dusk's release script no longer runs the slow tests and that its config declares them `after` with a JUnit report. It checks two static strings. The "recorded" half rests entirely on A19, the deferred live release.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/release/bugfix-plan.ts:167` — every bugfix brief says the file "still failed when run again", including when the project declares no `rerun`. Without one, nothing was run again (ADR D5: "Without `rerun`, every failure is recorded").
- `apps/indusk-mcp/src/lib/release/bugfix-plan.ts:106` — if `archive/fix-<stem>` exists, the new plan's brief asserts at `:171` that it "follows" that plan, "the bugfix plan that fixed an earlier failure of this file". `chooseName` never checks that the archived plan was about this file. Two files sharing a basename in different directories (the case A26 covers for open plans) get a false lineage.
- `apps/indusk-mcp/src/lib/release/route.ts:226` — a row whose `For` names a retired or unknown promise is treated as unclaimed, because `live()` returns nothing. The resulting bugfix brief says "No promise's test row names it" and lists the row as one that "proves no promise" (`bugfix-plan.ts:162`), which is false for that row.
- `apps/indusk-mcp/src/bin/commands/release.ts:64` — after a red `when: before` run, nothing was published, yet failures are still routed. Incidents and bugfix plans name `releaseVersion` (the version in `version_file`), a release that never shipped. The brief promises only that such failures are "still recorded" (A2), not that they become incidents naming a release.

## Which skip reason would you not accept?
- `.indusk/planning/release-records-its-failures/impl.md` (approved at `c87f2946`, Deferred Verification) — A19, the live check that a real dusk release through `indusk release` publishes, then runs the slow tests and prints what it recorded, is deferred because "a publish runs only from `main` at a release commit". That reason holds for the publish. It does not hold for the rest of what A19 is the only proof of: dusk's real `pnpm -w test:system` writing three reports under `apps/*/test-results/`, `rerun-system.js`, and routing over dusk's own impls. All of that could run before landing with the release command stubbed. The stated mitigation also depends on the routing under test to report that routing's own failure.

## What else would have to change for each promise to hold?
- `apps/indusk-mcp/src/lib/plans/start.ts:66` — untouched. `startPlan` refuses a name that has a trunk folder or an existing `plan/<name>` branch, and `bugfix-plan.ts` `chooseName` checks neither, so `an-unclaimed-failure-opens-a-bugfix-plan` fails permanently for a file whose fix plan landed but was not archived, or whose branch survived its worktree. Either `chooseName` must treat a trunk copy as open (extend it) and skip a taken branch, or `startPlan` must expose a "name available" check that the release uses.
- `apps/indusk-mcp/src/lib/promises/reopen.ts:53` — untouched. A test-born incident reopens its owner through the watcher's Maintenance-phase template. That template's verification asks for the promise "seen upheld after the fix (`indusk promises status`)", and with the OTel gate adds "the fixed code still marks the promise on its span". Neither names the failing slow-test file or a slow run, so for `a-failing-slow-test-breaks-its-promise` the reopened phase points the fixer at a span or status check rather than the test that broke (confidence: moderate; I did not check what `promises status` reports for a test-proven state promise).
- `package.json` (root) — untouched. `pnpm -w test:system` runs indusk-mcp's `test:system`, which starts with `pnpm run prepublishOnly`, a full build. If that build fails after the publish, indusk-mcp writes no fresh report. The environment rule then counts only the other packages' files (`settle.ts:26`), and `a-failure-is-read-from-the-report` names nothing for the package that broke. The build belongs outside the slow command, or the release should treat a declared package that wrote no fresh report as unreadable.
