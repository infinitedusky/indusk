# Audit — a-plan-says-how-long-it-took

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/lib/timing/phase-close.test.ts:815` — Narrower. A2 and A3 (trajectory rows asserting that closing a phase records a close no earlier than its opening, and that a double or orphan close keeps one honest record) call `recordPhaseClose` directly. Nothing in production calls `recordPhaseClose`; `apps/docs/src/decisions/plan-timing.md:24` says so. Both rows can pass while no real phase ever records a close. The brief's `phases-are-timed` clause (brief.md:32, "each phase records when it opened and when it closed") is therefore not proved for the close half. The view hides the gap by deriving ends (see the next question).
- `apps/indusk-mcp/src/lib/timing/phase-close.test.ts:808` — Narrower. A1 (the row asserting that opening a phase records its opening time) calls the existing `recordPhaseStart` by hand. It proves the function writes. It does not prove that phases are opened: the only writer is an agent pasting the snippet in `apps/indusk-mcp/skills/work.md:162`, and the docs page says the Dawn loop writes none.
- `apps/indusk-mcp/src/lib/timing/timed-step.test.ts:1` — Narrower. A4 and A5 (rows asserting that a finished planning step and a blocked, failed or stopped build step each leave a start, an end and the outcome) wrap a fake `run`, and the blocked and stopped cases come from a stubbed `classify` that returns the outcome. The real classifier (`apps/indusk-admin/src/lib/build-host.ts:85`) and the two wrap sites are never exercised. Both admin test files mock `timedStep` as the identity (`apps/indusk-admin/src/__tests__/sessions-per-plan.test.ts:39`, `apps/indusk-admin/src/lib/build-host.release.test.ts:20`). A4's "still there after the step's session is gone" is not asserted either: the test has no session to delete.
- `apps/indusk-mcp/src/lib/timing/test-run.test.ts:1091` — Narrower on "how many files it ran for each reason". A7 (the row asserting that a phase's test run records the counts per reason) only ever sees `reached: 0`. `planTestSet` (`apps/indusk-mcp/src/lib/plans/test-set.ts:60`) produces only `row …` and `must not break: …` reasons. `countByReason` (`apps/indusk-mcp/src/lib/timing/test-run.ts:26`) puts any other reason in `reached`. The `reached` count is a catch-all that no current input can make non-zero, and no row shows it counting a reached file.
- `apps/indusk-mcp/src/lib/plans/plan-tests.ts:94` — Narrower on "each run". A7 to A9 (rows asserting that phase runs, landing runs, failing runs and repeat runs each leave a record) all use runners that resolve. `recordTestRun` runs only after `runFiles` returns, not in a `finally`. If `runFiles` rejects (a runner crash or a spawn error), nothing records that run.
- `apps/indusk-mcp/src/lib/timing/view.test.ts:1570` — Narrower. A11 (the row asserting that the total runs from the brief's acceptance to the landing) injects `landedAt` and `acceptedAt`. The real sources are never run against a real plan in any row: the `git log --grep` landing search (`apps/indusk-mcp/src/lib/timing/view.ts:343`) and the `accepted_at` regex (`view.ts:296`). A22 (the row asserting that a workbench plan's landing is read from the code repo's trunk) also uses a fake `runGit`. Nothing pins the grep pattern to the subject `plans land` actually writes (`apps/indusk-mcp/src/lib/plans/land.ts:92`).
- `apps/indusk-mcp/src/lib/timing/view.test.ts:1664` — A20, the row asserting that "between" is never negative or printed as 0s to hide a negative, is tested as "between is printed signed". That satisfies the row. It contradicts the test plan's `one-view` Measure (test-plan.md, `one-view` section: "expect the sum of the parts to be no greater than the total"). Separately, `between` is total minus phases only (`view.ts:201`). ADR Decision 8 says it is the time "not inside any listed item", so steps and test runs are not accounted.
- `apps/indusk-mcp/src/lib/timing/phase-close.test.ts:886` — Narrower. A14 (the row asserting that opening and closing a phase still succeed with the phase record unwritable) proves only that `recordPhaseClose` resolves. That function has no caller, and opening a phase never touches the timing log. So the `a-record-never-blocks` clause (brief.md:36) is proved for test runs (A16) and for a fake step (A15), but not for any real phase path.

## What does the diff change that no row touches?
- `apps/indusk-admin/src/lib/build-host.ts:85` — `classifierFor` has no row. It maps an error containing "on a signal" to `stopped`, and it reads the plan's blocker after the step to return `blocked`. It is called for failed results too: `timedStep` lets its answer override `failed` (`apps/indusk-mcp/src/lib/timing/timed-step.ts:56`). Nothing prevents a step that errored, on a plan that already carried a blocker line, from being recorded `blocked` instead of `failed`. No test would notice.
- `apps/indusk-admin/src/lib/build-host.ts:109` — Both production wrap sites have no row: the build/release `run` and the planning `run` at line 401. With `timedStep` mocked as the identity in both admin test files, removing either wrap leaves every test green.
- `apps/indusk-mcp/src/lib/timing/view.ts:330` — No row runs the default `landingTime` path against a real repository: `--first-parent`, the `-E` grep, the `%aI` author time and `mainCheckoutOf` of the code root. The same goes for `defaultReads`' `accepted_at` regex (`view.ts:296`) and `liveRootOf`/`livePlanCopy` (A23, the row asserting that openings are read from the plan's worktree, passes `liveRoot` explicitly).
- `apps/indusk-mcp/src/lib/timing/timed-step.ts:43` — The log path is computed once, when the wrapper is built (inside `depsFor` and `startPlanning`), outside `recordSafely`. This spawns git through `bookkeepingRoots` on every build start. No row covers a failure there. Today the helpers do not throw, so this is a scenario only.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/timing/view.ts:112` — The view invents phase ends. A phase with no recorded close ends at the next phase's opening, and the last one ends at the landing (A20). The brief promises that a phase records its close. The ADR's Accepting line (adr.md:33) accepted "an open end until that path is found". The ADR's open decision allowed a derived close only if `phases-are-timed` was amended by a person (adr.md:60). The brief at brief.md:32 is unamended. The printed "ended when the next opened" marks the row as derived, but a phase's duration now includes any idle time before the next phase opened.
- `apps/indusk-mcp/src/lib/timing/view.ts:367` — `planTimeText` refuses an unknown plan name with exit 1 (A24, the row asserting that refusal). It also resolves the plan's live worktree for its reads (A23). Neither is in the brief. Both are reasonable falsification fixes under `one-view`.
- `apps/indusk-admin/src/lib/build-host.ts:89` — Reading the plan after a step to decide `blocked` is a choice the brief did not make. The brief says only "how it ended". The code takes "the plan carries a blocker after the step" as the meaning, so a pre-existing blocker colours every later step's outcome.
- `apps/indusk-mcp/src/lib/plans/plan-tests.ts:102` — A `--list` invocation records nothing. This is consistent with "a run", but it is a scope choice the brief did not state.

## Which skip reason would you not accept?
- `.indusk/planning/a-plan-says-how-long-it-took/brief.md:32` — The phase-close wiring item was resolved by not wiring it (`apps/docs/src/decisions/plan-timing.md:24`: "the one deterministic close point is the check-gates hook, a gate, which this plan does not change"). The ADR's open decision (adr.md:60) made that fallback conditional on "`phases-are-timed` is amended by a person". The clause still reads "each phase records … when it closed", so the skip's own condition is unmet. The given reason also overlooks a non-gate site: the work skill already instructs the agent to write the opening (`apps/indusk-mcp/skills/work.md:162`) and could instruct the close the same way.
- `.indusk/planning/a-plan-says-how-long-it-took/test-plan.md:86` — The reason for having no promise-level row, "(none needed — no production behavior to watch)", does not hold well (moderate confidence). For a CLI and an admin daemon, a user's machine is production. Each clause's Signal describes a broken state a watcher could read: a step with no end, a closed phase with no close, a lost record. Yet the only trace of a lost record is a `console.warn` (`apps/indusk-mcp/src/lib/timing/safe.ts:996`). Nothing would surface `a-record-never-blocks` or `phases-are-timed` being broken in use.

## What else would have to change for each promise to hold?
- `apps/indusk-mcp/skills/work.md:162` — `phases-are-timed`: the only writer of phase openings is this skill's hand-run snippet, and the skill has no matching close step. Either this file (and its synced `.claude/skills/work.md`) or `apps/indusk-mcp/hooks/check-gates.js` would have to call `recordPhaseClose` for any real close to be recorded. Alternatively, brief.md:32 would have to be amended as the ADR required.
- `apps/indusk-mcp/src/lib/run/driver.ts:1` — `steps-are-timed` says "each unattended planning or build step". The Dawn loop (`indusk run`) runs phases unattended and is not wrapped by `timedStep`, so its steps leave no timing record. Either it is wrapped, or the clause is read as "the admin's unattended steps" and said so.
- `apps/indusk-mcp/src/lib/plans/test-set.ts:60` — `test-runs-are-recorded` ("how many files it ran for each reason"): the selector tags no file as reached by the plan's changes. The `reached` count can only become real if this file emits a distinct reason, or if `/decisions/tests-never-make-us-wait` reach-selection lands here. Until then the column is always 0.
- `apps/indusk-mcp/src/lib/plans/land.ts:92` — `one-view`'s total depends on this subject string (`Merge <branch>: <plan> landed`, also at line 155) staying exactly as `landingTime` greps it. Nothing ties the two together. A reworded merge message would make every landed plan read "so far, not yet landed" without any error.
- `apps/indusk-admin/src/lib/build-host.release.test.ts:20` — `steps-are-timed` and `a-record-never-blocks` for real steps: the admin's tests would need at least one case that does not mock `timedStep`, so that the wrap at both sites is held by a test.
