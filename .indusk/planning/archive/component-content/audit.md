# Audit — component-content

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/lib/looks/compose.test.ts:85` — Narrower. Rows A1–A3 are unit rows asserting that a button, a step and a container placed with content show that content. They prove compose against hand-written content maps (`{ children: [[0, 0]] }`) on one-line snapshots. Row A5, a contract row asserting that each admin state lists the properties a mockup may fill (`looks-component-content.contract.test.ts:64`), checks only the property names on four states, never the paths. Row A14, which checks the recorded `before` and `nodes` on two places, does not test path correctness either. No row composes a real admin story with real recorded places and checks the output, so nothing proves that the real marker render's paths land on the story's words. That is the core of promise `a-placed-component-shows-its-content`, which says the mockup shows the approved component with the mockup's words in place of the story's.
- `apps/indusk-mcp/src/lib/looks/compose.ts:228` — Narrower. "The approved component" is checked only by byte equality on snapshots that parse5 serializes back unchanged. When content is filled, the whole snapshot is re-serialized through parse5. No row covers a snapshot that parse5 would rewrite, such as a `<table>` without `<tbody>`, void tags or entity forms. The ADR's own risk also stands: a property that also sits in an attribute (an `aria-label`) keeps the story's words. So "in place of the story's" holds for text nodes only.
- `apps/indusk-mcp/src/__tests__/looks-component-content-lint.test.ts:24` — Narrower. Rows A6–A8 are lint rows: A6 says an element inside a placed component is refused, A7 says content for a property the state does not take is refused, and A8 says words and components are accepted. Promise `placed-content-is-only-words-and-components` says anything else "is refused". In fact the refusal happens only when `indusk looks lint` runs. Compose still renders a `<div style=…>` placed inside a component into the composed mockup (`compose.ts:219`, where the bare content goes into `children`). The cockpit's approve route (`apps/indusk-admin/src/app/api/looks/[app]/approve/route.ts:151`) never consults the lint, so nothing prevents a person approving a mockup that carries a drawing inside a component.
- `apps/indusk-mcp/src/__tests__/looks-component-content-falsification.test.ts:72` — Narrower. Row A15 asserts that compose never puts an `<indusk-content>` element into a composed mockup. It tests that only inside a reference. An `<indusk-content>` outside any `<indusk-component>` is emitted verbatim: with no references the source is returned as is (`compose.ts:231`), and with references it is left untouched between them. `contentFindings` looks only inside references, so the lint does not refuse it either. A reference whose story has no snapshot also returns its raw source, `<indusk-content>` included (`compose.ts:208`).
- `apps/indusk-mcp/src/__tests__/looks-component-content-approval.test.ts:25` — Proves the sentence for its case. Row A9 asserts that a mockup placing a component with words returns to proposed, naming the component, when that component's story changes. It covers a button nested inside a box, so promise `a-changed-component-reopens-its-mockups` holds there.
- `apps/indusk-mcp/src/__tests__/looks-component-content-approval.test.ts:41` — Proves the sentence. Row A10 asserts that changing only the placed words reopens an approved mockup, which is promise `a-mockup-is-approved-by-a-person`.
- `apps/indusk-mcp/src/__tests__/looks-admin-approvals-hold.test.ts:24` — Narrower. Row A11 asserts that every admin mockup approved before the change is still approved. That is a guard on approvals, not on promise `a-mockup-composes-approved-components` (components appear only by name). No current admin mockup places content, so the row cannot see whether content lets a component appear other than by name.

## What does the diff change that no row touches?
- `apps/indusk-mcp/src/lib/looks/compose.ts:208` — A reference whose story has no snapshot used to be left in place while the references nested inside it were still composed: the old loop only skipped the outer one. Now the whole raw slice is returned, nested references uncomposed. No row covers a missing outer snapshot.
- `apps/indusk-mcp/src/lib/looks/markup.ts:78` — `elementsOf` now ends every hyphenated element written `/>` at its start tag, not only `<indusk-component>`. Its other callers (`lint.ts:29`, `lint.ts:54`, `component-styles.ts:28`, `markedElementsOf`) get the new `end` for any custom element. Row A17, which asserts that a self-closing `<indusk-component />` does not swallow the paragraph after it, covers only `indusk-component` in compose and lint.
- `apps/indusk-mcp/src/lib/looks/stories.ts:353` — Any exception in the second render is swallowed, and `{}` is written as that story's content. A story that fails to re-render silently becomes "takes no content". No row would notice a state losing its content map.
- `apps/indusk-mcp/src/lib/looks/stories.ts:256` — `markerPlaces` silently records nothing in two cases: two markers in one parent whose child counts differ, and a parent that shrank. In the committed catalog, `decision-card.alert` lists no `title` while its sibling states do, and `rail-group` lists no `children` although it takes them. Row A5 checks four states and would not notice.
- `apps/indusk-mcp/src/lib/looks/stories.ts:448` — Snapshots are written `.trim()`med, while places are paths into the untrimmed canvas. Nothing checks that a canvas starting with a whitespace text node keeps top-level paths aligned.
- `apps/indusk-mcp/src/lib/looks/stories.ts:328` — The second render mounts a React root into `document.body` before the app's CSS is collected from `document.styleSheets`. A component that injects styles on mount could change the captured `_app.css`, and no row compares that file before and after this change.
- `apps/indusk-mcp/src/lib/looks/compose.ts:221` — Content for a state whose catalog entry has no `content` (an older catalog), or for a property not in its map, is silently dropped and the story's words show. Only the lint (`component-takes-no-content`) reports it, and only when the catalog lists the state (`lint-components.ts:114`).

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/looks/lint-components.ts:126` — A third lint rule, `content-given-twice`. It refuses content that is still only words: two `<indusk-content for="x">`, or bare words next to `for="children"`. The brief's promise refuses only what is not text or components, and the ADR names two rules.
- `apps/indusk-mcp/src/lib/looks/markup.ts:78` — HTML parsing is redefined for every custom element written self-closing, across all looks readers. That is a markup policy no promise or scope line covers.
- `apps/indusk-mcp/src/lib/looks/stories.ts:316` — A string property becomes fillable only if its value appears as a whole, trimmed text node in the first render. ADR decision 2 says "every string property". A prop that is shown transformed (uppercased, formatted, interpolated) is silently never fillable.
- `apps/indusk-mcp/src/lib/looks/compose.ts:882` — Places carry `nodes`, `before` and `after`: static story words kept around the filled words, and one property spanning several nodes. This refines decision 2's plain child-index paths without an ADR amendment, and it re-inserts story text that the snapshot hash does not bind separately.

## Which rejected ADR alternative does the code quietly take?
- `apps/indusk-mcp/src/lib/looks/stories.ts:316` — Partly "Replace the story's words by text match". Where content lands is still found structurally, by the markers. But which properties get a marker at all is decided by matching each arg's text against the first render's text nodes. That is the text-match reliance the ADR rejected, applied to whether a property is fillable rather than where it lands. A string arg whose value happens to equal an unrelated text node is marked. One whose rendered form differs is not.

## Which skip reason would you not accept?
- nothing

## What else would have to change for each promise to hold?
- `apps/indusk-admin/src/__tests__/composition.contract.test.ts:392` — Untouched by the plan. Row A30 of storybook-components, the contract asserting that each placed component draws as its story does, indexes `uses` against the outermost `[data-component]` roots (`readDrawn`, line 116). It then compares every descendant with the story's descendants. `uses` includes nested references, and a filled component's descendants differ from the story's. So once a mockup places a component inside a container, or adds words that change the node count, nothing prevents that contract from failing or mis-pairing roots. It was not adapted for promise `a-placed-component-shows-its-content`.
- `apps/indusk-admin/src/app/api/looks/[app]/approve/route.ts:167` — Untouched. For promise `placed-content-is-only-words-and-components` to mean refused and not just reported, Approve (or `looks/approve`) would have to refuse a mockup with content findings. Today it checks hashes only.
- `.indusk/mockups/admin/screens/` — The brief's Expectation 1 is that new-project-flow's five screens, with components placed by name, draw nothing but declared new components. No new-project-flow mockup exists in the checkout, so that expectation depends entirely on files the plan neither has nor touches.
