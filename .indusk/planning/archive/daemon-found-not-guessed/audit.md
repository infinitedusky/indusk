# Audit — daemon-found-not-guessed

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/lib/telemetry/daemon-reports.ts:122` — A6, the row asserting that `status` sends upheld for `one-daemon-on-its-own-ports` when one Jaeger and one collector hold the four stored ports, proves less than it says. The verdict compares the record's ports with the stored address (`portDifferences`, `daemon-address.ts:84`), and that comparison returns nothing when no address is read. So a running daemon with no address stored, or with an address file that cannot be read, is reported upheld. That can happen after a takeover at first setup whose `chooseAddress` refused (`start-plan.ts:82-88` then stores nothing and says nothing), or after the file is deleted by hand. The clause promises "one address chosen once and kept", and nothing in that path checks that an address exists.
- `apps/indusk-mcp/src/lib/telemetry/daemon-state.ts:69` — A6 and A19 (status lists every InDusk Jaeger and collector the record does not name) count only processes of this home. The clause says "at most one InDusk daemon runs on a machine", and A19's sentence says "every InDusk Jaeger and collector". A daemon run from another real home, such as a custom `INDUSK_HOME` outside a temp root, never counts as an extra process. Other homes' orphans are computed (`state.orphans`, line 102), but `renderStatus` never prints them (lines 207-211).
- `apps/indusk-mcp/src/__tests__/telemetry-address.test.ts:93` — A29, the row asserting that every InDusk reader takes the daemon's ports from the stored address or the record and never from a literal, is checked by scanning eleven named modules. It does not see the extension's health checks (`extensions/local-telemetry/manifest.json:10,14`, which read `~/.indusk/telemetry.json` straight from `homedir()`), the shipped `.env.example` (block ports written as literals, offered for copying into `.env`), the admin, or the editor. No row asserts the clause's last part, that "what `init` hands an application" reads the stored address: `init` (`src/bin/commands/init.ts`) hands nothing today.
- `apps/indusk-mcp/src/lib/telemetry/daemon.ts:336` — A3, the row asserting that a block port held at first setup is replaced by a free port picked once and stored, passes with an OS-assigned ephemeral port (`listen(0)`). That port number sits in the range the OS hands out again to other programs' `listen(0)` and outgoing connections. Nothing prevents a later stranger from taking it, and at that point the "never moved" rule refuses every start. The clause's "kept" holds, but the picked port is the one most likely to collide later.
- `apps/indusk-mcp/src/lib/telemetry/register.ts:79` — A17, the row asserting that registering points the project's own entry at the stored MCP port, proves the entry matches the address, not the daemon. A daemon taken over where it stands (for example on 4318/16686/62843, which D5 says only an explicit `restart` moves) keeps its old MCP port. Meanwhile `register` and `update`'s sync (`mcpPortOf`, `daemon-address.ts:196-201`) point the entry at the stored 24317, where nothing listens until a restart. Claude Code's `jaeger` entry then reaches no daemon, against the parent promise that every reader reaches the one running.
- `apps/indusk-mcp/src/lib/telemetry/register.ts:102` — A18, the row asserting that registering sends broken for `nothing-starts-a-second` naming each other project's entry it changed, is proved only through `daemonReports` with a hand-built state. Real `register` always passes `otherEntriesChanged: []`, so that broken half can never fire from production code. The `strays` half also blames `register` for any stray of this home, including one that existed before it ran.
- `apps/indusk-mcp/src/lib/telemetry/start-plan.ts:202` — A16, the row asserting that with a daemon running `init`/`update`/enabling start none, is tested with a daemon `running` or `found`, never `partial` (the record names two processes and only one is alive) or `stale` (the record names dead processes while unrecorded daemon processes of this home run). Both map to `none`, so `ensureDaemon` plans a fresh start. With no address stored, which is this machine's case before the migration, the block is free, a new daemon starts beside the surviving process, and the record is overwritten. That is the second daemon the clause forbids. We have not seen it happen, and nothing prevents it.
- `apps/indusk-mcp/src/lib/telemetry/daemon-state.ts:290` — A7/A8, the rows asserting that no read removes the record and that a slow port reads slow, prove the record survives. The clause also says a daemon is never read "as gone", but the resolver returns `null` for a `partial` daemon. A dead collector therefore makes every promise reader, the admin and the evaluator report "no telemetry daemon is running" while the Jaeger they query still answers.
- `apps/indusk-mcp/src/lib/telemetry/reap-plan.ts:100` — A21, the row asserting that `reap` sends upheld for `strays-are-cleared` when none remains, counts a stray dropped by the second identity check (`isOwnProcess` with `daemonConfigPath`) as neither stopped nor still running. Such a stray is reported cleared while it runs. One case: a process `daemonProcessOf` accepts by its home directory alone (`daemon-process.ts:84-86`) but whose config file has another name.
- `apps/indusk-mcp/src/lib/telemetry/daemon-state.ts:221` — A23/A24, the rows asserting that the log holds no line of Jaeger failing to trace itself, count only lines that contain `4317` together with `traces export` or `addrConn.createTransport failed`. The brief's clause and its third expectation cover any such line. A self-tracing failure worded differently, or aimed at another port, would read upheld.
- `apps/indusk-mcp/src/lib/eval/otel.ts:327` — A31, the row asserting that the evaluator's log records go to the logs port, adds a new no-op fallback ("the daemon's logs port is unknown; falling back to no-op logger") for a found daemon whose logs port was not read. The brief's second expectation counts only "endpoint unset; falling back to no-op logger" (line 317), so its measure cannot see this new fallback.

## What does the diff change that no row touches?
- `apps/indusk-mcp/src/lib/telemetry/reap-plan.ts:27` — With a `stale` record (it names dead processes) and this home's daemon running unrecorded, `daemonState` puts the live pair in `strays` (`daemon-state.ts:100`), and `reapPlan` returns them. `reap` then stops the only running daemon and loses its in-memory traces. ADR D3 says a stale record with an own daemon running is `found` and rewritten, but the code finds only when the record is missing (`daemon-state.ts:88`), so readers also report no daemon. D7's guard ("with no record, reap stops nothing a takeover might want") covers only `meta === null`. No row has a stale record beside a running daemon.
- `apps/indusk-mcp/src/lib/telemetry/reap-plan.ts:27` — `reap` no longer stops orphans of deleted temporary homes; `orphans.ts` was removed and `reapPlan` returns only this home's strays. This was the cleanup behind the 2,058-process leak recorded in `src/__tests__/helpers/telemetry-reap.ts:19`. ADR D7 says reap returns "the strays plus the orphans". The refusal text still tells the person that "`indusk telemetry reap` stops an orphan" for another home's daemon (`start-plan.ts:138`), and now it does not. No row asserts that an orphan from another home is still cleared by anything.
- `apps/indusk-mcp/src/lib/telemetry/daemon-find.ts:109` — The finder pairs a Jaeger with a collector only by start time within 20 s. It never uses ADR D4's first rule, "paired with the collector holding the stored logs port". A collector restarted on its own more than 20 s after its Jaeger is never paired, so the daemon is not found and `start` refuses on its own Jaeger's ports. No row covers that pairing.
- `apps/indusk-mcp/src/lib/telemetry/daemon-find.ts:275` — A record that exists but does not parse reads as missing (`daemon-reads.ts:241-245`). The finder's exclusive create then fails on the existing file, and `takeOverLocked` still returns a finding, so `start` prints "took over the running daemon" without having written a record. `stop` then meets the unparseable file, deletes it and says "not running" (`daemon.ts:526-531`) while the daemon runs. The non-exclusive record write after a spawn (`start-plan.ts:277`) is not atomic, so a cut-short record is a reachable state.
- `apps/indusk-mcp/src/lib/telemetry/daemon-process.ts:84` — `isOwn` compares `dirname(configPath)` with the home string exactly. ADR D2(b) compares the home "both as given and after resolving its real path". An `INDUSK_HOME` given with a trailing slash or through a symlink would not recognise its own daemon: status reads it as not running, and start refuses on its own ports. No row gives a home in a second spelling.
- `apps/indusk-mcp/src/lib/telemetry/daemon-reads.ts:289` — `holders()` reads only `lsof`. Without `lsof` (the Linux case D4 gave a `/proc` fallback for, but only for `listening()`), and for a listener `lsof` cannot see (another user's), every port reads free. First setup then stores block ports a stranger holds instead of picking, and the start fails on bind rather than naming the holder.
- `apps/indusk-mcp/src/bin/commands/telemetry.ts:389` — `telemetry reset` restarts onto the stored address like `restart` does, but no longer re-points any project's `jaeger` entry (`restart` does, at line 149). A reset that moves a daemon off old ports leaves every entry on the old MCP port. No row covers reset.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/telemetry/daemon-address.ts:238` — `indusk telemetry address --reset` re-chooses and rewrites the stored address. The brief's clause says the address is picked once, "recorded and never changed", and the ADR's Risks left a re-choose command as Sandy's call. A30 (the row asserting that `--reset` is the only way the address changes) adopts it with no brief line behind it.
- `apps/indusk-mcp/src/lib/promises/status.ts:60` — `promises status` now prefixes break counts with "broken —" or "broke — fixed —" from `healthOf`'s incident or newest rule, in the single-source case too (`commands/promises.ts:107`). A34, a regression guard over `a-promise-is-upheld-or-broken`, covers only the production-plus-local case; nothing in this brief promises a change to `promises status` wording.
- `apps/indusk-mcp/src/lib/eval/otel.ts:344` — The evaluator's log export is re-routed (an explicit logs endpoint, else the shell's `OTEL_EXPORTER_OTLP_ENDPOINT`, else the daemon's logs port), with a new no-op fallback. The brief does not promise it, and the impl's Out of Scope gave it to `a-new-project-starts-instrumented` unless Sandy took it here.
- `apps/indusk-mcp/src/lib/telemetry/daemon-reports.ts:379` — Every promise reader now writes a per-project stamp file (`telemetry-read-report.<project>.stamp`) into the InDusk home, and nothing removes it. With the 2,663 registry entries the brief mentions, nothing bounds how many accumulate.

## Which rejected ADR alternative does the code quietly take?
- `apps/indusk-mcp/extensions/local-telemetry/manifest.json:10` — The extension's `telemetry-daemon-running` health check still judges the daemon by `process.kill(pid, 0)` on the recorded PIDs. That is "Liveness only (`kill(pid, 0)`) for readers", which the ADR rejected because a recycled PID reads as the daemon. Its sibling check at line 14 judges by a port answering, which "Identity by a port answering…" rejected. Both read `~/.indusk/telemetry.json` from `homedir()`, ignoring `INDUSK_HOME`. A7 names "extension health check" among the reads it covers, yet the file is untouched.

## What else would have to change for each promise to hold?
- `apps/indusk-mcp/extensions/local-telemetry/manifest.json:10` — For `a-read-never-loses-the-daemon` and `a-lost-daemon-is-found`, the health checks would have to go through `resolveLocalDaemon`, for example a `indusk telemetry status --json` exit code. Today, with the record lost, they report the daemon down while it runs and never find it.
- `apps/indusk-mcp/src/bin/commands/init.ts:487` — For the clause "what `init` hands an application read[s] that stored address", `init` and the instrumentation templates (`templates/instrumentation.ts:32`, which fall back to a console exporter when `OTEL_EXPORTER_OTLP_ENDPOINT` is unset) would have to write the address. Neither is in `stat`. Until `a-new-project-starts-instrumented` lands, an application reaches the daemon only when a person copies the address by hand.
- `apps/indusk-mcp/extensions/local-telemetry/.env.example:22` — For "never assume one", the shipped reference card still names the block ports as values to copy into `.env`. On a machine with picked ports they are wrong. This repo's installed copy, `.indusk/extensions/local-telemetry/.env.example:32`, still names 16686.
- `packages/telemetry-binaries-shared/README.md:56` — The shipped binaries' README still tells a person to query `localhost:16686`, a port the laptop daemon no longer uses once it moves onto the block.
