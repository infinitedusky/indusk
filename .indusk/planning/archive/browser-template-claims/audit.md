# Audit — browser-template-claims

## Does each row prove its promise's sentence, or something narrower?
- `brief.md:17` — promise `a-propagation-entry-covers-what-it-names` has four clauses: path coverage, default port tolerance, "to no others", and "an exact entry and a pattern entry treat both the same way". Rows T1, T2, T3, T6 name it. Together they prove path coverage for one exact and one pattern entry, and default-port tolerance for pattern entries only. They do not prove the parity clause.
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:216` — T1 (exact entry with path: `/v1/seats` covered, `/v2`, `/v10` not) proves the path clause for exact entries only. Narrower than the sentence: no query-string, no trailing-slash entry (`https://api.example.com/v1/`) and no case where the request URL carries an explicit default port.
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:243` — T3 tests only a pattern entry with `:443` and a request that omits the port. The sentence's "an entry with a default port" covers exact entries too; an exact entry with `:443` is not exercised by any row of this plan (it rests on an earlier plan's A-cases), and `:80` under `http` is never exercised.
- `apps/indusk-mcp/templates/instrumentation.web.ts:111` — the parity clause is false for a trailing slash. An exact entry `https://api.example.com/v1/` is trimmed to `/v1` and matches `/v1/seats`; the pattern entry `https://*.dev.example.com/v1/` is not trimmed (`entrySource` keeps the `/`), compiles to `...\/v1\/(?:[/?#]|$)`, and matches neither `/v1/seats` nor `/v1`. Checked by evaluating the shipped regex logic. `https://*.dev.example.com/` matches only a request starting `//`. No row covers it, so the promise as worded ("treat both the same way") is not proven, and is untrue for this case.
- `apps/indusk-mcp/templates/instrumentation.web.ts:147` — the same asymmetry applies to a query on an entry: an exact entry has its query dropped by `new URL(...).pathname`; a pattern entry keeps it literally. Unrowed; unpromised in the docs, but it is a "treated the same way" divergence.
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:253` — T4 is a regression guard for a "Not promised" limit; it proves the limit, not any promise. Honestly labeled in the trajectory.
- `apps/indusk-mcp/src/__tests__/otel-docs-claims.test.ts:20` — T5/T7 prove that sentences matching a keyword heuristic (`follows the click` + `.then(`/timer/ES20xx, minus a phrase allow-list) are absent. That is narrower than "the docs say only what the template does": a reworded claim without those tokens (for example "a promise chain keeps the click's trace" or "async callbacks inherit the click") passes.
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:276` — T6 (path case) proves path case-sensitivity for one exact and one pattern entry, and host/scheme case for one exact entry; a pattern entry with an upper-case host or scheme is not tested, though `entrySource` lower-cases both.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/templates/instrumentation.web.ts:111` — path matching is now case-sensitive. The brief's promise sentence says nothing about case; the decision ("a server tells /Admin from /admin") came from the falsification phase and appears in the docs (`apps/docs/src/reference/tools/otel.md:302`) and the changelog, never in the brief or the approved trajectory (T1-T5). T6 and T7 were added to the impl trajectory after approval.
- `apps/indusk-mcp/templates/instrumentation.web.ts:114` — an exact entry's query string and fragment are silently discarded (only `origin + pathname` is kept). An entry `https://api.example.com/v1?x=1` therefore covers every `/v1` request regardless of query. Unpromised and undocumented.
- `apps/indusk-mcp/templates/instrumentation.web.ts:114` — trailing slashes are trimmed from exact entries only (`replace(/\/+$/, "")`); a pattern entry with a trailing slash is a dead entry with no warning (the warning at line 104 covers only a missing scheme).
- `apps/indusk-mcp/templates/instrumentation.web.ts:111` — scheme and host are lower-cased for patterns, so `HTTPS://*.Dev.Example.com` works; promised nowhere.
- `apps/docs/src/reference/tools/otel.md:302` — the docs say "a pattern entry follows the same rule" and "exact and pattern alike", which asserts more parity than the code delivers (trailing slash, query).
- `apps/docs/src/reference/tools/otel.md:302` — the page's first bullet still opens "An entry without `*` is an exact origin (scheme, host and port)" and then says an entry carries a path; the two sentences in one bullet describe different things.
