# Audit — decided-prompts-stay-closed

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-admin/src/components/session/SessionPanel.test.tsx:288` — For `a-prompt-shows-only-when-a-person-must-choose` (the panel offers a choice only for a request waiting on a person), rows A1 and A2 (a build's inside write shows already allowed, an outside write already denied with the reason) are proved in two halves that never meet. The panel half renders a hand-built `[permission, decided]` list. The package half (`build-session.test.ts:195`) reads the events through the build's own `onEvent`, not through `subscribe`, which is what the panel's event stream reads. No row runs a build's events through the real event stream into the panel. The pairing is enough today only because `decisionsOf` ignores the order events arrive in (see the next section).
- `apps/indusk-mcp/src/lib/session/manager.test.ts:280` — Row A5 (a planning session's auto-allowed write appears in the log as allowed) covers only the planning path (`decideBuildPermission`). The confined path a new-project draft takes (`decideConfinedPermission`, `manager.ts:135`) also now records a `decided` event, and no row exercises it. Row A4 (`conversation-turns.test.ts:171`, the new-project thread lists a rule-decided request as not waiting) feeds `turnsOf` a hand-built `decided` event, so nothing shows that a draft's rule decision ever produces one.
- `apps/indusk-admin/src/components/session/SessionPanel.test.tsx:316` — For `a-decided-request-stays-decided` (every request appears in the panel's log and stays done after a reload or reconnect), row A6 (a person's allow or deny shows their outcome, and a panel connecting afterwards shows it decided) renders only a person's *deny* in the panel. The sentence's "allowed" outcome for a person's click is covered by `manager.test.ts:293` alone, not in the panel.
- `apps/indusk-admin/src/components/session/BuildControls.tsx:131` — The same promise says "every request appears in the panel's log … and it stays done after the page reloads". Every row checks a single running session. A build is a series of step sessions, and the panel is keyed by each step's `sessionId`, so a step's requests leave the log when the next step starts. Once a step ends, its events are gone (`manager.ts:164` deletes the holder, and the events route returns 404). The rows prove "stays decided while this step's session runs", which is narrower than the sentence.
- `apps/indusk-admin/src/components/new-project/ConversationThread.tsx:158` — Row A4 is filed under the promise that a prompt shows only when a person must choose, and for the thread it proves exactly that: a rule-decided request is not waiting. But in the thread a decided request is not drawn at all. `turnsOf` keeps only `waiting` items, and `TurnView` passes no `decision`. So a draft conversation, which uses the thread in place of the session panel, never shows a request "as done with its outcome". No row is aimed at that, and the docs claim the opposite (next section).
- `apps/indusk-admin/src/components/session/use-answered-requests.test.tsx:14` — Rows A10 (a refused reply brings the buttons back) and A11 (one hook closes a request on click and reopens it on refusal) are tagged `promise: a-prompt-shows-only-when-a-person-must-choose`. They assert the opposite case: a request still waiting keeps its buttons after a failed reply. That is a real behaviour, but it is not the promise's sentence, which is about decided requests not offering choices.
- `.indusk/planning/decided-prompts-stay-closed/impl.md` — Row A8 (a live check: watching a real build in the cockpit, no prompt is left undecided and a reload leaves every one decided) is the only row that covers a real build end to end and the brief's expectation. Its evidence is "recorded in this impl, Build Phase 2", which is outside this audit's inputs. Its `passing` state could not be checked.

## What does the diff change that no row touches?
- `apps/docs/src/reference/admin-ui/sessions.md:16` — The docs say "In the panel and in the project conversation's thread, a request with a `decided` event … shows *Allowed* or *Denied — the reason* … *Answered*". The thread never draws a decided request (`ConversationThread.tsx:158` renders only `turn.waiting`, with no `decision`). No row checks the thread's outcome line, so nothing prevents the docs and the code from staying apart.
- `apps/indusk-mcp/src/lib/session/manager.ts:176` — For a build, `record` pushes the permission and then calls `opts.onEvent`. Inside that call `build-session.ts:114` replies, which records the `decided` event and notifies listeners. Only after that does the outer `record` notify listeners of the permission. So a live subscriber (the panel's event stream) hears `decided` before the permission it decides, while the stored `events` array, which is what replays on reconnect, has them in the right order. No row checks the order a live listener hears. Nothing prevents a future consumer that reads events in order, such as an incremental reducer in place of today's whole-list `decisionsOf`, from treating the permission as undecided.
- `apps/indusk-admin/src/components/session/SessionPanel.tsx:80` — Every `decided` event gets its own `<li>` in the log, and `EventView` returns `null` for it, so each decision adds an empty, gap-spaced list item. No row looks at the rendered log's structure.
- `apps/indusk-admin/src/lib/new-project-session.ts:45` — Because `decideByRule` now records into `holder.events` and notifies listeners, a draft's `transcript.jsonl` (appended by this subscriber) now gains every confined rule-decided permission and its `decided` line. A refused one is also still written as a separate `refused` line through `onRefused`. A reopened draft replays these through `historyBefore`. No row covers a reopened draft's transcript or `conversationFigures` reading it.
- `apps/indusk-admin/src/components/new-project/use-project-session.ts:19` — `post` now returns `false` when there is no session id, and `SessionConnector.tsx` returns `r.ok`, which is what reopens a prompt. Rows A10 replace `onAnswer`/`onDecide` with mocks, so the real wiring from a failed HTTP reply to a reopened prompt is not exercised.

## What does the code do that the brief never promised?
- `apps/indusk-admin/src/components/session/use-answered-requests.ts:30` — When the server refuses a click, the prompt reopens with its buttons back (rows A10 and A11, added in Build Phases 3 and 4). The brief has no promise, expectation or scope line about refused replies. Its promises cover decided requests only.
- `apps/indusk-admin/src/components/session/QuestionView.tsx:113` — An answered question shows "Answered — question: answer", and the `decided` event carries the person's `answers` (`start.ts`, `manager.ts` `decidedBy`). The brief names the outcomes as "allowed, or denied with the reason", and neither the brief nor the approved impl's event shape includes answers (row A9 was added at Build Phase 3).
- `apps/indusk-mcp/src/lib/session/manager.ts:183` — A draft's confined rule decisions, which used to be dropped before the log, are now written to the draft's on-disk `transcript.jsonl` along with the person's answers to questions. This is a new kind of persisted content in a draft, and no brief line speaks to it.

## What else would have to change for each promise to hold?
- `apps/indusk-admin/src/app/api/sessions/[id]/events/route.ts:18` — For `a-decided-request-stays-decided` ("stays done after the page reloads"), the log comes only from the manager's in-memory holder, and this route refuses with 404 once the session has ended. A reload after a build step finishes, or after the admin daemon restarts, shows none of that step's requests. For the promise to hold beyond a running session, a build's session log would need to be persisted and served, as a draft's `transcript.jsonl` is. This plan did not touch the route.
- `apps/indusk-admin/src/components/session/BuildControls.tsx:131` — The build panel is remounted per step (`key={sessionId}`), so "every request appears in the panel's log" holds per step, not per build. Keeping earlier steps' decided requests visible would need this component, or a build-level log, to change. The plan did not touch it.
- `apps/indusk-admin/src/components/session/use-session-events.ts:50` — "Stays done after … the panel reconnects": on any stream error the hook closes the source and marks the session not running, with no reconnect. Only a page reload reconnects. The promise's reconnect case rests on this untouched file.
- `apps/indusk-admin/src/lib/decisions-reader.ts:40` — The cockpit's Needs you and decision card read `manager.pendingQuestion`, which uses the manager's private `answered` set (`manager.ts:268`), not the `decided` event. `a-prompt-shows-only-when-a-person-must-choose` holds on that surface only because `reply()` updates both. Nothing prevents a future path that records `decided` without adding to `answered`, or the reverse, from showing a question as waiting there that the panel shows as done.
- `apps/indusk-admin/src/lib/new-project-session.ts:45` — A draft keeps its decisions after a reopen only because this untouched subscriber appends every listener event to `transcript.jsonl`. The approved impl's Build Phase 1 assumed `opts.onEvent` did that, but `decideByRule` deliberately does not forward to `opts.onEvent` (`manager.ts:189`), so persistence depends on this subscriber staying in place.
