# Audit — display-names

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/lib/promises/display.ts:87` — The promise `a-plan-shows-when-it-shipped` says a plan shows "the release version and date that shipped it, or that it is not released yet." Rows A12 and A13 (trajectory rows asserting that the earliest changelog release naming the plan is found, and that a landed plan in no release reads `released: null`) pass only against a made-up changelog written in the `(my-plan)` style. On the real repository, `readHealthNames` gives 94 landed plans, and 79 of them read "not released yet", among them `day-promises`, `dawn-verify` and `context-tiers`, which all shipped. Those changelog entries name the plan as `/decisions/day-promises` (changelog.md:378) or as "(`dawn-verify`, Component 6…" (changelog.md:612), and the regex rejects both. Only 52 of 347 bold changelog entries carry a bare `(plan-name)`. So the ADR's "as every entry does" is false, and the panel tells a person something untrue. A10, the live-check row, only requires `shipped > 0` (`apps/vscode-extension/e2e/live.e2e.test.ts:79`), so 15 correct groups out of 124 pass it. High confidence.
- `apps/vscode-extension/src/core/panel-html.ts:36` — The same promise says "wherever the editor names a plan" it shows the dates. A broken card names its plan ("plan VS Code extension") with no dates; only group headings carry `planWhen`. No row asserts dates on a card. The test that does check panel dates is labelled A5 (`names.test.ts:85`), not A11 or A13, and A11 to A13 test `planDates` output in the package, not what the panel shows.
- `apps/indusk-mcp/src/lib/promises/display.ts:133` — "When it landed": for 10 archived plans with no retrospective (`local-telemetry`, `doppler-extension`, `context-budget`, …), `landed` is the impl's frontmatter `date`, which is when the impl was written. A14, the row added in Build Phase 3 for archived plans with no landing line, says "dated by its retrospective's `date`". It does not cover this impl fallback, so a guessed date passes as a landing.
- `apps/indusk-mcp/src/lib/promises/after-close.ts:43` — The promise `display-names-are-defined-once` says a plan's dates are "worked out in one place in the package". `closedAt` in the package is a second reader of the same "Landed on main at …" line, with a different regex and a different fallback (retrospective date, else null, where `planDates` falls back to retrospective, then impl). It feeds the admin's "closed" date in the monitor window. On the real repo the two disagree for those 10 archived plans: `display.landed` is a date, `closedAt` is null. A8, the single-definition row, only scans `apps/indusk-admin/src` and `apps/vscode-extension/src`, so it cannot see a second definition inside the package.
- `apps/indusk-mcp/src/__tests__/display-names-single-definition.test.ts:44` — A8 is narrower than "a second definition … fails the build". It matches only functions named `promiseWords|planTitle|planDates` and two literal spellings, `replace(/-/g, " ")` and `replaceAll("-", " ")`. A `split("-").join(" ")`, an arrow function under another name, or a regex over "Landed on main at" in the admin would all pass.
- `apps/indusk-mcp/src/lib/promises/display.test.ts:44` — The promise `a-promise-reads-as-words` relies on A3, a row asserting "a project can name its own product words". A3 hands a map straight to `promiseWords`. The project's actual mechanism, `display.words` in `.indusk/config.json` read by `displayWords` (display.ts:138), is never exercised by any test.
- `apps/vscode-extension/src/extension.ts:137` — The same promise says "wherever the editor names a promise in prose". The break notification, "`${b.promise} is broken in …`", and the quick-fix title "Fix ${m.promise} with Claude" (extension.ts:209) still show the handle. A1, the row asserting words on card, row, activity and hover, covers only the four places the brief lists, so the promise as worded ("wherever") does not hold.
- `apps/indusk-mcp/src/lib/promises/display.ts:177` — The promise `a-plan-reads-by-its-title` says the title comes "from its brief". A5, A6 and A7 (panel uses `planTitle`; `planTitle` falls back to the folder; `healthLine` passes titles through) all start from a title already in hand. No row reads a real `brief.md` through `readHealthNames` and checks the title, so the actual brief-to-title path has no test. The A14 test reads only `planDates` out of `readHealthNames`.

## What does the diff change that no row touches?
- `apps/indusk-mcp/src/bin/commands/promises.ts:473` — `promises health` now calls `readHealthNames` every line with no guard, unlike the registry read just above it, which keeps the last good result. If reading a plan folder throws on the first `once()`, the whole command fails and the editor shows "stopped reading". On later ticks a whole health line is dropped. Promise health is now hostage to plan-name reading. No row calls the CLI. A7 calls `healthLine` with names written by hand. Moderate confidence that a throw is reachable (a folder removed between readdir and read).
- `apps/indusk-mcp/src/lib/promises/display.ts:87` — The comma-list form of the release regex (`(a, my-plan)`) and the escaping of regex characters in plan names are untested.
- `apps/indusk-mcp/src/lib/promises/display.ts:175` — When a plan name exists both active and archived, the active folder wins and the archived one is skipped. No row covers this.
- `apps/indusk-mcp/src/lib/promises/display.ts:138` — `displayWords` (config read, lowercasing keys, dropping non-string or empty spellings, swallowing errors) has no test.
- `apps/indusk-mcp/src/lib/promises/display.ts:116` — Archived plans get a `released` lookup even with no landing date (`landed || opts.archived`). That can show "started …" alone while the release is computed and then discarded by `whenWords` (panel.ts:99, which hides `released` when `landed` is null). No row covers it.

## Which rejected ADR alternative does the code quietly take?
- `apps/vscode-extension/src/core/panel.ts:99` — `whenWords` builds the sentence "started …, landed …, released X.Y.Z (date)" / "not released yet" inside the extension. The ADR's rejected alternative "Words computed in the extension" ("fails A8 the day the admin names a promise") applies equally here: plan-cockpit, the next plan, will have to write a second copy of this phrasing. The package defines the dates; the extension defines how a person reads them. Moderate confidence that this counts, because the ADR's rejection names promise words, not date wording.
