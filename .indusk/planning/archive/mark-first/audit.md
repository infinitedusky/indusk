# Audit — mark-first

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-mcp/src/lib/promises/clause-proof.ts:225` — Narrower, for `verified-before-release` (the clause: a clause's tests pass before anything ships, and a change that breaks one is stopped before release). A1, A2, A3 and A36 are the rows asserting that closing and landing refuse a clause whose test fails or ran nothing, naming the clause. They prove this only when the plan that owns the promise closes or lands, because `clauseTestPlan` selects `p.owner === plan`. After that plan closes, a later plan whose change breaks one of its clause tests is never refused by clause. Release (`lib/release/run.ts`, `route.ts`) runs no clause half, and the project rule is that the slow tier never blocks landing or release. So "stopped before release" holds only for the owning plan's own landing. A3 (the row asserting a failing test is reported against the clause its file names) is likewise proved only for the close/land refusal text, not for "a person reading a red suite".
- `apps/indusk-mcp/src/__tests__/clause-signal.live.test.ts:71` — A11 is the live-check row asserting a clause's signal reaches the real daemon and reads upheld end to end. It proves less than its sentence in two ways. First, the child process writes spans directly with `commandTracer()` + `markPromise`, so the CLI path is never exercised: `indusk promises confirm` → `markClosing` → `localSignalReader` → `confirmPlan`. Second, the whole file is `describe.skipIf(!live)` unless `INDUSK_LIVE_CHECK=clause-signal`. That also bears on this plan's own close. The row names this file for `upheld-by-its-signal`, and the clause test runner refuses a file whose every test was skipped (A36). So mark-first's own `promises confirm` fails on its tests half for that clause unless the person knows to export the variable. Nothing in the refusal text tells them to.
- `apps/indusk-mcp/src/lib/promises/closing-signal.ts:44` — Narrower, for `upheld-by-its-signal` (a clause is upheld only when its signal reported it upheld in a real run; a passing test never stands in). The signal for this promise's own two closing clauses is written as `broken = result.ok && half.refused.length > 0`. A close whose clause halves refused always returns `ok: false` (`confirm.ts` returns early), so the broken branch cannot be reached, and every refused close writes `upheld`. That includes a close refused precisely because no signal had reported. A first `indusk promises confirm mark-first` therefore produces the signal that lets the second one pass. The A9/A10 rows (closing refuses when a half is missing; a close that passes enforces) pass, but they do not show that the signal was earned by anything other than running the command.
- `apps/indusk-mcp/src/lib/promises/standing.ts:322` — Narrower, for `no-signal-is-not-holding` (a clause with no report, or a blind watcher, never reads as holding). A15 is the row asserting a promise made only of resting clauses takes the standing of what it rests on. A resting clause on a pre-clause promise reads `holding` whenever that promise is `enforced`, whether or not anything has reported. Yet the admin draws that same promise grey "no signal" (`readsNoSignal`, `held === null`). So a clause resting on a silent enforced behaviour promise reads holding with no report behind it. A12 (never-reported reads no signal), A14 (the worst clause decides) and A38 (the admin's grey dot) never build that case.
- `apps/indusk-mcp/src/lib/promises/health.ts:510` — Narrower, for `no-signal-is-not-holding`'s "everywhere it is shown". A12 and A38 are the rows asserting no signal on the promise page, in `promises status` and in the admin list. `healthOf`, which feeds the admin chips, `promise_health` and the editor's `promises health --json`, is untouched. It still gives a behaviour promise a green chip on any `lastUpheld`, even when one of its clauses never reported. It gives no chip at all to a state promise with clauses.
- `apps/indusk-mcp/src/lib/promises/clause-standing.ts:67` — Narrower, for the parent sentence of `a-clause-is-proved-twice` ("upheld only when both say so"). Standing as shown by status, the admin and the promise page takes no test input (ADR D4, A5). After a close, a clause whose test now fails but whose signal is upheld reads `holding` everywhere it is shown. "Both say so" is checked only at the moment of close or land.
- `apps/indusk-mcp/src/lib/promises/telemetry.ts:442` — Narrower, for A7 (the row asserting a broken signal reads broken and opens an incident naming the clause). A34 is the row asserting an `upheld` span measured past its bound reads broken for a limit. That path reads broken in standing and at close, but the recorder's `violations` keep only `outcome === "broken"` (`watch.ts:126`). A limit broken by measurement therefore opens no incident and reopens no owner, which A7's sentence says it should.
- `apps/indusk-mcp/templates/signal.ts:58` — Narrower, for `a-break-names-its-clause` (the signal's event names the promise and the clause). A16 is the row asserting the break event carries both, and it is proved only for InDusk's own `markPromise`. The app helper (`templates/signal.ts`, `signal.py`, the demo's `signal.ts`) still writes an event carrying only the symptom. The incident still names the clause, read from the span (A17, A33), but "the signal's event" does not for any application.
- `apps/indusk-mcp/src/__tests__/suite-speed.test.ts:100` — A31 is the row asserting the suite-speed script and the demo write `broken`. Both halves are source-text regexes that were green before any build phase (the script marks no promise at all, and the demo already wrote `broken`). They prove that a word is absent, not that a writer writes `broken`. The approved Test Phase 1 expected them red.
- `apps/indusk-mcp/src/__tests__/signal-word.test.ts:22` — A30 is the row asserting no skill, tool description, comment or doc page calls a promise's telemetry a mark. It matches a fixed phrase list. Forms such as "every mark it has read" (`store.ts`) or "the marks came from" (admin tests) pass it. It does not scan `templates/planning/CLAUDE.md`, the admin app or the editor extension, so it proves the listed phrases are gone, not the word.

## What does the diff change that no row touches?
- `apps/indusk-mcp/src/lib/telemetry/command-tracer.ts:31` — The command tracer, a carried item with no row (it was deferred). It caches its provider for the life of the process at the address found on the first ask. A long-lived MCP server or admin daemon keeps exporting to that address after the daemon moves. Its "silent when no daemon runs" half has no check at all.
- `apps/indusk-mcp/src/lib/new-project/create.ts:344` — `new_project.create` now goes through a separate, unregistered provider with `service.name=indusk`, and flushes it in `finally`, instead of the process's global tracer. Nothing in the trajectory notices if the span stops arriving or arrives under another service.
- `apps/indusk-mcp/src/lib/promises/closing-signal.ts:44` — Every `promises confirm` (CLI and MCP tool) now writes one `promises.confirm` span per half to the daemon. No trajectory row names `closing-signal.test.ts`.
- `apps/indusk-mcp/src/lib/promises/record.ts:168` — Every recorder pass now writes a verdict span for each incident it opened from a clause's break. No trajectory row names `record-clause-break.test.ts`.
- `apps/indusk-mcp/src/lib/promises/incident-signal.ts:57` — That verdict span carries no `indusk.project`. The reader keeps spans with no project tag for every project (`telemetry.ts:370`), and the daemon is shared by the whole machine. Nothing prevents a recorder pass in another project from making dusk's `a-break-names-its-clause` read holding, and no row covers it.
- `apps/indusk-mcp/src/lib/promises/watch.ts:126` — Upheld spans measured past their bound are left out of the recorder's breaks. Nothing in the trajectory would notice that difference between standing and incidents (see the first section).
- `apps/indusk-mcp/src/lib/promises/closing-inputs.ts:36` — Closing or landing a clause plan in a project with no `verify.testRunner`/`testCommand` is now refused ("names no test command"). No row asserts that refusal or its wording.

## Which rejected ADR alternative does the code quietly take?
- `apps/indusk-mcp/src/lib/promises/status-signal.ts:33` — This is close to "a signal derived from the test that proves the same clause", which the ADR rejected because it runs the same check elsewhere and fails exactly where the test would. The signal of `no-signal-is-not-holding` re-checks whether `clauseStanding` ever returned `holding` without a report. That is the predicate A12 and A5 already assert, computed by the same function. Its heartbeat input is hard-coded `true` (`promises.ts:109`, `status.ts:57`), so the blind-watcher half can never report broken. It can only fire when the code A12 tests regresses.
- `apps/indusk-mcp/src/lib/promises/closing-signal.ts:44` — The same pattern. The closing signal reports broken only when `confirmPlan` accepted despite a refused half, which is the invariant A1 and A9 assert. It cannot be reached in the current control flow. It watches the decision code's consistency, not anything a test did not choose.
- `apps/indusk-mcp/src/lib/promises/closing-signal.ts:44` — This leans toward "the agent states in the impl that a signal reported", which was rejected because "every proof that an agent can state without anyone reading it can be gamed". Nothing is written in the impl. But an agent running `indusk promises confirm` twice manufactures the `upheld` reports for this plan's two closing clauses, because a refused close writes upheld (moderate confidence that this is the same failure the ADR rejected).
