- `apps/indusk-mcp/src/lib/admin/daemon.ts:102` — `daemonStart` now spawns with `env: daemonEnv(opts)` instead of building the object inline. No row checks that `daemonStart` uses `daemonEnv`: a revert to the inline object would keep T1 green, because T1 calls `daemonEnv` directly.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/session/start.ts:33` — `sessionEnv` strips the handed root from every Claude session the admin starts (`start.ts:99`). The brief's scope is "the daemon's environment and a server module only" (brief Looks line), and the approved impl's Notes say the opposite: the variable is inherited by anything the daemon spawns, "the planning session's `claude`, hooks", and "that is intended". The falsification phase reversed an approved decision without an amendment. The change is defensible, but it was never promised or re-approved.
- `apps/indusk-mcp/src/lib/admin/daemon.ts:75` — `daemonEnv` drops an inherited `INDUSK_MCP_PACKAGE_ROOT` when no root is passed. The approved impl specifies this (Build Phase 1, second item), but no promise or expectation in the brief asks for it. It is a safety choice made in the impl.
- `apps/indusk-mcp/src/lib/package-root.ts:32` — The handed root is honoured by every process that inherits the variable, not only by code in the admin's bundle. That includes non-session children the admin spawns, such as `create.ts:419` running `dist/bin/cli.js` and the hooks `read-planning` runs with `process.execPath`, and any shell where a person exported the variable. The brief speaks only of "code inside the daemon". This broader reach is intended in effect but never stated.

## Which skip reason would you not accept?
- `.indusk/planning/the-admin-knows-the-package-root/impl.md:13` — The reason given for skipping cleanup, "two env-stripping spots are below the rule of three", is acceptable on its face. However, `daemonEnv` (`daemon.ts:75`) and `sessionEnv` (`start.ts:33`) are the same rest-destructure of `PACKAGE_ROOT_ENV`, and they enforce opposite policies about one variable in two modules. The more useful cleanup question is whether one helper should own "who may see the handed root", not duplication count. This is low severity; I would accept the skip.
- `.indusk/planning/the-admin-knows-the-package-root/test-plan.md:57` — The test plan says "Untestable Assertions: (none needed — … A2 and A3 depend on a built admin bundle and a running daemon, which the slow tier provides)". A2 and A3 are the test plan's two live-check assertions: that the lookup inside the production bundle returns the right folder, and that a planning run there ends "ready for approval". T6 and T7, the impl rows that carry them, are `skipped` with a `manual:` procedure. No slow-tier test file exists for either; `stat` adds none and the trajectory names no `vitest.tiers.ts` entry. So "the slow tier provides" them does not hold: they are untested until someone runs the procedure by hand. I would not accept this reason as written.
- `apps/indusk-mcp/src/lib/package-root.test.ts:7` — The impl allowed the test to declare `const ENV = "INDUSK_MCP_PACKAGE_ROOT"` as a literal so the file could load before `PACKAGE_ROOT_ENV` existed. That reason expired at Build Phase 1, when the constant landed. The literal remains, so renaming the constant would leave this test checking a variable nobody sets, and the T4 fallback cases would still pass vacuously. Not a skip row, but a deferral whose reason no longer holds.

## What else would have to change for each promise to hold?
- `apps/indusk-mcp/src/bin/commands/ui.ts:84` — When a daemon is already running, `uiStart` returns early without restarting it. `pnpm install:local` (`package.json:11`) does not restart the admin either. An admin started before this fix keeps running without `INDUSK_MCP_PACKAGE_ROOT`, and its planning runs keep ending "cannot continue" until someone runs `indusk ui restart`. Neither the changelog nor any landing step says so; only T6 and T7's manual procedures were updated to use `restart`. Untouched file, needed for the promise to hold after landing.
- `.indusk/promises/an-accepted-brief-is-planned-unasked.md:15` — The promise's `tests:` list does not include `package-root.test.ts`, `daemon-env.test.ts` or `start-env.test.ts`, and its `sites:` list does not include `package-root.ts`, `admin/daemon.ts`, `bin/commands/ui.ts` or `session/start.ts`. A later change that breaks the hand-off would not run under the promise's tests. The tests do carry the `promise:` token, so whether that is enough depends on how `indusk plans tests` resolves a promise's tests.
- `apps/indusk-mcp/src/lib/package-root.ts:33` — A daemon outlives its install (test plan Decision 3). If the install it was handed moves or is removed, `holdsThisPackage` rejects the stale value and the lookup falls back to the walk-up. Inside the bundle, that walk-up is the broken `apps/apps` path. The trust check therefore turns a stale root into the original failure rather than a correct lookup; nothing logs that a handed root was rejected, so the failure looks like the bug this plan fixed. Recovery again depends on a restart that nothing triggers.
- `apps/indusk-admin/src/lib/project-root.ts:1` — The admin's other environment-handed root (`INDUSK_PROJECT_ROOT`) is read through its own module. If `next dev` or any admin start path other than `indusk ui` is used (for example during admin development), no package root is handed and the bundle's walk-up is what runs. The brief scopes this out by naming `indusk ui` as the admin's only starter. That holds for `lib/admin/daemon.ts`, but any dev-mode planning run in the admin would still fail (confidence: moderate; I did not verify whether dev mode rewrites `import.meta.url` the same way).
