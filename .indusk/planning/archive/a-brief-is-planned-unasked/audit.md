## Does each row prove its promise's sentence, or something narrower?

It asserts that a look is "approved last" by calling `startPlanning` twice, with a faked read in between. No row checks that the look-approval route actually calls `startPlanning` (`apps/indusk-admin/src/app/api/looks/[app]/approve/route.ts:208`), or that `indusk plans accept-brief` reaches the admin. `ask-admin.test.ts` covers the second, but it is not a row on the trajectory. Observed.
- `apps/indusk-admin/src/lib/build-host.test.ts:38` — Narrower. T2, T11, T12, T19 and T21 are the host rows for `starts-on-acceptance` and the one-run-per-plan rule. Every one of them mocks `readPlanningState` and `runPlanning`. So no row ever runs the real reader, the real runner and `runStepSession` together. The only row that would is T9, the end-to-end live check, and it is skipped. Observed.
- `apps/indusk-mcp/src/lib/build/read-planning.ts:173` — Narrower. T4 is the row for `each-document-passes-its-check` (each document passes the contract check and the impl's structure check before the next is written). It tests `nextPlanningStep` over `ok` flags it is handed. The reader sets those flags so that an ADR passes if it is non-empty, and a test plan passes unless a contract refusal names `test-plan.md` (line 171). So the ADR step is never checked, and a contract refusal attributed to the brief or to no file lets the next document be written. The clause's wording promises more than this. Observed for the ADR; inferred for refusals that name no file.
- `apps/indusk-mcp/src/lib/build/build-session.test.ts:259` — Narrower. T5 is the row for "each planning step is told to write only that document". It asserts the prompt's wording only. Nothing checks that a step wrote only its own file. A test-plan step that also writes `adr.md`, edits `brief.md` or touches code moves the loop on, and no row notices. "In order" holds only as far as the session obeys the prompt. Observed.
- `apps/indusk-admin/src/lib/build-host.test.ts:129` — Narrower than it looks. T6 and T2 are the rows for `never-approves` (the session never approves the plan or a look, and never starts the build). They test the `INDUSK_BUILD_STEP` environment refusal inside the calling process. A planning session reaches the admin over HTTP, where the admin's own process never has that variable set, so `startBuild`'s environment check (`apps/indusk-admin/src/lib/build-host.ts:141`) never fires in production. Two other guards actually hold there. One is T16 (`apps/indusk-admin/src/app/api/plans/approve/route.ts:54`, approval refused while a run is going). The other is `startBuild`'s "being planned" refusal (`build-host.ts:145`), and no row covers that one. Inferred from `adminOnly` accepting a forged `Origin` (`apps/indusk-admin/src/lib/session-host.ts:67`).
- `apps/indusk-mcp/src/lib/build/planning-runner.test.ts:61` — Narrower. T7 and T17/T18 are the rows for `decides-and-records` (an open choice is decided and recorded with its reason; a choice the session cannot make ends the run with a blocker). They prove that a `blocker:` line ends the run, and that the prompt asks for decisions to be recorded. Nothing checks that a decision was recorded with its reason. And the run's stop reason lives only in the admin's memory, which nothing displays (see question 6). Observed.
- `apps/indusk-admin/src/app/api/plans/approve/route.test.ts:85` — Narrower. T8 is the row for `approval-starts-the-build` (approving the plan starts the build). It asserts that the approval stands, and the build does not start, when `startBuild` throws (for example, at the session cap). The clause says approving "starts the unattended build". It holds only from the admin route and only when a build slot is free. `indusk plans approve` from the CLI starts nothing. Observed.
