# Audit — browser-telemetry-leftovers

## Does each row prove its promise's sentence, or something narrower?
- `brief.md:19` — Promise 1, `a-click-and-its-server-work-share-a-trace`, says "every request the browser makes to the project's own services ... carries the trace it started in". Its rows (A1, A2, A3 plus falsification rows A9, A10, A11 in the working trajectory) prove a narrower thing: a `fetch()` issued synchronously inside the click handler. `apps/indusk-mcp/templates/instrumentation.web.test.ts:59` fires every URL with `void fetch(url)` before any `await`. A request made after a native `await` is not covered, and the one row that asserts it (A11, `instrumentation.web.test.ts:131`) is `it.skip`.
- `apps/indusk-mcp/templates/instrumentation.web.ts:138-146` — Only `FetchInstrumentation` is registered. Requests made by XHR (axios, many SDKs), `sendBeacon`, `EventSource` and `WebSocket` carry no `traceparent`, so "every request" is false for any project using them. No row names this; the file header still advertises "HTTP requests (fetch/XHR)" at line 4. The impl's scope said "and `XMLHttpRequestInstrumentation` if the template gains it", but nothing makes the template gain it.
- `brief.md:19` — The promise also says "so the server's spans and its promise marks belong to the click". No row asserts anything about promise marks. A4 (the live check) used a plain auto-instrumented Node `http` API (recorded as trace `7e25854e...` in the working impl), not a project with a promise mark. The "promise marks" half is unproven.
- `brief.md:19` — "In a project `indusk init` instrumented" includes Next.js. A1-A3 test the shared template in a bare page; A4 ran a Vite SPA only. The Next.js path reads `process.env.NEXT_PUBLIC_OTEL_PROPAGATE_TO` behind a `typeof process` guard (`instrumentation.web.ts:46,63-66`); Next's build-time inlining of that guarded form is asserted only in a comment, never by a row. A7 proves `init` prints the Next setting name, not that setting it works.
- `brief.md:8-10` — The brief's Expectation ("the next project scaffolded ... shows one trace ... in local Jaeger") is the observable claim. A4 is a one-off manual row whose evidence (trace ids) lives only in the working impl.md and an ephemeral local Jaeger; nothing in a test or a promise mark re-proves it.
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:76-103` — A2 and A3 prove the named origin and pattern are propagated and a third party is not. They do not prove the "origin pattern" case the brief names for preview URLs where the entry carries a port or nested subdomain (`https://a.b.dev.example.com` does not match `https://*.dev.example.com` by design, `instrumentation.web.ts:104`). Documented, but a user reading the promise's "any origin pattern" would not expect it.
- `brief.md:20` — Promise 2, `init-writes-no-vendor-into-an-app`, says "Nothing `indusk init` writes into an application names or imports an observability vendor". A5 (`init-browser-telemetry.test.ts:69-98`) checks only files that appear on a `create:` line inside the `[OpenTelemetry]` section (`otelLines`, `createdPaths`, lines 56-66). Everything else init writes (skills, CLAUDE.md, hooks, extension skills) is not scanned. A6 scans `templates/instrumentation*`, `filtering-exporter.ts` and `logger.ts` only (lines 102-107). It also passes `@vercel/otel`, a vendor-published SDK that `instrumentation.next.ts` imports, because `VENDORS` (line 20) does not list it.
- `brief.md:20` — The second half of Promise 2, "what it prints names the file and the SDK it actually wrote", is asserted only for the React SPA and Next.js. `init-browser-telemetry.test.ts:90` explicitly skips `node`, and the Python branch is never run. For Node, `init.ts` prints `create: instrumentation.ts` / `create: filtering-exporter.ts` / `create: logger.ts` (`init.ts` Node branch, ~line 990) with no SDK named. So passing A5 proves the promise for two of four scaffolds.
- `apps/indusk-mcp/src/__tests__/init-browser-telemetry.test.ts:94` — The SDK check is `/opentelemetry|otel/i`, which also matches `@vercel/otel` and the word "otel" anywhere; it cannot distinguish "the OpenTelemetry SDK" from a vendor wrapper.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/templates/instrumentation.web.ts:92-98` — an entry with no `<scheme>://` is dropped with a `console.warn`; the brief promised propagation to named origins, not entry validation or a console message in every end user's browser.
- `apps/indusk-mcp/templates/instrumentation.web.ts:100,110-116` — exact entries are rewritten through `new URL(entry).origin`, so an entry that carries a path (`https://api.example.com/v1`) is silently reduced to its origin. That is a decision about what a "name" means that nobody wrote down.
- `apps/indusk-mcp/templates/instrumentation.web.ts:105` — patterns are compiled with the `i` flag and a path-boundary suffix `(?:[/?#]|$)`; `*` also matches in the scheme position (`*://`) and in port position. None of that is in the brief; docs state only a subset.
- `apps/indusk-mcp/templates/instrumentation.web.ts:92` — trailing slashes are stripped from every entry.
- `apps/indusk-mcp/templates/instrumentation.web.ts:45-66` — runtime sniffing (`typeof process`) so one file works in both Vite and Next. A scaffold-shape change, not a propagation one.
- `apps/indusk-mcp/src/lib/trajectory/audit.ts:22` — removing `grafana` from the audit keywords (and `dash0`) changes planning-gate behavior for all plans, justified in the working impl by a "vendor name is not instrumentation" rationale; the brief only promised vendor-free scaffolding.
- `apps/indusk-mcp/src/bin/commands/init.ts:228-236` — `init` now prints two extra instruction lines on every React/Next init, including projects with no separate API (the common case). The brief promised the printed lines would be truthful, not longer.
- `apps/docs/src/reference/tools/otel.md` (diff) — documents "a request made after a native `await` ... is in its own trace" as a known limit. The code deliberately ships a behavior the promise's sentence contradicts, and the brief was not amended to say so.

## Which skip reason would you not accept?
- `apps/indusk-mcp/templates/instrumentation.web.test.ts:131` and the trajectory's A11 row (`skipped`, `For: promise: a-click-and-its-server-work-share-a-trace`) — the technical reason (zone.js cannot follow native `await`) holds, but the row stays attached to the promise while `brief.md:19` still reads "every request". The honest outcome of the skip is a narrower promise, or a `Not promised` line in the brief; as shipped the promise is declared intact with a documented hole. I would not accept the skip without an amended brief.
- `A11` skip reason, second half — "unskip when browsers have AsyncContext": no plan owns it, and the working trajectory's own deferral says "no other plan owns it today". A skip with no owner and no trigger that anything watches is a permanent skip.
- `impl.md` frontmatter `cleanup: skipped` / `cleanup_reason` — the reason says it "reviewed all 12 changed files", but `stat` lists 15 (the lockfile, ledger and impl account for the difference only by assumption). It also asserts the `process.env` reads cannot be factored because "Next inlines literal process.env.NEXT_PUBLIC_*"; true for the four reads in `instrumentation.web.ts:48-66`, but the cleanup did not address the near-duplicate `pnpm add` install strings in `init.ts` (Next.js line ~955 and SPA line ~976 differ only by `@vercel/otel pino pino-opentelemetry-transport`), nor the hand-copied `optimizeDeps` list in `vitest.templates.config.ts:15-26`. The skip reason does not hold for the full diff.
- `A4` ("manual: recorded in Build Phase 1", state `passing`) — not a skip, but its evidence is a note inside a working document; a reader without the working impl cannot re-check it. I would not accept "passing" for a promise-bearing live row with no retained artifact.
- Both `(none needed)` items in the Build Phase 2 checklist hold only because of the user's option (b) decision; they record a choice, not an absence of work, and neither updates the brief to match.
