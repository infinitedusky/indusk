# Audit — plan-page-promise-health

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-admin/src/__tests__/plan-parts.test.tsx:199` — A1, the trajectory row asserting that an enforced behaviour promise with a live, unrecorded break is the broken colour on its plan's page, is proved in two halves that never meet: the package half (`apps/indusk-mcp/src/__tests__/plan-parts-health.test.ts:122`) shows `readPlanParts` carries `health: "red"` when it is handed one, and the drawing half renders `PlanParts` with `health: "red"` typed in by hand. Neither renders the plan page or the brief page with health flowing from `readPlanHealth`, and every page test mocks `readPlanHealth` to `{}` (`apps/indusk-admin/src/__tests__/helpers/cockpit-fixture.ts:563`). The clause `broken-reads-broken` says "on its plan's page and its brief page"; the rows prove the component and the reader, not the pages. The brief page has no row at all.
- `apps/indusk-admin/src/__tests__/plan-parts.test.tsx:209` — A2, the row asserting that a broke-and-fixed, holding, no-signal, known-broken and state promise each take the Promises page's colour, hands each health in directly and compares against class names the plan itself chose (`dot` in `apps/indusk-admin/src/components/bars/labels.ts:64-94`). It proves the mapping, not that the package produces `fixed`, `amber` or `unverified` for a real promise in those situations on a plan's page. It also proves "the Promises page's colour" only by the plan's own translation: the Promises page draws no-signal as a hollow chip (`bg-surface`, `border-ink-faint`) and known-broken as a wash (`bg-warn-wash`), while the plan page's dots are filled `bg-idle` and `bg-warn`.
- `apps/indusk-mcp/src/__tests__/plan-parts-health.test.ts:134` — A3, the row asserting the plan's parts read health as the nav's red dot does, checks one case (production holding beside a local break gives `green` and no red plan). The clause `no-rule-of-its-own` says the pages decide no health themselves; nothing in A3 covers the checkout-only promises that `readPlanHealth` adds (`apps/indusk-admin/src/lib/plan-health.ts:22-27`), the one place the plan page and the nav can answer differently (see the next heading).
- `apps/indusk-mcp/src/__tests__/plan-parts-health.test.ts:145` — A4, a row added in a later phase asserting that an enforced behaviour promise "added, or changed to a behaviour promise, on the plan's branch" reads no signal rather than green, tests only the added case. For the changed case, `planPromiseHealth` skips any name the trunk's registry already has (`apps/indusk-mcp/src/lib/promises/health.ts:545`); a promise that is a state promise on the trunk and a behaviour promise on the branch gets no health entry from the trunk (`healthOf` returns null for non-behaviour) and is skipped as an extra, so nothing prevents it falling back to the enforced green — the exact case A4's wording claims to cover.

Nothing tests a promise whose state differs between the two (for example retired on the branch, enforced and broken on the trunk), where the chip's `data-state` and its dot colour would disagree.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/promises/health.ts:504` — a known-broken state or structure promise now gets health `amber` from `healthOf`, so its dot changes from the registry colour `bg-bad` to `bg-warn`. The brief's Not promised line (`.indusk/planning/plan-page-promise-health/brief.md:45`) says a state or structure promise's dot keeps the colour of its registry state; for known-broken ones the code does otherwise. Retired ones get `grey`, which draws the same `bg-idle` as before, so only known-broken ones change colour.
- `apps/indusk-admin/src/lib/plan-health.ts:22-27` — health for promises that only the plan's checkout registers, judged against the trunk's incidents and the alarm source. The brief's promise speaks of "the same health the Promises page shows" and "the source the nav's red dot reads"; neither the Promises page nor the nav knows these promises, so a branch-only promise with a live break can be red on its plan page while the nav's red dot (`apps/indusk-admin/src/app/p/[project]/layout.tsx:95`, `redPlans` over the trunk registry only) stays off. That is the divergence the test plan names as the signal that `no-rule-of-its-own` is broken.
- `apps/indusk-admin/src/components/plan/PlanParts.tsx:81` — a new `data-health` attribute on each promise chip. The brief's looks `brief.approved`, `brief.writing` and `plan.master` say the chips keep their markup; the approved impl planned the attribute for tests, but the brief did not.
