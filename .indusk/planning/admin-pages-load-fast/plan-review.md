## Which way could a clause fail that no signal would see?

- test-plan.md:39 — `one-read-per-page`: the signal is the page-reads report, written only by pages that call `readPageReads`; ways to fail include per-run `ps` from the layout/nav (build-host.ts:188), per-commit `git log` on the scorecards page (vcs.ts:22), `gitCommonDirOf` per worktree on the looks page (layout.ts:83), and API routes; places the promise is shown are the plan, promises, looks, scorecards, research, draft and home pages plus the live refresh and nav. None of the starts made outside the module's own `startProgram` wrapper (impl.md:249, decision 15) are counted, so any sync start in an imported package module is invisible to the count.
  - breaks when: a page or route makes N per-item program starts through an unwrapped call (e.g. `getCommitMessage` per commit, `gitCommonDirOf` per worktree), and the count of wrapped starts stays at 1.
  - answer: nothing — the signal for `one-read-per-page` is already the counted starts in the page-reads report (decision 15); an unwrapped start is stopped at test time by A13 (decision 10, with decision 17's inventory) and seen at run time by the elapsed-time and blocked-time breaks of `never-freezes` (decision 14), so a page of N unwrapped starts is slow and reports broken.
- test-plan.md:59 — `kept-briefly`: failure ways include a bundle-duplicated Map, differing windows on a shared key, `forgetKept` called too often (every Build press, every release end), and a failed read retried on every request. The signal reports `refreshedEarly` only for a successful previous read inside the window; a failing read retried each request (A10 by design) is not counted as refresh.
  - breaks when: `ps` or `git` times out on every request, so each page load pays the 3 s read limit again with no kept reading and no `refreshedEarly` flag, and the report shows only a slow page, if it reports at all.
  - answer: nothing — a page that waits out a failed read is over one second, so the elapsed-time break of `never-freezes` (decision 14, never throttled) reports it on every such load; `kept-briefly` reading upheld there is right, because a failure is never kept by design (decision 5).
- test-plan.md:77 — `never-freezes`: the signal uses `monitorEventLoopDelay` (process-wide) and a 100 ms bound, sent through `after()`; a freeze that happens in a request that does not call `finishPage` (API route, SSE events route, the instrumentation recorder loop, `register()` background work) is attributed to no page and reported nowhere.
  - breaks when: the background recorder pass (`recordBreaks` every `refresh_ms`) or an API route blocks the loop for seconds while a page is waiting; the page report's `maxBlockedMs` is process-wide so it may report it, but under the name of an innocent page, or nothing at all if no page was in flight.
  - answer: nothing — the clause is about the server not answering, so a page report that sees process-wide blocking is the intended detector and a mislabelled page is accepted (decided in the first review); the recorder pass's own starts are moved off the loop by decision 19, and a freeze with no page in flight is a freeze nobody waited on.
- test-plan.md:77 — `never-freezes`, a hung program: the 3 s kill covers `ps` and the merge-subject `git`, but the page waits up to 3 s for it, which exceeds the one-second promise; the signal's `never-freezes` is broken only when elapsed time is over 1 s, which a timed-out read always is, but the report's cause is attributed by the planning text to "a blocked interval", not to the program.
  - breaks when: `git` stalls on a network filesystem (a slow trunk repo), every page takes 3 s on each window expiry and the signal says `never-freezes` is broken though the loop was never blocked, sending the diagnosis to the wrong clause.
  - answer: fix — decision 14's report names the cause: the Build Phase 1 report task writes `elapsed` and `blocked` as separate fields in the broken report's message, so a slow program reads as elapsed-only; no change to the limit.
- impl.md:496 — A route the page-reads module is never called from reads "no signal", and impl.md:496 accepts that residual; the home page and the draft page (listed by A1) show the promise sentence "every admin page" but have no reader that counts.
  - breaks when: the home or draft page is slow, no clause report names it, and `indusk promises status` shows the clauses as unknown rather than broken.
  - answer: nothing — accepted residual, recorded in impl Notes: A1 times every page route at close, and a home or draft page that reads no process list or landings has nothing in the three clauses to break.
- impl.md:355 — The report's own writing: `reportPageReads` swallows errors ("never raises") and `writeClauseSignals` swallows span errors (clause-signal.ts:54-56); a daemon address that is wrong or a tracer not configured in the admin process loses every report silently.

  - answer: nothing — a clause closes only when its signal has reported in a real run and a stopped daemon refuses close (`mark-first`), so a plan whose reports never arrive does not close; "no signal" is the designed reading for it.
