# Audit — admin-pages-load-fast

## Does each row prove its promise's sentence, or something narrower?
- `apps/indusk-admin/scripts/measure-pages.mjs:64` — A1, the trajectory's only live check of the headline sentence "every admin page answers in under a second", proves something narrower. The script drops every route whose parameter it was not given: research and draft (lines 64–65) and the plan document page (line 66, always `null`). It never lists the root page (`app/page.tsx`) or `app/new/*` (line 88 keeps only `/p/<project>/…`). It takes the median of three loads (line 102), so one slow load in three passes. It counts a page as passing on time alone (line 125) and never checks the HTTP status. Its "fresh" load comes after waiting 9 s, but the nav's health, look standing and plan names are served from `standingKept` for up to 60 s, so a "fresh" load is not a cold one. The recorded run gave no `--research` or `--draft` and ran with `INDUSK_SKIP_TELEMETRY_AUTOSTART=1` on a separate `next start`, not on the daemon.
  - breaks when: the first load after the daemon starts (the notes say it still waits for every reading), a load more than 60 s after the last one, the research, draft, document or root page, or a page that answers a fast 500 is over one second or broken, and A1 still exits 0.
  - answer: fix — Build Phase 3 item "Make the page-timing measure time every page, take the slowest of its loads, and fail a page that answers with an error"
- `apps/indusk-admin/src/lib/page-reads.ts:131` — The `one-read-per-page` signal's read counts are constants, not counts: `processReads` is set to `1` (or `0`) and `landingReads` to `1` whatever the readers did. `judgePageReads` (`page-reads-signal.ts:52`) can therefore never see more than one read. A24, a trajectory row asserting that the finish call hands the report "the page's real read counts … not zeros", passes on these constants. A22, the row asserting that a page whose starts grow with its plans reports broken, is a test of the pure judge.
  - breaks when: a page reads the process list or the trunk log a second time outside `page.reads()` (through `readProcessReads`, `readNow` or `keptProcessTable` on a missed kept key), and the report still says one read of each. Only `programStarts` against a bound of 6 per repository could notice, and one extra read stays under that bound.
  - answer: fix — Build Phase 3 item "Count the process-list and trunk-history reads a page really makes, instead of reporting one of each"
- `apps/indusk-mcp/src/lib/run-record/kept-reads.ts:109` — `refreshedEarly`, the only thing that turns `kept-briefly` broken when a reading is not reused, is true only when the clock runs backwards. A fresh read happens only after `age >= max(done.windowMs, callerWindow)`, so `age < done.windowMs` is false whenever age is non-negative. A23, a trajectory row asserting "a load that reads fresh although the last fresh reading was inside the window reports kept-briefly broken", is tested by handing `judgePageReads` a `true` flag (`page-reads-signal.test.ts:132`) and by a backwards clock (`kept-reads.test.ts:244`). The second half of the clause signal (`page-reads-signal.ts:64`, a reading older than its window) reports the stored entry's window while reuse uses the larger caller window (`kept-reads.ts:85,93`). It can fire falsely when the machine-wide `ps` key was stored with 8 s (for example by `endpoint-async.ts:45` off a page) and is reused by a project whose `admin.refresh_ms` gives it a 15 s window.
  - breaks when: the kept readings stop being shared (the `globalThis` slot is lost, a `forgetKept` runs on every page, keys differ per request), every load reads fresh, and `kept-briefly` still reads upheld. Or a project with a refresh over about 5.3 s reads `kept-briefly` broken while the window is holding.
  - answer: fix — Build Phase 3 item "Make the reuse signal notice a page that reads fresh inside the window, and judge a reading's age against the window that reuse used"
- `apps/indusk-admin/src/lib/page-reads.contract.test.ts:47` — A12, the row asserting that "the plan page, the promises page and the looks page loaded one after another … make one process-list read and one trunk-history read together", never loads a page. It calls `startPage` with the labels "plan", "promises" and "looks" over an empty planning folder and calls `reads()` once each. It proves that `readThrough` reuses `keptRead`. It does not prove that the real pages route all their process-list and trunk reads through `reads()`. A2–A4 and A14 are likewise run through `withSituations`, not a rendered layout and page.
  - breaks when: a real page or the layout reaches a process list or trunk log through another path (`onThisPage` in `telemetry/status.ts:154`, `look-standing.ts:263`, `firstParentLogAsync`), and A12 stays green.
  - answer: signal — a page reads the process list and the trunk history at most once; `reportPageReads` in `apps/indusk-mcp/src/lib/run-record/page-reads-signal.ts`, called from each page's `finish`; every page load (upheld reports throttled to one per 15 s per page), counting real reads once the Build Phase 3 counting item lands; clause: admin-pages-load-fast/one-read-per-page
- `apps/indusk-admin/src/__tests__/no-sync-starts.contract.test.ts:87` — A13, the source scan proving `never-freezes`, allow-lists `psAll` and `lsofOrNull` (line 105) because they are "reached only through realDaemonReads' synchronous closure, which a page's resolver is never handed". Whether the closure is handed is decided at run time: `onThisPage` (`apps/indusk-mcp/src/lib/telemetry/status.ts:154`) returns the synchronous `realDaemonReads` whenever `onPage()` is false. `onPage()` depends on `AsyncLocalStorage.enterWith` in `startPage` reaching the code. The brief page, the document page and the project home never call `startPage`. The recorder's `markIncidentVerdict` still calls the synchronous `commandTracer()` (`apps/indusk-mcp/src/lib/promises/incident-signal.ts:56`), which resolves the daemon through `liveOtlpEndpointSync` (`ps` and `lsof`). The notes record this failure mode once: the promise page ran 1.7 s of `spawnSync` until it opened a page. A14 covers only `withSituations`.
  - breaks when: a page that does not open its own count (the brief page's `readPlanHealth` refresh, for instance) or the recorder recording a break with no tracer provider yet runs `ps`/`lsof` synchronously on the server's event loop, and A13 stays green.
  - answer: fix — Build Phase 3 item "Put the brief page, the document page and the project home on the page's reads, and have the recorder find the daemon without a synchronous process start"
