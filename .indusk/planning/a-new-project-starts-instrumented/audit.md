# Audit — a-new-project-starts-instrumented

## Does each row prove its promise's sentence, or something narrower?
- `.indusk/planning/a-new-project-starts-instrumented/brief.md:35` — The first promise, `a-new-project-reports-from-its-first-run`, says a scaffolded project reports "with no file edited by hand". Only T11 tests that part. T11 is a manual live check of a Next.js app's server side, run once. The plan's own printed next steps say a hand edit is needed everywhere else. For Node, `apps/indusk-mcp/src/lib/scaffold/apply.ts:93` says `wire: node --import ./src/instrumentation.ts src/index.ts`. For Python, `apply.ts:111` says to add `import instrumentation` to the entry point. For the browser half of a Next.js app, `apply.ts:99` says to import `./instrumentation.web` from a client component. So the rows prove the promise for one runtime's server side, not for every project InDusk scaffolds (observed).
- `apps/indusk-mcp/src/__tests__/init-scaffold-runtimes.test.ts:87` — T3 is the trajectory row for the `the-service-is-named` clause: every template sets the service name in code. Its test passes if the project's name appears as a quoted string in any file init wrote. The rendered settings line always contains that string, so T3 passes even if a setup file stops passing `settings.serviceName` to its SDK (observed: the regex at `:87`).
- `apps/indusk-mcp/src/__tests__/init-scaffold-runtimes.test.ts:100` — T7 is the row for `every-span-says-where-it-ran`: every runtime's files put `indusk.project` and `deployment.environment` on every span. Its test joins all the written files and checks that both key strings appear somewhere. The settings file always contains both, so T7 still passes for Next.js if `attributes: settings.resource` is dropped from `registerOTel`, or for Node if the `resource:` line is dropped (observed).
- `apps/indusk-mcp/src/__tests__/telemetry-settings.test.ts:23` — T5 is the row for `the-spans-reach-the-daemon`: with nothing set, an app exports to the daemon. It tests the `telemetrySettings` function, not the templates that use it. T14 is the contract row with a real daemon, but it builds its own provider (`signal-helper-daemon.contract.test.ts`). No automated row runs or reads `instrumentation.ts`, `instrumentation.web.ts`, `instrumentation.py` or `logger.ts` to check that they pass `tracesUrl`/`logsUrl` to their exporters. The Python template is never run by any test.
- `apps/indusk-mcp/src/__tests__/signal-helper.test.ts:66` — T13 is the row for `a-signal-names-its-promise-and-clause`. That clause lists a promise, an optional clause, upheld or broken, a symptom, a measured value and bound, and the plan and phase. T13 writes value, bound, plan and phase but asserts only promise, clause, outcome and symptom (`:66-71`). The only other check on those four keys is T12, the vocabulary pin, and it only finds the key strings in the source. A helper that dropped `indusk.signal.value` from the span it writes would pass every row (observed).
- `.indusk/planning/a-new-project-starts-instrumented/test-plan.md:117` — In the test plan, T15 (the row for `a-test-run-says-so`, which says every span a project's test run makes carries the test-run marker) includes pytest. The approved impl's T15 row and its tests cover only Vitest, Jest, `MODE=test` and `NODE_ENV=test`. No test exercises the Python marker (`instrumentation.py:65`, `signal.py:40`). The row is narrower than both the test plan and the clause.
- `apps/indusk-mcp/src/__tests__/init-next-steps.test.ts:33` — T16 is the row for `next-steps-exist`: every file `init` tells a person to run exists afterwards. Its fixture writes `src/index.ts` itself ("The app's own entry, which the printed `wire:` line runs"), then checks that the file exists. Init never creates `src/index.ts`, and a real app's entry point may be named differently. The row passes because the test planted the file (observed). It is also possible, though not run here, that the printed `node --import ./src/instrumentation.ts` fails on plain Node: the template imports `./filtering-exporter` and `./telemetry-settings` without file extensions.
- `apps/indusk-mcp/src/__tests__/telemetry-skills-name-the-daemon.test.ts:26` — T17 is the row for `the-skills-name-the-daemon`: the skills never send a person to a vendor. Its test bans five names (dash0, datadog, newrelic, honeycomb, sentry). Any other vendor would pass. The row is narrower than "never to a vendor".
- `examples/seat-holds/src/telemetry.ts:24` — The `every-span-says-where-it-ran` clause promises "development unless set". The demo that `indusk demo` scaffolds spreads the settings and then overrides the environment with `SEAT_HOLDS_ENV ?? "local"`. Its spans say `local`, and no row reads the demo's environment (observed).

## What does the diff change that no row touches?
- `apps/indusk-mcp/src/bin/commands/update.ts:426` — `update` now catches any scaffold error and prints `could not scaffold: …`, and the command still succeeds. An unreadable `.indusk/scaffold.json` (`record.ts:25`) therefore quietly stops every future refresh. No row covers this.
- `apps/indusk-mcp/src/lib/scaffold/apply.ts:223` — A `beside` file is rewritten and announced on every `update` for as long as the edited file differs. A `.indusk-new` file the person has already merged is never removed. No row checks repeat runs.
- `examples/seat-holds/src/server.ts:38` — The demo's release span changed. Its name went from `seat.release` to the promise name, the `seat.number` and `seat.late_ms` attributes were dropped (the lateness becomes `indusk.signal.value`), the outcome word went from `violated` to `broken`, and `indusk.project` is now set on the span. The old test comment (removed in `seats.test.ts`) said a deployed recording server reads only `violated`. No row covers the demo's span shape or an older server reading it.
- `apps/indusk-mcp/src/bin/commands/init.ts:1141` — A re-run of `init` now keeps any `disabled_extensions` already in the config, for every project, not only the new-project flow's declined telemetry. Only T20 covers it, and T20 is the row asserting that a project created with telemetry declined records the reason, enables neither telemetry extension and gets no instrumentation.
- `apps/indusk-mcp/src/lib/promises/telemetry.ts:245` — The shared span reader `parseMarkedSpan` now returns `clause`, and every reader in the package goes through it. T13 relies on the new field but does not guard the reader's other callers.

## What does the code do that the brief never promised?
- `apps/indusk-mcp/src/lib/scaffold/plan.ts:286` — There is an "existing setup" rule, ADR decision 9: an app that already lists an OpenTelemetry SDK gets only the helper, and a browser-only app with its own setup gets nothing (`apply.ts:184`). The brief has no such exception. Its first promise covers every project InDusk scaffolds, and the ADR concedes such apps get no project or environment attributes.
- `apps/indusk-mcp/src/lib/scaffold/plan.ts:42` — There is a `removed` action: a recorded file the person deleted stays deleted, with a `left out:` line, and `init --force` brings it back. It was added in Build Phase 4. The brief's limit clause covers edits, not deletions.
- `apps/indusk-mcp/src/lib/promises/telemetry.ts:245` — The reader now parses `indusk.clause`. The brief's Not promised section gives "Reading a signal, standing per clause" to mark-first and says "This plan writes; that one reads."
- `examples/seat-holds/src/seats.test.ts:69` — The demo now writes `broken`. The root context's one-promise-language line says InDusk's own writers keep `violated` until mark-first. The ADR argues that rule for files an app owns, but the demo is InDusk's own example, and the brief carries only "the demo writes through the helper".
- `apps/indusk-mcp/src/bin/commands/extensions.ts:654` — Auto-enable by detection now respects `disabled_extensions` for every extension, not only the two telemetry ones the brief names.

## Which rejected ADR alternative does the code quietly take?
- `apps/indusk-mcp/src/lib/scaffold/apply.ts:245` — The ADR rejected naming the service after the workbench, in the alternative "The service named after the workbench". When a workbench has no declared repos, the code takes the project root as the target and `basename(projectRoot)` as the service. Nothing prevents a workbench with no declared repos and a `package.json` at its root (the test fixtures create one, `init-scaffold-placement.test.ts:56`) from being scaffolded at the workbench root under the workbench's name. That takes both the rejected naming and the "never at a workbench root" exclusion. This was not observed in a real project.

## Which skip reason would you not accept?
- `apps/indusk-mcp/src/__tests__/workbench-code-repo-mcp-json.test.ts:21` — Commit `f6daf9ee7` skipped cleanup with the reason "no cross-file extraction warranted". The same fixture is copied across files: a code repo beside a workbench whose root has a `package.json`, then `init --workbench --wrapped-repo --sibling-parent`. It appears here in `bench()`, again in `init-scaffold-placement.test.ts:41`, and the approved impl says to build it "the way `init-workbench.test.ts` makes one". That is three copies, which meets the rule of three. Python's settings logic is also a hand copy that has already drifted: `instrumentation.py:52` does not percent-decode, while T28 holds that `telemetry-settings.ts` does. The duplication is the ADR's choice, but the drift is real. No trajectory row is `skipped`, and the approved impl has no `(none needed)` gate.

## What else would have to change for each promise to hold?
- `examples/seat-holds/.indusk/scaffold.json:4` — The recorded hash for `src/telemetry-settings.ts` (`b19fbd…`) matches neither the committed file (`eda542…`, whose RENDERED line is spread over several lines at `src/telemetry-settings.ts:31`) nor a fresh rendering. Running `indusk init` on a fresh copy of the demo prints `beside: src/telemetry-settings.ts.indusk-new (you changed src/telemetry-settings.ts…)` and leaves that file behind (observed, in a temporary copy with a temporary home). T24, the row asserting that init on a fresh copy of the demo adds no second OpenTelemetry setup, checks only that no setup files were added.
- `apps/indusk-mcp/templates/biome.template.json:11` — `init` installs this formatter config, with `lineWidth: 100`, into the same project. The one-line RENDERED object is about 150 characters (`render.ts:37`). The first formatter run reflows it, as happened to the demo. From then on the file reads as edited: every `update` writes it beside, and an address reset never reaches the app. That defeats the ADR's "An address reset reaches an untouched app through the next update". Either the render or the record has to tolerate formatting, or the template has to put the values on lines a formatter leaves alone.
- `apps/indusk-mcp/src/bin/commands/demo.ts:39` — `indusk demo <dir>` copies the demo, whose committed settings set `project: "seat_holds"`. The helper copies that onto every signal span (`signal.ts:52`), and the reader drops a mark naming a different project (`lib/promises/telemetry.ts:302-306`). A demo copied under any folder name except `seat-holds` therefore has its signals dropped. The re-rendered settings go beside and are never used. This is inferred from the code, not run end to end.
- `apps/indusk-mcp/src/lib/new-project/prompt.ts:83` — `disableDeclinedTelemetry` (`create.ts:239`) fires only when a recommendation is named exactly `telemetry`. The new-project agent's prompt, which this plan did not touch, tells it to write `"name": "<practice>"` with no fixed name. A decline named `observability` or `local-telemetry` would still enable both extensions and scaffold, which breaks the must-not-break promise `a-recommendation-can-be-declined`. T20 passes because its fixture names it `telemetry`.
- `apps/indusk-mcp/extensions/otel/manifest.json:12` — The test plan names the otel extension's health check as the signal for `the-scaffold-sits-where-the-app-runs`. Its `otel-packages-installed` check requires `@opentelemetry/sdk-node` or a Python `opentelemetry`. A scaffolded Next.js app (which installs `@vercel/otel`) or a browser app may never install that package, so the check could report unhealthy where the scaffold is correct. This was not run.
