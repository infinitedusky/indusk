# The daemon is found, not guessed — Test Plan

## Purpose

This is the clause plan for the one promise the [brief](brief.md) makes. It has one section for the promise and one for each of its six clauses. Each clause section gives the clause's signal (where it is read, who sends it and when, what counts as upheld, what a break reports) and the assertions that prove the clause before release. Each assertion names its level: the smallest of unit, contract, live check, smoke and promise that can prove it. The impl's Test Trajectory rows are derived from these assertions, and the ADR that follows is held to "what makes all of these true?". The findings behind every row are in [research.md](research.md), with file and line on trunk.

Two words used throughout. **The record** is the daemon's two files under `~/.indusk`, `telemetry.json` and `telemetry.pid`, which name its processes and ports; today it is the daemon's only identity, and a read can delete it. **An InDusk daemon process** is a Jaeger or collector started from InDusk's shipped binary with its config under `~/.indusk`, the brief's own definition in its first expectation. A daemon in a temporary home, as tests start, is not one.

## At a glance

The plan makes one promise, stated as six clauses. Every assertion below sits under one clause, except the regression guards at the end.

| Promise | Clause | Kind | What the clause says |
|---|---|---|---|
| `the-daemon-readers-follow-is-the-one-running` | `one-daemon-on-fixed-ports` | limit | at most one InDusk daemon, on 4318 (traces), 4319 (logs), 16686 (interface) and one fixed MCP port; a start that finds one held by something else refuses and names the holder |
| | `a-read-never-loses-the-daemon` | limit | no status read, health check or promise reader deletes the record; a slow port reads as slow, never as gone |
| | `a-lost-daemon-is-found` | split | with the record missing, a running InDusk daemon is found from the process list, its record written again, and `telemetry start` takes it over |
| | `nothing-starts-a-second` | limit | enabling the telemetry extension, `init` and `update` never start a daemon beside a running one or re-point another project's MCP entry |
| | `strays-are-cleared` | split | `telemetry status` lists every InDusk daemon process the record does not name, and `telemetry reap` stops them |
| | `the-log-is-readable` | split | the daemon's log carries no lines of Jaeger failing to send its own traces |

## Behavioral Assertions

Every assertion is observable from outside: what a person running `indusk telemetry` commands, `init` or `update` sees printed and in the process list; what a promise reader (`indusk promises status`, the admin's promise page, the editor's health line) shows; what an application or Claude Code reaches on a port. Code that decides — which daemon is InDusk's, which ports it holds, whether the record is stale, what report to send — takes the process list, the listening sockets, the record and the clock as inputs, so its rules are unit tests (`lesson: code-that-decides-takes-its-clock-and-its-reads`). A test that starts a real Jaeger is a contract test in the system tier (`lesson: everyday-tests-never-wait`).

## `the-daemon-readers-follow-is-the-one-running`

**The promise:** Every reader of promises, every InDusk command and every application on a machine reaches the same one local telemetry daemon.

**Its six clauses:** `one-daemon-on-fixed-ports`, `a-read-never-loses-the-daemon`, `a-lost-daemon-is-found`, `nothing-starts-a-second`, `strays-are-cleared`, `the-log-is-readable`.

**How its signal is sent.** The promise is of kind behaviour, so today's promise readers already read its signal. Every report is a span that an InDusk command or promise reader sends to the local daemon (the one the record names, after any finding), under InDusk's own service name, carrying `indusk.promise=the-daemon-readers-follow-is-the-one-running`, `indusk.promise.outcome` set to upheld or broken, and the clause on `indusk.clause`. That clause attribute is the one named by decision D1 of the proposed ADR in `mark-first` (`.indusk/planning/mark-first/adr.md` on branch `plan/mark-first`: a signal's spans carry the promise and the clause). Today's readers ignore it, so a broken report's symptom also opens with the clause's name, which `promises status` and the admin's promise page show today. Broken is written in the same wire word every other InDusk signal writes today: the one-promise-language decision (`/decisions/one-promise-language`) has every reader take both spellings of broken, and InDusk's own writers switch to the new one together, in `mark-first`. Reports sent by telemetry commands carry no `indusk.project`: one daemon serves every project on the machine, and only this repository's registry holds the promise. Its readers here are `indusk promises status`, `promises watch`, the `promise_health` tool and the admin's promise page for this repository, and they read these spans from the local Jaeger like any application's. As any behaviour promise does, it reads broken while a broken report inside the health window has no incident or an open one, holding when an upheld report is inside the window and no break is live, and no signal when nothing has reported within it. A report is never sent to a port held by a process that is not InDusk's. The signal is always telemetry the running daemon receives, never a test run's result.

### `one-daemon-on-fixed-ports` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** At most one InDusk daemon runs on a machine, on fixed ports: 4318 for traces, 4319 for logs, 16686 for its interface and one fixed port for its MCP server; a start that finds one of them held by something else refuses and names what holds it.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry status` on every run that finds a daemon running, and by `indusk telemetry start` and `restart` once the daemon they started or took over is ready. Each reads the process list and the listening sockets first, then sends a span with the promise, the outcome, `indusk.clause=one-daemon-on-fixed-ports`, and the Jaeger and collector process ids and the four ports as attributes. Upheld when exactly one InDusk Jaeger and one InDusk collector run and together they hold 4318, 4319, 16686 and the fixed MCP port. A broken report's symptom opens with the clause's name and names every InDusk daemon process beyond the first (its process id, start time and ports) or each fixed port the daemon does not hold. When a start refuses because a process that is not InDusk's holds a fixed port, no report is sent: there is no InDusk daemon to receive one, and the port belongs to someone else. The refusal is printed, the command exits non-zero, and the clause keeps its last report.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A1 | On a machine with no daemon, `indusk telemetry start` gives the daemon 4318 for traces, 4319 for logs, 16686 for its interface and the fixed MCP port, and `start` and `status` both print all four. Neither prints the logs port today. | unit |
| A2 | A daemon started in a temporary InDusk home binds every port the test gives it: a trace sent to its traces port appears in its interface, and a log record sent to its logs port is accepted and written to its logs file. | contract |
| A3 | When 4318, 4319, 16686 or the fixed MCP port is held by a process that is not InDusk's, a start starts nothing, exits non-zero, and names the port and the process holding it, with that process's id and command. | unit |
| A4 | The automatic start run by `init`, `update` and enabling the telemetry extension never moves the daemon to another port. When a fixed port is held by something that is not InDusk's, it refuses as `start` does, naming the holder; today it falls to a random port. No start in the real InDusk home, by hand or automatic, puts the daemon on any port but the four. | unit |
| A5 | For an InDusk daemon on ports other than the fixed four, such as one started before this change, `telemetry status` says which ports differ, and `telemetry restart` brings it back on the four. | unit |
| A6 | `telemetry status` sends an upheld report for this clause when one InDusk Jaeger and one collector hold the four fixed ports. Otherwise it sends a broken one naming every extra InDusk daemon process, or every fixed port the daemon does not hold. | unit |

### `a-read-never-loses-the-daemon` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** No status read, health check or promise reader deletes the daemon's record; a port slow to answer reads as slow, never as gone.

- Signal: read by this repository's promise readers from the local daemon's traces. Upheld reports ride on the probe span that every promise reader already sends through the daemon's intake before it reads anything. That probe comes from the watcher-heartbeat decision (`/decisions/watcher-heartbeat`): every reader proves the daemon hears before trusting what it reads. When a reader reaches the local daemon through its record, its probe of that daemon also carries the promise, outcome upheld and `indusk.clause=a-read-never-loses-the-daemon`, along with the `indusk.project` the probe already carries, so this repository's reads uphold it here. A break cannot be sent when it happens: the read that removes the record is the fault itself and does not know it erred, and once the record is gone no command knows the daemon's processes. It is sent when the loss is found. A command that finds a running InDusk daemon from the process list, while the record is missing or names processes that are gone, does the finding of `a-lost-daemon-is-found` below: it writes the record again, then sends the found daemon a broken report. The report's symptom opens with this clause's name and says that the record was missing while the daemon ran, since when the daemon has run, and which command found it. The finding cannot tell what removed the record (a reader of this version, a reader from an install that predates this change, such as the global install on this machine, or a person), so every loss it finds is reported broken. A loss that no command finds while the daemon lives, and a read that calls a slow daemon gone without touching the record, send no report. Their backstop is the brief's second expectation: the evaluator's lines saying it fell back to a no-op logger, which it writes exactly when it reads the daemon as gone.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A7 | No `telemetry status` read, extension health check, `promises status`, `promises watch`, admin page or evaluator lookup removes the record. If a port is slow to answer, the daemon reads as running and slow, with the port named and how long the read waited. If a recorded process is really gone and no InDusk daemon runs, the daemon reads as not running, with the stale record named, and the record stays until `start` replaces it or `stop` removes it. | unit |
| A8 | A real daemon runs in a temporary home while the reading process is kept busy longer than the port check waits. A status read then reports the daemon slow, not gone, and its record is still there afterwards, the failure behind the retry added on 2026-10-05. | contract |
| A9 | A promise reader's read that reaches the daemon through its record sends an upheld report for this clause on its probe. A read that first had to find the daemon sends the finding's broken report, not an upheld one. | unit |

### `a-lost-daemon-is-found` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** When the record is missing, a running InDusk daemon is found from the process list, its record is written again, and `telemetry start` takes it over instead of starting another.

- Signal: read by this repository's promise readers from the local daemon's traces. Two moments send it. The first is a finding, by whichever InDusk command does it: `telemetry status`, `telemetry start`, the automatic start, a promise reader resolving the local daemon, or the evaluator looking for its endpoint. Once that command has found the record missing (or naming processes that are gone), found a running InDusk Jaeger and collector in the process list, and written the record again, it sends the found daemon a span with the promise, outcome upheld, `indusk.clause=a-lost-daemon-is-found`, the found process ids and ports, and the command that found them. The second is a start, by hand or automatic, that started a daemon: once its own daemon is ready it reads the process list and sends that daemon (the one the record now names) a span with the clause, upheld when no other InDusk daemon runs beside it. Upheld means a lost daemon was found and its record rebuilt, or a start had nothing to take over. A broken report comes from a start that finds another InDusk daemon running beside the one it started; its symptom opens with the clause's name and names the daemon it should have found, with its process ids, start time and ports. A finding that cannot recognise a running InDusk daemon sends nothing, since it does not know that daemon is there; a start then finds the fixed ports held by a process it takes for someone else's, refuses and prints the holder. Its backstop is the brief's first expectation, which counts starts in the daemon's log with no shutdown before them.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A10 | The record is missing while an InDusk daemon runs, its Jaeger and collector in the process list. `telemetry status` then reports the daemon running, with its process ids and its ports read from the sockets it listens on (not from its config file, which is rewritten on every start), and the record is written again. | unit |
| A11 | With the record missing and an InDusk daemon running on the fixed ports, `telemetry start` takes it over: it writes the record, starts nothing, prints that it took over the running daemon with its process ids and ports, and exits zero. Until now it refused and offered a port bump or other ports. | unit |
| A12 | With the record missing and several InDusk daemons running, `telemetry start` takes over the one holding the fixed ports and lists every other as a stray for `telemetry reap`. When none holds the fixed ports, it takes over none, starts nothing, and lists them all. | unit |
| A13 | With the record missing and the daemon running, `promises status`, the admin's promise page and the editor's health line read the running daemon's traces. Today they say no telemetry daemon is running. | unit |
| A14 | A finding sends the found daemon an upheld report for this clause, and a broken report for `a-read-never-loses-the-daemon` whose symptom says when the daemon started and that its record was missing. A start that started a daemon sends an upheld report for this clause when no other InDusk daemon runs beside it once it is ready, and a broken one naming the daemon it missed when one does. | unit |
| A15 | On this machine, with the daemon running, its record is moved aside and `indusk telemetry start` run: it takes the daemon over, starts nothing and writes the record. The record is moved aside again and `indusk telemetry status` run: it finds the daemon and writes the record. The process list then still shows one InDusk Jaeger and one collector, on 4318, 4319, 16686 and the fixed MCP port. `indusk promises status` in this repository shows the promise broken, its symptom naming `a-read-never-loses-the-daemon`, and the daemon's interface shows the upheld reports for this clause that both findings sent. | live check |

### `nothing-starts-a-second` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** Enabling the telemetry extension, `init` and `update` never start a daemon beside a running one and never point another project's MCP entry somewhere else.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry register` once it finishes. Register is how the other three reach the daemon: enabling the telemetry extension runs it, and `init` and `update` run it when they enable the extension for a project that does not have it yet; an `update` on a project that already has it registers nothing, starts nothing and sends nothing. The report is a span with the promise, the outcome, `indusk.clause=nothing-starts-a-second`, the project registered, and whether it found, took over or started the daemon. Upheld when the process list, read once register has finished, shows no InDusk daemon beside the one the record names, and no other project's MCP entry was changed. A broken report's symptom opens with the clause's name and names either the second daemon, by both process ids, or each other project's MCP entry it changed, by that project's path, the old address and the new one; it goes to the daemon the record now names. A register that refuses because a process that is not InDusk's holds a fixed port sends nothing, as a refused start does.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A16 | With an InDusk daemon running (recorded or found), `init` on a new project, `update` and enabling the telemetry extension start no daemon and register the project against the running one. The process list afterwards shows the same one Jaeger and one collector. Until now, with the record unreadable, they started another on bumped ports. With no daemon running and the fixed ports free, they start exactly one, on the fixed ports. | unit |
| A17 | Registering a project points its own MCP entry at the fixed MCP port and leaves every other registered project's MCP entry as it was, whatever port that entry names. | unit |
| A18 | Registering sends an upheld report for this clause when it found or started the one daemon and changed no other project's MCP entry. It sends a broken one naming both process ids when, after its start, another InDusk daemon is running beside the one it started, and one naming each other project's entry it changed. | unit |

### `strays-are-cleared` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** `telemetry status` lists every InDusk daemon process the record does not name, and `telemetry reap` stops them.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry reap` when it finishes, to the daemon the record names, as a span with the promise, the outcome, `indusk.clause=strays-are-cleared` and the process ids it stopped. Upheld when the process list read after the reap shows no InDusk daemon process the record does not name. A broken report's symptom opens with the clause's name and names each stray still running, with its process id, start time and ports. Strays that `telemetry status` finds break `one-daemon-on-fixed-ports` and are reported there; this clause reports whether `reap` cleared them. When no recorded daemon is left to receive a report, `reap` sends nothing: its result is printed, and the next start's report for `one-daemon-on-fixed-ports` reads the process list again. A stray that `status` cannot recognise as InDusk's is neither listed nor reaped and sends nothing; its backstop is the brief's first expectation, whose count of starts with no shutdown before them is read from the daemon's log, not from that recognition.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A19 | `telemetry status` lists every InDusk Jaeger and collector the record does not name, each with its process id, start time, ports and the install it was started from, and says that `telemetry reap` stops them. | unit |
| A20 | `telemetry reap` stops every stray, including one whose config file still exists, which it skipped until now. It leaves the recorded daemon running and every process that is not InDusk's untouched. | unit |
| A21 | `telemetry reap` prints each stray it stopped, and exits non-zero naming each one that would not stop. It sends an upheld report for this clause when no stray remains, and a broken one naming each that does. | unit |
| A22 | With two daemons started in a temporary home and the record naming one, `telemetry reap` stops the other, and the recorded one still receives traces afterwards. | contract |

### `the-log-is-readable` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** The daemon's log carries no lines of Jaeger failing to send its own traces.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry status` on every run while the daemon runs. Status reads the lines of `~/.indusk/telemetry.log` written since the running daemon started, counts those that are Jaeger failing to send its own traces (its client failing to reach `localhost:4317`), and sends a span with the promise, the outcome, `indusk.clause=the-log-is-readable` and the count. Upheld when the count is zero. A broken report's symptom opens with the clause's name and gives the count and the first such line. Lines written between status runs are heard at the next run. A daemon whose status nobody asks is not heard; the brief's third expectation, the share of such lines one week after landing, is its backstop.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A23 | A daemon started from the shipped Jaeger with the config InDusk renders writes no line of Jaeger failing to send its own traces over half a minute, several times the interval at which those lines were written, while traces and logs sent to it still arrive. | contract |
| A24 | `telemetry status` sends an upheld report for this clause when the log since the daemon started holds no such line, and a broken one giving their count and the first of them. | unit |

## Not for a promise

Each of these guards a promise already in force that this plan comes near, as the brief's "Must not break" lists, or a lesson.

| ID | Assertion (user-visible behavior) | Level | Why |
|----|-----------------------------------|-------|-----|
| A25 | Taking over and reaping judge a process by its command line, as `stop` does. A process holding 4318 that is not InDusk's, and an InDusk daemon in a temporary home, are never signalled or taken over by a command run in the real home. After `telemetry start` takes a daemon over, `telemetry stop` stops that daemon and says, non-zero, if one of its processes would not stop. | unit | guards `indusk-stops-only-its-own-daemons`: `telemetry stop` and `ui stop` judge a process by its command line, never by whether its port answers, signal only their own, and say, non-zero, when one would not stop |
| A26 | A test's daemon runs in a temporary home on the ports the test gives it, never the fixed four, and only in the system tier. The everyday suite starts no daemon, and no start, takeover or reap in the real home reaches a test's daemon. | unit | guards `everyday-tests-never-wait`: the everyday suite never starts a server or waits on the clock. Fixed ports belong to the real home only |
| A27 | Starting, restarting or taking over the daemon leaves a `.mcp.json` that already names the fixed MCP port unchanged, and `.mcp.json` stays untracked. `update` in a checkout with no `.mcp.json` writes one naming `indusk`, with `jaeger` at the fixed MCP port. | unit | guards `the-mcp-config-is-not-tracked` (`.mcp.json` is not tracked and its ignore rule holds) and `a-clone-without-an-mcp-config-gets-the-keep-list` (a checkout without one gets one naming `indusk`, and an existing one is never overwritten) |
| A28 | The evaluator exports to the daemon the record names, or to the one found when the record is missing. While a daemon runs, it writes no "endpoint unset; falling back to no-op logger" line. | unit | guards `every-commit-evaluated`: each evaluation's report reaches the local Jaeger and is read by `promises status` |

## Notes

- **Levels.** Every row that says what report a command sends is a unit test: it reads the report the command decides to send from the process list, sockets, record and clock it is handed. That a report reaches the daemon and a reader is proved once, by the live check in row A15. Four rows (A2, A8, A22, A23) start a real Jaeger in a temporary home and are contract tests in the system tier.
- **Decisions this test plan leaves to the ADR.** The number of the fixed MCP port. What counts as InDusk's when a global install runs beside a repository's own (this machine has both). The Jaeger 2.17.0 setting that silences its self-tracing, which nothing on trunk has verified (research, "The daemon log is two-thirds Jaeger failing to trace itself"). Whether the always-on server's Jaeger gets the same setting; the clause names only the local daemon's log. Whether `init` exits non-zero when a process that is not InDusk's holds a fixed port, or completes with the refusal printed; the 1.36.2 failure, where `init` failed on every machine already running a daemon, does not return, because a running InDusk daemon is now taken over. How projects whose MCP entry names an old random port (this repository's and Homework Gate's name 54677) come to name the fixed port: registering a project changes no other project's entry (row A17, the assertion that register leaves every other project's MCP entry as it was, follows the clause's "never point another project's MCP entry somewhere else"), so each project's own `update`, or a `telemetry restart`, which the clause does not name, has to do it. Whether `--allow-port-bump` and the explicit port options are removed or refused in the real home, since row A4, the assertion that no start in the real home puts the daemon on any port but the four, rules out both there.
- **Three decided reversals** flip behaviour that tests pin today, and those tests will be rewritten rather than added beside. `start` takes over a running InDusk daemon instead of refusing (row A11; `port-guard.test.ts`). The automatic start never bumps ports (rows A4 and A16; `port-guard.test.ts` and `telemetry-mcp-port-sync.test.ts`). `reap` clears a stray whose config still exists (row A20; `orphans.test.ts`). The lifecycle suite in `telemetry-cli-lifecycle.test.ts` walks start, status, stop and restart with automatically bumped ports and is rewritten to the ports its temporary home gives.
- **The live check breaks the promise on purpose.** In row A15, the live check that moves the record aside on this machine, the record really is gone while the daemon runs, and the finding cannot tell a person's hand from a faulty read, so `a-read-never-loses-the-daemon` reports broken. This repository names no production source, so its local daemon is the one whose breaks raise the alarm: the promise reads broken while that report is inside the health window, and a `promises watch` run in that time records it as an incident against this plan and reopens it with a Maintenance phase. Its precondition: the daemon started by hand on 2026-10-16 (Jaeger process 43599) runs its MCP server on 62843, not on the fixed port. The first `telemetry restart` after the build (row A5) moves it, and the live check runs after that.
- **`instance-ports`' per-instance-ports promise is superseded** by `one-daemon-on-fixed-ports` (Sandy, 2026-10-16), as the brief's "Not promised" says; nothing here tests several daemons on one machine except as strays.
