# The daemon is found, not guessed — Test Plan

## Purpose

This is the clause plan for the one promise the [brief](brief.md) makes. It has one section for the promise and one for each of its six clauses. Each clause section gives the clause's signal (where it is read, who sends it and when, what counts as upheld, what a break reports) and the assertions that prove the clause before release. Each assertion names its level: the smallest of unit, contract, live check, smoke and promise that can prove it. The impl's Test Trajectory rows are derived from these assertions, and the ADR that follows is held to "what makes all of these true?". The findings behind every row are in [research.md](research.md), with file and line on trunk.

Three terms used throughout. **The record** is the daemon's two files under `~/.indusk`, `telemetry.json` and `telemetry.pid`, which name its processes and ports; today it is the daemon's only identity, and a read can delete it. **The stored address** is the daemon's four ports (traces, logs, interface, MCP server), chosen once at the first setup in the installed InDusk's home and kept from then on: InDusk's own port block, 24318, 24319, 24316 and 24317, or free ports picked in place of any of those that were held at that first setup. Unlike the record, no `stop` removes it, and InDusk never moves it on its own: `indusk telemetry address --reset` is the one deliberate way a person chooses it again. It did not exist before this plan. **An InDusk daemon process** is a Jaeger or collector started from InDusk's shipped binary with its config under `~/.indusk`, the brief's own definition in its first expectation. A daemon in a temporary home, as tests start, is not one.

## At a glance

The plan makes one promise, stated as six clauses. Every assertion below sits under one clause, except the regression guards at the end.

| Promise | Clause | Kind | What the clause says |
|---|---|---|---|

| | `a-read-never-loses-the-daemon` | limit | no status read, health check or promise reader deletes the record; a slow port reads as slow, never as gone |

| | `strays-are-cleared` | split | `telemetry status` lists every InDusk daemon process the record does not name, and `telemetry reap` stops them |
| | `the-log-is-readable` | split | the daemon's log carries no lines of Jaeger failing to send its own traces |

## Behavioral Assertions

Every assertion is observable from outside: what a person running `indusk telemetry` commands, `init` or `update` sees printed and in the process list; what a promise reader (`indusk promises status`, the admin's promise page, the editor's health line) shows; what an application or Claude Code reaches on a port. Code that decides — which daemon is InDusk's, which ports it holds, whether the record is stale, what report to send — takes the process list, the listening sockets, the record and the clock as inputs, so its rules are unit tests (`lesson: code-that-decides-takes-its-clock-and-its-reads`). A test that starts a real Jaeger is a contract test in the system tier (`lesson: everyday-tests-never-wait`).

## `the-daemon-readers-follow-is-the-one-running`

**The promise:** Every reader of promises, every InDusk command and every application on a machine reaches the same one local telemetry daemon.

**Its six clauses:** `one-daemon-on-its-own-ports`, `a-read-never-loses-the-daemon`, `a-lost-daemon-is-found`, `nothing-starts-a-second`, `strays-are-cleared`, `the-log-is-readable`.

**How its signal is sent.** The promise is of kind behaviour, so today's promise readers already read its signal. Every report is a span that an InDusk command or promise reader sends to the local daemon (the one the record names, after any finding), under InDusk's own service name, carrying `indusk.promise=the-daemon-readers-follow-is-the-one-running`, `indusk.promise.outcome` set to upheld or broken, and the clause on `indusk.clause`. That clause attribute is the one named by decision D1 of the proposed ADR in `mark-first` (`.indusk/planning/mark-first/adr.md` on branch `plan/mark-first`: a signal's spans carry the promise and the clause). Today's readers ignore it, so a broken report's symptom also opens with the clause's name, which `promises status` and the admin's promise page show today. Broken is written in the same wire word every other InDusk signal writes today: the one-promise-language decision (`/decisions/one-promise-language`) has every reader take both spellings of broken, and InDusk's own writers switch to the new one together, in `mark-first`. Reports sent by telemetry commands carry no `indusk.project`: one daemon serves every project on the machine, and only this repository's registry holds the promise. Its readers here are `indusk promises status`, `promises watch`, the `promise_health` tool and the admin's promise page for this repository, and they read these spans from the local Jaeger like any application's. As any behaviour promise does, it reads broken while a broken report inside the health window has no incident or an open one, holding when an upheld report is inside the window and no break is live, and no signal when nothing has reported within it. A report is never sent to a port held by a process that is not InDusk's. The signal is always telemetry the running daemon receives, never a test run's result.

### `one-daemon-on-its-own-ports` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** At most one InDusk daemon runs on a machine, on one address chosen once and kept until a person chooses it again with `indusk telemetry address --reset`: InDusk's own port block (24318 for traces, 24319 for logs, 24316 for its interface, 24317 for its MCP server), or, when one of those is held at first setup, free ports picked once and recorded, which InDusk never changes on its own; every reader, every InDusk command and what `init` hands an application read that stored address and never assume one.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry status` on every run while the recorded Jaeger is alive, including a partly running daemon whose collector has died, and by `indusk telemetry start` and `restart` once the daemon they started or took over is ready. When the recorded Jaeger is dead, `status` sends nothing: nothing is there to receive it. Each reads the stored address, the process list and the listening sockets first, then sends a span with the promise, the outcome, `indusk.clause=one-daemon-on-its-own-ports`, and as attributes the Jaeger and collector process ids, the four ports of the stored address, and whether that address is the block or has ports picked at first setup. Upheld when exactly one InDusk Jaeger and one InDusk collector run and together they hold the four ports of the stored address. Picking free ports at first setup, because a port of the block was held, is the clause working, not a break: that first start's report is upheld and carries the held port and its holder as attributes. A broken report's symptom opens with the clause's name and names every InDusk daemon process beyond the first (its process id, start time and ports) or each port of the stored address the daemon does not hold, with the port it holds instead, or each recorded process that is no longer running, with the stored ports it no longer holds. When a later start refuses because a process that is not InDusk's holds a port of the stored address, no report is sent: there is no InDusk daemon to receive one, and the port belongs to someone else. The refusal is printed, names `indusk telemetry address --reset` as the way to choose the address again, and the command exits non-zero; the stored address stays as it was, and the clause keeps its last report. An address file that exists but cannot be read refuses the same way and sends nothing.

### `a-read-never-loses-the-daemon` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** No status read, health check or promise reader deletes the daemon's record; a port slow to answer reads as slow, never as gone.

- Signal: read by this repository's promise readers from the local daemon's traces. Upheld reports are sent at the moment of the probe that every promise reader already sends through the daemon's intake before it reads anything. That probe comes from the watcher-heartbeat decision (`/decisions/watcher-heartbeat`): every reader proves the daemon hears before trusting what it reads. When a reader reaches the local daemon through its record, it sends that daemon its own span, beside the probe and under InDusk's own service, carrying the promise, outcome upheld, `indusk.clause=a-read-never-loses-the-daemon` and the reader's `indusk.project`, so this repository's reads uphold it here. It is throttled to one per project every 15 minutes, so the readers' frequent probes cannot crowd broken reports out of the query window (ADR decision D9, the decision on how each clause's signal is sent). A break cannot be sent when it happens: the read that removes the record is the fault itself and does not know it erred, and once the record is gone no command knows the daemon's processes. It is sent when the loss is found. A command that finds a running InDusk daemon from the process list, while the record is missing or names processes that are gone, does the finding of `a-lost-daemon-is-found` below: it writes the record again, then sends the found daemon a broken report. The report's symptom opens with this clause's name and says that the record was missing while the daemon ran, since when the daemon has run, and which command found it. The finding cannot tell what removed the record (a reader of this version, a reader from an install that predates this change, such as the global install on this machine, or a person), so every loss it finds is reported broken. A loss that no command finds while the daemon lives, and a read that calls a slow daemon gone without touching the record, send no report. Their backstop is the brief's second expectation: the evaluator's lines saying it fell back to a no-op logger, which it writes exactly when it reads the daemon as gone.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A7 | No `telemetry status` read, extension health check, `promises status`, `promises watch`, admin page or evaluator lookup removes the record. If a port is slow to answer, the daemon reads as running and slow, with the port named and how long the read waited. If a recorded process is really gone and no InDusk daemon runs, the daemon reads as not running, with the stale record named, and the record stays until `start` replaces it or `stop` removes it. | unit |
| A8 | A real daemon runs in a temporary home while the reading process is kept busy longer than the port check waits. A status read then reports the daemon slow, not gone, and its record is still there afterwards, the failure behind the retry added on 2026-10-05. | contract |
| A9 | A promise reader's read that reaches the daemon through its record sends an upheld report for this clause at its probe, as its own span, at most once per project every 15 minutes. A read that first had to find the daemon sends the finding's broken report, not an upheld one. | unit |

### `a-lost-daemon-is-found` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** When the record is missing, a running InDusk daemon is found from the process list, its record is written again, and `telemetry start` takes it over instead of starting another.

- Signal: read by this repository's promise readers from the local daemon's traces. Two moments send it. The first is a finding, by whichever InDusk command does it: `telemetry status`, `telemetry start`, the automatic start, a promise reader resolving the local daemon, or the evaluator looking for its endpoint. Once that command has found the record missing (or naming processes that are gone), found a running InDusk Jaeger and collector in the process list, and written the record again, it sends the found daemon a span with the promise, outcome upheld, `indusk.clause=a-lost-daemon-is-found`, the found process ids and ports, and the command that found them. Only the command whose exclusive create wrote the record sends it, and it names that command, never a made-up one. A `telemetry start` that takes the daemon over sends these finding reports and its report for `one-daemon-on-its-own-ports`, not the start's report below. The second is a start, by hand or automatic, that started a daemon: once its own daemon is ready it reads the process list and sends that daemon (the one the record now names) a span with the clause, upheld when no other InDusk daemon runs beside it. Upheld means a lost daemon was found and its record rebuilt, or a start had nothing to take over. A broken report comes from a start that finds another InDusk daemon running beside the one it started; its symptom opens with the clause's name and names the daemon it should have found, with its process ids, start time and ports. A finding that cannot recognise a running InDusk daemon sends nothing, since it does not know that daemon is there; a start then finds the stored address held by a process it takes for someone else's, refuses and prints the holder. Its backstop is the brief's first expectation, which counts starts in the daemon's log with no shutdown before them.

### `nothing-starts-a-second` — a limit of `the-daemon-readers-follow-is-the-one-running`

**The clause:** Enabling the telemetry extension, `init` and `update` never start a daemon beside a running one and never point another project's MCP entry somewhere else.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry register` once it finishes. Register is how the other three reach the daemon: enabling the telemetry extension runs it, and `init` and `update` run it when they enable the extension for a project that does not have it yet; an `update` on a project that already has it registers nothing, starts nothing and sends nothing. The report is a span with the promise, the outcome, `indusk.clause=nothing-starts-a-second`, the project registered, and whether it found, took over or started the daemon. Upheld when the process list, read once register has finished, shows no InDusk daemon beside the one the record names, and no other project's MCP entry was changed. A broken report's symptom opens with the clause's name and names either the second daemon, by both process ids, or each other project's MCP entry it changed, by that project's path, the old address and the new one; it goes to the daemon the record now names. A register that refuses because a process that is not InDusk's holds a port of the stored address sends nothing, as a refused start does.

|----|-----------------------------------|-------|
| A16 | With an InDusk daemon running (recorded or found), `init` on a new project, `update` and enabling the telemetry extension start no daemon and register the project against the running one. The process list afterwards shows the same one Jaeger and one collector. Until now, with the record unreadable, they started another on bumped ports. With no daemon running, they start exactly one, on the stored address, choosing it first when none is stored. | unit |

### `strays-are-cleared` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** `telemetry status` lists every InDusk daemon process the record does not name, and `telemetry reap` stops them.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry reap` when it finishes, to the daemon the record names, as a span with the promise, the outcome, `indusk.clause=strays-are-cleared` and the process ids it stopped. Upheld when the process list read after the reap shows no InDusk daemon process the record does not name. A broken report's symptom opens with the clause's name and names each stray still running, with its process id, start time and ports. Strays that `telemetry status` finds break `one-daemon-on-its-own-ports` and are reported there; this clause reports whether `reap` cleared them. `reap` also stops orphans, daemons of any home whose config file is gone, since that home is no one's any more. When no recorded daemon is left to receive a report, `reap` sends nothing: its result is printed, and the next start's report for `one-daemon-on-its-own-ports` reads the process list again. A stray that `status` cannot recognise as InDusk's is neither listed nor reaped and sends nothing; its backstop is the brief's first expectation, whose count of starts with no shutdown before them is read from the daemon's log, not from that recognition.

| A20 | `telemetry reap` stops every stray, including one whose config file still exists, which it skipped until now. It leaves the recorded daemon running and every process that is not InDusk's untouched. | unit |

### `the-log-is-readable` — a split of `the-daemon-readers-follow-is-the-one-running`

**The clause:** The daemon's log carries no lines of Jaeger failing to send its own traces.

- Signal: read by this repository's promise readers from the local daemon's traces. It is sent by `indusk telemetry status` on every run while the daemon runs. Status reads the lines of `~/.indusk/telemetry.log` written since the running daemon started, counts those that are Jaeger failing to send its own traces (its client failing to reach `localhost:4317`), and sends a span with the promise, the outcome, `indusk.clause=the-log-is-readable` and the count. Upheld when the count is zero. A broken report's symptom opens with the clause's name and gives the count and the first such line. Lines written between status runs are heard at the next run. A daemon whose status nobody asks is not heard; the brief's third expectation, the share of such lines one week after landing, is its backstop.

| ID | Assertion (user-visible behavior) | Level |
|----|-----------------------------------|-------|
| A23 | A daemon started from the shipped Jaeger with the config InDusk renders writes no line of Jaeger failing to send its own traces over half a minute, several times the interval at which those lines were written, while traces and logs sent to it still arrive. | contract |
| A24 | `telemetry status` sends an upheld report for this clause when the log since the daemon started holds no such line, and a broken one giving their count and the first of them. | unit |

## Not for a promise

Each of these guards a promise already in force that this plan comes near, as the brief's "Must not break" lists, or a lesson.

- **Row A29.** The clause gained one assertion when the fixed ports became a stored address (Sandy, 2026-10-16): that every reader and command reads the stored address and that it is printed for `init`. It takes the next free number, A29, rather than renumbering A7 to A28.
- **Rows A30–A37.** Added after approval, each taking the next free number. A30 (`--reset`) and A31 (the evaluator's logs port) came from Sandy's decisions of 2026-10-16. A32, A33 and A34 came from the falsification phase, Build Phase 6: a half-running daemon reported, a damaged address file refused, and each source judged by its own rule. A35 came from the cleanup phase, Build Phase 7: one reading and one comparison of a record's ports. A36 and A37 came from the audit of 2026-10-17 and are made true by Build Phase 8. The ADR's amendments of 2026-10-17 record the decisions behind them.
- **Levels.** Every row that says what report a command sends is a unit test: it reads the report the command decides to send from the process list, sockets, record and clock it is handed. That a report reaches the daemon and a reader is proved once, by the live check in row A15. Four rows (A2, A8, A22, A23) start a real Jaeger in a temporary home and are contract tests in the system tier.
- **Decisions this test plan leaves to the ADR.** Where the stored address is kept, and what happens when its file is lost. Whether a block port held at first setup by another home's InDusk daemon counts as held by someone else. What counts as InDusk's when a global install runs beside a repository's own (this machine has both). The Jaeger 2.17.0 setting that silences its self-tracing, which nothing on trunk has verified (research, "The daemon log is two-thirds Jaeger failing to trace itself"). Whether the always-on server's Jaeger gets the same setting; the clause names only the local daemon's log. Whether `init` exits non-zero when a later start finds a port of the stored address held by a process that is not InDusk's, or completes with the refusal printed; at first setup nothing refuses, since free ports are picked, and the 1.36.2 failure, where `init` failed on every machine already running a daemon, does not return, because a running InDusk daemon is now taken over. How projects whose MCP entry names an old random port (this repository's and Homework Gate's name 54677) come to name the stored MCP port: registering a project changes no other project's entry (row A17, the assertion that register leaves every other project's MCP entry as it was, follows the clause's "never point another project's MCP entry somewhere else"), so each project's own `update`, or a `telemetry restart`, which the clause does not name, has to do it. Whether `--allow-port-bump` and the explicit port options are removed or refused in the real home, since row A4, the assertion that every start in the real home uses the stored address, rules out both there.
- **Three decided reversals** flip behaviour that tests pin today, and those tests will be rewritten rather than added beside. `start` takes over a running InDusk daemon instead of refusing (row A11; `port-guard.test.ts`). The automatic start never bumps ports (rows A4 and A16; `port-guard.test.ts` and `telemetry-mcp-port-sync.test.ts`). `reap` clears a stray whose config still exists (row A20; `orphans.test.ts`). The lifecycle suite in `telemetry-cli-lifecycle.test.ts` walks start, status, stop and restart with automatically bumped ports and is rewritten to the ports its temporary home gives.
- **The live check breaks the promise on purpose.** In row A15, the live check that moves the record aside on this machine, the record really is gone while the daemon runs, and the finding cannot tell a person's hand from a faulty read, so `a-read-never-loses-the-daemon` reports broken. This repository names no production source, so its local daemon is the one whose breaks raise the alarm: the promise reads broken while that report is inside the health window, and a `promises watch` run in that time records it as an incident against this plan and reopens it with a Maintenance phase. Its precondition: the daemon started by hand on 2026-10-16 (Jaeger process 43599) runs on 4318 and 16686 with its MCP server on 62843, not on the stored address, which does not exist yet. The first `telemetry restart` after the build (row A5, the assertion that restart brings a daemon onto its stored address) chooses the address and moves the daemon onto it, and the live check runs after that.
- **`instance-ports`' per-instance-ports promise is superseded** by `one-daemon-on-its-own-ports` (Sandy, 2026-10-16), as the brief's "Not promised" says; nothing here tests several daemons on one machine except as strays.
