# Admin UI Hosting — Retrospective

## What We Set Out to Do

Replace the broken per-project `indusk ui` model from 1.26.0 with a single long-lived native Node daemon that serves every InDusk project on the machine. The brief promised:

- One daemon covers all projects, lifecycle via `indusk ui start/stop/status`
- `~/.indusk/projects.json` registry populated by `indusk init` / `indusk update`
- Routes scoped under `/p/[project]/...` with `/` as the project grid
- Pre-built Next.js bundle shipped in the indusk-mcp tarball — consumers need zero extra tooling
- Ship as 1.27.0

Six phases planned: bundling spike → registry + daemon CLI → route restructure → cross-project scorecards + stale-entry page + cwd-aware ui → ship → UX polish.

## What Actually Happened

The core plan shipped as designed through Phase 5 (1.27.0) and Phase 6 (1.27.2). The breaking change from 1.26.0's per-project model was real but low-impact (no users outside dusk). Bundling variant A3 survived the `npm pack` round-trip cleanly — 12 MB tarball, well under the 50 MB cap.

**Six extra releases shipped after the original plan closed**, each one a discovery from actually using what we built:

- **1.27.1 (same-day as 1.27.0)** — `indusk ui restart` subcommand, surfaced during smoke when 1.26.0 leftovers held port 3939 and `indusk ui start` no-op'd on running daemon per T4's contract. The one-command upgrade path for `npm i -g` flows.
- **1.27.2 (Phase 6)** — scorecards project-siloing + per-project research section + Brief collapsible. Three UX polish items batched together.
- **1.27.3 (Phase 6 bugfix)** — stripped stale top-level nav links from admin UI header; 1.27.2 removed the `/scorecards` route but left the Scorecards link in `app/layout.tsx`, which then 404'd.
- **1.27.5 (Phase 7 — falsification)** — `verifyIdentity(pid, port)` helper composes PID liveness with port-listening probe; `daemonStatus` and `daemonStop` both gate on it (PID-reuse hardening). `readRegistry` quarantines malformed `projects.json` to `.corrupt.{ISO}.bak` instead of silently overwriting. `resolveOpenPath` walks up cwd's parents to find the nearest registered project. All four were specific hypotheses generated by `/falsify admin-ui-hosting` — none of them would have been caught by the happy-path tests we authored.
- **1.27.6 (Phase 8 — first falsification follow-up)** — admin UI falsification-aware rendering. Dogfood of the new `/falsify` phase-authoring flow from 1.27.4 surfaced that `PlanDetail`'s `FalsificationSection` only knew about the legacy `falsification.md` file and rendered "No falsification ritual run for this plan" for any plan using the new flow. Added `splitPhasesAroundFalsification` to hoist the falsification phase out of `Phases`, render its trajectory rows as a Hypotheses table + checklist as Fix items, and render any phases after it as a "Follow-up Phases" section.
- **1.27.7 (Phase 9 — second falsification follow-up)** — `<CollapsibleSection>` persists open/closed state to `localStorage` via a new `persistKey` prop. Surfaced by the user mid-dogfood: "every time I come, the brief is open when I have to close it." Wired into every CollapsibleSection in PlanDetail with `plan:{name}:section:{slug}` / `plan:{name}:phase:{N}` keys.

## Getting to Done

Things that cost time I didn't budget for:

- **commander@13 silent option-drop on subcommands.** Debugging why `indusk ui start --port 0` kept producing `opts.port === "3939"` (the default) took longer than it should have. The discovery was that commander routes a flag token to the PARENT command when the same option is declared on both parent and child — the child's action receives the default. Fix: declare options only on the parent, read via `this.optsWithGlobals()` in each subcommand action. Now baked into CLAUDE.md.
- **Vitest `fileParallelism: false` in the node project.** Multiple HTTP smoke tests each spawn `next dev`. Under CPU contention, the child misses its "Ready in" stdout within 30s and the test fails with ECONNREFUSED. Serializing the node project eliminated the flake. Tiny cost for non-HTTP tests, big win for HTTP ones.
- **macOS `/var` ↔ `/private/var` symlink asymmetry.** `mkdtempSync` returns the unresolved form; `process.cwd()` returns the fully resolved realpath. Raw string compare of registered project paths missed this and T16 "cwd-aware open" failed intermittently on macOS. Fix: `safeRealpath` both sides before comparing — landed in `resolveOpenPath`. Documented in CLAUDE.md.
- **Test-mock omission from Phase 6 found during Phase 7 regression check.** Phase 6 added `readProjectResearch` to the layout but `page.test.tsx` didn't update its `@/lib/planning-reader` mock to include it. Phase 6's regression check ran `tsc --noEmit` (which doesn't load test files) so the miss survived until Phase 7's `pnpm vitest run` caught it. Fixed in Phase 7 as discovered work.
- **T30 test interference from unmount().** First shape of the Phase 9 T30 integration test used `unmount()` + fresh `render()` to simulate navigation; vitest-browser-react left enough state behind that downstream tests in the same file failed. Switched to a pre-seeded `localStorage` pattern — test sets storage, renders once, asserts state. Cleaner isolation, and exercises the same user-facing contract.

Things that went right:

- **Phase 1 (bundling spike) was worth its full budget.** The de-risking work structurally addressed ADR Risks #1 and #2 before committing the route work in Phase 3. `npm install /path/to/tarball.tgz` into a clean tempdir + `next start` was the right portability test, not `tar xzf` extraction (which missed the module-resolution reality of what a user's machine looks like).
- **Phase 2's test-isolation via `INDUSK_HOME` env var** paid for itself repeatedly. Every admin + registry test redirects away from the real `~/.indusk/` by setting the env var; pollution was impossible.
- **Test Trajectory discipline held.** 30 rows, each with a clear `Passes at` and honest `Writable at`. No rubber-stamp rows. Phase 7 and 8 and 9 each opened with writable-at-phase-0 tests red, ran the fix items, flipped green at phase close.

## What We Learned

- **Dogfood every surface you ship.** Each of 1.27.5, 1.27.6, 1.27.7 came from actually using what shipped in 1.27.0. The /falsify dogfood on admin-ui-hosting surfaced real bugs (PID-reuse in `daemonStatus`, silent data loss on corrupt registry, cwd-walk-up regression); using the resulting admin UI to view plans surfaced the falsification-rendering gap; using THAT surfaced the persistKey gap. The initial plan didn't anticipate any of them, and they're all now shipped hardening.
- **PID-based identity checks are insufficient on their own.** `kill(pid, 0)` checks only that SOME process has that PID — the OS recycles PIDs after death, and a recycled PID can point at a totally unrelated process. Any "is this process still alive?" check for a specific *identity* must include a second signal: port listening, argv contents, a PID file's mtime vs. process creation time, something. We landed port-listening because it's portable; other options exist but for this case it's the right trade.
- **Silent-data-loss hazards hide in "return empty on error" patterns.** The original `readRegistry` swallowed parse errors and returned an empty registry. The subsequent `writeRegistry` then cleanly overwrote the damaged file with an empty one. No warning, no backup. The fix (quarantine to `.corrupt.{ISO}.bak`) isn't about preventing corruption — it's about making sure the corrupt state *survives* rather than being silently destroyed. The user who edits `~/.indusk/projects.json` by accident now has a recovery path.
- **Falsification phase-authoring needs admin UI awareness.** The new flow from 1.27.4 changed the discipline (falsification is impl phases now, not a sidecar log), but the admin UI wasn't updated at the same time. The dogfood on admin-ui-hosting was the first real test of the new flow end-to-end, and it revealed a rendering gap that was explicitly out-of-scope in the plan that introduced the flow. Lesson: when a convention changes, check every rendered surface for that convention — don't just check the code that writes the new shape.
- **Persistence-by-default for UI state is usually the right trade.** Users close sections because they've read them. Re-opening on every page visit is an unstated usability tax. LocalStorage per-section keys are cheap to implement (no server round-trip, no schema) and the SSR-hydration flash is acceptable for a reader-only admin UI. The prior-art objection is "but what about mobile?" — not relevant for a local dev-time admin.

## What We'd Do Differently

- **Schedule a falsification dogfood pass BEFORE marking a plan completed.** This plan ran `/retrospective` prep on a "completed" state, discovered two real admin-UI gaps during dogfooding, reopened to Phase 8 + 9, then closed again. Doing the falsification dogfood before the first "completed" flip would have caught those gaps in the normal flow — the discipline is sound, but the ordering within /work didn't account for discovery work.
- **The `/falsify` skill should explicitly remind the author to dogfood every changed surface.** The admin-UI-rendering gap for the new phase-authoring flow was acknowledged as out-of-scope in falsify-phase-authoring's plan, but since the admin UI is the only way a human reads an impl.md, "out of scope" effectively meant "invisible until someone tries to view it." Future cross-cutting flow changes should list every rendered surface and call out which ones are in-scope for update.
- **Validator rule for the falsification-phase title convention.** The admin UI's `splitPhasesAroundFalsification` matches title substring `"Falsification"` case-insensitively. The convention is lenient by design, but nothing structurally enforces it — a plan could ship with `### Phase 8: Post-mortem — things we found` and silently fail to surface. A pre-commit hook or validator rule that warns when a plan has a phase authored by `/falsify` but no substring match would close the loop.
- **Admin-UI test suite discipline: separate browser-mode + node-mode running rules.** Running `pnpm vitest run` from the repo root picks up the wrong vitest config for browser tests and 14 files fail. Running from the admin-ui app directory is correct (104/104 passing). This is a workspace-config trap that's easy to fall into and hard to debug without context — it belongs in CLAUDE.md Known Gotchas (it isn't yet).

## Insights Worth Carrying Forward

- **Writable-at-Phase-0 tests authored red are the cheapest, most honest falsification artifact.** All four Phase 7 hypotheses were writable as unit tests against the existing 1.27.0 code — no infrastructure changes needed — and each one reproduced its failure mode immediately. That's the signal the falsification ritual exists to produce, and Phase 0 writability is usually the right default when the subject is an existing running system.
- **Admin UI is a load-bearing rendering surface for every other convention.** The falsification phase convention, the trajectory-row state convention, the phase-close gate convention, the legacy-log convention all show up rendered in PlanDetail. When any of them changes, PlanDetail needs to change with it — it's not peripheral documentation, it's the primary reader interface for everything the agent produces.
- **Release hygiene: a 1.27.x chain of seven patch releases tells a real story.** 1.27.0 shipped the feature. 1.27.1 fixed a real user-reported papercut found in smoke. 1.27.2 added UX polish. 1.27.3 fixed a bug introduced by 1.27.2. 1.27.5 added hardening from falsification. 1.27.6 and 1.27.7 landed the dogfood-discovered fixes. Each one was the minimum change to unblock the next step. The chain works because each release was usefully small, not because it was planned out upfront.
